# T2 · 云同步长期规范

> 最后更新：2026-06-29
> 定位：StoneFlow 云同步协议、数据语义和使用约束。开发迁移与代码落地计划放在 `Docs/02-重构方案/03-云同步重构/StoneFlow 云同步重构方案.md`。

---

## 1. 结论

StoneFlow 云同步不按“新设备、老设备、空设备、有数据设备”分类设计。长期规范只按数据事实收敛：

- 本地缺远端数据，就 pull 补齐。
- 远端缺本地数据，就 push mutation。
- 两边都改了同一实体，就由 resolver 产出 canonical result。
- 本地 cursor 不存在或过旧，就返回完整 authoritative snapshot。
- 软删除是可恢复状态，硬删除是永久移除事件，二者不能混用。

这不是 CRDT，也不是多人协作系统。它是单人多设备的 local-first sync protocol：本地写入立即成功，网络只负责后台收敛。

---

## 2. 目标与非目标

### 目标

- 支持单人 2 到 3 台设备长期稳定同步。
- 离线可写，联网后自动追平。
- 任意设备都可以从空库、半旧库、有本地数据、cursor 丢失等状态恢复到一致。
- 同步协议能解释新增、修改、软删除、恢复、硬删除、冲突、断网、重复请求和并发触发。
- Rust 侧是唯一同步协议真相源，前端只展示状态与触发命令。

### 非目标

- 不做多人协作。
- 不做账号系统。
- 不做设备间 P2P。
- 不把业务读写改成远端优先。
- 不引入 CRDT/OT 作为当前阶段默认方案。
- 不做复杂同步工作台。

## 3. 术语

| 术语 | 含义 |
|---|---|
| `client_id` | 当前设备稳定 ID，本地生成后长期保存 |
| `client_seq` | 单设备单调递增 mutation 序号 |
| `server_seq` | 远端全局单调确认序号 |
| `mutation` | 本地业务意图，例如 upsert、soft_delete、restore、hard_delete |
| `canonical row` | 远端当前权威实体状态 |
| `change log` | 远端按 `server_seq` 记录的可拉取变更 |
| `shadow` | 本地最近一次远端确认基线 |
| `cursor` | 本地已应用到哪个 `server_seq` |
| `snapshot` | 远端当前 authoritative 全量视图 |

---

## 4. 核心原则

### 4.1 数据事实优先

同步引擎只回答三个问题：

- 远端有哪些 canonical changes 是本地没有的？
- 本地有哪些 pending mutations 是远端没有确认的？
- 同一实体同一字段发生竞争时，resolver 应产出什么结果？

设备状态只用于诊断，不参与协议分支。

### 4.2 本地优先

所有业务读写仍然先写本地 SQLite。同步失败不能阻塞任务创建、编辑、归档和删除。

### 4.3 服务端序列决定收敛

用远端生成的 `server_seq` 作为全局确认顺序。不要用设备本地 `updated_at` 决定跨设备胜负。

### 4.4 幂等与可重试

任何 `push` 都必须能重复提交。远端以 `(client_id, client_seq)` 去重，已经应用过的 mutation 直接返回确认结果。

### 4.5 删除语义必须分清

- 软删除：实体仍存在，带 `deleted_at`，可以恢复。
- 硬删除：实体永久移除，canonical row 立即物理删除，不能恢复。
- 不存在：远端从未有过该实体，或 full snapshot 中已经确认没有该实体。

硬删除不是“软删除到期后的清理”。用户确认硬删除后，远端当前状态就是没有这条实体。

### 4.6 前端薄边界

React 只消费 Rust 返回的 `SyncStatusPayload` 和触发命令。不要在前端派生第二套同步状态机，不用多个 boolean prop 表示同步变体。

## 5. 同步数据模型

### 5.1 本地事实源

#### `sync_clients`

记录当前设备身份。

| 字段 | 说明 |
|---|---|
| `client_id` | 稳定设备 ID |
| `created_at` | 创建时间 |
| `last_seen_at` | 最近启动或同步时间 |

#### `sync_mutations`

本地 mutation log。业务写入和 mutation 写入必须在同一个本地事务内完成。

| 字段 | 说明 |
|---|---|
| `client_id` | 设备 ID |
| `client_seq` | 当前设备单调递增序号 |
| `entity_type` | `task/project/space/view/setting/task_link` |
| `entity_id` | 实体 ID |
| `operation` | `upsert/soft_delete/restore/hard_delete` |
| `payload` | 结构化 mutation payload |
| `base_server_seq` | 写入时本地已知远端基线 |
| `status` | `pending/acked/failed` |
| `created_at` | 本地创建时间，仅用于诊断和排序展示 |

#### `sync_shadow`

本地最近一次远端确认基线，用于 rebase 和冲突判断。

| 字段 | 说明 |
|---|---|
| `entity_type` | 实体类型 |
| `entity_id` | 实体 ID |
| `server_seq` | 最近确认的远端序号 |
| `snapshot` | canonical snapshot |
| `deleted_at` | 软删除时间；硬删除后本地应移除 shadow |

#### `sync_cursor`

只保存协议 cursor，不保存“设备是否新旧”的判断。

| scope | 说明 |
|---|---|
| `sync:last_pulled_server_seq` | 本地已应用的远端全局序号 |
| `sync:next_client_seq` | 下一条本地 mutation 序号 |
| `sync:last_success_at` | 最近一次完整 sync 成功时间 |

### 5.2 远端事实源

#### `remote_mutations`

幂等 receipt。

| 字段 | 说明 |
|---|---|
| `client_id` | 来源设备 |
| `client_seq` | 来源设备序号 |
| `received_at` | 远端接收时间 |
| `server_seq` | 应用后生成的全局序号 |
| `status` | `applied/duplicate/rejected/conflict` |

唯一约束：`UNIQUE(client_id, client_seq)`。

#### `remote_change_log`

远端权威 change log。它必须能支撑 `pull(cursor)`。

| 字段 | 说明 |
|---|---|
| `server_seq` | 全局单调序号 |
| `entity_type` | 实体类型 |
| `entity_id` | 实体 ID |
| `change_kind` | `upsert/soft_delete/restore/hard_delete/conflict_notice` |
| `patch` | canonical patch；`hard_delete` 可为空 |
| `changed_by_client_id` | 来源设备 |
| `changed_by_client_seq` | 来源 mutation |
| `committed_at` | 远端提交时间 |

#### canonical tables

远端保留与本地业务表同构或接近同构的当前基线表，并额外包含：

- `server_seq`
- `deleted_at`
- `updated_by_client_id`
- `updated_by_client_seq`

硬删除后 canonical table 不保留该 row；传播依赖 `remote_change_log` 的 `hard_delete` 事件和 full snapshot 的 authoritative sweep。

## 6. 统一同步协议

长期只有一个公开动作：`sync()`。

```text
sync()
  1. pull(last_pulled_server_seq)
  2. apply remote changes to local shadow and business tables
  3. rebase pending local mutations onto new shadow
  4. push pending mutations by client_seq
  5. pull latest confirmations
```

### 6.1 `pull(cursor)`

输入：

- `client_id`
- `last_pulled_server_seq`
- `known_schema_version`

返回之一：

- `changes`: cursor 之后的远端 patch 列表。
- `snapshot`: 当 cursor 为 null、过旧或远端日志已裁剪时返回完整当前基线。
- `schema_mismatch`: 本地 schema 太旧，需要先迁移。

规则：

- `pull(null)` 必须是合法路径，不能要求用户手动 restore。
- 返回 snapshot 时必须按依赖顺序：`spaces -> projects -> tasks -> task_links -> views -> settings`。
- snapshot 是 authoritative。应用 snapshot 时，本地不存在 pending mutation 的同步实体若不在 snapshot 中，应删除本地残留。
- incremental `changes` 只按 change log 操作，不允许把“没返回某实体”解释成删除。
- 应用 patch 必须在本地事务内完成。
- FK 无法满足时进入 repair queue，不允许半应用。

### 6.2 `push(mutations)`

输入：

- `client_id`
- 连续或可验证的 `client_seq`
- mutation 列表

远端处理：

1. 先检查 `(client_id, client_seq)` 是否已存在。
2. 不存在则在单个事务内调用 resolver。
3. 写 canonical tables。
4. 写 `remote_change_log`。
5. 写 `remote_mutations` ack。

返回：

- 每条 mutation 的 ack。
- 最新 `server_seq`。
- 如果发生可恢复冲突，返回 canonical patch，不让客户端猜。

### 6.3 `rebase`

本地 pending mutation 不应被远端 patch 直接覆盖。正确流程是：

1. 把远端 patch 应用到 shadow。
2. 用 shadow 更新本地已确认字段。
3. 对 pending mutation 涉及的字段重新叠加本地意图。
4. 如果 resolver 判定本地意图已经无效，保留 conflict notice。

## 7. 写入规则

### 7.1 本地写入

- 业务表写入和 `sync_mutations` 写入必须同事务提交。
- 不允许 command/UI 层散落记录“本地有修改”的标记。
- `updated_at` 只用于展示和本地排序，不参与跨设备冲突裁决。
- 每条 mutation 必须能被远端幂等处理。

### 7.2 远端写入

- 所有远端 canonical 更新必须生成 `server_seq`。
- 所有远端 canonical 更新必须写入 `remote_change_log`。
- 远端拒绝 mutation 时必须返回可诊断原因，不能让客户端猜。

### 7.3 前端使用

- 用户点击“立即同步”只触发 `sync()`。
- 前端只展示同步状态，不展示 push/pull 内部阶段。
- 前端不直连 Turso，不维护第二套同步状态机。

### 7.4 旧协议到当前协议的基线迁移

- `sync()` 入口必须先确保同步基线存在，再执行 pull / push。
- 远端 `remote_change_log` 为空时，允许从当前 canonical tables 生成一次初始 `upsert` 基线。
- 本地已有业务数据但缺少 `sync:last_pulled_server_seq` 时，只允许写入 `sync_shadow` 和 cursor，不允许用 snapshot 覆盖本地业务表。
- 本地空副本缺少 cursor 时，走 `pull(null)` snapshot 自动补齐。
- 迁移必须幂等；重复执行不能重复生成 `remote_change_log`，也不能重复写 pending mutation。
- S1 `sync_operations` / `sync_outbox` 只能作为迁移兼容事实源，不能继续作为长期同步入口。

## 8. 冲突策略

StoneFlow 当前是单人多设备，不需要 CRDT。推荐 resolver 分层处理。

| 数据 | 策略 |
|---|---|
| `task.title` / `task.note` | 字段级 LWW，使用 `server_seq`，不用设备时间 |
| `task.status` / `priority` / 日期字段 | 字段级 LWW |
| `task.project_id` | 目标项目存在则应用；目标不存在则落到 no-project 并记录 repair |
| `project.space_id` | 目标 space 存在则应用；不存在则拒绝 mutation 并返回 conflict |
| `sort_order` | 长期改为可合并 sort key；短期按字段级 LWW |
| `settings` | 用户偏好可同步；设备偏好不进云同步 |
| 软删除 vs 修改 | 软删除赢，修改转 conflict notice |
| restore vs soft_delete | `server_seq` 后者赢；restore 必须生成新 mutation |
| hard_delete vs 任何修改 | hard_delete 赢，实体不可恢复 |

### 8.1 为什么不用 `updated_at`

`updated_at` 适合本地展示，不适合跨设备裁决。设备时钟漂移、离线编辑、系统时间调整都会破坏它的顺序含义。

### 8.2 为什么不用 CRDT

当前实体主要是任务、项目、视图、设置，不是多人实时协作文本。CRDT 会显著增加 schema、调试、UI 冲突解释和迁移成本。字段级 resolver 已足够覆盖当前目标。

## 9. 删除与恢复规范

### 9.1 软删除

普通删除写 `deleted_at`，产生 `soft_delete` change。任何设备 pull 到后隐藏该实体，但实体仍可恢复。

### 9.2 恢复

恢复是新的 `restore` mutation。它不会“撤销历史”，而是写入新的 canonical state。

### 9.3 硬删除

硬删除表示用户已经确认永久删除：

- 远端 canonical row 立即物理删除。
- 远端必须写一条 `hard_delete` change log，用于让已有设备删除本地残留。
- 已 pull 到 `hard_delete` 的设备必须删除本地业务 row 和对应 shadow。
- 未见过该实体的新设备不需要知道这条历史。
- cursor 过旧的设备走 full snapshot；snapshot authoritative sweep 会删除本地多出来且没有 pending mutation 的实体。

硬删除和“不存在”最终状态相同，但协议含义不同：硬删除是一个需要传播给旧设备的事件；不存在只是 snapshot 当前没有该实体。

## 10. 状态模型

Rust 同步状态对前端暴露用户可理解状态，不暴露内部协议细节。

| 状态 | 含义 |
|---|---|
| `disabled` | 未配置远端 |
| `synced` | 无 pending mutation，已追到最新远端 |
| `syncing` | 正在执行统一 `sync()` |
| `offline_pending` | 本地有 pending mutation，但当前网络不可用 |
| `error` | 最近一次 sync 失败，可自动重试或手动重试 |
| `needs_attention` | 凭证失效、schema 不兼容、不可自动修复冲突 |

诊断字段：

- `client_id`
- `last_pulled_server_seq`
- `latest_remote_server_seq`
- `pending_mutation_count`
- `failed_mutation_count`
- `conflict_notice_count`
- `repair_queue_count`
- `last_success_at`
- `last_error`

## 11. 调度使用规范

### 自动触发

- 本地 mutation 写入成功后，短延迟触发 `sync()`。
- App 启动后触发 `sync()`。
- App 回到前台后触发 `sync()`。
- 网络恢复后触发 `sync()`。
- 定时轻量触发可保留，但不是主要一致性来源。

### 手动触发

用户点击“立即同步”也只调用同一个 `sync()`。手动和自动不能有不同协议路径。

### 并发控制

- 同一设备同时只允许一轮 sync。
- sync 运行期间新增 mutation，只设置 pending flag。
- 当前轮结束后如果 pending flag 存在，立即补一轮。

## 12. 验收矩阵

| 场景 | 预期 |
|---|---|
| 全新空设备连接已有远端 | `pull(null)` 拉完整 snapshot，写 cursor |
| 全新设备先离线创建数据再配置同步 | 本地 mutation push 到远端，再 pull canonical result |
| 老设备删除 cursor | 下一轮返回 snapshot 或明确 repair，不回放不完整日志 |
| 老设备本地无数据但远端有数据 | full snapshot 补齐 |
| 两台设备同时改标题 | 按 `server_seq` 字段级 LWW 收敛 |
| 一台软删除一台修改 | soft_delete 赢，修改生成 conflict notice |
| 一台硬删除一台修改 | hard_delete 赢，实体在所有设备最终消失 |
| push 请求重复发送 | 远端返回已有 ack，不重复应用 |
| pull 中断 | 本地事务回滚，cursor 不前进 |
| schema 版本不兼容 | sync 暂停并提示升级 |
| 外键目标缺失 | 进入 repair queue，不写坏本地库 |

## 13. 参考模型

> 参考资料校验日期：2026-06-29。以下只作为协议设计参考，不代表 StoneFlow 直接依赖这些库。

- WatermelonDB：`synchronize()` 由 `pullChanges` / `pushChanges` 驱动，后端协议围绕 changes、deleted IDs、timestamp/cursor 组织。
  - <https://watermelondb.dev/docs/Sync/Frontend>
  - <https://watermelondb.dev/docs/Sync/Backend>
  - <https://watermelondb.dev/docs/Implementation/SyncImpl>
- Replicache：本地 mutation 是同步核心；pull 后会把未确认 mutation 重新 replay 到新服务端状态上，形成类似 rebase 的语义。
  - <https://doc.replicache.dev/concepts/how-it-works>
  - <https://doc.replicache.dev/byob/local-mutations>
  - <https://doc.replicache.dev/strategies/global-version>
- CouchDB：复制目标是让目标库拥有源库的 active documents 和 deleted documents；冲突以 revision/conflict 历史暴露，应用层负责解释和清理。
  - <https://docs.couchdb.org/en/stable/replication/intro.html>
  - <https://docs.couchdb.org/en/stable/replication/conflicts.html>
- Turso Sync：官方推荐新同步场景使用显式 `push()` / `pull()` 的 local-first sync，而不是只依赖 Embedded Replicas 的远端主写入模型。
  - <https://docs.turso.tech/features/embedded-replicas/introduction>
  - <https://docs.turso.tech/sdk/rust/quickstart>
  - <https://docs.turso.tech/sdk/ts/reference>

StoneFlow 不直接照搬任一套。原因是当前没有自建后端、没有多人协作、实体模型也不是实时文本编辑；我们只取“可确认、可补全、可重试、可解释”的协议骨架。

## 14. 最终判断

长期云同步的关键不是更多状态，而是更少入口和更强数据协议：

- 一个公开动作：`sync()`。
- 一个全局顺序：`server_seq`。
- 一个本地事实源：`sync_mutations`。
- 一个远端事实源：`remote_change_log`。
- 一个冲突出口：resolver。
- 一个前端状态源：Rust payload。

后续所有实现、重构和 UI 都应以本文档为准。
