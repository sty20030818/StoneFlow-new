# StoneFlow 文档架构说明

> 最后更新：2026-07-16  
> 作用：定义 `Docs/` 的正式层次、命名规则、落点规则和维护规则。

---

## 1. 正式结构

```txt
Docs/
├─ INDEX-文档索引.md
├─ P1-产品内核.md
├─ P2-产品蓝图.md
├─ D1-领域与数据模型.md
├─ T1-系统设计.md
├─ T2-云同步设计.md
├─ U1-设计系统.md
├─ X1-决策日志.md
├─ 文档治理与迁移方案.md
├─ 文档架构说明.md
├─ 01-执行计划/              # 进行中的功能执行主题
├─ 02-重构方案/              # 进行中的结构重构主题
├─ 03-前端架构解析/          # 前端 As-Is / Gap / To-Be / Migrate 细账
├─ 98-归档/                  # 已完成 / 失效 / 历史
├─ 99-素材/                  # 图片、HTML 原型、附件
└─ superpowers/              # 局部 plan / spec / report（工具链）
```

说明：仓库文档根目录名为 **`Docs/`**（不是历史中的 `Documents/`）。旧链接若仍写 `Documents/` 或 `执行层/`，以本结构与 [INDEX](./INDEX-文档索引.md) 为准。

## 2. 顶层职责

### 2.1 根目录

根目录只放长期稳定文档：

- 产品 / 蓝图 / 数据模型 / 系统设计 / 云同步 / 设计系统 / 决策日志
- 文档治理与架构说明
- 总索引

禁止：

- 把阶段计划直接堆在根目录
- 把专题稿直接堆在根目录
- 把图片、HTML、脚本放在根目录

### 2.2 `01-执行计划/`

放正在推进的执行主题（功能落地）。

规则：

- 一个主题一个子目录
- 同主题的调研、执行计划、实施稿、审计稿尽量放一起
- 主题结束后整体移入 `98-归档/`

### 2.3 `02-重构方案/`

放正在推进的**结构重构**主题（非日常功能切片）。

规则：

- 一个重构主题一个子目录
- 动机、方案、迁移步骤、风险分析放一起
- 完成后整体移入 `98-归档/`

### 2.4 `03-前端架构解析/`

放前端架构的**调研与目标细账**，不替代根 `T1` 总览，也不替代 `src/**/ARCHITECTURE.md` 短契约。

| 子树 | 职责 |
|------|------|
| `01-As-Is/` | 调研期现状（可能滞后） |
| `02-Gap/` | 债与评估 |
| `03-To-Be/` | 目标架构与原则（分层、路由、数据、壳、Feature） |
| `04-Migrate/` | Phase D 史诗、执行计划、路线图 |
| `附录/` | Session 日志、漂移台账、doctor 基线 |

入口：[03-前端架构解析/README.md](./03-前端架构解析/README.md)。

规则：

- 前端结构/边界的细颗粒讨论写这里
- 日常「新代码落哪」优先看 `src/ARCHITECTURE.md` + 本目录 To-Be
- 根 `T1` 只保留总览，并链接到本目录

### 2.5 `98-归档/`

放：已完成主题、已失效主题、旧文档、历史阶段文档（含原 V1 `执行层/`）。

### 2.6 `99-素材/`

放：图片、HTML 原型、临时脚本、附件。

### 2.7 `superpowers/`

放工具链产出的局部 plan / specs / reports；不替代正式执行计划目录。

## 3. 子目录命名规则

### 3.1 使用数字前缀

进行中目录下的主题统一使用：

```txt
01-主题名
02-主题名
03-主题名
```

原因：顺序稳定、便于扩展、目录列表不乱跳。

### 3.2 主题名规则

主题名直接写业务或系统主题，不要写抽象空词。

推荐：`01-命令与快捷键系统`、`02-快捷创建全局弹窗`、`01-详情弹窗重构`  
不推荐：`01-优化`、`02-方案`、`03-收口`

---

## 4. 文档命名规则

### 4.1 常青文档

维持编号体系：`P1`、`P2`、`D1`、`T1`、`T2`、`U1`、`X1`。

### 4.2 主题文档

主题目录内可用原始中文名；同一主题只能有一个「总方案」类主文档。  
`v2 / 第二轮 / 阶段A` 类文件需标注状态或逐步合并。

### 4.3 归档文档

归档后保留原文件名，避免历史引用断裂。

## 5. 文档落点判断规则

新增文档前先问：

1. 长期稳定文档吗？  
2. 正在推进的执行主题吗？  
3. 正在推进的重构主题吗？  
4. 前端架构细账吗？  
5. 历史材料还是素材？

对应落点：

| 类型 | 落点 |
|------|------|
| 长期稳定 | 根目录 |
| 功能执行 | `01-执行计划/` |
| 结构重构方案 | `02-重构方案/` |
| 前端架构细账 | `03-前端架构解析/` |
| 历史 | `98-归档/` |
| 素材 | `99-素材/` |

---

## 6. 代码架构文档与 Docs 的关系

`Docs/` **不是**代码同位架构文档的替代品。

| 类型 | 路径 | 职责 |
|------|------|------|
| 系统总览 | `Docs/T1-系统设计.md` | 技术栈、分层、边界口径 |
| 前端细账 | `Docs/03-前端架构解析/**` | As-Is / Gap / To-Be / Migrate |
| 短契约 | `src/**/ARCHITECTURE.md`、`src/CONVENTIONS.md` | 日常开发「落哪、禁什么」 |
| 后端短契约 | `src-tauri/ARCHITECTURE.md` 等 | Rust workspace 边界 |

冲突时：

1. 以当前代码事实为准  
2. 先改同位 `ARCHITECTURE.md`  
3. 再视需要回写 T1 / 03-前端架构解析 / 本说明 / INDEX  

---

## 7. 维护规则

1. 新增常青文档或顶层目录 → 同步 [INDEX-文档索引.md](./INDEX-文档索引.md) 与本文 §1。  
2. 前端大重构落地 → 更新 `03-前端架构解析/04-Migrate` 状态，并检查 T1 前端段是否仍正确。  
3. 主题结束后 → 整夹迁入 `98-归档/`，不在 `01`/`02` 留死文件。  
4. 不在根目录堆阶段稿。
