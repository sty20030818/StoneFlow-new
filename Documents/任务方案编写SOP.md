# SPEC-PLAN-TASKS 编写 SOP

> 定位：这是《文档体系 SOP》的配套文档，只回答一件事——活跃任务的 `SPEC.md`、`PLAN.md`（按门槛创建）与 `TASKS.md` 该按什么顺序写、写到什么颗粒度、什么时候可以进入下一阶段。不重新定义模板、目录、命名、Owner 规则，那些以《文档体系 SOP》为准。

## 0. 与文档体系 SOP 的关系

- 创建门槛、目录结构、文件命名、模板骨架、更新触发器：全部复用《文档体系 SOP》，本文档不重复。
- 本文档新增的是缺失的一层：**编写流程**——谁在什么时候写哪一部分、写完要不要停下来等确认、颗粒度怎么判断。
- 关于"PLAN"：默认不新增独立文件，技术方案写在 SPEC 的"当前技术方案"章节。当方案触发《文档体系 SOP》"按复杂度增加文档"一节的门槛（非平凡数据流/状态机/协议设计/算法/第三方集成，或需要对比权衡多个备选方案）时，才从 SPEC 拆出独立的 `PLAN.md`——这条逻辑和模块级 ARCHITECTURE/DESIGN 的拆分完全一致：简单合并、复杂拆开，不做固定套餐。三段式 workflow 因此映射为：

  ```
  阶段 1 需求      → 写 SPEC 前半部分（背景/范围/不做什么/场景/DoD/验收标准）
  阶段 2 方案      → 写 SPEC 的"当前技术方案"；触发门槛时拆出 PLAN.md
  阶段 3 任务拆解  → 写 TASKS，引用 SPEC（与 PLAN，若存在）
  阶段 4 执行与收尾 → 更新 TASKS，归档时核对 SPEC 与 PLAN
  ```

## 1. 核心原则

1. **需求与方案分离，方案与任务分离**——三者回答不同问题，写的时候不要互相渗透。验收标准里出现具体技术选型（"用 Redis 做缓存"），或方案里出现执行步骤（"先改 A 文件再改 B"），都是写串了。
2. **验收标准必须可测试**——用 EARS 句式写（见第 3 节），拒绝"体验要好""性能要快"这类不可验证的表述。
3. **方案需要人确认才能往下走**——技术方案（无论写在 SPEC 里还是拆成 PLAN）写完后停下来，等确认后再拆 TASKS。不允许方案和任务在同一轮生成，否则等发现方案有问题时任务已经跑了一半。
4. **TASKS 不复制 SPEC/PLAN**——每个 task 引用对应的验收标准编号，不重新描述一遍验收标准或方案内容。
5. **Out of scope 和 in-scope 同等重要**——每份 SPEC 至少写 2-3 条"这次不做什么"，专门用来防 scope creep。
6. **偏差显式记录，不悄悄改 SPEC/PLAN**——执行中发现方案不可行，先在 TASKS 的"与 SPEC/PLAN 的实施偏差"里写清楚，再回头改对应文档，不能直接改掉了事，让方案失去可信度。
7. **是否拆分 PLAN 是判断出来的，不是习惯性动作**——每次进入方案阶段都要过一遍拆分门槛，不要因为"上次拆了这次也拆"或"嫌麻烦就不拆"而跳过判断。

## 2. 完整工作流

### 阶段 0：触发判断

直接使用《文档体系 SOP》里的创建门槛（需要分阶段执行/涉及多模块/存在需确认的技术方案/验收标准不易直接说明/预计跨多个工作时段）。不满足门槛的任务不建 SPEC/TASKS，直接改代码。

### 阶段 1：需求阶段（写 SPEC 前半部分）

| 项目 | 说明 |
|---|---|
| 输入 | 一句话到几句话的原始诉求 |
| 产出 | SPEC.md 的：背景与目标 / 范围 / 不做什么 / 用户场景与需求 / 能力边界 / Definition of Done / 验收标准 |
| 完成标志 | 范围和验收标准无歧义，任务发起人确认后才能进入阶段 2 |

写法：

- **用户场景**用"作为 [角色]，我想要 [诉求]，以便 [收益]"的句式，逼自己想清楚"为谁做、为什么做"，不是直接跳到功能点。
- **验收标准**逐条用 EARS 句式（见第 3 节），每写一条自检一次：这条能不能被测试或验证？是否只有一种解读？
- **不做什么**至少列 2-3 条，优先写"看起来相关但这次故意不做"的东西，而不是随便写几条无关的。
- **DoD 和验收标准不互相复制**：DoD 是交付门槛（"功能可用、无阻塞 bug、文档已同步"），验收标准是可验证的用户行为/数据结果/质量检查，两者是不同粒度的东西。

常见错误：把实现细节写进验收标准（该写在阶段 2 的方案里）；范围写得含糊导致后面验收对不上。

### 阶段 2：方案阶段（先判断是否拆出 PLAN.md）

| 项目 | 说明 |
|---|---|
| 输入 | 已确认的需求（阶段 1 产出） |
| 产出 | 简单方案：SPEC.md 的"当前技术方案"章节；复杂方案：独立 PLAN.md |
| 完成标志 | 方案被确认后才能进入阶段 3 |

**第一步：判断要不要拆出 PLAN.md**——按《文档体系 SOP》的门槛检查，命中任一条就拆：

- 涉及非平凡数据流、状态机或协议设计
- 涉及算法或第三方集成
- 存在需要对比权衡的多个备选方案
- 决策会长期影响全局架构或模块边界（需要登记同步项）

都不命中 → 方案直接写在 SPEC 的"当前技术方案"，一两句话说清结论即可，不新建文件。

**第二步：按结果分配内容**——两边不互相复制：

| 内容 | 不拆分时 | 拆分后 |
|---|---|---|
| 方案结论（一两句话） | SPEC「当前技术方案」 | SPEC「当前技术方案」改为摘要 + 链接 PLAN |
| 备选方案与取舍 | 一并写在 SPEC | PLAN「备选方案与取舍」 |
| 数据流/状态机/协议细节 | 一并写在 SPEC | PLAN 对应章节 |
| 关联模块 | SPEC | PLAN「关联模块」 |
| 风险 | SPEC | PLAN「风险」 |
| 完成后需要同步的长期文档 | SPEC | PLAN「完成后需要同步的长期文档」 |

写法（两种情况通用）：

- 只写**这次真正要做的选择和权衡**，不复述通用架构（那是 A2/模块 ARCHITECTURE 的事）。如果这次决策会长期影响全局架构或模块边界，登记进"完成后需要同步的长期文档"，归档时才落地同步。
- 每个关键决策写"选了什么 / 为什么 / 放弃了什么"，只写结论看不出权衡过程，以后自己都看不懂当初为什么这么定。
- 决策若**跨模块或难逆转**，按《文档体系 SOP》判断是否需要单独开 ADR；SPEC/PLAN 里链接过去，不重复写全文。

Gate：方案（SPEC 的方案章节或独立 PLAN）确认后才能生成 TASKS。防止"方案和任务同时生成、人来不及审查方案就已经在执行"。

### 阶段 3：任务阶段（写 TASKS.md）

| 项目 | 说明 |
|---|---|
| 输入 | 已确认的 SPEC（需求 + 方案，或 SPEC + 独立 PLAN） |
| 产出 | TASKS.md 的：当前阶段 / 阶段任务 / 阻塞 / 与 SPEC/PLAN 的实施偏差 / 完成记录 |
| 完成标志 | 所有 task 完成，且逐条对照验收标准核对通过 |

写法：

- 每个 task 是一个**可独立验证的最小单元**，附：涉及的文件/模块、依赖的其他 task、对应的 SPEC 验收标准编号。
- 能写自动化测试的 task，测试先行——task 完成 = 测试通过，而不是"感觉写完了"。
- 阻塞要写清楚原因（"依赖 X 模块接口未定"），不是写"卡住了"三个字了事。
- 执行中发现方案不可行或范围需要调整：先写进"与 SPEC/PLAN 的实施偏差"，再回头更新对应文档（SPEC 的技术方案或 PLAN），两边保持一致——不能只改一边。

### 阶段 4：收尾与归档

1. 逐条核对 DoD 和验收标准（建议用清单形式一条条打勾，不是笼统说"做完了"）。
2. 补齐"完成后需要同步的长期文档"列出的项（在 SPEC 或 PLAN 里，同步到 A2 / ARCHITECTURE / 模块 DESIGN）。
3. TASKS 里仍未解决的事项，按《文档体系 SOP》的"延后项三种合法去向"转成明确的后续任务，不能悬空留在已归档文档里。
4. 任务目录移入 `98-归档/`，SPEC、PLAN（若存在）与 TASKS 冻结。

## 3. 验收标准写作速查（EARS）

| 场景 | 句式 | 示例 |
|---|---|---|
| 事件触发 | 当 [事件] 时，系统应当 [行为] | 当用户点击"发布"时，系统应当校验必填字段 |
| 条件前提 | 如果 [条件]，则系统应当 [行为] | 如果角色资产未生成完成，则系统应当禁用"下一步"按钮 |
| 事件+条件组合 | 当 [事件] 且 [条件] 时，系统应当 [行为] | 当用户提交表单且存在必填项为空时，系统应当在对应字段旁显示错误提示 |
| 持续状态 | 只要 [状态持续]，系统应当 [行为] | 只要生成任务在排队中，系统应当显示进度指示 |
| 兜底/异常 | 如果 [异常情况] 发生，系统应当 [兜底行为] | 如果生成失败，系统应当保留用户已上传的素材并提示重试 |

不确定的需求不要脑补成具体数值——SPEC 里写"待确认：xxx"，而不是自己编一个看起来合理的默认值蒙混过去。

## 4. Task 颗粒度自检

| 信号 | 说明 |
|---|---|
| 太大 | 涉及 3 个以上模块 / 无法在一个专注时段内完成 / 验收标准要引用 5 条以上 SPEC 条目 |
| 太小 | task 之间没有独立验证意义，纯粹是把一个动作机械拆成三步 |

判断标准：拆出来的每个 task，单独看都应该能回答"做完了怎么验证"。回答不了，说明要么太大（验证点混在一起），要么太小（这一步本身不构成验证单元）。

## 5. 编写者行为约束

无论执行者是人还是 AI，写作过程都遵守：

- 阶段 1 写完必须停下来等确认，不能自己接着写方案。
- 进入阶段 2 先过一遍拆分门槛，不能默认合并或默认拆分，更不能拆完 PLAN 才发现方案其实很简单。
- 阶段 2 写完（无论是否拆出 PLAN）必须停下来等确认，不能自己接着拆 TASKS。
- SPEC 缺少"不做什么"时，不能开始写方案——先补上或标注待确认。
- 验收标准存在歧义时，标注"待确认"，不能替用户做决定。
- TASKS 执行中发现方案有问题，先写偏差，不能直接改 SPEC/PLAN 的方案内容掩盖过去。

## 6. 写作前自检清单

新建或修改 SPEC/PLAN/TASKS 前，依次确认：

1. 我现在写的是需求、方案还是执行状态？是否写进了不该属于这一部分的内容？
2. 每条验收标准是否可测试、是否只有一种解读？
3. 是否明确写了"不做什么"？
4. 方案是否触发了 PLAN 拆分门槛？拆分决定是判断出来的，还是习惯性动作？
5. 技术方案是否写清楚了"为什么选这个、放弃了什么"，而不只是结论？
6. 这次决策是否需要同步进长期文档或开 ADR？是否已登记？
7. TASKS 里的阻塞和偏差是否写明了原因，而不是含糊带过？
8. 归档前，是否所有未解决事项都有了明确的后续去向？
