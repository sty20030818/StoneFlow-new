# 任务方案编写 SOP

> 定位：全权负责活跃任务的 `SPEC.md`、`PLAN.md`（按门槛创建）、`TASKS.md`——创建门槛、拆分判断、模板、写作流程、格式规范、要写什么、不该写什么。任务目录在项目结构里的位置、全局架构文档、模块文档，见《文档体系 SOP》；本 SOP 只管任务目录内部这三份文档。

## 0. 创建门槛

只有任务满足以下任一条件时才创建 SPEC/TASKS：

- 需要分阶段执行
- 涉及多个模块
- 存在需要确认的技术方案
- 验收标准不容易直接说明
- 预计跨多个工作时段

不满足门槛的任务直接改代码，不建文档。

## 1. 三份文档的边界

| 文档 | 回答什么 | 何时创建 |
|---|---|---|
| `SPEC.md` | 要什么：目标、范围、不做什么、验收标准（编号）、关联模块、Definition of Done | 命中第 0 节门槛时 |
| `PLAN.md` | 怎么做：备选方案与取舍、数据流/状态机/协议、风险、需同步的长期文档 | 命中"PLAN 拆分门槛"时，从 SPEC 拆出 |
| `TASKS.md` | 做到哪：执行状态、阻塞、偏差 | 与 SPEC 同时创建 |

三者互不复制：SPEC 不写执行步骤，PLAN 不写验收标准，TASKS 不写需求或方案原文——各自出问题就改各自的文档，不在别的文档里垫一份备份。

## 2. PLAN 拆分门槛

命中任一条，就从 SPEC 拆出独立 `PLAN.md`：

- 涉及非平凡数据流、状态机或协议设计
- 涉及算法或第三方集成
- 存在需要对比权衡的多个备选方案
- 决策会长期影响全局架构或模块边界（需要登记同步项）

都不命中 → 方案直接写在 SPEC 的"当前技术方案"，一两句话说清结论，不新建文件。这条逻辑和模块级 ARCHITECTURE/DESIGN 的拆分完全一致：简单合并、复杂拆开，不做固定套餐。

### 拆分后的内容分配（两边不互相复制）

| 内容 | 不拆分时 | 拆分后 |
|---|---|---|
| 方案结论（一两句话） | SPEC「当前技术方案」 | SPEC「当前技术方案」改为摘要 + 链接 PLAN |
| 关联模块（涉及哪些模块） | SPEC「关联模块」 | 仍在 SPEC「关联模块」，PLAN 不重复列，需要时直接引用 |
| 备选方案与取舍 | 一并写在 SPEC | PLAN「备选方案与取舍」 |
| 数据流/状态机/协议细节 | 一并写在 SPEC | PLAN 对应章节 |
| 风险 | SPEC | PLAN「风险」 |
| 完成后需要同步的长期文档 | SPEC | PLAN「完成后需要同步的长期文档」 |

## 3. 核心原则

1. **需求与方案分离，方案与任务分离**——三者回答不同问题，写的时候不要互相渗透。验收标准里出现具体技术选型（"用 Redis 做缓存"），或方案里出现执行步骤（"先改 A 文件再改 B"），都是写串了。
2. **验收标准必须可测试且编号**——用 EARS 句式写（见第 6 节），逐条用加粗前缀编号（`- **AC-1**：…`）；不编号，TASKS 就没法准确引用，只能整段复制，直接违反 DRY。
3. **方案需要人确认才能往下走**——技术方案（无论写在 SPEC 里还是拆成 PLAN）写完后停下来，等确认后再拆 TASKS。不允许方案和任务在同一轮生成，否则等发现方案有问题时任务已经跑了一半。
4. **TASKS 不复制 SPEC/PLAN**——每个 task 引用对应的验收标准编号，不重新描述一遍验收标准或方案内容。
5. **Out of scope 和 in-scope 同等重要**——每份 SPEC 至少写 2-3 条"这次不做什么"，专门用来防 scope creep。
6. **偏差显式记录，不悄悄改 SPEC/PLAN**——执行中发现方案不可行，先在 TASKS 的"与 SPEC/PLAN 的实施偏差"里写清楚，再回头改对应文档，不能直接改掉了事，让方案失去可信度。
7. **是否拆分 PLAN 是判断出来的，不是习惯性动作**——每次进入方案阶段都要过一遍第 2 节的门槛，不要因为"上次拆了这次也拆"或"嫌麻烦就不拆"而跳过判断。
8. **单条 task 的描述行必须自足**——清晰动作 + 精确文件路径直接写在 checkbox 那一行，判断标准是"单独摘出这一行，一个没看过 SPEC 的新对话能不能照着做对"，不是"写没写额外说明"。
9. **执行前重新扎根，不依赖对话记忆**——开始任何一个 task 前，重新读一遍 SPEC（和 PLAN）里对应的验收标准与方案，尤其是 task 被拆给不同 agent 实例、或隔了很久再回来执行时；task 描述行是自包含摘要，不是免读源文档的许可证。

## 4. 文档模板

```markdown
# 任务名称 - Spec

## 背景与目标
## 范围
## 不做什么
## 用户场景与需求
## 能力边界
## Definition of Done
## 验收标准（逐条编号：AC-1、AC-2…）
## 关联模块
## 当前技术方案（简单方案直接写在这里；复杂方案见 PLAN.md）
## 关联文档
```

```markdown
# 任务名称 - Plan（仅复杂方案创建）

## 方案概述
## 备选方案与取舍
## 数据流 / 状态机 / 协议（视任务而定）
## 风险
## 完成后需要同步的长期文档
```

```markdown
# 任务名称 - Tasks

## 当前阶段
## 阶段任务
## 阻塞
## 与 SPEC/PLAN 的实施偏差
## 完成记录
```

"阶段任务"下每条 task 用勾选框写，不用 H3 标题、也不用独立的"状态"字段——勾选框本身就是唯一状态源：

```markdown
- [ ] T1 清晰动作 + 精确文件路径（这一行本身要自足，能脱离对话历史直接执行）
  - 关键实现点或子步骤（仅当一行装不下时才加，1-3 条）
  - 依赖：T0（仅当不是"接在上一条后面做"这种默认顺序依赖时才写）
  - _对应验收标准：AC-1, AC-3_
  - _测试先行：对应测试文件（如有）_
```

完成时把 `- [ ]` 改成 `- [x]`。只有两态（未完成/已完成），不设"进行中"——task 本身要拆得够小（见第 7 节），小到不需要一个中间状态来描述"做了一半"。task 之间默认按列表顺序依赖，不需要给每条都标 `[P]` 或写依赖，只有非顺序依赖才显式写出来。

**设计取舍**：这里没有采用业界工具常见的 `[P]` 并行标记和两级任务编号（如 T1.1 这种子任务）。前者是因为目前顺序执行为主，没有并行跑多个 agent 的需求；后者是因为第 7 节的颗粒度规则已经要求 task 本身拆得够小，不需要再拆子任务。之后如果开始并行跑多个 agent 实例，或任务规模明显变大，可以重新评估这两条。

活跃任务中，验收标准用加粗前缀的列表项写，例如 `- **AC-1**：当用户点击"发布"时，系统应当校验必填字段`——加粗编号是给 TASKS 引用用的锚点，不能把编号埋在一段自然语言里，否则等于没编号。

活跃任务中，SPEC 始终维护当前已确认的目标与范围；PLAN（若存在）维护当前已确认方案；TASKS 只在阶段、状态、阻塞或偏差变化时更新。任务归档后，三者冻结。

`SPEC` 是当前版本范围的唯一 Owner：它必须写清用户得到什么、明确不做什么、异常边界在哪里、涉及哪些模块，以及何时可以宣布完成。`Definition of Done` 描述交付门槛；验收标准给出可验证的用户行为、数据结果或质量检查，二者不互相复制。`PLAN`（若存在）是当前任务技术方案的唯一 Owner：备选取舍、风险、需同步的长期文档都归它管，不在 SPEC 里重复；关联模块始终属于 SPEC，PLAN 不重复列。

## 5. 完整工作流

### 阶段 0：触发判断

按第 0 节门槛判断是否创建；命中则创建任务目录（位置见《文档体系 SOP》目标目录：`02-开发任务/YYYY-MM-DD-task-slug/` 或 `03-重构任务/YYYY-MM-DD-task-slug/`）。

### 阶段 1：需求阶段（写 SPEC 前半部分）

| 项目 | 说明 |
|---|---|
| 输入 | 一句话到几句话的原始诉求 |
| 产出 | SPEC.md 的：背景与目标 / 范围 / 不做什么 / 用户场景与需求 / 能力边界 / Definition of Done / 验收标准 / 关联模块 |
| 完成标志 | 范围和验收标准无歧义，任务发起人确认后才能进入阶段 2 |

写法：

- **用户场景**用"作为 [角色]，我想要 [诉求]，以便 [收益]"的句式，逼自己想清楚"为谁做、为什么做"，不是直接跳到功能点。
- **验收标准**逐条用 EARS 句式（见第 6 节）写，并逐条编号（AC-1、AC-2…）。每写一条自检一次：这条能不能被测试或验证？是否只有一种解读？
- **不做什么**至少列 2-3 条，优先写"看起来相关但这次故意不做"的东西，而不是随便写几条无关的。
- **DoD 和验收标准不互相复制**：DoD 是交付门槛（"功能可用、无阻塞 bug、文档已同步"），验收标准是可验证的用户行为/数据结果/质量检查，两者是不同粒度的东西。

常见错误：把实现细节写进验收标准（该写在阶段 2 的方案里）；范围写得含糊导致后面验收对不上。

### 阶段 2：方案阶段（先判断是否拆出 PLAN.md）

| 项目 | 说明 |
|---|---|
| 输入 | 已确认的需求（阶段 1 产出） |
| 产出 | 简单方案：SPEC.md 的"当前技术方案"章节；复杂方案：独立 PLAN.md |
| 完成标志 | 方案被确认后才能进入阶段 3 |

按第 2 节的门槛判断是否拆分，再按分配表填内容。写法：

- 只写**这次真正要做的选择和权衡**，不复述通用架构（那是 A2/模块 ARCHITECTURE 的事）。如果这次决策会长期影响全局架构或模块边界，登记进"完成后需要同步的长期文档"，归档时才落地同步。
- 每个关键决策写"选了什么 / 为什么 / 放弃了什么"，只写结论看不出权衡过程，以后自己都看不懂当初为什么这么定。
- 决策若**跨模块或难逆转**，判断是否需要单独开 ADR（规则见《文档体系 SOP》）；SPEC/PLAN 里链接过去，不重复写全文。

Gate：方案（SPEC 的方案章节或独立 PLAN）确认后才能生成 TASKS。防止"方案和任务同时生成、人来不及审查方案就已经在执行"。

### 阶段 3：任务阶段（写 TASKS.md）

| 项目 | 说明 |
|---|---|
| 输入 | 已确认的 SPEC（需求 + 方案，或 SPEC + 独立 PLAN） |
| 产出 | TASKS.md 的：当前阶段 / 阶段任务 / 阻塞 / 与 SPEC/PLAN 的实施偏差 / 完成记录 |
| 完成标志 | 所有 task 完成，且逐条对照验收标准核对通过 |

写法：

- 每个 task 用第 4 节的勾选框格式写：`- [ ]` 后接编号和一句自足的描述（清晰动作 + 精确文件路径），不是先写标题再补一堆字段。
- **描述行本身要够精确，不是靠额外说明兜底**：自测标准是"把这一行单独发给一个没看过 SPEC 的新对话，能不能照着做对"。做不到，该补的是动作和文件路径，不是加一段模糊的背景介绍。多步骤的 task 才在下面加 1-3 条子步骤，不是每条都要写。
- task 之间默认按列表顺序依赖（前一条做完才做下一条）；只有跳跃式、非顺序的依赖才显式写"依赖：T0"。
- 每个 task 末尾附对应验收标准编号（`_对应验收标准：AC-1_`，不是重新描述一遍验收标准），能写测试的附测试文件路径。
- 能写自动化测试的 task，测试先行——task 完成 = 测试通过，而不是"感觉写完了"；完成时把 `- [ ]` 改成 `- [x]`，不需要额外的状态字段。
- 阻塞写在 TASKS 的"阻塞"章节里，写清楚原因（"依赖 X 模块接口未定"），不是写"卡住了"三个字了事。
- 执行中发现方案不可行或范围需要调整：先写进"与 SPEC/PLAN 的实施偏差"，再回头更新对应文档（SPEC 的技术方案或 PLAN），两边保持一致——不能只改一边。
- **开始执行任意一个 task 前，先重新读一遍 SPEC（和 PLAN，若存在）里这个 task 对应的验收标准和方案，不要只依赖对话历史里的记忆**——这条对单开新对话执行某个 task，或者任务跨了很长时间/很多轮对话再回来做，尤其重要。task 描述行能保证本身可读，但不能替代回去核对源头的动作。

### 阶段 4：收尾与归档

1. 逐条核对 DoD 和验收标准（建议用清单形式一条条打勾，不是笼统说"做完了"）。
2. 补齐"完成后需要同步的长期文档"列出的项（在 SPEC 或 PLAN 里，同步到 A2 / ARCHITECTURE / 模块 DESIGN，规则见《文档体系 SOP》）。
3. TASKS 里仍未解决的事项，按《文档体系 SOP》的"延后项三种合法去向"转成明确的后续任务，不能悬空留在已归档文档里。
4. 任务目录移入 `98-归档/`，SPEC、PLAN（若存在）与 TASKS 冻结。

## 6. 验收标准写作速查（EARS）

| 场景 | 句式 | 示例 |
|---|---|---|
| 事件触发 | 当 [事件] 时，系统应当 [行为] | 当用户点击"发布"时，系统应当校验必填字段 |
| 条件前提 | 如果 [条件]，则系统应当 [行为] | 如果角色资产未生成完成，则系统应当禁用"下一步"按钮 |
| 事件+条件组合 | 当 [事件] 且 [条件] 时，系统应当 [行为] | 当用户提交表单且存在必填项为空时，系统应当在对应字段旁显示错误提示 |
| 持续状态 | 只要 [状态持续]，系统应当 [行为] | 只要生成任务在排队中，系统应当显示进度指示 |
| 兜底/异常 | 如果 [异常情况] 发生，系统应当 [兜底行为] | 如果生成失败，系统应当保留用户已上传的素材并提示重试 |

不确定的需求不要脑补成具体数值——SPEC 里写"待确认：xxx"，而不是自己编一个看起来合理的默认值蒙混过去。

## 7. Task 颗粒度自检

| 信号 | 说明 |
|---|---|
| 太大 | 涉及 3 个以上模块 / 无法在一个专注时段内完成 / 验收标准要引用 5 条以上 SPEC 条目 |
| 太小 | task 之间没有独立验证意义，纯粹是把一个动作机械拆成三步 |

判断标准：拆出来的每个 task，单独看都应该能回答"做完了怎么验证"。回答不了，说明要么太大（验证点混在一起），要么太小（这一步本身不构成验证单元）。

## 8. 编写者行为约束

无论执行者是人还是 AI，写作过程都遵守：

- 阶段 1 写完必须停下来等确认，不能自己接着写方案。
- 进入阶段 2 先过一遍第 2 节的拆分门槛，不能默认合并或默认拆分，更不能拆完 PLAN 才发现方案其实很简单。
- 阶段 2 写完（无论是否拆出 PLAN）必须停下来等确认，不能自己接着拆 TASKS。
- SPEC 缺少"不做什么"时，不能开始写方案——先补上或标注待确认。
- 验收标准存在歧义时，标注"待确认"，不能替用户做决定；验收标准必须编号，不能写成无编号的自然段。
- 写 TASKS 时必须用第 4 节的勾选框格式，描述行必须写到能脱离对话历史独立执行（清晰动作 + 精确文件路径），不能只写一句任务名了事。
- TASKS 执行中发现方案有问题，先写偏差，不能直接改 SPEC/PLAN 的方案内容掩盖过去。
- 执行任意 task 前，重新读取 SPEC（和 PLAN）对应章节，不依赖对话历史里的记忆。

## 9. 写作前自检清单

新建或修改 SPEC/PLAN/TASKS 前，依次确认：

1. 我现在写的是需求、方案还是执行状态？是否写进了不该属于这一部分的内容？
2. 每条验收标准是否可测试、是否只有一种解读、是否已编号（AC-1…）？
3. 是否明确写了"不做什么"？
4. 方案是否触发了 PLAN 拆分门槛？拆分决定是判断出来的，还是习惯性动作？
5. 技术方案是否写清楚了"为什么选这个、放弃了什么"，而不只是结论？
6. 这次决策是否需要同步进长期文档或开 ADR？是否已登记？
7. 每条 task 的描述行是否可以脱离对话历史、单独摘出来就能看懂、能照做（而不是靠额外字段兜底）？
8. TASKS 里的阻塞和偏差是否写明了原因，而不是含糊带过？
9. 归档前，是否所有未解决事项都有了明确的后续去向？

## 10. 命名

| 对象 | 命名 |
|---|---|
| 任务文档 | `SPEC.md`、`TASKS.md`；方案复杂时加 `PLAN.md` |
| 验收标准编号 | `AC-1`、`AC-2`… |
| Task 编号 | `T1`、`T2`…（flat，不设两级子编号） |
| 任务状态 | `- [ ]` 未完成 / `- [x]` 已完成（不设"进行中"） |
| 任务目录 | `YYYY-MM-DD-task-slug`，位置见《文档体系 SOP》目标目录 |
