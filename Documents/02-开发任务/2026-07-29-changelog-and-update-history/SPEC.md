# 更新记录与 Changelog - Spec

## 背景与目标

StoneFlow 已有应用内更新检查、下载、安装与当前版本更新弹窗，但用户无法稳定回看更新历史，且更新成功重启后没有明确反馈。本任务建立一套低维护成本的用户 changelog：发布者只维护一份内容，用户可在更新前、主动查看记录和更新成功后读取对应版本的用户可见变化。

## 范围

- 新增根 `CHANGELOG.md`，作为唯一人工维护的用户 changelog。
- 发布时将 changelog 作为独立 R2 静态文件发布；updater manifest 不再携带 changelog。
- 在头像菜单的“应用”分组增加“更新记录”，打开非路由弹窗。
- 更新弹窗展示目标版本条目；无条目不显示空白说明区。
- 通过应用内更新完成重启后显示一次成功 Toast，并可定位到对应记录。
- 远端读取失败时使用随应用打包的 changelog 快照回退。

## 不做什么

- 不增加主导航、路由页面、设置子页面或命令面板入口。
- 不从 Git 提交自动生成用户文案，也不维护 `RELEASE_NOTES.md` 或每版本 JSON 内容副本。
- 不改变更新检查频率、渠道设置、下载、跳过版本和安装行为。
- 不支持图片、GIF、视频、HTML、链接、引用、代码块或完整 Markdown 方言。
- 不为没有用户可见变化的版本伪造 changelog 条目。

## 用户场景与需求

### US-1：发布者维护可读的版本变化

作为发布负责人，我想在每次有用户可见变化的 Beta 或 Stable 发布前维护一段用户文案，以便同一份内容同时服务发布、更新弹窗和历史记录。

### US-2：Stable 用户主动回看正式更新

作为 Stable 用户，我想从头像菜单查看正式版本记录，以便了解产品已经发生的变化，而不被 Beta 测试过程干扰。

### US-3：Beta 用户核对测试变化

作为 Beta 用户，我想看到正式版本和每个 Beta 的增量，以便知道当前测试版本相对前一版本的实际变化。

### US-4：用户在更新前和更新后获得恰当说明

作为正在更新的用户，我想在发现目标版本时看到该版本的简短说明，并在应用内更新重启成功后得到一次确认，以便决定是否更新并确认安装结果。

## 能力边界

- 条目只支持用户可见的功能、体验、修复和必要风险说明，不写 PR、Issue、内部模块名、依赖升级或实现细节。
- 内容格式只支持版本二级标题、分类三级标题、列表、加粗、普通段落与 Unicode 图标；空分类不写。
- Stable 视图只显示 Stable 条目；Beta 视图显示 Stable 与 Beta 条目。弹窗不提供独立渠道切换器，始终跟随当前更新渠道。
- 无对应条目、远端不可读或本地快照没有该版本时，更新功能仍可用，只是不展示 changelog 区块。
- 只有应用内更新触发的、版本匹配的重启安装成功后才显示 Toast；首次安装、外部覆盖安装和后续启动不显示。

## Definition of Done

- 所有验收标准通过定向自动化或明确的手动验证。
- 发布链、内容读取、渠道过滤、更新弹窗和一次性 Toast 均无阻塞性回归。
- 文档 Owner 已同步，且没有遗留双写的 changelog 内容源。
- 根目录质量检查和受影响 Rust 检查通过；真实 R2 发布或跨平台安装只在获得单独授权后执行。

## 验收标准

- **AC-1**：当发布脚本发布任一渠道时，系统应当先上传唯一的 `CHANGELOG.md`，再覆盖该渠道的 `updates/<channel>/latest.json`。
- **AC-2**：当生成 updater manifest 时，系统应当省略 `notes` 字段，且客户端更新检查不再依赖该字段。
- **AC-3**：当根 `CHANGELOG.md` 含有版本条目时，系统应当校验版本标题格式与重复版本；当目标版本没有条目时，发布应当继续完成。
- **AC-4**：当用户在 Stable 渠道打开“更新记录”时，系统应当仅显示 Stable 条目并按版本倒序排列。
- **AC-5**：当用户在 Beta 渠道打开“更新记录”时，系统应当显示 Stable 与 Beta 条目并按版本倒序排列。
- **AC-6**：当发现目标版本且存在对应条目时，系统应当在现有更新弹窗显示该条目；当内容不可读或不存在时，系统应当继续提供更新操作且不显示空说明区。
- **AC-7**：当远端 changelog 不可读时，系统应当使用当前应用打包的快照；当两者都不可读时，系统应当展示可用的空状态或无说明状态。
- **AC-8**：当用户通过应用内流程重启安装且新进程版本与待确认版本一致时，系统应当仅显示一次成功 Toast；当用户点击“查看更新内容”时，系统应当打开并定位到该版本。
- **AC-9**：当首次安装、外部安装、版本不匹配或第二次启动时，系统不得显示更新成功 Toast。
