## 3. 系统总览

StoneFlow 当前是一个 **单 Tauri binary 的本地优先桌面应用**。

可以把它理解成下面这条主链：

```txt
React UI
  -> feature api / hooks (Query·Mutation)
  -> Tauri command / event
  -> runtime
  -> usecase
  -> storage
  -> SQLite
```

其中：

- 前端负责界面、交互、路由、客户端状态和 command 调用；
- Rust 负责窗口、命令、业务编排、持久化和系统级能力；
- SQLite 是本地唯一事实源；
- 前端不直接访问数据库。

前端架构日常以 `src/ARCHITECTURE.md`、`src/CONVENTIONS.md` 与各层 `ARCHITECTURE.md` 为准。历史解构卷宗见 `Docs/98-归档/04-前端架构解析-2026-07/`（已归档，禁止当改码依据）。若冲突，以代码事实为准并回写短契约 / T1。

## 4. 前端架构

## 4.1 当前心智模型

前端不是“所有状态丢给一个 store”，也不是“大 Shell + 散落页面”。稳定心智是：

```txt
启动接线在 app · 铬架在 layout · URL 薄页在 routes ·
能力在 features（model/api/hooks/components + public）·
纯零件在 shared · 样式在 styles
```

依赖只允许向「更稳定、更无业务」的方向；**跨 feature 只走 public**（`features/<name>/index.ts`，以及少数 `contract.ts` / `page.ts`）。

状态视角：

```txt
TanStack Query
  -> 管服务端状态 / 可回源数据

Zustand / React state / useSyncExternalStore
  -> 管客户端 UI 状态
```

## 4.2 目录结构

当前前端正式目录如下：

```txt
src/
├─ main.tsx                 # 入口：bootstrap → RouterProvider
├─ app/                     # 组合根：Providers、router 装配、导航语义
│  ├─ providers/            # QueryClient 等全局 Provider
│  └─ navigation/           # path 语义、intent、route memory（非视觉）
├─ layout/                  # 应用铬架：侧栏/顶栏/主区/overlay/command-bridge
├─ routes/                  # TanStack file routes + 薄页（无顶层 pages/）
├─ features/                # 业务垂直切片（可删单位）
├─ shared/                  # 与业务实体无关的 UI / hooks / lib
├─ styles/                  # token / base / utilities
├─ test/                    # 测试基建
├─ ARCHITECTURE.md
└─ CONVENTIONS.md
```

### `app/`

职责：启动接线、全局 Provider 树、router 实例装配、导航语义与记忆。

不负责：侧栏/顶栏视觉、实体业务规则、list-scene 实现。

关键路径：

- `app/App.tsx`、`app/router.tsx`
- `app/providers/`
- `app/navigation/`

### `layout/`

职责：产品铬架 UI、EntityScene 槽位编排、壳级 overlay 挂载、CommandBridge 装配（组合各 feature 的 public 切片）。

不负责：实体 Query 编排、task/project 业务板实现。

关键路径：

- `layout/AppLayout.tsx`、`ShellRouteLayout.tsx`、`ShellChrome.tsx`
- `layout/header/`、`sidebar/`、`overlays/`
- `layout/command-bridge/`、`layout/entity-scene/`

### `routes/`

职责：URL 匹配、loader/redirect、薄页接线（挂 feature 的 page/scene，不写厚业务）。

主结构示意：

```txt
routes/
├─ __root.tsx
├─ index.tsx                 # 根恢复 / redirect
├─ launcher.tsx
├─ settings.tsx
├─ debug.activity.tsx
└─ _shell/
   ├─ route.tsx              # 挂 AppLayout + Outlet
   ├─ all/…                  # 全局 scope 下各 section 薄页
   └─ spaces/$spaceId/…      # space scope 下对称薄页
```

### `features/`

职责：某一产品能力的全栈（model → api → hooks → components），并通过 **public 入口** 对外暴露。

典型约定（可按 feature 省略空夹）：

| 目录          | 职责                                                                  |
| ------------- | --------------------------------------------------------------------- |
| `model/`      | 类型、纯规则、ports                                                   |
| `api/`        | 仅 IO：invoke / Store / listen                                        |
| `hooks/`      | Query / Mutation / list-scene facade                                  |
| `components/` | 业务 UI                                                               |
| `index.ts`    | **唯一默认 public**（跨 feature / layout / routes 只应从这里 import） |
| `contract.ts` | 可选；极窄契约（如 settings 侧栏意图类型）                            |
| `page.ts`     | 可选；供 routes 挂载的页面出口                                        |

**禁止：** 跨 feature 深路径 import 对方私有文件；`shared` 反向依赖 features/layout/app。

边界脚本：`scripts/check-feature-boundaries`（随 `bun run check`）。

当前 feature 集合（目录名，会随产品演进）：`activity`、`bulk-action`、`command`、`danger-confirm`、`display-options`、`entity-detail`、`filter`、`global-search`、`lifecycle`、`metadata-fields`、`project`、`project-overview`、`launcher`、`selection`、`settings`、`space`、`submit`、`sync`、`task`、`update`、`view`、`workspace`。

列表类场景（inbox / all-tasks / no-project / archive / trash 等）**不再各自成 feature 壳**；路由薄页 + `task` 等 domain feature 的 list-scene facade（如 `useTaskListScene`）承接。

### `shared/`

职责：跨 feature 共用且**不带产品业务归属**的内容。

当前常见子树：`components/`（含 base/shadcn、main-card、board/row 壳等）、`hooks/`、`lib/`、`query/`（跨 feature invalidation 等）、`types/`、`events/`、`form/`、`config/`、`autosave/`、`validation/`。

### `styles/`

职责：样式 token、shadcn adapter、base / utilities、Tailwind v4 入口。

## 5. 前端状态边界

## 5.1 Server State

服务端状态统一由 `TanStack Query` 承接。

主要覆盖：`space`、`project`、`task`、`lifecycle`、`view`、`activity`、`search`、`settings`（含设备偏好等）、`sync` / `update` 相关查询切片等。

落点规则：

- `features/{feature}/api/`：Tauri invoke / facade
- `features/{feature}/hooks/`：query keys、hooks、mutations、数据组合（旧称 `query/` 已收敛到 hooks）
- `shared/query/`：跨 feature 失效与通用 query 工具

`QueryClient` 默认值适配本地桌面应用（见 `app/providers`）：

- `staleTime: 30s`
- `gcTime: 10min`
- `refetchOnWindowFocus: false`
- query `retry: 1`
- mutation `retry: 0`

## 5.2 Client UI State

客户端 UI 状态由 Zustand、React state 和少量 `useSyncExternalStore` 组合承接。

典型范围：Shell 瞬时态、Drawer / Dialog 打开态、selection、filters、command runtime、launcher session、submit registry 等。

规则：

- 可持久化、可回源的数据优先进 Query
- 纯 UI 瞬时交互状态才放 Zustand / 本地 state
- 不允许回到「server state 与 client state 混写在一个大 store」的旧模式

## 6. 路由设计

当前前端路由使用 **TanStack Router**，**hash history** + **file-based routes**（`src/routes`，生成 `src/routeTree.gen.ts`）。

主 URL 语义（示意）：

```txt
/
  -> 根恢复 redirect

/launcher
  -> Launcher 窗口页

/debug/activity
  -> Activity 调试页

/all/*
  -> 全局 scope 壳内各 section

/spaces/:spaceId/*
  -> Space scope 壳内各 section
```

壳内 section 包括（与 `_shell` 下薄页对应）：`inbox`、`tasks`、`tasks/:taskId`、`views`、`views/:viewId`、`projects`、`projects/:projectId`、`archive`、`trash`、`settings`、`no-project` 等。

### 导航语义层

URL ↔ 产品语义不散落在组件里手拼路径，而集中在：

- `app/navigation/`：解析 canonical path、shell section、scope-aware path、route memory / 历史
- layout / command 通过统一语义消费路由，而不是各自拼字符串

结论：

- 当前项目是 **TanStack Router + app/navigation 语义层 + layout 铬架**
- 不是 React Router；也不是「路由文件直接堆业务组件」

细账（归档）见 `Docs/98-归档/04-前端架构解析-2026-07/03-To-Be/02-路由与导航生命周期.md`；日常以 `src/app/navigation/ARCHITECTURE.md` 为准。

## 7. App Shell 与页面装配

当前正式装配链：

```txt
routes/_shell (TanStack layout route)
  -> AppLayout / ShellRouteLayout
    -> ShellChrome（header + sidebar + main）
      -> MainCard / EntityScene
        -> 路由薄页 → feature page / list-scene / board
```

职责划分：

| 层                  | 负责                                                           |
| ------------------- | -------------------------------------------------------------- |
| `routes`            | 匹配、redirect、把 props/params 交给 feature 出口              |
| `layout`            | 稳定铬架、overlay 挂载点、CommandBridge 装配、EntityScene 槽位 |
| `features`          | 业务查询、列表场景、详情、命令实现切片                         |
| `shared/components` | 无业务归属的 card / board / row 等零件                         |

原则：

- layout 只负责稳定宿主与装配，不写实体规则
- 业务渲染下沉到 feature；跨业务零件在 shared
- board / row / field 等基建不反向塞回 layout
- 壳组合 feature 时只依赖 **public**（及约定的 contract/page）

细账（归档）见 `Docs/98-归档/04-前端架构解析-2026-07/03-To-Be/04-壳与平台拼装.md`；日常以 `src/layout/ARCHITECTURE.md` 为准。

## 8. Launcher 前端结构

Launcher 不是普通页面，而是有独立 session / domain / chrome 分层的浮窗系统。

当前正式结构：

```txt
features/launcher/
├─ api/
├─ session/
├─ domain/
├─ chrome/
├─ composer/
├─ create/
├─ results/
└─ model/
```

职责边界：

- `session`：窗 phase 与事件桥接
- `domain`：业务态、草稿、搜索、提交、派生状态
- `chrome`：固定壳槽位与 Surface
- `composer` / `create` / `results`：输入、新建行、列表 IA
- `api`：窗 IPC + 到 task / global-search 的适配

活跃契约：`src/features/launcher/ARCHITECTURE.md`。

## 9. Command 与批量操作系统

### 9.1 Command

命令系统当前已经是独立 feature，不再只是几个快捷键工具函数。

正式目录：

```txt
features/command/
├─ adapters/
├─ commands/
├─ core/
├─ keybinding/
├─ runtime/
├─ shortcuts/
└─ components/
```

核心链路：

```txt
Command Registry
  -> Keybinding Registry
  -> CommandShortcutLayer
  -> CommandRuntime
  -> Shell Adapter / Feature action
  -> CommandMenu / ShortcutHelp / ChordHint
```

### 9.2 Bulk Action

批量操作当前也是独立 feature：

```txt
features/bulk-action/
├─ actions/
├─ adapters/
├─ core/
├─ runtime/
├─ selection/
└─ components/
```

它的职责是统一：

- snapshot
- action registry
- confirmation
- bulk mutation capability injection
- result feedback

页面不应再手写一套本地批量循环。

## 11. Rust / Tauri 架构

当前后端正式结构以 `src-tauri/ARCHITECTURE.md` 为准。

核心心智：

- 单生产 binary：`stoneflow`
- 主窗口与 Launcher 浮窗由同一 Tauri Core 管理
- 业务规则在 `domain / usecase`
- 持久化在 `storage`
- Tauri 壳层与窗口在 `runtime / platform`

### 11.1 Workspace

当前 workspace 成员：

- `runtime`
- `platform`
- `domain`
- `usecase`
- `storage`
- `schema`
- `migration`
- `test-support`
- `integration-tests`

### 11.2 各层职责

#### `runtime`

职责：

- Tauri builder
- commands 注册
- 主窗口 / Launcher 窗口 / tray / shortcut
- Tauri state
- usecase adapter 装配

#### `platform`

职责：

- macOS / Windows 平台窗口差异
- Quick window 平台行为

#### `domain`

职责：

- 纯领域规则
- 值对象
- 枚举
- 领域错误

#### `usecase`

职责：

- 用例编排
- DTO
- ports

#### `storage`

职责：

- SQLite
- repositories
- mappers
- bootstrap

#### `schema`

职责：

- SeaORM entity

#### `migration`

职责：

- schema 迁移

#### `test-support`

职责：

- 测试基础设施

#### `integration-tests`

职责：

- 集成测试宿主

### 11.3 依赖方向

当前正式依赖方向：

```txt
stoneflow(root)
  -> stoneflow-runtime

runtime
  -> usecase, storage, platform, domain, schema

platform
  -> tauri, OS bindings

usecase
  -> domain

storage
  -> domain, usecase, schema, migration

migration
  -> schema

schema
  -> sea-orm
```

禁止：

- `domain` 依赖 Tauri / SeaORM / runtime
- `usecase` 依赖 `storage` 实现
- `storage` 依赖 `runtime`
- 生产代码依赖 `test-support`

## 12. 数据与命令边界

StoneFlow 当前数据流原则：

1. 前端通过 feature API 调用 Tauri command
2. command 把输入转换成 usecase 输入
3. usecase 编排业务规则
4. storage 负责查询和写入 SQLite
5. 前端通过 Query 失效与重拉保持 UI 一致

关键约束：

- 前端不直接访问数据库
- Tauri command 的输入输出是 IPC DTO，不是领域模型直出
- SeaORM `Model` 不应泄漏到 usecase 公共 API

## 13. 当前长期约束

### 13.1 前端

1. Server state 默认走 TanStack Query。
2. Client UI state 才进入 Zustand / React state。
3. Feature 内优先分清 `api / query / model / ui`。
4. Layout 只做装配，不做业务实现。
5. 代码附近 `ARCHITECTURE.md` 是局部结构真相位。

### 13.2 后端

1. Tauri 壳层只放在 `runtime / platform`。
2. 业务规则优先沉淀在 `domain / usecase`。
3. `storage` 只做持久化与映射。
4. 当前单 binary 心智不再回退到 `helper-app + desktop-app`。

### 13.3 文档

1. 本文是系统总览，不再承担迁移计划。
2. 局部结构变化时，优先改对应 `ARCHITECTURE.md`，再视需要回写本文。
3. 若未来路由、状态管理、Rust workspace 再发生明显变化，本文必须同步更新。

## 14. 当前最容易漂移的点

后续最容易再次写错的地方有三类：

1. 把前端状态又写回“Zustand 单中心”。
2. 把 Rust 架构又写回 `desktop-app / helper-app / IPC` 旧心智。
3. 把代码同位架构文档与 `Docs/T1` 写成两套互相冲突的描述。

因此后续维护时，优先检查：

- 当前路由是不是仍在 TanStack Router（hash + file routes）体系下
- 当前 server state / client state 边界有没有变化
- 当前 `features/*/index.ts` public 与 boundaries 有没有被破坏
- 当前 Rust workspace 结构有没有变化
