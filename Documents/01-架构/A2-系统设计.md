# 系统设计

## 技术目标

- 本地优先，离线时可完整读写个人任务。
- 前后端与平台能力保持明确边界。
- 后台同步尽量无感，不把同步协议复杂度暴露为日常工作流。
- 保持模块内聚，避免业务数据出现多份真相。

## 整体技术栈

| 层 | 当前技术 |
|---|---|
| 桌面壳 | Tauri v2 |
| 前端 | React 19、TypeScript、Vite、Tailwind CSS v4、HeroUI OSS 3.2.4、HeroUI Pro 1.0.0-beta.8 |
| 路由 | TanStack Router（Hash + file routes） |
| 业务数据 | TanStack Query |
| 跨组件 UI 状态 | Zustand（限定使用） |
| 表单与校验 | React Hook Form、Zod |
| 本地持久化 | SQLite、SeaORM、SeaORM Migration |
| 同步云端副本 | 用户自备 PostgreSQL（Neon / 自建同一路径）；客户端直连 sqlx |
| 后端 | Rust workspace、Tokio |
| 测试与检查 | Vitest、Testing Library、oxlint、oxfmt、Cargo tests |

标准界面直接组合锁定版 HeroUI OSS/Pro，不建立第二套控件库或一对一视觉 wrapper。HeroUI Pro 通过固定版 CollectUI `hpsetup@4.7.0` 取得；`HEROUI_KEY` 只允许作为安装进程环境变量存在，不进入 renderer、运行时配置、仓库文件或构建产物。

## 前端运行机制

路由管理 URL、历史与**可恢复 Filter Draft**（search 键 `f` = 编码后的完整 `FilterQuery` 快照）。TanStack Query 是 Task、Project、Space、Saved View 等业务数据的前端缓存与失效层；Zustand 仅用于跨组件 UI 状态；React local state 仅保留在单个组件的瞬时交互中。

不允许同一业务数据同时作为 Query、Zustand 和组件 state 的独立真相。Feature 的 API facade 是唯一 `invoke()` 入口，页面与 shared 不直接调用 Tauri。

工作区集合页面统一由 `shared/components/page-frame` 提供 Header、HeroUI Toolbar 与 Body 的纯视觉骨架；Default View、筛选和显示动作进入同一个标准 Toolbar，`filterBar` 作为其下方的独立区域，只在 Filter Draft dirty 时产生内容。所有任务、独立事项、项目详情与 Saved View 详情共用唯一 **Task Workspace**：页面只提供 `scope + context + base`、Default View 集合和页面专属动作；任务结果、Filter Draft、Display、选择、预览与 TaskBoard 接线归该工作台。`/views` 根页只是 Saved View Library，不拥有第二套任务结果场景。批量操作只由 Shell 组合根挂载一个 viewport-fixed `BulkActionBar`，其按钮与可用性统一投影自 Command Runtime。

标准设置控件直接使用 HeroUI：同步分钟由 OSS `NumberField` 处理数字输入，Space 固定色板由 OSS `ColorSwatchPicker` 处理选择，设置开关行由 Pro `CellSwitch` 处理整行交互，默认 Space 由 Pro `CellSelect` 处理下拉语义。StoneFlow 只持有受控草稿、业务 mutation、canonical 回写和错误反馈，不复制输入、键盘、Focus 或 Overlay 状态机。

跨 Feature 日期继续使用 `YYYY-MM-DD` 的本地日历日期合同。Launcher 与全局日期 Modal 在各自既有 overlay 内组合 OSS `Calendar`，共享的 Date view adapter 只负责与 `DateValue` 双向转换；UI 供应商类型不得进入 reducer、Command、Task DTO、Tauri API 或持久化层。

### Default View / Saved View / Filter Draft（2026-08 已确认目标）

| 概念 | 真源 | 说明 |
|---|---|---|
| **FilterQuery** | `shared/types/filterQuery` + `features/filter/core` | clause 列表：`field + op + values`；Default、Saved 与 Draft 共用形状 |
| **Default View** | 页面策略 | 代码定义的 `key + label + baseViewKey`；必须单选，不入库 |
| **Saved View** | SQLite | 持久化 `scope + context(all | standalone | projectId) + baseViewKey + filters`；不保存 Display |
| **Filter Draft** | 路由 search `f` | 完整 FilterQuery 快照；只在与 base 语义不同时存在并驱动 FilterBar |
| **Effective FilterQuery** | Task Workspace 派生 | `dirty ? draft : base`；不建第二份持久化状态 |
| **Display** | renderer localStorage（personal + page default） | 只负责分组、排序和行字段；不决定任务是否进入结果集 |

- `context` 是 Task Workspace 的不可移除查询边界，不是 FilterQuery clause；不增加与它重复的 origin/page metadata。保存时写入当前 `scope + context + baseViewKey + effective filters`。
- 路由必须区分“无 Draft”与“空 FilterQuery Draft”；dirty 由规范化后的 draft/base 语义相等性决定，不由 clause 数量决定。恢复当前 View 只删除 Draft。
- `FilterBar` 在 clean Default View 或 clean Saved View 上必须完全隐藏；只有 dirty Draft 时才显示当前完整筛选公式、恢复和保存操作。FilterMenu 仍以 effective query 表达选中项。
- Default View 用稳定业务 key 而不是数组 index。Toggle 在 selection change 的同一交互提交中立即反馈；URL 与查询刷新是后续非紧急工作。短生命周交互 intent 可用于衔接路由提交，但不得成为第二业务真源。
- 任务结果宿主只有 Task Workspace。`/views` 渲染 Saved View Library；`/views/:viewId` 保留稳定路径并向 Task Workspace 提供 saved-view source。
- Task 查询只有一个无损执行器：`run_task_query(scope + context + baseViewKey + filters)`；Default View 直接调用，`run_task_view` 仅负责读取并校验 Saved View 定义后委托同一执行器。两条入口不得各自解释 FilterQuery。
- 主 UI 保留锚定 `FilterMenu` + 条件式 `FilterBar`；`F` / 筛选命令打开锚定菜单，不以全页 filter picker 为主路径。`PageFilterController` 只保留 Command 所需的最小投影与 action port，不持有第二份筛选状态；重复 UI event 发射与 `showCompleted` 投影已删除。

任务列表读路径约定（性能基线）：

- `run_task_query` / `run_task_view` 均返回窗口页（`items` + `nextCursor`）；仅首屏携带精确 `totalCount`，续页为 `null` 且不得重复 COUNT，默认页大小约 150；前端 `useInfiniteQuery` 续拉。
- **筛选下推**：Task Workspace 合成 `scope + context + baseViewKey + effective FilterQuery`；storage 用同一 SQL predicate 执行精确 count 与 `(position, id)` keyset 窗口，完整支持 status / priority / project / due / planned 的 `is` 与 `is_not`。禁止先全量 materialize 再在应用层切页；`totalCount` 未就绪为 `undefined`，禁止与 0 条混淆。侧栏 badge 走 count-only 用例，不加载任务窗口或 lookup。
- **旧 Saved View 解码**：旧 `filters_json` 仅在 application 存储解码边界转换；可无损表达的条件精确升级，当前 FilterQuery 无法表达的旧条件显式失败，不得用近似条件扩大或缩小结果集。无效定义仍可在 Saved View Library 单独删除，但不可编辑或执行，且不影响其它 Saved View 列表与运行。
- **Board**：`taskBoardModel` 纯几何 + `useTaskBoardSticky`；内容定高直接决定原生 viewport 的 `scrollHeight`，折叠后由浏览器自动更新 HeroUI 主题滚动条。
- 列表 DTO **不含 note**；备注仅详情 / 预览 `get_task_detail` 读取。
- Space/Project 名称用 `WHERE id IN (...)` 批量补齐，禁止列表主路径串行 `get`。
- 任务 Board：`@tanstack/react-virtual` + **状态分区 sticky**；几何在 `taskBoardModel`（pure）。
  - 内容总高 = 当前 flat（折叠已反映）+ 未加载行占位（仅 `hasNextPage` 时）。
  - **折叠后总高与拇指随可见结构变化**；续拉只填占位。
  - sticky 顶替：push 位移纯 DOM；滚动容器由 `AppScrollArea` viewport ref Context 提供。
  - 行内 priority/status 下拉 options 为 module 单例。

## Rust 运行机制

Rust workspace 分为：

- `domain`：纯领域规则和值对象。
- `application`：用例编排、DTO 与 ports。
- `storage`：SQLite、repository、mapper、表映射与启动迁移。
- `runtime`：Tauri 装配、commands、事件和应用生命周期。
- `platform`：窗口、快捷键、tray 等平台行为。
- `sync`：不依赖 Tauri 的远端协议、schema、operation 提交、增量读取与远端诊断。

业务核心不依赖 Tauri、SQLite 或平台 API；这些依赖只在外层适配器出现。

## 本地数据与事件

SQLite 是业务数据的本地事实源。业务写入与待同步 Outbox 条目在同一事务中提交。同步或外部变更完成后，Rust 发送工作区变更事件，前端统一失效相关 Query；同步模块不直接维护 Task/Project 的前端缓存。

## 发布、更新与 Changelog

| 事实 | Owner | 边界 |
|---|---|---|
| 运行中更新会话 | Rust `application::update` 的会话快照 | 检查、下载、待安装与安装状态的唯一权威；前端只做投影和发起动作 |
| 全局版本身份 | Git 远端 annotated Tag | 将一个版本唯一绑定到一个 commit，各平台补发时复用同一 Tag |
| 渠道发布前沿 | Git 远端 `release-ledger/<channel>` | 与新 Tag 原子推进，序列化同渠道版本分配 |
| 平台发布证据 | R2 不可变 platform release record | 记录指定版本、commit、平台与内容寻址产物 |
| 平台可用版本 | R2 per-platform pointer | macOS 与 Windows 分别推进，不要求各平台同时可用 |
| 用户可见发布历史 | 仓库根 `CHANGELOG.md` | Changelog 内容的编辑真源；发布脚本校验后以 CAS 发布公开投影 |

发布工具负责 Tag、ledger、平台 record 与 pointer；Tauri runtime 只消费当前平台 pointer 和公开 Changelog。Changelog 与更新会话保持独立，发布说明暂时不可用不影响已检查更新的下载或安装。

## 云同步

当前同步服务于单人多设备：每台设备保留本地 SQLite 副本（业务事实源）；用户自备 PostgreSQL（Neon/自建）作「云端副本」，只存协议变更日志与实体投影。客户端直连 Postgres 上传/下载；主进程无 libsql。同步使用设备 ID、operation ID、同步序号与本地待上传队列保持幂等与可恢复。

用户体验采用后台自动收敛：设置页配置「同步数据库连接」、展示状态与手动重试；不提供常规同步工作台或手动冲突流程。完整连接串保存在系统钥匙串，日志与 UI 仅展示脱敏地址。

协议按字段级 LWW、生命周期优先、generation 和 tombstone 收敛。正常同步为分页增量；首次或同步位置过期时应用全量基线。本机 `sync_protocol_entities` 是协议文档；业务表是其投影。产品目标是避免用户可见冲突，但不能把「不会冲突」写成协议保证。

## 跨模块协作

- Feature 之间只通过 public API 或窄 contract 协作，禁止深路径依赖。
- Command、快捷键、多选和批量操作由平台 Feature 提供运行时能力，实体 Feature 注册自己的动作。
- Launcher 是独立 Tauri 窗口与独立前端会话；它复用 Task 创建与全局搜索的后端契约，不复用主应用 UI 状态。

## 全局质量要求

- 路由、Query、UI state 的职责边界可从代码直接判断。
- 任何 schema 或领域模型重构必须包含迁移、同步影响和恢复路径验证。
- 需要至少通过 `bun typecheck`、`bun lint`、`bun run lint:boundaries`、`bun format:check`、`bun test:run`、`bun run test:release` 与相关 Rust 校验后才能作为完整变更交付。
