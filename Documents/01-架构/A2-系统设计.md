# 系统设计

## 技术目标

- 本地优先，离线时可完整读写个人任务。
- 前后端与平台能力保持明确边界。
- 后台同步尽量无感，不把同步协议复杂度暴露为日常工作流。
- 保持模块内聚，避免业务数据出现多份真相。

## 整体技术栈

| 层 | 当前技术 |
|---|---|
| 桌面壳 | Tauri v2 |
| 前端 | React 19、TypeScript、Vite、Tailwind CSS |
| 路由 | TanStack Router（Hash + file routes） |
| 业务数据 | TanStack Query |
| 跨组件 UI 状态 | Zustand（限定使用） |
| 表单与校验 | React Hook Form、Zod |
| 本地持久化 | SQLite、SeaORM、SeaORM Migration |
| 同步远端 | Turso/libSQL |
| 后端 | Rust workspace、Tokio |
| 测试与检查 | Vitest、Testing Library、oxlint、oxfmt、Cargo tests |

## 前端运行机制

路由只管理 URL、历史和可恢复筛选。TanStack Query 是 Task、Project、Space、View 等业务数据的前端缓存与失效层；Zustand 仅用于跨组件 UI 状态；React local state 仅保留在单个组件的瞬时交互中。

不允许同一业务数据同时作为 Query、Zustand 和组件 state 的独立真相。Feature 的 API facade 是唯一 `invoke()` 入口，页面与 shared 不直接调用 Tauri。

## Rust 运行机制

Rust workspace 分为：

- `domain`：纯领域规则和值对象。
- `usecase`：用例编排、DTO 与 ports。
- `storage`：SQLite、repository、mapper 和启动迁移。
- `schema` / `migration`：表映射与版本化结构变更。
- `runtime`：Tauri 装配、commands、事件和应用生命周期。
- `platform`：窗口、快捷键、tray 等平台行为。
- `sync-worker`：同步协议、远端应用与诊断。

业务核心不依赖 Tauri、SQLite 或平台 API；这些依赖只在外层适配器出现。

## 本地数据与事件

SQLite 是业务数据的本地事实源。业务写入与待同步 mutation 在同一事务中提交。同步或外部变更完成后，Rust 发送工作区变更事件，前端统一失效相关 Query；同步模块不直接维护 Task/Project 的前端缓存。

## 云同步

当前同步服务于单人多设备：每台设备保留本地 SQLite 副本，Turso/libSQL 保存远端副本和变更日志。同步使用设备 ID、递增客户端序号、远端序号与 pending mutation 保持幂等和可恢复。

用户体验采用后台自动收敛：设置页展示状态、远端配置和手动重试入口，不提供常规同步工作台或手动冲突流程。同步凭证仅保存在设备安全边界，不进入同步数据、日志或前端领域模型。

当前协议包含副本基线检测、pull/push、远端变更应用和诊断；已有本地数据但缺少同步 cursor 时会停止自动覆盖，并要求先完成基线迁移。产品目标是避免用户可见冲突，但不能把“不会冲突”写成协议保证。

## 跨模块协作

- Feature 之间只通过 public API 或窄 contract 协作，禁止深路径依赖。
- Command、快捷键、多选和批量操作由平台 Feature 提供运行时能力，实体 Feature 注册自己的动作。
- Launcher 是独立 Tauri 窗口与独立前端会话；它复用 Task 创建与全局搜索的后端契约，不复用主应用 UI 状态。

## 全局质量要求

- 路由、Query、UI state 的职责边界可从代码直接判断。
- 任何 schema 或领域模型重构必须包含迁移、同步影响和恢复路径验证。
- 需要至少通过 `bun typecheck`、`bun lint`、`bun run lint:boundaries`、`bun format:check`、`bun test:run` 与相关 Rust 校验后才能作为完整变更交付。
