# StoneFlow 文档体系 SOP

> 目标：让人和 AI 能快速找到入口、理解边界、修改实现，并让文档持续可信。

## 核心规则

### 一个事实只有一个 Owner

同一事实只在一份文档中完整维护，其他文档只链接。

| 事实 | Owner |
|---|---|
| 项目入口与快速开始 | 根 `README.md` |
| 系统结构与全局架构约束 | 根 `ARCHITECTURE.md` |
| 产品定义 | `Documents/00-产品/P1-产品内核.md` |
| 用户路径与信息架构 | `Documents/00-产品/P2-产品蓝图.md` |
| 领域实体与生命周期 | `Documents/01-架构/A1-领域模型.md` |
| 全局技术栈与跨模块机制 | `Documents/01-架构/A2-系统设计.md` |
| 全局界面规则 | `Documents/01-架构/A3-界面系统.md` |
| 模块公开入口 | 模块 `README.md` |
| 模块边界与不变式 | 模块 `ARCHITECTURE.md` |
| 模块当前实现 | 模块 `DESIGN.md` |
| 重大决策历史 | `Documents/01-架构/adr/` |
| 当前任务目标与方案 | `SPEC.md` |
| 当前任务执行状态 | `TASKS.md` |

### 文档只服务一个目的

- `README`：这是什么、怎么开始、怎么调用。
- `ARCHITECTURE`：系统或模块如何组织，哪些边界不能破坏。
- `DESIGN`：当前实现如何工作。
- `SPEC`：本次任务要达到什么结果，准备怎么做。
- `TASKS`：本次任务做到哪一步，有什么阻塞或偏差。
- ADR：为什么做了一个重大且需要追溯的选择。

### 长期文档只写当前真相

长期文档不记录开发进度、阶段百分比、临时待办、未落地方案、每日工作日志或已废弃方案的完整历史。任务期信息写入 `SPEC/TASKS`；需追溯的重大决策写 ADR；时间线由 Git 提供，不写“最后更新”。

### 按复杂度增加文档

- 每个一级模块固定有极简 `README.md`。
- 有职责边界、依赖方向、跨层规则或不变式时，创建 `ARCHITECTURE.md`。
- 有非平凡数据流、状态机、协议、算法、第三方集成或恢复机制时，创建 `DESIGN.md`。

`ARCHITECTURE` 与 `DESIGN` 独立触发，但重型模块通常两者都有。不要为内部 `components/`、`hooks/`、`services/` 递归创建 README，除非其已升级为独立一级模块。

## 文档模板

### 根 README

```markdown
# 项目名称

> 一句话说明

## 这是什么
## 快速开始
## 仓库结构
## 文档入口
```

不写完整架构、技术栈细节、内部实现或开发进度。

### 根 ARCHITECTURE

```markdown
# 项目名称 - 整体架构

## 系统边界
## 架构总览
## 核心模块
## 模块依赖方向
## 关键运行关系
## 全局架构约束
## 相关文档
```

它负责系统如何组织；全局技术机制进入 A2；模块内部实现进入模块 DESIGN。

### 模块 README

```markdown
# 模块名称

> 模块职责：一句话

## 公开入口
## 最小使用示例
## 相关文档
```

只维护稳定入口和最小示例。参数、类型与实现细节以代码为准。

### 模块 ARCHITECTURE

```markdown
# 模块名称 - 架构

## 职责边界
## 依赖方向
## 稳定架构单元
## 对外协作关系
## 架构约束与不变式
## 已知局部限制
## 相关 DESIGN 与 ADR
```

不写完整流程、任务进度或 ADR 的历史过程。

### 模块 DESIGN

```markdown
# 模块名称 - 设计

## 设计范围
## 实现总览
## 核心流程
## 状态与数据模型
## 实现单元及协作
## 异常与恢复
## 关键设计问答
## 已知限制
## 验证方式
```

只描述当前已实现或已确认的长期方案。模块内取舍写“关键设计问答”；旧方案直接删除。跨模块、难逆转或高迁移成本的选择才写 ADR。

### SPEC 与 TASKS

只有任务满足任一条件时才创建：需要分阶段执行、涉及多个模块、存在需要确认的技术方案、验收标准不容易直接说明，或预计跨多个工作时段。

```markdown
# 任务名称 - Spec

## 背景与目标
## 范围
## 不做什么
## 需求
## 验收标准
## 当前技术方案
## 关联模块
## 风险
## 完成后需要同步的长期文档
```

```markdown
# 任务名称 - Tasks

## 当前阶段
## 阶段任务
## 阻塞
## 与 SPEC 的实施偏差
## 完成记录
```

活跃任务中，SPEC 始终维护当前已确认方案；TASKS 只在阶段、状态、阻塞或偏差变化时更新。任务归档后，两者冻结。

## 更新触发器

| 变化 | 更新文档 |
|---|---|
| 一级模块新增、删除或职责变化 | 根 ARCHITECTURE、模块 README |
| 模块公开入口变化 | 模块 README |
| 模块边界、依赖或不变式变化 | 模块 ARCHITECTURE |
| 模块实现机制变化 | 模块 DESIGN |
| 全局技术栈或跨模块机制变化 | A2 |
| 系统整体结构变化 | 根 ARCHITECTURE |
| 实体、关系或生命周期变化 | A1 |
| 用户路径或信息架构变化 | P2 |
| 全局界面规则变化 | A3 |
| 重大、难逆转决策 | 新建 ADR |

## 工作流

1. 判断任务是否达到 `SPEC/TASKS` 的创建门槛。
2. 创建 `Documents/02-开发任务/YYYY-MM-DD-task-slug/` 或 `03-重构任务/YYYY-MM-DD-task-slug/`。
3. 在 SPEC 中写清目标、范围、验收与关联模块；在 TASKS 中维护执行状态。
4. 代码改变时，同一变更更新对应长期文档。
5. 完成后按验收标准验证，补齐遗漏的长期文档或 ADR，再将任务目录移入 `98-归档/`。

## 命名

| 对象 | 命名 |
|---|---|
| 根入口 | `README.md`、`ARCHITECTURE.md` |
| 模块入口 | `README.md` |
| 模块架构 | `ARCHITECTURE.md` |
| 模块设计 | `DESIGN.md` |
| 全局长期文档 | `P1/P2/A1/A2/A3` 加中文名 |
| ADR | `ADR-NNNN-kebab-title.md` |
| 任务目录 | `YYYY-MM-DD-task-slug` |
| 任务文档 | `SPEC.md`、`TASKS.md` |

大类目录与全局长期文档使用中文；代码同位模块目录和任务 slug 使用英文。
