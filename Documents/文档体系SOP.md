# StoneFlow 文档体系 SOP

> 目标：让人和 AI 能快速找到入口、理解边界、修改实现，并让文档持续可信。

## 设计目标

这套体系同时解决五个问题，但不通过五份固定文档机械实现：

| 问题 | 现有 Owner | 必须回答的事 |
|---|---|---|
| 为什么做、长期往哪里演进 | `00-产品/P1-产品内核.md` | 产品原点、北极星、阶段边界、Anti-Goals |
| 用户如何理解和操作产品 | `00-产品/P2-产品蓝图.md`、`01-架构/A3-界面系统.md` | IA、关键路径、Screen/布局规则、全局交互 |
| 当前这轮做什么、做到什么算完成 | 活跃任务 `SPEC.md` | 范围、能力边界、用户场景、DoD、验收 |
| 当前这轮打算怎么做（仅复杂方案需要） | 活跃任务 `PLAN.md`（按门槛创建） | 技术方案、备选方案与取舍、关联模块、风险 |
| 系统如何实现且不破坏边界 | `A1`、`A2`、模块文档和源码 | 领域模型、跨模块机制、模块边界、实现细节 |
| 如何执行、处理风险和延后项 | 活跃任务 `TASKS.md` | 阶段、阻塞、偏差、验证、明确的后续去向 |

目标是形成一条连续链路：**P1 定方向，P2/A3 定用户路径和界面规则，SPEC 定当前承诺，PLAN 定实现方案（仅复杂任务需要），A1/A2 与模块文档定实现边界，TASKS 记录执行事实，源码保存精确 API 与类型真相。**

不为“覆盖完整”预建固定套餐。没有真实内容、稳定 Owner 或维护动作的文档不创建。

## 核心规则

### 一个事实只有一个 Owner

同一事实只在一份文档中完整维护，其他文档只链接。

| 事实 | Owner |
|---|---|
| 项目入口与快速开始 | 根 `README.md` |
| 系统结构与全局架构约束 | 根 `ARCHITECTURE.md` |
| 产品定义 | `Documents/00-产品/P1-产品内核.md` |
| 用户路径与信息架构 | `Documents/00-产品/P2-产品蓝图.md` |
| 当前版本/任务的功能范围、能力边界与 DoD | 活跃任务 `SPEC.md` |
| 领域实体与生命周期 | `Documents/01-架构/A1-领域模型.md` |
| 全局技术栈与跨模块机制 | `Documents/01-架构/A2-系统设计.md` |
| 全局界面规则 | `Documents/01-架构/A3-界面系统.md` |
| 模块公开入口 | 模块 `README.md` |
| 模块边界与不变式 | 模块 `ARCHITECTURE.md` |
| 模块当前实现 | 模块 `DESIGN.md` |
| 重大决策历史 | `Documents/01-架构/adr/` |
| 当前任务目标、范围与验收 | `SPEC.md` |
| 当前任务技术方案、备选取舍与风险 | `PLAN.md`（不存在时并入 `SPEC.md` 的"当前技术方案"章节） |
| 当前任务执行状态 | `TASKS.md` |

版本号级的 TypeScript interface、Rust struct、IPC 参数、数据库字段和 API 返回值以源码、schema、migration 与测试为准；文档只描述稳定概念、协议语义、不变式和重要约束，不能复制成第二份类型真相。

### 文档只服务一个目的

- `README`：这是什么、怎么开始、怎么调用。
- `ARCHITECTURE`：系统或模块如何组织，哪些边界不能破坏。
- `DESIGN`：当前实现如何工作。
- `SPEC`：本次任务要达到什么结果，边界在哪里。
- `PLAN`（按门槛创建）：准备怎么做，权衡了哪些备选方案。
- `TASKS`：本次任务做到哪一步，有什么阻塞或偏差。
- ADR：为什么做了一个重大且需要追溯的选择。

### 长期文档只写当前真相

长期文档不记录开发进度、阶段百分比、临时待办、未落地方案、每日工作日志或已废弃方案的完整历史。任务期信息写入 `SPEC/TASKS`；需追溯的重大决策写 ADR；时间线由 Git 提供，不写“最后更新”。

战略文档可以描述当前有效的演进阶段和进入下一阶段的条件，但不写按周排期、燃尽数据或进行中任务清单。执行文档可以记录当前阻塞和风险，但归档后必须冻结；仍未解决的事项必须转入明确的后续任务，不能停留在已归档任务里。

不维护没有处理机制的全局 Backlog 或“技术债大杂烩”文档。延后项只有三种合法去向：

1. 当前 `TASKS.md` 中的明确阻塞或后续阶段。
2. 新建或已存在任务目录的 `SPEC.md` / `TASKS.md`。
3. 紧贴代码的、带升级条件的技术债注释。

### 按复杂度增加文档

- 每个一级模块固定有极简 `README.md`。
- 有职责边界、依赖方向、跨层规则或不变式时，创建 `ARCHITECTURE.md`。
- 有非平凡数据流、状态机、协议、算法、第三方集成或恢复机制时，创建 `DESIGN.md`。
- 活跃任务默认只有 `SPEC.md`、`TASKS.md`；技术方案涉及非平凡数据流、状态机、协议设计、算法、第三方集成，或需要对比权衡多个备选方案时，从 SPEC 拆出 `PLAN.md`。

`ARCHITECTURE` 与 `DESIGN` 独立触发，但重型模块通常两者都有。不要为内部 `components/`、`hooks/`、`services/` 递归创建 README，除非其已升级为独立一级模块。`SPEC` 与 `PLAN` 的拆分逻辑与之相同：简单任务合并，复杂任务拆开，不做固定套餐。

## 目标目录

```text
README.md
ARCHITECTURE.md
Documents/
├── _INDEX.md
├── 00-产品/
│   ├── P1-产品内核.md
│   └── P2-产品蓝图.md

│   ├── A2-系统设计.md
│   ├── A3-界面系统.md
│   └── adr/
├── 02-开发任务/         # 每个任务目录含 SPEC.md、TASKS.md，方案复杂时另加 PLAN.md
```

全局长期文档和目录仅在有真实内容时创建。存量项目允许新旧格式并存，目标是接触到的文档可信，不是一次性补齐所有文件。

## 文档模板

### P1：产品内核

```markdown
# 产品名称 - 产品内核

## 产品原点
## 北极星与成功标准
## 当前阶段与阶段边界
## 核心能力与能力边界
## Anti-Goals
## 相关产品与架构文档
```

它回答“为什么做、当前阶段解决什么、明确不做什么”。阶段只描述有效的能力分界和升级条件，不写周计划、功能实现状态或技术细节。

### P2：产品蓝图

```markdown
# 产品名称 - 产品蓝图

## 目标用户与核心路径
## 信息架构
## Screen/页面清单
## 导航与返回规则
## 关键状态与异常路径
## 与 A3、SPEC 的边界
```

P2 是用户心智模型和信息架构的 Owner。页面需要稳定追踪时可定义 Screen ID；简单产品不强制引入编号。全局布局语言、响应式规则和 modal 覆盖优先级进入 A3，不重复写进每个页面方案。

### A1/A2/A3：全局架构文档

- `A1-领域模型.md`：稳定实体、关系、生命周期和跨模块业务不变式。
- `A2-系统设计.md`：技术栈、跨模块机制、IPC/事件语义、存储策略和运行边界。
- `A3-界面系统.md`：全局布局、设计 token、响应式原则、导航和 overlay 规则。

它们不复制源码中的完整字段、函数签名或 API 参数；需要精确接口时链接到源码、schema、migration 或测试。

### 根 README

```markdown
# 项目名称

> 一句话说明

## 这是什么
## 快速开始
## 仓库结构
## 文档入口
```

不写完整架构、技术栈细节、内部实现或开发进度。

### 根 ARCHITECTURE

```markdown
# 项目名称 - 整体架构

## 系统边界
## 架构总览
## 核心模块
## 模块依赖方向
## 关键运行关系
## 全局架构约束
## 相关文档
```

它负责系统如何组织；全局技术机制进入 A2；模块内部实现进入模块 DESIGN。

### 模块 README

```markdown
# 模块名称

> 模块职责：一句话

## 公开入口
## 最小使用示例
## 相关文档
```

只维护稳定入口和最小示例。参数、类型与实现细节以代码为准。

### 模块 ARCHITECTURE

```markdown
# 模块名称 - 架构

## 职责边界
## 依赖方向
## 稳定架构单元
## 对外协作关系
## 架构约束与不变式
## 已知局部限制
## 相关 DESIGN 与 ADR
```

不写完整流程、任务进度或 ADR 的历史过程。

### 模块 DESIGN

```markdown
# 模块名称 - 设计

## 设计范围
## 实现总览
## 核心流程
## 状态与数据模型
## 实现单元及协作
## 异常与恢复
## 关键设计问答
## 已知限制
## 验证方式
```

只描述当前已实现或已确认的长期方案。模块内取舍写“关键设计问答”；旧方案直接删除。跨模块、难逆转或高迁移成本的选择才写 ADR。

### SPEC、PLAN 与 TASKS

只有任务满足任一条件时才创建：需要分阶段执行、涉及多个模块、存在需要确认的技术方案、验收标准不容易直接说明，或预计跨多个工作时段。

```markdown
# 任务名称 - Spec

## 背景与目标
## 范围
## 不做什么
## 用户场景与需求
## 能力边界
## Definition of Done
## 验收标准
## 当前技术方案（简单方案直接写在这里；复杂方案见 PLAN.md）
## 关联文档
```

方案简单时，"当前技术方案"直接写一两句结论，不建 PLAN.md。方案触发第 4 节的门槛时，从这里拆出去，本章节改为一句话摘要 + 链接到 PLAN.md。

```markdown
# 任务名称 - Plan（仅复杂方案创建）

## 方案概述
## 备选方案与取舍
## 数据流 / 状态机 / 协议（视任务而定）
## 关联模块
## 风险
## 完成后需要同步的长期文档
```

```markdown
# 任务名称 - Tasks

## 当前阶段
## 阶段任务
## 阻塞
## 与 SPEC/PLAN 的实施偏差
## 完成记录
```

活跃任务中，SPEC 始终维护当前已确认的目标与范围；PLAN（若存在）维护当前已确认方案；TASKS 只在阶段、状态、阻塞或偏差变化时更新。任务归档后，三者冻结。

`SPEC` 是当前版本范围的唯一 Owner：它必须写清用户得到什么、明确不做什么、异常边界在哪里，以及何时可以宣布完成。`Definition of Done` 描述交付门槛；验收标准给出可验证的用户行为、数据结果或质量检查，二者不互相复制。`PLAN`（若存在）是当前任务技术方案的唯一 Owner：关联模块、风险、需同步的长期文档都归它管，不在 SPEC 里重复。

## 更新触发器

| 变化 | 更新文档 |
|---|---|
| 一级模块新增、删除或职责变化 | 根 ARCHITECTURE、模块 README |
| 模块公开入口变化 | 模块 README |
| 模块边界、依赖或不变式变化 | 模块 ARCHITECTURE |
| 模块实现机制变化 | 模块 DESIGN |
| 全局技术栈或跨模块机制变化 | A2 |
| 系统整体结构变化 | 根 ARCHITECTURE |
| 实体、关系或生命周期变化 | A1 |
| 用户路径或信息架构变化 | P2 |
| 全局布局、响应式、导航或 overlay 规则变化 | A3 |
| 当前版本范围、用户场景、能力边界或 DoD 变化 | 活跃任务 SPEC |
| 当前任务技术方案、备选取舍或风险变化 | 活跃任务 PLAN（不存在则 SPEC 的"当前技术方案"章节） |
| 延后风险、技术债或未完成事项有了明确后续任务 | 当前/后续任务 TASKS |
| 重大、难逆转决策 | 新建 ADR |

## 工作流

1. 判断任务是否达到 `SPEC/TASKS` 的创建门槛。
2. 创建 `Documents/02-开发任务/YYYY-MM-DD-task-slug/` 或 `03-重构任务/YYYY-MM-DD-task-slug/`。
3. 在 SPEC 中写清目标、范围与验收；若方案触发第 4 节门槛，拆出 PLAN 写清方案、关联模块与风险；在 TASKS 中维护执行状态。
4. 代码改变时，同一变更更新对应长期文档。
5. 完成后按验收标准验证，补齐遗漏的长期文档或 ADR，再将任务目录移入 `98-归档/`。

## 写作与审查清单

新建或修改文档前，依次确认：

1. 这份事实的唯一 Owner 是谁；是否正在复制已有 Owner 的内容？
2. 这是长期真相、当前任务的目标承诺、方案承诺，还是执行状态？分别落在长期文档、`SPEC`、`PLAN`、`TASKS`。
3. 它是否回答了用户价值、范围或边界；若只是复述代码、提交记录或会议过程，应该删掉或链接真相源。
4. 若本次决定改变 P1/P2/A1/A2/A3 的 Owner 内容，是否同步更新对应长期文档？
5. 若有延后项，是否已写明升级条件和后续任务去向？
6. 归档前，是否有仍在执行的状态、待办或风险被错误留在长期文档或已冻结任务中？

## 命名

| 对象 | 命名 |
|---|---|
| 根入口 | `README.md`、`ARCHITECTURE.md` |
| 模块入口 | `README.md` |
| 模块架构 | `ARCHITECTURE.md` |
| 模块设计 | `DESIGN.md` |
| 全局长期文档 | `P1/P2/A1/A2/A3` 加中文名 |
| ADR | `ADR-NNNN-kebab-title.md` |
| 任务目录 | `YYYY-MM-DD-task-slug` |
| 任务文档 | `SPEC.md`、`TASKS.md`；方案复杂时加 `PLAN.md` |

大类目录与全局长期文档使用中文；代码同位模块目录和任务 slug 使用英文。
