## ADR-008 · 系统级 Global Command 采用独立 Command Agent 方案，并在 V1 后段收口

**日期**：2026-04-19  
**状态**：已采纳

### 背景

StoneFlow 已经明确把“极速捕获”视为核心卖点之一，因此：

- 顶部 `Global Command Bar` 只能代表主应用内的入口形态
- 真正的系统级 `Global Command` 需要做到应用外唤起
- 该能力最终应具备类似 `Raycast / uTools` 的捕获体验，而不是简单拉起主窗口

同时，当前执行层的 `M2` 目标仍然是先打通：

- 创建
- Inbox 承接
- Project 执行
- Drawer 编辑
- 删除收口

如果把系统级 `Global Command` 的完整基础设施过早并入 `M2-B`，会把主链路阶段扩展为：

- Helper / Agent 进程
- 全局快捷键
- Quick Capture 浮窗
- 主应用与 Agent 的共享状态或通信
- 生命周期与异常恢复

这会明显拖慢 `M2` 的业务闭环推进。

### 决策

选择：

- `V1` 仍然必须落地系统级 `Global Command`
- 该能力采用“独立 Command Agent / Helper + Quick Capture”的方案方向推进
- `M2-B` 只负责：
  - 创建 `Task` 的真实能力
  - 主应用内的最小创建入口
- 系统级 `Global Command` 的完整基础设施放在 `M4` 收口

换句话说，StoneFlow 采用“两层捕获入口”：

- 应用内入口：主应用 Header / 最小创建层
- 系统级入口：独立 Command Agent + Quick Capture

### 备选方案

**方案 A：把系统级 Global Command 直接并入 M2-B**

优点：

- 更早得到最终入口形态
- 执行层看起来一步到位

缺点：

- 会把 `M2-B` 从“创建链路”膨胀成“桌面平台基础设施”
- 直接拖慢 Inbox、Project、Drawer 等主链路段落
- 调试、打包和状态一致性风险显著上升

否决原因：

- 不符合 `M2` 先打通主链路、后收口高价值基础设施的执行节奏。

**方案 B：V1 只保留主应用内入口，不做系统级 Global Command**

优点：

- 范围更小
- 实现更快

缺点：

- 无法兑现 StoneFlow 的“应用外极速捕获”核心价值
- 会削弱产品的长期辨识度

否决原因：

- 不符合产品对 `Global Command` 的长期定位。

### 影响范围

- 影响文档：`E1-V1执行文档.md`、`E1-V1-M2拆分执行文档.md`、后续独立 `Global Command` 执行文档
- 影响代码：主应用创建入口、后续 Command Agent / Helper 架构、共享创建能力与状态同步
- 后续关注：Helper 形态、共享状态存储、异常恢复、唤起速度与测试策略

## ADR-007 · UI 壳层采用顶部全局 Command、左侧 Sidebar、右侧覆盖式 Drawer

**日期**：2026-04-17  
**状态**：已采纳

### 背景

StoneFlow 早期讨论中，曾默认使用：

- 顶部 `Space Tabs`
- 中间 `Main`
- 右侧常驻 `Drawer`

但随着产品方向继续收敛，已经明确：

- 顶部最重要的不是 Space 切换，而是全局 `Command`
- `Space Tabs` 更适合放进 Sidebar，作为当前领域上下文切换器
- `Drawer` 如果默认常驻，会持续压缩主工作区，削弱列表扫描效率

同时，StoneFlow 的目标不是三栏信息同时常驻，而是：

- 默认保持界面干净
- 任务浏览时让 `Main` 成为绝对主视区
- 需要编辑时，再临时进入详情层

### 决策

选择：

- 顶部采用 `Window Chrome + Global Command Bar`
- 左侧 `Sidebar` 内部承载 `Space Tabs + Navigation + Project Tree`
- 中间 `Main` 作为默认稳定工作区
- 右侧 `Drawer` 采用 `默认隐藏 + 从右侧覆盖打开`
- `Drawer` 打开时允许叠加一层非常轻的背景遮罩

### 备选方案

**方案 A：顶部 Space Tabs + 三栏常驻布局**

优点：

- 信息同时可见
- 结构直观

缺点：

- 顶部全局入口不够强
- `Space Tabs` 占用了全局最显眼位置
- `Drawer` 常驻会压缩主内容区

否决原因：

- 不符合 StoneFlow 以“全局快速入口 + 主区聚焦执行”为核心的方向。

**方案 B：Drawer 默认隐藏，但打开时挤压 Main 形成临时双栏**

优点：

- 层级清楚
- 结构更接近传统工作台

缺点：

- 打开详情时主区宽度变化，列表会发生重排
- 破坏浏览和编辑之间的稳定感

否决原因：

- StoneFlow 更需要保持主区稳定，而不是为结构整齐牺牲连续性。

### 影响范围

- 影响文档：U1、后续 U2
- 影响代码：App Shell、Sidebar、Command Bar、Drawer 交互实现
- 后续关注：轻遮罩透明度、Drawer 宽度、窄窗口下 Sidebar 折叠策略

## ADR-006 · 前端采用 feature-first，Rust 采用 workspace + crate 拆分

**日期**：2026-04-17  
**状态**：已采纳

### 背景

StoneFlow 既不是极简 Demo，也不是纯前端页面项目。它已经明确包含：

- 多个核心功能域：Inbox、Focus、Project、Task、Trash、Space
- 本地数据库与持久化
- Tauri 前后端边界
- 后续仍会持续演进的桌面产品结构

如果继续使用松散的分层目录，很容易在后期出现：

- 前端共享目录膨胀
- 业务代码散落
- Rust 侧职责混乱

因此需要尽早确定一套能长期扩展的目录策略。

### 决策

选择：

- 前端采用 `feature-first`
- 前端 feature 内部固定使用 `ui / hooks / model`
- Rust 采用 `Cargo workspace + 分职责 crate`
- Rust 在 app crate 内部继续按 feature 组织业务入口

### 备选方案

**方案 A：传统前端分层目录 + Rust 单 crate**

优点：

- 上手快
- 初期目录看起来简单

缺点：

- 功能增长后容易把共享目录变成杂物间
- 前后端复杂度会迅速积累

否决原因：

- 不适合 StoneFlow 这种会持续增长的桌面产品。

**方案 B：前后端全部纯 feature-first，不做 crate 拆分**

优点：

- 结构统一
- 按功能查找文件直观

缺点：

- Rust 侧数据库、实体、迁移的职责边界容易模糊
- 不利于 SeaORM 推荐的实体与迁移组织

否决原因：

- Rust 侧需要比前端更清晰的职责分隔，纯 feature-first 不够稳。

### 影响范围

- 影响文档：T1
- 影响代码：前端目录、Rust workspace 结构、初始化脚手架
- 后续关注：feature 边界是否稳定，shared 是否被污染

## ADR-005 · SQLite 接入采用 SeaORM，而不是 rusqlite / sqlx

**日期**：2026-04-17  
**状态**：已采纳

### 背景

StoneFlow 当前虽然是本地优先单机桌面应用，但数据结构已经明确包含：

- Space
- Project / Subproject
- Task
- FocusView
- Resource
- TrashEntry

同时还需要：

- 迁移机制
- 结构化实体管理
- 后续可演进的数据访问抽象

因此 ORM / 数据访问层需要在“简单”与“可扩展”之间做取舍。

### 决策

选择：**SeaORM**

理由：

- 你明确希望 ORM 一步到位
- SeaORM 更适合组织实体、迁移和关系模型
- 和 SQLite 场景兼容
- 更符合后续模型增长预期

### 备选方案

**方案 A：rusqlite**

优点：

- 更轻
- 更直接
- 对 SQLite 贴合度高

缺点：

- 抽象层偏低
- 后续模型增加时，手写查询和映射成本会上升

否决原因：

- 不符合当前“一步到位”的偏好。

**方案 B：sqlx**

优点：

- 兼顾一定抽象和可控性
- 查询层表达灵活

缺点：

- 在当前场景下，没有比 SeaORM 明显更强的收益
- 对实体统一管理不如 SeaORM 更自然

否决原因：

- 当前产品更需要统一模型管理，而不是偏查询式抽象。

### 影响范围

- 影响文档：T1、D1
- 影响代码：Rust workspace、entity crate、migration crate、repository/service 层
- 后续关注：性能敏感查询是否需要局部退回手写 SQL

## ADR-004 · Sidebar 采用 Space Tabs + Inbox + Focus + Projects List + Trash 结构

**日期**：2026-04-17  
**状态**：已采纳

### 背景

StoneFlow 的导航不只是页面入口问题，它直接影响用户如何理解这个产品。

当前产品已经明确包含：

- 顶级上下文：Space
- 过渡模块：Inbox
- 聚合视图：Focus
- 长期归宿：Project
- 删除承接：Trash

因此 Sidebar 需要同时承载：

- 系统模块
- 聚合视图入口
- 项目树

### 决策

选择：

`Space Tabs -> Inbox -> Focus -> Projects List -> Trash`

其中：

- Space 用顶部 tabs 切换
- Focus 承载多个视图 tabs
- Trash 放在项目列表之后

### 备选方案

**方案 A：把 Upcoming、最近添加、高优先级全部直接摊在 Sidebar**

优点：

- 入口直接

缺点：

- Sidebar 会迅速膨胀
- 系统模块和视图入口混杂

否决原因：

- StoneFlow 后续还会增加视图，不能让左侧导航无限增长。

**方案 B：Inbox 视为普通项目放进 Projects List**

优点：

- 模型统一

缺点：

- 会模糊 Inbox 的特殊语义
- 不利于强调“过渡态”的使用心智

否决原因：

- Inbox 必须是特殊系统模块，而不是普通项目。

### 影响范围

- 影响文档：P2、T1
- 影响代码：Router、Sidebar、Focus 页面、Project 树
- 后续关注：Trash 是否支持恢复、Focus tabs 是否继续精简

## ADR-003 · Focus 采用聚合容器页，而不是多个独立页面

**日期**：2026-04-17  
**状态**：已采纳

### 背景

在讨论 `Today / Upcoming / 最近添加 / 高优先级` 时，出现了两个方向：

- 把每个视图都作为独立页面
- 让它们成为一个更高层聚合页下的不同视图

同时，用户明确希望：

- 这些视图本质上都是任务集合视图
- 同一个任务可以出现在多个视图中
- Focus 能成为执行的主入口

### 决策

选择：

- 保留一个顶层 `Focus` 页面
- 在 Focus 内部使用 tabs 切换不同视图
- 第一版 tabs 暂定：
  - Focus
  - Upcoming
  - 最近添加
  - 高优先级

其中：

- Focus tab 第一版只承载手动 pin 的任务

### 备选方案

**方案 A：每个视图单独成为 Sidebar 一级入口**

优点：

- 直观

缺点：

- Sidebar 会臃肿
- 页面层级不够克制

否决原因：

- 不利于长期扩展，也不够专业。

**方案 B：只保留单一 Focus，不区分内部视图**

优点：

- 更简洁

缺点：

- 无法承接不同执行语义
- 未来用户自定义视图难以落位

否决原因：

- 无法满足聚合视图体系的扩展需求。

### 影响范围

- 影响文档：P2、D1、T1
- 影响代码：Focus 页面、tabs 组织方式、视图规则模型
- 后续关注：高优先级 tab 是否长期保留

## ADR-002 · 产品主结构采用 Space -> Project -> Task

**日期**：2026-04-17  
**状态**：已采纳

### 背景

在产品讨论早期，需要确定 StoneFlow 的主组织轴到底是什么：

- 按时间组织
- 按状态组织
- 按项目组织

用户最终明确提出：

- 任务主线希望按项目归类
- 顶层要有 `Space`
- 中间是 `Project`
- 底层是 `Task`
- 时间视图应作为视图，而不是主存储结构

### 决策

选择：**Space -> Project -> Task**

并补充：

- Project 第一版支持一层子项目
- 时间相关页面只作为视图存在

### 备选方案

**方案 A：按时间视图为主**

优点：

- 更轻量
- 更接近日历和传统待办体验

缺点：

- 不利于长期项目管理
- 无法承接工作 / 学习 / 生活等上下文层次

否决原因：

- StoneFlow 目标不是简单的时间清单工具。

**方案 B：按状态为主**

优点：

- 执行感强

缺点：

- 对多项目长期管理支撑不足

否决原因：

- 状态更适合作为项目内部分组，而不是整个产品的主轴。

### 影响范围

- 影响文档：P1、P2、D1、T1
- 影响代码：数据模型、Sidebar、路由、项目页、Inbox 整理逻辑
- 后续关注：Project 是否继续向“执行单元”演化

## ADR-001 · StoneFlow 定位为 macOS 个人执行系统，而非普通 TODO

**日期**：2026-04-17  
**状态**：已采纳

### 背景

项目起点是“想做一个快和专业的桌面 TODO”，但随着讨论深入，问题变成：

- 这是一个简单待办工具
- 还是一个完整的个人执行系统

用户明确强调：

- 不是只想做一个极简 TODO
- 更想做完整的个人执行系统
- 但入口亮点必须是快、顺手、低摩擦

### 决策

选择：

- StoneFlow 定位为 `macOS 个人执行系统`
- 不是大众化轻量 TODO
- 不是团队工作管理系统
- 以极速捕获为入口，以整理和聚焦执行为核心价值

### 备选方案

**方案 A：极简桌面 TODO**

优点：

- 更容易做
- MVP 边界更窄

缺点：

- 很容易沦为普通待办
- 无法承载你真正想要的长期产品形态

否决原因：

- 不符合用户本人对产品上限的要求。

**方案 B：直接做团队工作管理系统**

优点：

- 理论上功能更完整

缺点：

- 范围爆炸
- 账号、协作、同步、权限都要提前进入

否决原因：

- 当前阶段完全不适合。

### 影响范围

- 影响文档：P1、P2
- 影响代码：整体架构、边界控制、V1 不做事项
- 后续关注：如何避免产品在“完整系统”和“低摩擦”之间失衡
