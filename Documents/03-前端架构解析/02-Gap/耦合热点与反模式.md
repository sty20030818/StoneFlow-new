## 4. 与「删 feature 只改装配+route」的差距叙事（定稿）

1. **场景层已经接近理想。** archive/trash 极薄，多数 scene 外部只被 route 引用；删页面 feature 往往只需改对称叶子。这是决策 2=A 在「叶子」上已经成立的部分。

2. **列表 composition 可删但难改。** inbox / all-tasks / no-project 几乎同构（22 个共同 import）。Delete 分高，但改标准列表能力要动三处——这是 **可维护性债（SCN-D1）**，不是「删不掉」。

3. **平台 feature 理论可插拔，实践焊在 God Shell + 巨型 CommandActions。** 装配职责属于壳是对的，但 1271 行内联 actions 使「卸装配一行」不可达（SHELL-D1 + PLAT-D2）。

4. **task/project 网状互依是产品结构，不是失败。** 失败的是 **metadata 反向依赖 task/ui**、以及 command 与壳的实现纠缠。

5. **shared 反向依赖 app/features 破坏分层防火墙（SHR-D1）。** 在修复之前，任何「shared 可安全依赖」的假设都不成立；这是可删除性与长期演进的 **P0 泄漏点**，且修复切片小于拆壳。

**一句话差距：**  
> 叶子可删，树干（Shell+command+task 网）拔不动；shared 还在漏气。下一步是 **先补防火墙（M-1），再拆装配根与命令桥（M-2），并行清死代码（M-0）与列表 DRY（M-3）**——而不是再拆 scene 目录名。
