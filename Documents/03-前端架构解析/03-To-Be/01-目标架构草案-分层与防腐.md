## 0. 本轮结论

| 项 | 结论 |
|----|------|
| 垂直切片 | **`features/`** + 内 `components/hooks/api/model` + `index.public` |
| 全局无业务 | **`shared/{components,hooks,lib}`** |
| 页入口 | **`routes/**` 薄页**（无独立 pages/） |
| **壳** | **上提 `src/layout/`**（不再塞在 `app/shell` 里）——见 §3.0 |
| **app** | **真正变薄**：bootstrap +（可选）router 工厂；导航语义可旁挂 `app/navigation` 或 `src/navigation` |
| monorepo | 不上 |

## 1. 参考结构：好在哪、别照抄哪

你给的模板（行业极常见，Bulletproof / 多数「feature folders」同源）：

```txt
src/
  features/
    auth/
      components/
      hooks/
      api/
      types.ts
    dashboard/
      components/
      hooks/
      api/
      types.ts
  shared/
    components/
    hooks/
    lib/
  app/
    layout.tsx
    page.tsx
```

### 1.1 值得吸收

| 优点 | 我们怎么用 |
|------|------------|
| **按产品能力垂直切** | 继续 `features/task`、`features/project`…；可整夹删除 |
| **feature 内用「技术夹」** | `components` / `hooks` / `api` 比 `domain/infra/application` **更好找、更好讲**；新人/AI 零学习成本 |
| **shared = 与业务无关** | 只放可被任意 feature 用的零件；**禁止** shared → features / app |
| **app 很薄** | app 不写业务规则；只做装配与壳 |
| **命名直白** | components 就是组件，hooks 就是钩子，api 就是外部 IO |

### 1.2 不能原样照搬（我们场景不同）

| 模板点 | 问题 | StoneFlow 改法 |
|--------|------|----------------|
| `app/page.tsx` + `layout.tsx` | Next App Router 心智 | **TanStack `routes/`** 承担页与 layout route |
| 只有 `types.ts` | 规则、Port、纯函数会无家可归或塞进 hooks | 用 **`model/`**（types + rules + ports） |
| `api/` 常混 invoke + React Query | 一夹两职责，UI 容易间接耦 Tauri 形状 | **api = 只 IO**；Query/用例进 **hooks**（或 `hooks/queries`） |
| 无跨 feature 纪律 | 互相深 import → 不可删 | **`index.public.ts` + B′**（示例缺的，我们加） |
| 无桌面壳 | 侧栏/命令板/多窗 | **`app/shell` + `app/navigation`** 显式存在 |
| 单 `layout.tsx` | 我们是壳 + EntityScene 槽位 | shell 可多文件，但仍属 app |

**原则：抄「垂直 + shared 防火墙 + 技术夹命名」，不抄「Next 目录」和「过瘦的 types/api」。**

## 2. 两个正交轴（规则不变，文件夹更接地气）

```txt
轴 B · 产品切片（垂直）     features/*
轴 A · 职责（映射进技术夹，见下表）

依赖方向（单向）：
  routes / app / layout  →  features(public)  →  shared
  layout                 →  shared, features(public)（装配，不写实体规则）
  features/A             →  shared, features/B(public only)
  shared                 →  （无 app / layout / features）
```

| 职责带 | 落在 feature 的哪 | 落在别处 |
|--------|-------------------|----------|
| Experience（薄页） | — | **`routes/**`** |
| Experience（业务 UI） | **`components/`** | — |
| Application（编排/Query） | **`hooks/`** | — |
| Domain（纯） | **`model/`** | — |
| Infra（Tauri/Store） | **`api/`** | — |
| 纯设计系统 / 通用 hook / 工具 | — | **`shared/{components,hooks,lib}`** |
| 应用铬架 / 主区槽位 | — | **`layout/`** |
| 组合根（启动接线） | — | **`app/`** |

**UI / 逻辑分离：**

- UI：`routes` 薄页 + `features/*/components` + `shared/components`
- 逻辑：`features/*/hooks` + `model` + `api`
- 页 **禁止** 直接调 `api/`（invoke）；只调 `hooks` facade

**防腐：**

| 边界 | 门面 |
|------|------|
| api ↔ model | api 实现 model 里的 ports / 映射成 model 类型 |
| components ↔ 数据 | 只经 hooks（facade） |
| feature ↔ feature | 只经对方 `index.public.ts` |
| shared | 无业务实体规则 |

## 3. 推荐目标树（v3.1）

### 3.0 为什么壳上提为 `src/layout`（采纳）

现状/草案里 `app/shell` 容易变成 **第二套 God 区**：侧栏、顶栏、抽屉、CommandBridge、EntityScene、settings 导航……和「组合根只接线」矛盾。

| | 塞在 `app/shell` | **顶层 `layout/`（推荐）** |
|--|------------------|---------------------------|
| 信号 | app 又胖又杂 | **铬架一等公民**，体积配得上独立树 |
| app 职责 | 名不副实 | app 回到 bootstrap / 启动 |
| 和 route layout | 易混 | 见下表：职责拆清 |
| 命名 | shell 偏实现黑话 | **layout** 更通用（注意与 routes 区分） |

**两个「layout」不要混：**

| 名字 | 路径 | 职责 |
|------|------|------|
| **产品铬架 layout** | `src/layout/**` | 侧栏、顶栏、主区框架、EntityScene 槽、壳级 Overlay 挂载、CommandBridge **装配** |
| **路由 layout** | `routes/_shell/route.tsx` 等 | 只做 **Outlet 挂载**：`return <AppLayout><Outlet /></AppLayout>`，尽量一行 |

导航语义（path/intent/memory）**不是视觉 layout**，建议仍放 `app/navigation`（或日后 `src/navigation`），**不要**塞进 `layout/` 以免 layout 又变上帝。

**layout 允许 / 禁止：**

| 允许 | 禁止 |
|------|------|
| 组合 features 的 **public** 注册（命令片、侧栏项配置入口） | 实体业务规则、list-scene 数据编排 |
| 使用 `shared/components` | 直接 `features/*/api` invoke |
| EntityScene 槽位（ReactNode） | 认识 Task DTO / 写 Query |

```txt
src/
├── main.tsx
│
├── app/                              # 真正的组合根 · 保持瘦
│   ├── bootstrap/                    # AppProviders, QueryClient
│   └── navigation/                   # path / intent / memory（非视觉）
│
├── layout/                           # ★ 应用铬架（原 app/shell 上提）
│   ├── AppLayout.tsx                 # 侧栏+顶栏+主区骨架
│   ├── header/
│   ├── sidebar/
│   ├── overlays/                     # 壳级抽屉/层（装配）
│   ├── command-bridge/               # 组合各 feature public 的 command slices
│   └── entity-scene/                 # 零业务槽位编排
│
├── routes/                           # 薄页 + 路由级 layout（只挂 AppLayout）
│   ├── __root.tsx
│   ├── index.tsx
│   ├── settings.tsx
│   ├── quick-create.tsx
│   └── _shell/
│       ├── route.tsx                 # → <AppLayout><Outlet /></AppLayout>
│       └── all/inbox/index.tsx       # 薄页
│
├── features/
│   ├── task/                         # ★ 试点
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   ├── model/
│   │   └── index.public.ts
│   ├── project/
│   ├── space/
│   ├── command/
│   ├── quick-create/
│   └── …
│
├── shared/
│   ├── components/                   # 含 main-card 等纯 UI
│   ├── hooks/
│   └── lib/
│
├── styles/
└── test/
```

### 3.1 和模板的「对照翻译」

| 模板 | 我们 |
|------|------|
| `features/x/components` | 同名同义 |
| `features/x/hooks` | 同名；**明确 = application**（含 React Query） |
| `features/x/api` | 同名；**收窄 = 只 IO** |
| `features/x/types.ts` | **`model/`**（类型 + 规则 + ports，可多文件） |
| `shared/components` | 同名 |
| `shared/hooks` · `lib` | 同名 |
| `app/layout.tsx` | **`src/layout/`**（整树）+ `routes/_shell/route.tsx`（一行挂载） |
| `app/page.tsx` | `routes/**/index.tsx` |
| （无） | **`index.public.ts`**、**navigation**、**entity-scene** |

### 3.2 feature 内：经典夹名 × 防腐职责（写进脑子即可）

```txt
features/task/
  model/          # 纯：无 React、无 invoke
  api/            # 只 IO：可依赖 model；被 hooks 调用
  hooks/          # 编排：依赖 model + api；导出 useXxxListScene 等
  components/     # 只认 hooks 的 state/actions/meta + shared/components
  index.public.ts # re-export 允许外用的 hooks/types/commands 面
```

**依赖（feature 内也单向）：**

```txt
components → hooks → api → model
                ↘____↗
components → shared
hooks      → shared（谨慎；优先 model）
```

### 3.3 薄页示例（吸收「page 很薄」）

## 4. UI 角色（吸收模板后的说法）

模板其实只分两层 UI：**feature components** vs **shared components**。
我们加壳与路由后是四角色，仍然 **不设 widgets/**：

| 角色 | 路径 | 一句话 |
|------|------|--------|
| 路由薄页 | `routes/**` | URL 接线 |
| 应用铬架 | **`layout/**`** | 侧栏/顶栏/命令桥/EntityScene |
| 业务 UI | `features/*/components` | 认识业务语义 |
| 纯 UI | `shared/components` | 不认识 Task/Project |
| 启动组合 | `app/**` | Provider / 导航语义，非铬架 UI |

```txt
有业务实体味道？ → features/*/components
纯视觉/通用复合？ → shared/components
主窗铬架 / 槽位？ → layout/
启动与导航语义？ → app/
只是这条 URL？   → routes/**
```

## 6. 命名选择小结（为什么不全叫 domain/ui）

| 候选 | 决定 | 理由 |
|------|------|------|
| modules vs **features** | **features** | 与模板/生态/现状一致 |
| ui-kit / 顶层 ui vs **shared/components** | **shared/** | 模板同构；hooks/lib 也有家，不必三棵顶层树 |
| feature 内 ui vs **components** | **components** | 更直白；hooks/api 并列好看 |
| domain/infra/application | **不作为文件夹名** | 作为**职责标签**映射到 model/api/hooks |
| pages/ | **不要** | routes 已够 |
| widgets/ | **不要**（默认） | 模板也没有 |

Clean Architecture 的词留在文档和 code review 话术里即可，**目录用大家一眼懂的英文。**

## 7. 防退化（不变，路径随 v3）

1. lint：shared ↛ features/app；features 互依仅 public；components ↛ api
2. 每 feature 一个 `index.public.ts`
3. api 外禁止 invoke
4. model 禁止 react / @tauri
5. 删除清单 + 史诗 `check` + doctor 复跑

**新代码决策树：**

```txt
1. 路由匹配 / loader / 薄页？        → routes/
2. 启动 Provider / QueryClient？     → app/bootstrap
3. 路径语义 / intent / 路由记忆？    → app/navigation
4. 侧栏顶栏主区 / 命令桥装配 / 槽位？ → layout/
5. 与业务无关的组件/hook/工具？     → shared/{components,hooks,lib}
6. 某能力的类型/纯规则/端口？       → features/X/model
7. 某能力的 invoke/Store？          → features/X/api
8. 某能力的 Query/用例/场景？       → features/X/hooks
9. 某能力的界面？                   → features/X/components
10. 否则：是否该新 feature？禁止扔 shared「暂时放放」
```
