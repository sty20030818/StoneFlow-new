## 1. 我们要达成什么

对清单里**有产品/装配意义**的模块（可按专场合并），弄清并留下记录：

| 议题 | 产出 |
|------|------|
| **边界** | 负责 / 不负责；依赖谁；谁依赖我；public 长什么样 |
| **最佳实践** | 对照品质标准 P0 + 六边形分层（model/api/hooks/components）；**点到为止** |
| **治理** | Keep / 收窄 public / 拆文件 / 迁职责 / 暂缓；本阶段默认 **decide-only** |
| **验收** | 讨论阶段：模块卡齐 + 无未决架构矛盾；改造阶段另开 |

**不是**再开一轮全仓搬家；**是**先谈清整体再写代码（决议 **A**）。

### 1.1 已锁定决议（2026-07-17 grill）

| 项 | 决议 |
|----|------|
| 谈 vs 写 | **先全部讨论再改代码**（A）· **讨论阶段已完成**（2026-07-17）；动刀见 [08-破坏性重构-准备清单](./08-破坏性重构-准备清单.md) |
| 破坏性 | **允许**为长期最佳实践做破坏性重构；不强制贴现网；目标见 [`04-长期目标-装配三角.md`](./04-长期目标-装配三角.md) |
| 范围 | **A2**：features 全覆盖 + app/layout/routes；shared 专场；非 56 ID 各开大会 |
| 深度 | 长期整洁 / 六边形 / 高内聚低耦合 → **可以多聊一点，但点到为止**；每场多方案对比 |
| 深谈 | navigation · layout · routes 场景 · task · command · QC · bulk · meta · shared 防火墙 |
| 浅谈 | submit · danger · filter · activity 等：半页卡即可 |
| 结束线 | 模块卡齐（深或浅）+ 第一梯队无未决架构矛盾 + 总图一页 → 才 govern-now |

## 2. 单模块讨论节奏（固定议程）

每次只深谈 **1 个 ID**（或预先声明的合并专场）。

### 2.1 会前（5～10 分钟材料）

- 清单上的路径与一句话  
- 现网：`index.ts` / 入口文件、主要消费者（layout / routes / 其它 feature）  
- doctor / 体量：是否有 >400 行文件  
- As-Is/Gap 旧债标签（若有，作参考）

### 2.2 会中议程（**必须带方案对比** · 2026-07-17 起）

禁止只「复述现网 + 盖章 decided」。每一场输出应包含：

| 块 | 内容 |
|----|------|
| **1. 边界争议** | 有什么**可能不该**在本模块？有什么**可能该进来**？ |
| **2. 分层/结构 · 多方案** | ≥2 种分法；每案 **优点 / 缺点 / 成本** |
| **3. 推荐方案** | 选哪个、为什么；未选的何时可回潮 |
| **4. 跨模块协作** | 和谁联动、谁调谁、数据/URL/命令怎么过边界 |
| **5. 最佳实践清单** | 点到为止的 do/don't |
| **6. 开放问题** | 未决 / park |
| **7. 决议** | decided 边界 + 是否改代码 |

可选：**若存在明显错放**，单独一节「迁出/迁入候选表」。

### 2.3 会后

- 新建 `模块/<ID>.md`（模板见 §6）  
- 更新清单「状态」列  
- 若 `govern-now`：拆 1 个可合并 PR，挂验收表

## 3. 讨论顺序（建议波次）

原则：**先定「装配与导航」骨架边界 → 再平台横切 → 再 domain 内核 → 再 scene/窗 → 最后 shared/styles。**  
同一波次内可按痛感调序。

### 波次 0 · 对齐清单（本次之后）

| 动作 | 说明 |
|------|------|
| 审清单 | 有无漏/应拆/应并 ID |
| 冻结 ID 命名 | 后续卡片用同一 ID |
| 选定第一场 | 建议 **M-APP-NAV** 或 **M-F-COMMAND** |

### 波次 1 · 组合根与路由（先谈清楚「谁装谁」）

| 序 | ID | 为何先谈 |
|----|-----|----------|
| 1 | **M-APP-NAV** | 全仓导航语义单点；command/layout 都依赖 |
| 2 | **M-APP-PROVIDERS** + **M-APP-ROUTER**（可一场） | Query 默认与 Router 实例 |
| 3 | **M-ROUTE-SHELL** + **M-ROUTE-SCENES** | 薄页契约；逻辑场景归属表确认 |

## 4. 合并专场规则

下列允许 **一场谈多个 ID**，减少会次：

| 专场名 | 包含 ID |
|--------|---------|
| App 启动 | M-APP-ROOT · M-APP-ROUTER · M-APP-PROVIDERS |
| Layout 壳 | M-LAYOUT-* 全部 |
| Routes 场景 | M-ROUTE-* + 逻辑场景表 |
| 小平台三件套 | SELECTION · SUBMIT · DANGER |
| 系统服务 | WORKSPACE · SYNC · UPDATE · SEARCH |
| Shared 防火墙 | 全部 M-S-* |

**禁止**一场同时谈 task + command + layout（发散）。

## 5. 与改造的关系

```txt
讨论 decide-only ──→ 只更新 模块/<id>.md
讨论 govern-now  ──→ 小 PR + 品质验收表 P0
讨论 park        ──→ 债台账记一笔，不阻塞下一模块
```

标杆改造建议仍单独开：**E-1 = 第一个 govern-now 的厚模块**（多半是 command 或 task），不必等 56 个都谈完才写第一行代码——但 **该模块本身必须先完成讨论卡**。
