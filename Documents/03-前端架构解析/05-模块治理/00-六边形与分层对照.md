# 六边形 / 分层 · 与本仓对照（点到为止）

> 2026-07-17 · 讨论用短文，不是论文。  
> 目的：后面逐模块时有同一套词，避免每人理解不一样。

---

## 1. 我们要的「整洁」是什么

| 词 | 白话 |
|----|------|
| **高内聚** | 改任务规则，主要只动 `features/task` |
| **低耦合** | 别人只用它的 public；不钻私有文件 |
| **六边形（端口与适配器）** | 核心规则不认 Tauri/React；外面通过门面进出 |
| **最佳实践** | 组合优于 boolean 丛林；Query/URL/UI 态分轨；体量可控 |

---

## 2. 映射到现有目录（已有，不是再发明一层）

```txt
                    ┌─────────────────────┐
   routes / layout  │  外侧：装配与展示      │  UI 适配器
   components       │  按钮、列表、壳        │
                    └──────────┬──────────┘
                               │ 只调 hooks / public
                    ┌──────────▼──────────┐
   hooks            │  应用层：用例编排      │  进出端口的「用例」
                    │  Query / Mutation     │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
   api              │  基础设施适配器       │  Tauri invoke / Store
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
   model            │  领域核心（尽量纯）   │  类型、规则、ports 接口
                    └─────────────────────┘
```

| 六边形说法 | 本仓落点 |
|------------|----------|
| 领域核心 | `features/*/model` |
| 出站适配器（IO） | `features/*/api` |
| 应用服务 / 用例 | `features/*/hooks` |
| 入站适配器（UI） | `features/*/components` + `routes` 薄页 |
| 驱动方装配 | `layout` · `app` |
| 跨上下文 ACL | `index.ts` public（+ contract/page） |
| 与实体无关的工具 | `shared`（严禁业务核心渗入） |

**跨 feature** = 两个限界上下文：只许 public，不许掏对方 model/api 私货。

---

## 3. 非 feature 模块怎么套

| 模块 | 在六边形里像什么 |
|------|------------------|
| **app/navigation** | 导航语境的「解析 + 意图」服务；尽量纯规则 + 少量 Store 适配 |
| **layout** | 主窗 **composition root**（装配），不是领域 |
| **routes** | 入站适配器边缘：URL → 挂哪个 page |
| **shared** | 通用库；**不是**领域层垃圾桶 |
| **styles** | 表现基础设施 |

---

## 4. 讨论时点到为止的清单（每个模块最多问这些）

1. 核心（model）是什么？有没有被 UI/IO 污染？  
2. 出站端口（api）是否唯一 IO 门？  
3. 用例（hooks）是否稳定 facade？  
4. UI 是否只依赖 facade？  
5. public 是否最小、按用例分组？  
6. 和谁耦合？能否画成「只指向更稳定一侧」？  

答完六句，就可以写模块卡，不必展开教科书。
