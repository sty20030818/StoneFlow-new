## 0. 共同原则（三角共享）

| # | 原则 |
|---|------|
| P1 | **URL 是位置唯一真相**（TanStack Router） |
| P2 | **领域在 features**；壳与路由不拥有实体规则 |
| P3 | **跨边界只经明确端口**（public / intent / ShellContext） |
| P4 | **依赖指向更稳定侧**：UI → 用例 → IO → model |
| P5 | **可删除性**：卸 feature 只摘注册与薄页，不掏壳私货 |
| P6 | 允许打破现网目录与双树，只要目标更简单、边界更硬 |

## 1. 三种「总蓝图」对比

### 蓝图 T1 · 巩固现网（小步）

保持：双树 all/spaces · layout L1–L7 · navigation 语义层 · bridge slices 在 layout。

| 优点 | 缺点 |
|------|------|
| 风险低、已跑通 | 双树重复、Bridge 仍「壳知道所有业务动作」 |
| 文档已对齐 | 不是最干净的六边形（入站动作集中在壳） |
| | 长期仍背「壳上帝适配器」税 |

**适合：** 只想还债、不大破。  
**与你的前提：** 偏保守，**不是你说的「只要长期最佳」首选**。

---

### 蓝图 T2 · 目标态（推荐）· 破坏性但可控

**一句话：**  
**Router 管树与 scope 上下文 · navigation 只管「产品路径语言」· layout 只管铬架与宿主 · 业务命令/创建由 feature 自注册。**

#### 1.1 模块边界（目标）

| 模块 | 长期只做 | 明确不做 |
|------|----------|----------|
| **navigation** | 产品 path 方言：canonical 生成、parse 成 ShellRoute、intent（跨页）、memory 规则+Store、session 历史模型 | 不持 React 大树；不持业务 Query；不实现「打开任务」业务策略 |
| **routes** | file tree、loader 门闸、redirect、把 **scope 放进 route context**、薄页只挂 feature | 不复制双树业务；不写壳 UI |
| **layout** | 铬架 UI、Provider 宿主、**ShellContext（只读：scope/route/能力槽）**、Overlays **挂载点**、EntityScene 槽位 | **不**再拥有「全部 command slices 业务表」；不写 taskOpen 规则 |
| **features** | 领域 + **自注册**命令/快捷键/创建入口；list-scene；public | 不 import layout；不手拼 URL |

#### 1.2 关键结构变化（相对现网）

| 现网 | 目标 T2 | 破坏性 |
|------|---------|--------|
| `all/**` 与 `spaces/$id/**` 对称复制叶子 | **一条工作区树** + `scope` 来自 pathless/layout context 或单一动态段 | **高**（路由大改） |
| `command-bridge/slices/*` 在 layout 集中实现动作 | **command 注册表**：feature 在启动/壳内 `registerCommands(ctx)`；layout 只提供 `ShellContext` | **高**（命令装配反转） |
| `taskOpenStrategy` 在 layout | **task public** 策略；壳/命令只调端口 | 中 |
| nav store 衍生 | **优先** `useRouterState` + parse；壳要的「当前 section」用 selector/hook，**尽量去掉可写 nav store** | 中 |
| EntityScene 在 layout | **保留**（页槽位属壳编排）或极薄进 `shared` 仅 MainCard 组合——**默认仍 layout** | 低 |
| SettingsSidebar 整包 layout | 壳只留「settings mode 骨架」；分区导航 **settings feature** | 中 |
| 启动恢复在 `routes/index` | **保留**（入站边缘正确） | 无 |

#### 1.3 目标依赖方向

```txt
features ──register──► command runtime（feature）
features ──public──► layout（只读消费）
layout ──ShellContext──► features（向下提供 scope/route，不提供业务）
layout / features ──intent──► navigation ──path──► Router
routes ──context.scope──► layout / loaders
routes ──ensureQueryData──► feature queryOptions
```

**六边形落点：**

- 领域：feature model  
- 出站 IO：feature api  
- 用例：feature hooks  
- 入站 UI：feature components + routes 薄页  
- **壳 = 另一只适配器**（主窗宿主），不是领域中心  

#### 1.4 优点 / 缺点

| 优点 | 缺点 |
|------|------|
| 真正高内聚：加业务命令改 feature，不改 layout 巨石 | 路由合并 + 命令反转，改造量大 |
| layout 可删性上升（卸 feature = 卸注册） | 迁移期要双轨或分 PR 刀 |
| 与 TanStack Router context/loader 更同构 | 团队要习惯「注册式」而非「壳里写 switch」 |
| 双树删除后改一页只改一处 | 要认真处理 all vs space 的 URL 产品语义 |

#### 1.5 成本量级

| 刀 | 量级 | 说明 |
|----|------|------|
| 命令反转（Bridge → 注册） | 大 | 可先 task/project 试点 |
| 路由单树 | 大 | 产品 URL 策略要先定 |
| 去掉可写 nav store | 中 | 配合 parse hook |
| Settings/策略迁出 | 中 | 可并行 |
| 巨石拆文件 | 中 | 可与上并行 |

---

### 蓝图 T3 · 更激进（最大破坏）

在 T2 之上：

- **取消独立 `app/navigation` 包**：path 生成尽量用 TanStack 的 `Link`/`ValidateSearch`/route `to` 类型；只留 memory 小模块  
- **layout 降级为几乎纯 CSS 骨架**；EntityScene 全进 shared 或各页自建  
- **无 ShellCommandActions 类型中心**：命令全动态注册无壳类型

| 优点 | 缺点 |
|------|------|
| 概念最少 | 丢失「产品路径方言」单点，memory/面包屑/intent 易再次散落 |
| | 桌面「启动恢复 / scope 记忆」仍要地方放，取消 navigation 会假干净 |
| | 强依赖 Router 类型，产品语义（inbox vs tasks）仍要模型 |

**推荐：** **不作为第一目标**。T2 已够「长期最佳」；T3 边际收益低、回归导航一致性风险高。

## 2. 推荐总案：**T2**

| 你的前提 | T2 是否满足 |
|----------|-------------|
| 可破坏现网 | ✅ 明确大破路由树与 Bridge |
| 长期最佳实践 | ✅ 依赖反转、单树、壳变瘦、URL 真相 |
| 六边形 / 高内聚低耦合 | ✅ feature 自包含 + 注册端口 |
| 一次谈完再写 | ✅ 本文先冻结目标，Migrate 另排刀 |

**相对 L-A：** L-A 是「现网解释」；**T2 是「愿意拆楼后的目标」**。  
实施时可 **T1 过渡 PR 不挡**，但决议与画图以 T2 为准，避免「永远巩固现状」。

## 3. 分模块：多方案 → 目标选型

### 3.1 navigation

| 方案 | 内容 | 优 | 劣 |
|------|------|----|----|
| N1 现网巩固 | 拆大文件，边界不变 | 稳 | 意图与策略仍可能渗业务 |
| **N2 目标（荐）** | 只做 **Path 方言 + Memory + SessionHistory**；`openTask` 类若含业务策略则 **下沉 feature**，navigation 只保留 `pathToTask(scope,id)` | 纯、可测 | 要清点 intents |
| N3 取消包 | 逻辑打进 routes/router | 少包 | 语义再次打散 |

**目标 N2 细则：**

- Keep：`routePaths` · `shellRoute` parse · `routeMemory*` · `sessionRouteHistory` 模型  
- Intents：**纯 path 映射**可留；依赖 settings contract 可留  
- **迁出：** 任何「先查 task 再决定打开方式」→ `features/task`  
- 大文件拆分仍按 [M-APP-NAV](./模块/M-APP-NAV.md) §4  
- 对外 API：逐步收成少数字（parse / build / remember / history），调用方不碰 Store 细节  

---

### 3.2 routes

| 方案 | 内容 | 优 | 劣 |
|------|------|----|----|
| R1 现网双树 | Keep all∥spaces | 零 URL 风险 | 双倍叶子、改一处漏一处 |
| **R2 目标（荐）** | **单工作区树** + scope 在 layout route context（或 `/w/$scopeId/...` 一类显式段，产品定） | DRY、loader 一处 | **URL 迁移 / 兼容 redirect 表** |
| R3 虚拟路由重度 | 强依赖 virtual routes | 灵活 | 心智与工具链成本 |

**R2 目标形态（示意，具体 path 可再定）：**

```txt
routes/
  __root.tsx
  index.tsx                 # 启动恢复
  quick-create.tsx
  _app/                     # 或 _shell
    route.tsx               # 提供 ShellContext：scope 从 URL 解析
    inbox.tsx
    tasks.tsx
    tasks.$taskId.tsx
    projects.tsx
    projects.$projectId.tsx
    ...
```

- `all` vs `space:xxx` 变成 **context.scope**，不再复制两套文件。  
- 旧 URL **永久 redirect 表**（破坏兼容用导航层 path builder 统一生成新 canonical）。  
- loader 门闸、薄页纪律 **不变**（[M-ROUTE](./模块/M-ROUTE.md) 实践仍成立）。  
- 详情 ensure 可留 `routes/-detail-*.ts` 或下沉 feature 的 `ensureXxxRoute` public。

**产品需先钉死（开放问题）：**

1. 「全部工作区」URL 长什么样？（`/all/...` 保留作 scope 字面量，还是改写？）  
2. 旧链接兼容多久？  

---

### 3.3 layout

| 方案 | 内容 | 优 | 劣 |
|------|------|----|----|
| L-A 现网细分层 | L1–L7 + Bridge 在 layout | 清晰、已存在 | Bridge 仍上帝适配 |
| L-B 合并上帝 | 少层 | 倒退 | 否 |
| **L-T2 目标（荐）** | **保留 L1–L5 铬架分层**；**删除「业务 Bridge 切片中心」**；改为 ShellContext + feature 注册；EntityScene 留；巨石拆文件；Settings 内容外迁 | 壳长期可瘦 | 命令改造大 |
| L-D Scene→shared | 仅 Scene | 收益有限 | 防火墙风险 |

**L-T2 后 layout 还剩什么：**

```txt
layout/
  ShellRouteLayout / AppProviders嵌套
  chrome/  (header, sidebar, main, footer, drawer)
  overlays/  (host only)
  entity-scene/  (slots + thin adapters)
  model/  (仅壳 UI：sidebar 折叠、dialog open 宿主态——非业务)
  shell-context.tsx  (scope, shellRoute, 只读)
```

**迁出 layout：**

| 迁出 | 去向 |
|------|------|
| command-bridge/slices 业务动作 | 各 feature `register*` 或 `command` 的 domain handlers |
| taskOpenStrategy | task public |
| 设置分区列表/文案 | settings |
| 过重 chrome 数据规则 | 已是 public 聚合则保留薄 hook |

**铬架分层（L1–L5）仍建议保留**——这是 UI 工程最佳实践，与「命令反转」不冲突。  
否决的是 **「layout 知道所有业务命令怎么执行」**，不是否决 Header/Sidebar 分文件。

## 4. 协作关系（目标态）

```txt
        ┌────────── register commands / overlays content ──────────┐
        ▼                                                            │
┌───────────────┐     ShellContext(scope,route)     ┌───────────────┐
│ layout chrome │ ───────────────────────────────► │   features    │
│ + hosts       │ ◄──── public UI / hooks ─────────│               │
└───────┬───────┘                                  └───────┬───────┘
        │ intent/path                                      │
        ▼                                                  │
┌───────────────┐     navigate / redirect                  │
│  navigation   │ ◄────────────────────────────────────────┘
└───────┬───────┘
        │ canonical path
        ▼
┌───────────────┐
│    routes     │  tree · loader · context.scope · thin page
└───────────────┘
```

| 场景 | 目标协作 |
|------|----------|
| 侧栏点收件箱 | Sidebar → `intent.openSection` → Router；高亮来自 route context |
| 命令改任务状态 | command runtime → **task 注册的 handler**（不再 layout bulkSlice 上帝） |
| 打开任务 | command/UI → **task.openTask port** → 内部再调 path/navigate |
| 启动恢复 | routes index → navigation memory → redirect 新 canonical |
| 列表页 | 薄页 → task list-scene；EntityScene 只收槽位 props |
