# StoneFlow 云同步调度与性能重构方案

> 最后更新：2026-06-30
> 依据：`Docs/T2-云同步设计.md`、`Docs/02-重构方案/03-云同步重构/云同步重构方案.md`
> 定位：在既有云同步协议基础上，重构运行时调度、启动检查、写入触发和设置页状态刷新，解决“应用运行时卡顿”和同步频率过高问题。

---

## 1. 结论

推荐把当前“本地写入后立即完整同步”的模型，收口为 **本地优先 + 策略调度同步**。

核心变化：

- 业务写入只落本地 SQLite，并标记 dirty，不直接启动完整同步。
- Rust runtime 新增 `SyncScheduler`，作为所有自动同步触发的唯一入口。
- 启动和恢复前台只做轻量 `probe`，确认远端有变化或本地到达同步窗口后才同步。
- 设置页提供同步频率选项，默认 `15 分钟自动同步`，保留手动立即同步。
- 前端状态刷新改为事件驱动 + 低频兜底，不再依赖 3 秒轮询。

这个方案不是临时加 debounce。它把同步从“每个写入点自己决定何时同步”改为“统一调度器按策略决策”，降低远端 RTT、worker 启动、数据库查询和前端 query invalidation 的总成本。

---

## 2. 当前问题

### 2.1 写入触发过重

当前业务 command 写入后调用 `sync::note_local_write()`，在远端配置存在时会尽快触发完整同步。完整同步包含：

```text
migrate -> pull -> push -> pull
```

这适合验证协议正确性，但不适合作为日常写入的默认运行模式。连续编辑、批量操作、Quick Create 快速创建都会放大 worker 启动和远端往返成本。

### 2.2 启动与恢复过积极

启动后会触发完整 sync。应用恢复前台也会触发 sync。对单人本地优先应用来说，启动时真正需要回答的是：

- 远端是否有新 `server_seq`？
- 本地是否有 pending mutation？
- 当前是否已经到了自动同步时间？

如果这些答案都不要求同步，就不应该启动 worker 跑完整链路。

### 2.3 状态读取承担了诊断成本

`get_sync_status` 当前会刷新本地 replica 状态。设置页和同步 UI 如果高频轮询，会把本应用不需要的数据库检查变成常驻成本。

### 2.4 同步完成后的刷新范围偏大

同步完成会广播 workspace changed，前端再 invalidate 多个 workspace domain。这个机制正确，但如果同步频率过高，前端会被迫频繁重拉已加载 query。

---

## 3. 设计原则

- 本地优先：创建、编辑、删除必须立即本地成功，网络不参与主交互链路。
- 单一调度入口：自动同步只能通过 `SyncScheduler`，不要让 command、启动、resume、设置页各自决定。
- 轻检查先行：启动、恢复、定时 tick 先 `probe`，只有必要时才 `pull` / `sync`。
- 少状态源：同步策略、下次同步时间、dirty 状态由 Rust 持久化和投影，前端只展示。
- 可解释：设置页能说明“为什么现在不同步”“下次什么时候同步”“是否有本地待上传”。
- KISS：先做固定策略和明确模式，不做复杂规则引擎、插件化、账号级策略或多人协作调度。

---

## 4. 目标与非目标

### 目标

- 降低日常写入后的同步频率。
- 降低启动和恢复前台的后台负载。
- 保留手动立即同步能力。
- 保证本地 pending mutation 不丢失。
- 保证远端有变化时仍能自动追平。
- 保持现有云同步协议边界：Rust 是唯一真相源，React 只消费状态和触发命令。

### 非目标

- 不做账号系统。
- 不做多人实时协作。
- 不做复杂同步工作台。
- 不引入新依赖或独立调度服务。
- 不把业务读写改成远端优先。
- 不为单人应用引入 CRDT/OT。

## 5. 推荐架构

### 5.1 模块边界

```text
src-tauri/crates/runtime/src/sync/
  engine.rs
    执行 pull / push / sync / diagnose，保留 worker 编排，不负责调度策略

  scheduler.rs
    自动同步唯一入口，处理 write dirty、startup、resume、timer、cooldown、debounce

  policy.rs
    同步策略类型、默认值、下一次同步时间计算

  probe.rs
    轻量远端 head check，判断远端 server_seq 是否变化

  state.rs
    同步运行态快照，增加 scheduler/status projection 字段

  config.rs
    持久化远端配置和同步策略配置

src-tauri/crates/sync-worker/
  main.rs
    新增 probe mode；已有 migrate/pull/push/diagnose 保持职责清晰

src/features/sync/
  api/sync.ts
    thin invoke API，增加策略配置与调度状态字段

  model/
    只做展示派生，不维护第二套调度状态机

src/features/settings/ui/
  SettingsPage.tsx
    展示同步状态、频率选择、下次同步时间、手动同步按钮
```

### 5.2 责任划分

`engine` 只回答“怎么同步”：

- 跑 worker。
- 处理 push/pull/sync 错误。
- 更新同步成功/失败状态。
- 广播 workspace changed。

`scheduler` 只回答“什么时候同步”：

- 本地写入后是否只标 dirty。
- 启动时是否 probe。
- 恢复前台是否跳过。
- 定时 tick 到期后是否 sync。
- 失败后何时重试。

`policy` 只回答“用户想要什么节奏”：

- 每 5 分钟。
- 每 15 分钟。
- 每 30 分钟。
- 仅手动。

`probe` 只回答“远端是否可能有新东西”：

- 返回 remote latest server seq。
- 不拉业务数据。
- 不触发 workspace refresh。

## 6. 同步策略

### 6.1 用户可选项

| 选项 | 含义 | 适用 |
|---|---|---|
| 每 5 分钟 | 较快自动追平 | 多设备频繁切换 |
| 每 15 分钟 | 默认推荐 | 日常使用，低打扰 |
| 每 30 分钟 | 更低频 | 主要单设备使用 |
| 仅手动 | 不自动上传本地变化 | 需要完全控制同步时机 |

默认值：`15 分钟自动同步`。

不建议把“实时同步”作为默认选项。实时同步可以未来作为高级选项，但当前阶段会重新引入写入即同步的性能问题。

### 6.2 持久化字段

建议在 settings / cursor 中保存：

```text
sync:policy.mode = interval | manual
sync:policy.interval_minutes = 5 | 15 | 30
sync:last_probe_at
sync:last_success_at
sync:next_sync_at
sync:last_remote_server_seq
sync:failure_count
```

已有字段继续保留：

```text
sync:last_pulled_server_seq
sync:device_id
sync:last_restore_at
```

`dirty_since` 可以继续放在 runtime state，但必须能从 `sync_mutations WHERE status = 'pending'` 恢复出来，避免重启后丢失“待同步”事实。

## 7. 运行流程

### 7.1 本地写入

```text
业务 command 成功
  -> 同事务写业务表和 sync mutation
  -> note_local_write()
       mark dirty
       update next_sync_at if needed
       notify status changed
       schedule debounce timer only
```

规则：

- 不直接完整 sync。
- 如果策略是 `manual`，只进入 `offline_pending`。
- 如果策略是 interval，计算 `next_sync_at`。
- 多次写入只更新 dirty 状态，不创建多轮 sync。

### 7.2 debounce

debounce 不是主要同步策略，只用于把同一操作簇合并为一次调度判断。

建议：

```text
write_debounce = 2s
```

2 秒后 scheduler 检查：

- 未到 `next_sync_at`：不跑 sync。
- 到了 `next_sync_at`：尝试 sync。
- 已有 sync 在跑：只设置 pending。

### 7.3 启动

```text
startup
  -> initialize_state()
  -> inspect pending mutation
  -> probe remote head
  -> decide
```

决策表：

| 本地 pending | 远端 server_seq 变化 | 到达同步时间 | 动作 |
|---|---|---|---|
| 否 | 否 | 任意 | 跳过 |
| 否 | 是 | 任意 | pull |
| 是 | 否 | 否 | 等待下次自动同步 |
| 是 | 否 | 是 | sync |
| 是 | 是 | 否 | pull 后等待上传窗口 |
| 是 | 是 | 是 | sync |

这个设计避免“每次启动都完整 sync”。

### 7.4 恢复前台

```text
resume
  -> if last_probe_at within 5min: skip
  -> probe remote head
  -> same decision table as startup
```

恢复前台不是强同步信号，只是轻量检查机会。

### 7.5 定时 tick

`SyncScheduler` 持有一个 runtime timer：

```text
timer wakes at next_sync_at
  -> if manual: skip
  -> if no pending and remote unchanged: skip
  -> if pending or remote changed: run needed mode
```

不需要高频轮询。timer 应直接睡到 `next_sync_at` 或最小 probe 间隔结束。

### 7.6 手动立即同步

设置页“立即同步”绕过 interval，但不绕过 execution lock 和 replica safety check：

```text
manual run
  -> cancel debounce wait
  -> acquire execution lock
  -> sync
  -> update last_success_at / next_sync_at
```

手动同步失败时记录错误和失败次数，但不改变用户的自动策略。

## 8. 轻量 probe

### 8.1 worker mode

新增：

```text
stoneflow-sync-worker --mode probe
```

返回：

```json
{
  "latestServerSeq": 123,
  "schemaVersion": 2
}
```

`probe` 只访问远端元信息，不读取全量业务表，不写本地数据库。

### 8.2 runtime API

Rust runtime 内部使用：

```rust
pub struct SyncProbeResult {
    pub latest_server_seq: Option<i64>,
    pub schema_version: Option<i64>,
}
```

比较逻辑：

```text
remote latest_server_seq > local last_pulled_server_seq
```

为真时才需要 pull。

## 9. 状态投影

`SyncStatusPayload` 建议扩展：

```text
policyMode
policyIntervalMinutes
nextSyncAt
lastProbeAt
lastSyncAt
pendingMutationCount
remoteChanged
cooldownUntil
failureCount
```

状态文案从 Rust payload 派生：

- `synced`：无 pending，远端无新变化。
- `offline_pending`：本地有 pending，但尚未到同步时间或当前离线。
- `syncing`：engine 正在执行。
- `needs_attention`：replica 不安全或 schema mismatch。
- `error`：最近自动或手动同步失败。
- `disabled`：无远端配置。

前端不再用多个 effect 猜同步阶段。

## 10. 设置页设计

设置页云同步 section 展示：

- 当前状态。
- 本地待上传数量。
- 最近成功同步时间。
- 下次自动同步时间。
- 同步频率选择。
- 立即同步按钮。
- 诊断按钮。
- 最近错误。

刷新策略：

- 进入设置页时 `get_sync_status()` 一次。
- 收到 sync status event 时刷新。
- 保留 60 秒兜底轮询。

不再使用 3 秒状态轮询。

## 11. 前端 query 刷新

workspace changed event 保留，但触发频率由 scheduler 降低。

规则：

- `pull` 成功且 remote changed：invalidate workspace domains。
- `push` 成功但没有远端新 canonical change：可只刷新 sync status，不必刷新全部 workspace。
- `sync` 完成：根据 worker 返回的 changed domains 精准 invalidate；如果 worker 暂时没有 domains，保留当前粗粒度刷新作为过渡。

长期目标是 worker 返回：

```text
changed_domains = tasks | projects | spaces | lifecycle | views | settings
```

但第一阶段可以先保持现有 invalidation，先解决同步频率。

## 12. 失败与重试

自动同步失败不应打断用户。

失败后：

```text
failure_count += 1
next_retry_at = now + backoff(failure_count)
```

建议退避：

| failure_count | retry |
|---|---|
| 1 | 1 分钟 |
| 2 | 5 分钟 |
| 3+ | 15 分钟 |

手动同步不受退避限制。

网络错误、远端不可达、token 错误要区分：

- 网络错误：等待下次重试。
- token/config 错误：`needs_attention`，不自动高频重试。
- schema mismatch：`needs_attention`，提示升级或迁移。
- replica unsafe：保持当前安全拦截，不自动覆盖。

## 13. 实施阶段

### Phase 1：调度状态与策略配置

- 新增 `policy.rs`。
- 扩展 `SyncRuntimeState`。
- 持久化同步策略和 `next_sync_at`。
- 设置页能读取和修改同步频率。

验收：

- 默认策略是 15 分钟。
- 切换策略后重启仍保留。
- `仅手动` 下本地写入只显示待同步，不自动跑 worker。

### Phase 2：写入只标 dirty

- 修改 `note_local_write()`，不再直接 schedule 完整 sync。
- 新增 write debounce，只触发 scheduler 决策。
- 保留手动 `run_sync()` 原行为。

验收：

- 连续创建多个任务只产生 dirty 状态，不立即产生多轮 sync。
- 手动同步仍能立即上传。

### Phase 3：轻量 probe

- sync-worker 新增 `probe` mode。
- runtime 新增 probe 调用。
- 启动和 resume 改为先 probe 再决策。

验收：

- 本地无 pending 且远端 seq 未变时，启动不跑完整 sync。
- 远端 seq 变更时，启动只 pull。

### Phase 4：定时 scheduler

- 新增 `scheduler.rs`。
- setup 后启动 scheduler runtime task。
- 根据 `next_sync_at` 唤醒。
- 处理 execution lock、pending、cooldown、backoff。

验收：

- 到达同步时间才自动 sync。
- 已有 sync 在跑时不会并发启动第二个 worker。
- 失败后按退避重试。

### Phase 5：状态事件与前端降频

- Rust 侧在状态变化时 emit sync status changed event。
- 前端设置页监听事件刷新。
- 兜底轮询调整为 60 秒。

验收：

- 设置页状态能及时更新。
- 不再每 3 秒调用 `get_sync_status()`。

### Phase 6：精准刷新优化

- worker 或 runtime 汇总 changed domains。
- 前端按 changed domains invalidate。
- 没有 changed domains 时才走当前全量 workspace invalidation。

验收：

- 远端无变化时同步完成不刷新所有 workspace query。
- 有 task/project 变化时只刷新必要 domain。

## 14. 测试策略

### Rust 单元测试

- `policy`：不同策略下 `next_sync_at` 计算。
- `scheduler`：write debounce、manual mode、interval mode、cooldown、backoff。
- `probe`：remote seq 与 local cursor 比较。
- `state`：pending mutation count 和 status projection。

### Rust 集成测试

- 启动无变化跳过完整 sync。
- 启动远端变化只 pull。
- 本地 pending 未到时间不 push。
- 本地 pending 到时间执行 sync。
- 手动同步绕过 interval。

### 前端测试

- 设置页展示频率选项。
- 切换频率调用 thin API。
- 状态事件后刷新。
- 60 秒兜底轮询。

### 手工验收

- 单设备连续编辑 10 次，期间不应每次都触发 worker。
- 两台设备：A 编辑后等待自动同步，B 恢复前台后能在 probe 后拉到变化。
- 切到仅手动后，自动同步完全停止，手动按钮仍可同步。
- 断网后编辑不影响本地操作，联网后按策略重试。

## 15. 风险与取舍

### 风险：多设备同步不再“秒级”

这是明确取舍。StoneFlow 当前是单人本地优先任务工具，不是实时协作产品。默认 15 分钟能明显降低卡顿和远端成本，同时保留手动立即同步。

### 风险：probe 增加一个 worker mode

这是值得的复杂度。它把“是否需要同步”的判断从完整 sync 中拆出来，能避免大量不必要 pull/push。

### 风险：状态字段变多

字段增加是为了让状态可解释，而不是让前端维护第二套状态机。字段必须由 Rust 统一投影，React 只展示。

### 暂不做

- 不做 cron 表达式。
- 不做 per-entity 同步策略。
- 不做按网络类型切换策略。
- 不做多账号、多远端或插件式 sync provider。

这些都可以未来再加，但当前会稀释核心目标。

## 16. 最终形态

用户日常操作路径：

```text
创建/编辑任务
  -> 本地立即完成
  -> 状态显示“等待同步”
  -> 到达同步窗口后后台同步
  -> 同步完成后低频刷新受影响数据
```

启动路径：

```text
打开应用
  -> 本地数据库和主窗口先 ready
  -> 后台 probe
  -> 无变化则不打扰
  -> 有变化才 pull 或 sync
```

设置页路径：

```text
用户选择同步频率
  -> Rust 保存 policy
  -> scheduler 重算 next_sync_at
  -> UI 展示下次自动同步时间
```

这才是 StoneFlow 更合适的长期同步体验：本地快、后台静、状态清楚、必要时可手动强制同步。
