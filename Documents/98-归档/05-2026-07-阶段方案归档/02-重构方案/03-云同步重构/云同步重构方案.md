# StoneFlow 云同步重构方案

> 最后更新：2026-06-29
> 依据：`Docs/T2-云同步设计.md`
> 定位：只记录把现有 S1 同步原型迁移到长期规范的开发落地计划。

---

## 1. 重构目标

- 停止扩展现有 S1 push / pull 原型。
- 建立 `sync_mutations + sync_shadow + sync_cursor` 本地事实源。
- 建立 `remote_mutations + remote_change_log + server_seq` 远端事实源。
- 把业务写入和 mutation 写入收口到同一事务。
- 前端只消费 Rust 同步状态，不维护第二套状态机。

---

## 2. 模块边界

```text
src-tauri/crates/sync-core
  protocol types
  resolver
  patch model
  conflict model

src-tauri/crates/sync-local
  mutation log
  shadow store
  local apply
  rebase

src-tauri/crates/sync-remote
  Turso schema
  pull
  push
  snapshot

src-tauri/crates/runtime/src/sync
  engine
  Tauri commands
  background scheduling
  status projection

src/features/sync
  thin invoke API
  status types

src/features/settings/ui
  composed status section
```

---

## 3. Rust 边界

- sync protocol 类型放在 `sync-core`，不要依赖 Tauri。
- local/remote I/O 分开，方便单测 resolver 和集成测试 Turso。
- 错误用精确 enum，crate 内用 `thiserror`，Tauri command 只负责序列化成前端可读 payload。
- 公共类型写 `///` 文档，复杂协议写在 `T2` 或 ADR，不靠长注释解释。
- 同步 engine 只允许单实例串行运行；新触发只合并为下一轮。

---

## 4. Tauri 边界

Tauri commands 保持薄：

- `get_sync_status`
- `configure_sync`
- `run_sync`
- `get_sync_diagnostics`
- `resolve_sync_conflict`

后台状态变化用 Tauri event 广播低频状态。长任务进度如首次 full snapshot 可用 channel，但默认不需要。

所有 async command 参数使用 owned type，返回 `Result<T, AppError>`。不要在 command 中阻塞主线程，不在前端直连 Turso。

---

## 5. React 边界

前端只用一个 provider 接住 Rust 状态：

```text
SyncStatusProvider
  state: SyncStatusPayload
  actions: refresh / runSync / configure / resolveConflict
  meta: isBusy / canRunSync
```

UI 用组合组件表达不同区域：

- `SyncStatusSection`
- `SyncStatusBadge`
- `SyncDiagnosticsPanel`
- `SyncConflictNotice`

不要做 `isRestoreMode/isPushMode/isPullMode/hasCursor` 这类 boolean prop 堆叠。派生状态在 render 中计算，异步刷新只依赖必要 primitive。

---

## 6. 迁移阶段

### Phase 0：冻结 S1 行为

- 保留现有同步入口但停止扩展新状态分支。
- 文档标记 S1 为原型，不再作为长期方案。

### Phase 1：建立协议骨架

- 新增 `sync_mutations`、`sync_shadow`、远端 `remote_mutations`、`remote_change_log`。
- 新增 `server_seq`。
- 保留旧 `sync_outbox`，只作为迁移兼容。

### Phase 2：本地写入同事务接入 mutation log

- 将 mutation 写入收口到 service/usecase 层。
- 移除 command 层散落的 `note_local_write()` 语义。
- 每个业务写入必须在同一事务里写业务表和 mutation。

### Phase 3：实现新 `pull`

- `pull(null)` 返回完整 snapshot。
- `pull(seq)` 返回 change log。
- cursor 过旧返回 snapshot。
- 本地应用支持 shadow、soft_delete 和 hard_delete。

### Phase 4：实现新 `push`

- 远端按 `(client_id, client_seq)` 幂等。
- resolver 产出 canonical result。
- ack 后本地清理已确认 mutation。

### Phase 5：替换 UI 状态

- 前端从 push/pull 文案迁移到 `synced/syncing/offline_pending/needs_attention`。
- 诊断面板展示数据事实，不展示设备状态猜测。

### Phase 6：基线迁移与切换收口

- 新增幂等 `migrate` worker。
- 远端 `remote_change_log` 为空时，从当前 canonical tables 生成初始 `upsert` 基线。
- 本地已有数据但缺少 `sync:last_pulled_server_seq` 时，只写 `sync_shadow + cursor`，不覆盖业务表。
- 本地空副本仍交给 `pull` snapshot 自动补齐。
- runtime `sync()` 在 `pull -> push -> pull` 前先执行一次迁移。

### Phase 7：删除 S1 表和旧 worker 语义

- 删除旧 `sync_operations` 回放依赖。
- 删除特殊 restore 入口。
- 删除旧 push/pull worker 语义。
- 删除 `sync_outbox` 兼容写入。
- 删除设置页恢复兜底按钮或下沉到诊断危险操作。

每个 phase 都必须可独立合并，不能要求所有 phase 完成后才可运行。

---

## 7. 测试策略

### Rust 单元测试

- resolver：字段级冲突、软删除赢、硬删除赢、restore、外键缺失。
- mutation log：client_seq 单调、幂等 ack、pending 查询。
- rebase：远端 patch 与本地 pending mutation 合并。

### Rust 集成测试

- 本地 SQLite + 远端 Turso/libsql 测试库跑完整 `sync()`。
- 断网、重复 push、重复 pull、cursor 过旧。
- full snapshot 与 incremental changes 结果一致。

### 前端测试

- `SyncStatusProvider` 只消费 Rust payload。
- 设置页按钮只调用薄 API。
- 派生状态不通过 effect 写二次 state。

### 手工验收

- 两台真实 Mac 互相新增、修改、软删除、恢复、硬删除。
- 一台离线编辑后联网。
- 一台清空本地库后重新接入。
- 一台使用旧 S1 数据库迁移到新协议。
- 迁移重复执行不会重复生成远端基线，不会覆盖本地业务表。
