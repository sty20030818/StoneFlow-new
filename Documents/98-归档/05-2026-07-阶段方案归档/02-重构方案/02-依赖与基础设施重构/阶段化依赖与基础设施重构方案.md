# StoneFlow 阶段化依赖与基础设施重构方案

## 0. 文档信息

| 项目 | 内容 |
|---|---|
| 文档名称 | StoneFlow 阶段化依赖与基础设施重构方案 |
| 文档目的 | 为 StoneFlow 在 TanStack Router 接入完成后的下一阶段依赖与基础设施演进提供单一推荐方案 |
| 适用范围 | 前端表单与校验、Rust 可观测性、国际化、错误监控、构建分析 |
| 当前阶段 | 方案文档，供后续拆执行计划或直接分阶段实施 |
| 核心策略 | 先补真实缺口，再上基础设施；拒绝“先装依赖再找场景”；每个阶段只解决一类明确问题 |

# 1. 背景与核心判断

## 1.1 当前事实

StoneFlow 当前已经完成 TanStack Router 接入，`package.json` 中已存在 `@tanstack/react-router` 与 `@tanstack/router-plugin`，路由文件也已经切到 file-based 结构。

因此，下一阶段的重点不应该再是“要不要上 TanStack Router”，而应该转向：

1. 统一前端输入与校验模型；
2. 补 Rust 侧结构化可观测性；
3. 建立长期可维护的国际化基座；
4. 建立生产错误监控与构建分析能力。

## 1.2 当前真正缺的不是“更多库”，而是“更清晰的基础设施边界”

当前仓库里已经存在两类不能再重复造轮子的能力：

1. 路由系统已经切到 TanStack Router，不应再把路由库当候选依赖。
2. 命令与快捷键系统已经是自研体系，不适合再叠加第二套快捷键运行时。

同时，当前仓库里又明显存在两类真实缺口：

1. 表单仍大量采用 `useState + 手写校验 + 手写错误态 + 手写提交态`。
2. Rust 侧日志仍以 `log + tauri-plugin-log` 为主，缺少结构化 span 与统一过滤能力。

## 1.3 单一推荐结论

下一阶段采用以下顺序推进：

```txt
Phase 2   表单与校验基座
Phase 2.5 Rust tracing 可观测性补齐
Phase 3   Paraglide 国际化基座
Phase 4   Sentry 监控与构建分析
```

本方案不建议在这四个阶段内正式引入以下依赖：

- `react-hotkeys-hook`
- `zundo`
- `zod-error-utils`
- `vite-bundle-visualizer`
- `ts-pattern`

这些库不是绝对不能用，而是当前不是 StoneFlow 的主路径缺口，不应抢占阶段预算。

# 2. 总体策略

## 2.1 设计原则

整个重构过程遵循以下原则：

1. 依赖只为已确认问题服务，不为“以后可能有用”提前铺路。
2. 每个阶段只引入一类新的基础设施，不混做。
3. 先建立项目内薄封装，再允许能力扩散到业务层。
4. 新能力必须有明确落点、明确范围、明确验证口径。
5. 不在同一阶段同时改动过多业务页面、构建链路和平台链路。

## 2.2 阶段依赖关系

推荐顺序如下：

```txt
Phase 2
  -> Phase 2.5
  -> Phase 3
  -> Phase 4
```

解释：

1. Phase 2 先统一输入与校验模型，后续国际化和错误上报都需要稳定的错误语义。
2. Phase 2.5 可以与 Phase 3 局部并行，但建议先完成日志基础口径，再接更高层基础设施。
3. Phase 3 先把文案来源统一，避免 Phase 4 上报错误时混入大量不稳定文案。
4. Phase 4 最后接入监控与构建分析，避免在前面几个阶段反复修改埋点与 sourcemap 策略。

## 2.3 本方案明确不做什么

本方案不包含以下内容：

1. 不重做路由系统。
2. 不重写命令与快捷键系统。
3. 不在本阶段引入全局 undo/redo 栈。
4. 不把所有页面一次性迁到新表单系统。
5. 不在国际化阶段做本地化路由。
6. 不在监控阶段同时引入一整套前后端 APM 大平台。

# 3. Phase 2：表单与校验基座

## 3.1 目标

建立 StoneFlow 前端统一的“输入状态 + 运行时校验 + 提交错误展示 + 提交行为接入”基础设施。

## 3.2 推荐依赖

前端正式引入：

```bash
bun add zod react-hook-form @hookform/resolvers
```

## 3.3 为什么是这三个，而不是别的

### `zod`

职责：

1. 定义运行时输入 schema；
2. 统一字段约束与错误语义；
3. 为路由 search、表单输入、未来命令 payload 校验提供同一套语言。

选择原因：

1. 生态成熟，和当前 React / TanStack 体系兼容最好。
2. 既能服务表单，也能服务 `validateSearch`、future payload parsing。
3. 后续与国际化结合时，错误码和 schema 结构都更稳定。

### `react-hook-form`

职责：

1. 统一表单状态管理；
2. 统一 dirty / submit / reset / field-level error 行为；
3. 降低业务组件中手写状态机的重复度。

选择原因：

1. StoneFlow 当前主要是 Dialog / Drawer / Popover 型表单，不需要先上更重的 form framework。
2. 接入成本低，能快速替换当前重复的 `useState + canSubmit + errorMessage` 模式。
3. 和现有 `SubmitRegistry` 体系更容易集成。

### `@hookform/resolvers`

职责：

1. 把 `zod` schema 直接接入 RHF；
2. 避免每个表单手写 schema 到 errors 的转换逻辑。

## 3.4 影响范围

优先处理以下已有表单密集区域：

1. `src/features/task/ui/TaskCreateContent.tsx`
2. `src/features/project/ui/ProjectCreateContent.tsx`
3. `src/features/view/ui/ViewEditorDialog.tsx`
4. `src/features/space/ui/SpaceEditorDialog.tsx`
5. `src/features/task/detail/ui/TaskLinkEditorPopover.tsx`

这些文件当前都属于“局部状态直写业务”的典型代表，适合作为第一批迁移样板。

## 3.5 推荐新增目录

建议新增但保持薄封装：

```txt
src/shared/form/
  zod/
  rhf/

src/shared/validation/
```

职责建议：

### `src/shared/validation/`

放：

1. 通用 schema 片段；
2. 字符串、标题、描述、URL、日期等共性校验；
3. 共享错误映射入口。

不放：

1. 具体 Task / Project 业务规则；
2. 依赖组件 UI 的展示逻辑。

### `src/shared/form/`

放：

1. RHF + Zod 接线薄封装；
2. `FormField`、`FormMessage`、`useZodForm` 一类小型基础设施；
3. 与 `SubmitRegistry` 对接的 glue code。

不放：

1. 业务表单本身；
2. 项目级复杂字段编排。

## 3.6 实施步骤

### Step 1：显式安装依赖

目标：

1. 把 `zod` 从间接依赖变为显式依赖；
2. 引入 RHF 与 resolver。

### Step 2：建立最小共享层

目标：

1. 提供统一的 RHF + Zod 初始化方式；
2. 统一字段错误展示口径；
3. 统一提交时机与禁用态约定。

要求：

1. 只做薄封装；
2. 不要提前造组件工厂或大型 DSL。

### Step 3：迁移一组代表性表单

推荐顺序：

1. `SpaceEditorDialog`
2. `ProjectCreateContent`
3. `TaskCreateContent`
4. `ViewEditorDialog`
5. `TaskLinkEditorPopover`

原因：

1. 从小到大递增复杂度；
2. 能尽早验证 `SubmitRegistry` 与 RHF 的兼容模式；
3. 能在进入更复杂表单前先固定公共抽象边界。

### Step 4：补测试与迁移约定

目标：

1. 补表单交互测试；
2. 沉淀“以后新表单默认怎么写”的标准口径。

## 3.7 Done 标准

满足以下条件才算 Phase 2 完成：

1. `zod`、`react-hook-form`、`@hookform/resolvers` 已显式接入。
2. 至少 3 个核心表单迁到统一方案。
3. 新表单不再重复手写 `errorMessage + canSubmit + submitState` 模式。
4. 表单与 `SubmitRegistry` 的集成方式已有稳定模板。
5. 测试与校验命令通过。

## 3.8 风险与控制

主要风险：

1. 过早把 RHF 抽象成项目级 DSL，导致理解成本上升。
2. 把业务规则错误塞进共享层，污染 `shared` 边界。
3. 在一个阶段内迁移过多表单，导致回归面过大。

控制方式：

1. 只做薄封装；
2. 只迁移第一批高频表单；
3. 每迁一个表单就补对应测试。

## 3.9 验证口径

```bash
bun run typecheck
bun run lint
bun run format:check
bun run test:run
```

# 4. Phase 2.5：Rust tracing 可观测性补齐

## 4.1 目标

在不推翻现有 Tauri 日志出口的前提下，为 StoneFlow Rust 侧补齐结构化日志与 span 能力。

## 4.2 推荐依赖

在 `src-tauri/Cargo.toml` 的 workspace dependencies 中引入：

```toml
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "fmt"] }
tracing-log = "0.2"
```

## 4.3 为什么不是“直接全量替换 log”

当前 Rust 侧已经存在：

1. `tauri-plugin-log`
2. `log` 宏调用
3. 面向平台初始化、快捷键、Quick Create、窗口事件的一批既有日志

因此 Phase 2.5 的目标不是“重写整个日志系统”，而是：

1. 先补 `tracing` 能力；
2. 通过桥接让旧 `log` 调用继续工作；
3. 在关键链路上新增 span，而不是一上来全仓替换。

## 4.4 首批关注链路

推荐优先覆盖：

1. app bootstrap
2. database bootstrap
3. quick create session 生命周期
4. command 调用链
5. 全局快捷键触发链
6. 平台窗口显隐与定位链

对应目录：

```txt
src-tauri/crates/runtime/
src-tauri/crates/platform/
src-tauri/crates/storage/
```

## 4.5 实施步骤

### Step 1：接入 subscriber 与过滤配置

目标：

1. 建立统一 tracing 初始化入口；
2. 明确 debug / release 下的默认日志级别；
3. 保留现有 `tauri-plugin-log` 输出能力。

### Step 2：桥接旧 `log`

目标：

1. 让现有 `log::info!`、`log::warn!` 等仍可工作；
2. 避免一开始就改动所有 crate。

### Step 3：为关键函数加 span

优先形式：

1. `#[instrument]`
2. 关键 session / entity id / scope 字段入日志
3. command 调用时带输入上下文，但避免敏感信息直出

### Step 4：补回归验证

目标：

1. 确认 debug 构建下日志输出正常；
2. 确认 release 不会因日志初始化异常破坏启动链。

## 4.6 Done 标准

1. workspace 已显式引入 `tracing` 生态依赖。
2. 应用启动链已初始化 tracing subscriber。
3. 至少一条核心命令链和一条 quick create 链具备 span。
4. 旧 `log` 宏调用未被强制一次性清空。
5. Rust 测试与编译检查通过。

## 4.7 风险与控制

主要风险：

1. 双日志管线导致重复输出。
2. 过度记录导致噪音过大。
3. 敏感信息误入日志。

控制方式：

1. 明确 single init 入口；
2. 先覆盖关键链路，不全量铺开；
3. 对 payload、标题、用户输入字段做审查，默认不整包输出。

## 4.8 验证口径

```bash
cargo check --manifest-path src-tauri/Cargo.toml --workspace
cargo test --manifest-path src-tauri/Cargo.toml --workspace
```

# 5. Phase 3：Paraglide 国际化基座

## 5.1 目标

建立 StoneFlow 的长期国际化基座，统一 UI 文案、错误文案、空状态文案与后续 Zod 错误映射来源。

## 5.2 单一推荐

选择 `Paraglide`，不选择 `i18next` 作为本阶段主方案。

原因：

1. StoneFlow 当前更适合 compiler-first、type-safe 的消息函数模型。
2. 项目是桌面应用，不需要为了网站 SEO 或本地化 URL 引入更重的 runtime 思维。
3. 未来如果 Zod 错误也接国际化，typed message key 比 runtime string key 更稳。

## 5.3 本阶段不做什么

1. 不做本地化路由。
2. 不做多语言 URL。
3. 不同时重做所有中文文案。
4. 不把业务 copy 与设计改稿混成一个大工程。

## 5.4 推荐范围

优先接入以下文案密集区域：

1. Dialog / Drawer 标题与按钮文案
2. Empty state
3. Toast
4. Command Menu 静态文案
5. 表单字段错误

暂缓区域：

1. 大段产品说明文案
2. 历史归档页面
3. 调试页面

## 5.5 推荐新增结构

具体目录可按 Paraglide 官方约定生成，但项目内应统一约束为：

```txt
messages/
src/shared/i18n/
src/shared/copy/
```

职责建议：

### `messages/`

放消息源文件。

### `src/shared/i18n/`

放 Paraglide 接入层、locale 读取、项目内帮助函数。

### `src/shared/copy/`

放跨 feature 复用的 copy helper，但不承接业务文本数据库。

## 5.6 与 Phase 2 的衔接方式

Phase 3 不应先单独引入 `zod-i18n-map` 一类外部生态，再尝试和 Paraglide 拼接。

推荐做法：

1. Phase 2 先让 Zod schema 与错误语义稳定；
2. Phase 3 再建立“Zod issue -> Paraglide message key”映射层；
3. 错误展示继续通过表单基础设施统一出到 UI。

这样做的好处是：

1. 错误文案来源统一；
2. 不会同时维护两套 i18n 语义；
3. 后续 toast / API error / form error 可以共用 key 空间。

## 5.7 实施步骤

### Step 1：接入 Paraglide 基础生成链路

目标：

1. 确立消息文件位置；
2. 确立编译与类型生成流程；
3. 确立项目内统一 import 入口。

### Step 2：建立项目级最小 i18n helper

目标：

1. 统一 locale 决策与消息调用方式；
2. 避免业务层直接到处碰生成细节。

### Step 3：迁移第一批高频文案

推荐顺序：

1. Dialog / Drawer 通用按钮
2. 表单错误
3. Empty state
4. Toast
5. Command 菜单静态文案

### Step 4：沉淀命名规则

目标：

1. 固定消息 key 命名方式；
2. 固定 feature 级消息边界；
3. 防止后续消息表无序膨胀。

## 5.8 Done 标准

1. Paraglide 已接入并可生成类型化消息函数。
2. 至少一组高频 UI 文案完成迁移。
3. 表单错误文案已有统一接线方式。
4. 后续新文案有明确新增位置与命名规范。

## 5.9 风险与控制

主要风险：

1. 一次性迁移太多文案，导致 diff 噪音过大。
2. 把消息 key 设计成 UI 文案本身，后续难维护。
3. 业务层直接依赖生成细节，造成耦合。

控制方式：

1. 只迁高频文案；
2. 先定命名规则，再扩散；
3. 通过 `shared/i18n` 做最小收口。

## 5.10 验证口径

```bash
bun run typecheck
bun run lint
bun run format:check
bun run test:run
```

# 6. Phase 4：Sentry 监控与构建分析

## 6.1 目标

建立生产错误可见性、前端 sourcemap 回溯能力，以及按需构建分析能力。

## 6.2 单一推荐

本阶段分为两块：

1. 监控：`@sentry/react` + `@sentry/vite-plugin`
2. 构建分析：`rollup-plugin-visualizer`

明确不推荐：

1. 不把 `vite-bundle-visualizer` 作为主方案；
2. 不一上来就全栈引入完整 APM 套件；
3. 不在同一轮把前端、Rust、profiling、session replay 全部铺满。

## 6.3 为什么此阶段才接 Sentry

原因不是 Sentry 不重要，而是前面三个阶段会显著改变：

1. 错误语义；
2. 文案来源；
3. 表单与提交流程；
4. Rust 侧日志结构。

如果太早接入，前几轮会产生大量低价值噪音与埋点返工。

## 6.4 前端监控范围

首批只做：

1. React runtime error 捕获
2. route-level error surface
3. source map 上传
4. release / environment 基础配置

先不做：

1. Session Replay
2. Profiling
3. 大规模自定义 performance transaction

## 6.5 Rust 侧监控策略

Phase 4 不要求立即把 Rust Sentry 全量接完。

推荐顺序：

1. 先把前端 `@sentry/react` 与 sourcemap 跑通；
2. 再评估 Rust 侧 `sentry` 与 `tracing` 的桥接；
3. 只把高价值 native error 纳入，不求一步到位。

## 6.6 构建分析策略

构建分析属于开发支持能力，不属于常驻生产依赖能力。

因此建议：

1. 使用 `rollup-plugin-visualizer`；
2. 仅在分析构建时启用；
3. 不污染常规 build；
4. 输出报告进入忽略目录，不进入正常源码路径。

## 6.7 对 `vite.config.ts` 的要求

本阶段需要重新审视当前 sourcemap 策略。

当前构建配置中：

1. `build.sourcemap` 与调试环境绑定；
2. 还没有面向生产错误回溯的明确策略。

因此本阶段必须补清楚：

1. release build 是否产出 hidden sourcemap；
2. sourcemap 上传与清理如何做；
3. 不同环境如何区分 release 与 DSN；
4. 本地开发环境如何避免无意义上报。

## 6.8 实施步骤

### Step 1：接入前端 Sentry 基础能力

目标：

1. 建立初始化入口；
2. 建立 env / release 配置；
3. 接入 React 错误捕获。

### Step 2：接入 Vite sourcemap 上传链路

目标：

1. 明确生产 build 的 sourcemap 策略；
2. 明确上传时机；
3. 确保 source map 不误进分发包。

### Step 3：引入按需构建分析

目标：

1. 通过单独脚本输出 bundle report；
2. 避免影响默认 build。

### Step 4：评估 Rust Sentry 接入窗口

目标：

1. 基于 Phase 2.5 的 tracing 基础，决定是否接 native error 上报；
2. 如果接，只接关键链路，不追求一步到位。

## 6.9 Done 标准

1. 前端 runtime error 能进入 Sentry。
2. 生产错误可通过 sourcemap 定位到源码。
3. 本地开发默认不上报或可控上报。
4. 有单独 bundle 分析脚本与输出结果。
5. Rust Sentry 是否接入有明确结论，而不是悬而未决。

## 6.10 风险与控制

主要风险：

1. sourcemap 配置不当，导致泄露或无法正确回溯。
2. 环境变量配置混乱，导致本地或测试环境误上报。
3. 过早接太多监控能力，噪音大于价值。

控制方式：

1. 先做最小监控闭环；
2. 先做前端，再决定 Rust；
3. 构建分析只做开发态能力。

## 6.11 验证口径

```bash
bun run build
bun run typecheck
bun run lint
bun run format:check
bun run test:run
```

如接入 Rust 侧能力，再补：

```bash
cargo check --manifest-path src-tauri/Cargo.toml --workspace
cargo test --manifest-path src-tauri/Cargo.toml --workspace
```

# 7. 暂不推荐引入的依赖

## 7.1 `react-hotkeys-hook`

暂不推荐。

原因：

1. 当前仓库已有自研命令与快捷键运行时；
2. 引入第二套快捷键系统会制造边界冲突；
3. 当前不是缺监听 API，而是要维护统一的 command semantics。

## 7.2 `zundo`

暂不推荐。

原因：

1. 当前还没有一个稳定、统一、长期存在的编辑态 store 作为 undo 主体；
2. 现在先上只会把技术能力提前于产品模型。

## 7.3 `zod-error-utils`

暂不推荐。

原因：

1. Zod v4 已具备更完整的错误定制能力；
2. 后续还要与 Paraglide 接线，不值得再加一层第三方错误格式化生态。

## 7.4 `vite-bundle-visualizer`

暂不推荐。

原因：

1. 主流方案更适合直接用 `rollup-plugin-visualizer`；
2. StoneFlow 当前需要的是“按需分析脚本”，不是再引一个命名相近的包装层。

## 7.5 `ts-pattern`

当前不列入阶段主计划。

原因：

1. 它是代码表达优化工具，不是当前的基础设施缺口；
2. 可以在后续复杂 union / command dispatch 场景里按点引入。

# 10. 最终结论

StoneFlow 在 TanStack Router 接入完成后，下一阶段不应继续围绕“再上哪些看起来先进的库”展开，而应围绕“当前最真实的基础设施缺口是什么”来排序。

最终推荐路线是：

1. 先用 `zod + react-hook-form + @hookform/resolvers` 收口前端输入与校验。
2. 再用 `tracing + tracing-subscriber` 补 Rust 结构化可观测性。
3. 再用 `Paraglide` 建立长期国际化基座。
4. 最后用 `@sentry/react + @sentry/vite-plugin + rollup-plugin-visualizer` 建立生产监控与分析能力。

这是当前最符合 StoneFlow 现状、改动边界、长期维护成本与收益比的路线。
