# E1 · V1 M3 拆分执行文档

> 最后更新：2026-04-20 · 当前版本：V1 · 适用范围：`E1-V1执行文档.md` 中的 `M3`

## 文档目标

本文档用于把 `E1` 中承担“聚合视图、资源与回收能力”的 `M3` 拆成五段顺序执行，降低单段复杂度，缩短交付反馈周期，并让 StoneFlow 从“主链路可用”进一步进入“可组织执行、可恢复、可挂载资源”的状态。

说明：

- `E1-V1执行文档.md` 仍然定义 `V1` 的总目标、总范围与总验收标准
- 本文档只负责回答 `M3` 应该怎么拆、按什么顺序做、每段做到什么算完成
- 后续实际推进 `M3` 时，以本文档中的 `M3-A ~ M3-E` 作为执行颗粒度

---

## 为什么要把 M3 拆成五段

原始 `M3` 同时包含：

- Focus 聚合视图查询与 tabs 组织
- Task `pin / unpin` 动作
- Resource 挂载与一键打开
- Trash 页面与恢复到原位
- 一层子项目的创建、展示与导航

这些内容继续放在一个大里程碑里，会有几个明显问题：

- 聚合查询、页面渲染、生命周期恢复、结构扩展会互相缠绕，推进节奏容易失控
- 如果先把 Resource、Trash、子项目同时铺开，会稀释 `Focus` 作为执行入口的优先级
- 如果太晚才补 Trash 恢复语义，删除链路会长期停留在“能删不能回”的半闭环状态
- 子项目涉及 Sidebar、Project 页和恢复原位规则，如果过早混入，会拖慢前面更高频的执行能力

因此这里把 `M3` 改成“五段顺序推进”的执行方式：先把 Focus 的真实查询能力和执行入口立住，再补 Resource 和 Trash 的横向能力，最后收口一层子项目结构。

---

## M3 拆分总览

| 段 | 名称 | 目标 | 完成标志 |
|------|------|------|------|
| M3-A | Focus 查询底座与 Pin 动作 | 先让 Focus 不再是静态页，而是有真实聚合规则的执行能力 | 四个系统视图查询规则可用，Task 可 `pin / unpin` |
| M3-B | Focus 聚合页落地 | 把 Focus 变成真实可切换、可执行的聚合入口 | `Focus / Upcoming / 最近添加 / 高优先级` 四个 tab 已接真实数据 |
| M3-C | Resource 挂载与一键打开 | 补齐任务外部资源能力 | Task 可挂载文档链接、本地文件、本地文件夹，并可直接打开 |
| M3-D | Trash 页面与恢复链路 | 把删除能力补成可查看、可恢复的闭环 | Trash 可展示 Project / Task，并支持恢复到原位 |
| M3-E | 一层子项目与项目树收口 | 让 Project 结构进入第一版可组织状态 | 子项目可创建、展示、导航，并在 Sidebar / Project 内成立 |

---

## 官方执行顺序

`M3-A -> M3-B -> M3-C -> M3-D -> M3-E`

原因：

- `M3-A` 先解决“聚合视图有没有真实规则和真实动作”的问题
- `M3-B` 再把 Focus 做成日常可进入、可切换的执行页
- `M3-C + M3-D` 再补齐任务周边资源和删除恢复闭环
- `M3-E` 最后收口一层子项目，避免结构扩展过早打断执行链路

这样做的收益是：你会先拿到一个真正能服务日常执行的 Focus，而不是把多个横向能力同时推进成半成品。

## 分段定义

### M3-A · Focus 查询底座与 Pin 动作

**目标**：

先把 `Focus` 所依赖的聚合规则、查询边界和 `pin / unpin` 动作立住，让 `Focus` 不再只是静态展示页。

**包含内容**：

- 实现系统 `FocusView` 的查询入口
- 落地四个系统视图的最小规则：
  - `Focus`：手动 `pinned = true` 的任务
  - `Upcoming`：存在 `due_at` 的任务，按截止时间升序
  - `最近添加`：按 `created_at desc` 回看最近新增任务
  - `高优先级`：聚合 `high + urgent`
- 实现 Task `pin / unpin` 动作
- 统一聚合视图的过滤边界：
  - 只看当前 `Space`
  - 排除已删除对象
  - 第一版默认只看可执行任务

**完成标志**：

- 四个系统视图已具备稳定查询规则
- Task 可在主视图或 Drawer 中切换 `pin / unpin`
- 聚合视图不会错误包含已删除或跨 Space 任务

**这一段的意义**：

这一步先解决 `Focus` 是否真的“有脑子”，避免前端页面先做出来，但背后还是一堆硬编码占位数据。

---

### M3-B · Focus 聚合页落地

**目标**：

把真实的 `Focus` 聚合能力接到页面上，让它成为 StoneFlow 的日常执行入口之一。

**包含内容**：

- 实现 `Focus` 页面真实数据查询与渲染
- 接通 `Focus / Upcoming / 最近添加 / 高优先级` 四个 tabs 的切换
- 保持四个视图属于同一个聚合容器，而不是拆成多个一级路由
- 为 `最近添加` 增加轻量时间窗筛选入口：
  - 使用 `shadcn/ui` 基础能力承接
  - 第一版只做轻量筛选，不引入复杂规则编辑器
- 支持从 `Focus` 视图打开 Task Drawer
- 保持聚合列表与 Project / Inbox / Drawer 的数据一致性

**完成标志**：

- Focus 页面不再依赖静态 mock 数据
- 用户可在四个 tabs 间切换真实任务集合
- 用户可在聚合视图中继续打开 Drawer、完成任务或调整 pin 状态

**这一段的意义**：

`M3-B` 完成后，StoneFlow 才真正拥有“按执行语义查看任务”的入口，而不只是按 Inbox 和 Project 两个存储语境查看任务。

---

### M3-C · Resource 挂载与一键打开

**目标**：

补齐 Task 的外部资源挂载能力，让任务不只是标题和备注，还能直接关联工作上下文。

**包含内容**：

- 实现 Resource 添加能力：
  - 文档链接
  - 本地文件
  - 本地文件夹
- 明确三种资源的最小字段校验与展示结构
- 在 Task Drawer 中展示资源列表
- 实现 Resource 一键打开
- 实现 Resource 删除动作

**完成标志**：

- 用户可在 Task Drawer 中添加三种类型资源
- 资源列表可稳定展示必要信息
- 用户可直接打开目标资源，移除资源后不会进入 Trash

**这一段的意义**：

这一步负责把任务从“记录事项”提升到“可承接上下文的执行单元”，但仍保持第一版克制，不扩成复杂附件系统。

补充说明：

- `文档链接` 使用表单输入
- `本地文件 / 本地文件夹` 使用系统选择器
- 第一版不做拖拽上传，不做复杂预览

---

### M3-D · Trash 页面与恢复链路

**目标**：

把删除链路补成“可查看、可恢复”的完整闭环，而不是只做到软删除和写入快照。

**包含内容**：

- 实现 Trash 页面真实查询与渲染
- 按对象类型展示 `Task / Project`
- 展示恢复到原位所需的必要提示信息
- 实现 Task 恢复到原位
- 实现 Project 恢复到原位
- 明确恢复成功后的 `TrashEntry` 移除规则

**完成标志**：

- Trash 页面可稳定展示当前 Space 下的回收项
- 用户可恢复 Task / Project 到删除前位置
- 恢复成功后对应 `TrashEntry` 已被移除

**这一段的意义**：

删除如果只有“能丢进去”，没有“能稳妥拿回来”，就还不是完整生命周期。`M3-D` 负责把这条链路真正闭合。

补充说明：

- `恢复到原位` 采用严格语义，不做自动回落
- 若原 `Project`、原父项目或必要父级对象不存在，应直接提示用户先恢复父级对象
- 第一版不在 `M3` 内实现 Trash 清空能力，避免把永久删除策略提前混入

---

### M3-E · 一层子项目与项目树收口

**目标**：

让 `Project` 在第一版进入真正可组织的结构状态，但坚持只支持一层子项目，不扩展为无限层级树。

**包含内容**：

- 实现一层子项目创建能力
- 在 Sidebar 中展示父项目与子项目结构
- 在 Project 页面中支持子项目基础导航
- 明确子项目与父项目的排序、归属与查询边界
- 校验删除与恢复时的父子关系一致性

**完成标志**：

- 用户可在父项目下创建子项目
- Sidebar 和 Project 页面已可稳定表达一层父子结构
- 子项目相关的导航、查询与恢复语义成立

**这一段的意义**：

子项目是 `Project` 第一版的结构增强能力，但它应建立在 Focus、Resource、Trash 都已经成立之后，避免过早把 StoneFlow 带入项目树工程。

补充约束：

- 只支持一层子项目
- 不在 `M3` 阶段引入多层折叠树、拖拽排序树或复杂批量移动能力

## 命名约定

当前推荐使用两套映射：

- 执行层正式编号：`M3-A ~ M3-E`
- 看板或 TODO 可选别名：`M3-1 ~ M3-5`

推荐保留字母编号作为正式执行命名，因为它更适合表达“同一主里程碑下的顺序分段”，并且与 `M1 / M2` 的执行层表达保持一致。

## 当前默认假设

以下假设用于支撑当前 `M3` 拆分，如后续决策变化，应同步回收：

- `高优先级` 第一版按 `high + urgent` 聚合，而不是只取最高档
- `最近添加` 默认按 `created_at desc` 回看，并允许补一个轻量时间窗筛选入口
- `Resource` 第一版只做挂载、展示与一键打开，不做拖拽导入和复杂预览
- `Trash 恢复` 采用严格原位恢复语义，不做自动回落
- 一层子项目能力只处理创建、展示、导航与恢复一致性，不扩展到无限层级树
