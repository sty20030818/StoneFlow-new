# E1 · V1 Global Command 执行文档

> 最后更新：2026-04-19 · 当前版本：V1 · 适用范围：`E1-V1执行文档.md` 中与系统级 `Global Command` 相关的范围

## 文档目标

本文档用于单独定义 StoneFlow `V1` 中系统级 `Global Command` 的执行边界、阶段定位、目标架构与落地顺序，避免该能力与 `M2` 主链路混在一起推进。

说明：

- 本文档不替代 `E1-V1执行文档.md`
- 本文档只回答系统级 `Global Command` 什么时候做、最终做到什么、按什么顺序落地
- 本文档默认承认该能力是 `V1` 必做项，而不是可选增强项

---

## 为什么要单独立文档

系统级 `Global Command` 对 StoneFlow 很重要，但它和普通页面功能不是同一类工作。

它同时涉及：

- 应用外全局快捷键
- 独立 Quick Capture 浮窗
- 后台常驻或独立 Agent / Helper
- 主应用与 Agent 的共享创建能力或通信
- 当前 `Space` 的共享状态
- 唤起速度、异常恢复、重复触发与生命周期管理

如果把这些内容直接混在 `M2-B` 的“创建链路”里，会产生两个问题：

- `M2` 的主链路推进会被平台基础设施拖慢
- 文档里会持续混淆“应用内入口”和“系统级入口”

因此，这里把系统级 `Global Command` 单独拉出来记录，并明确它在 `V1` 中放在后段收口。

---

## 在 V1 中的阶段定位

### 结论

系统级 `Global Command` 放在 `M4` 落地最合适。

### 原因

`M2` 的目标是先打通：

- 创建
- Inbox 承接
- Project 执行
- Drawer 编辑
- 删除收口

这些内容先跑通后，StoneFlow 才真正具备“任务进入系统后能被接住”的能力。

而系统级 `Global Command` 的职责是把“捕获入口”做到极致。它应该建立在以下前提已经成立之后：

- `create_task` 已可靠
- 当前 `Space` 与 `Inbox` 语义已稳定
- Inbox / Project / Drawer / 删除主链路已能接住真实任务
- 主应用结构和数据层不会频繁改动

因此，最合理的顺序是：

`M2` 先打通主链路 -> `M3` 补齐组织能力 -> `M4` 收口系统级 `Global Command`

---

## 最终方案定义

`V1` 的系统级 `Global Command` 采用“方案 D”方向落地：

- 独立 `Command Agent / Helper`
- 独立 `Quick Capture` 浮窗
- 应用外全局快捷键
- 与主应用分离的生命周期
- 与主应用共享任务创建能力

这里的目标不是“按快捷键把主窗口叫出来”，而是：

- 用户在任何应用里按下全局快捷键
- 直接出现轻量捕获窗口
- 输入一句话
- 回车即可写入当前 `Space` 的 `Inbox`

---

## 目标体验

### 触发链路

1. 用户在系统任意位置按下全局快捷键
2. 独立 `Quick Capture` 浮窗在当前桌面上下文出现
3. 输入任务标题
4. 回车创建任务
5. 浮窗关闭或保留，取决于后续交互策略
6. 任务进入当前 `Space` 的 `Inbox`
7. 如果主应用当前处于打开状态，对应视图能尽快感知到新任务

### 第一版必须做到

- 唤起足够快
- 输入足够短
- 失败反馈明确
- 不强依赖主窗口处于前台

### 第一版不要求

- 全文搜索
- 多步命令解析
- 参数化自然语言
- 多动作工作流编排
- 复杂候选列表

## 目标架构

```text
Global Shortcut
      |
      v
Command Agent / Helper
      |
      +-- Quick Capture Window
      |
      +-- Current Space Resolver
      |
      +-- Create Task Use Case
      |
      +-- Main App Bridge / Sync Hook
              |
              v
       ~/.stoneflow/app.db
              |
              v
          Main App UI
```

### 各层职责

#### 1. Main App

负责：

- Sidebar / Inbox / Project / Drawer 等主界面
- 主数据浏览、整理、执行与编辑
- 当前 `Space` 的切换与持久化

不负责：

- 直接承接系统级快捷键
- 直接作为 Quick Capture 浮窗

#### 2. Command Agent / Helper

负责：

- 注册系统级全局快捷键
- 唤起和关闭 `Quick Capture` 浮窗
- 在主应用不在前台时仍可承接捕获动作
- 调用共享创建能力，把任务写入数据库

#### 3. Quick Capture Window

负责：

- 单一输入框体验
- 最小提示与错误反馈
- 不承担完整搜索与导航

#### 4. Shared Create Task Capability

负责：

- 把捕获内容稳定写入当前 `Space` 的 `Inbox`
- 统一字段校验
- 统一错误表达

这层能力必须与主应用内创建入口共享，而不是在 Agent 中重写一套逻辑。

---

## 与当前架构的衔接方式

当前仓库已经具备：

- `core`
- `entity`
- `migration`
- `desktop-app`

要走方案 D，后续建议补出一层共享应用能力：

- `application` 或 `usecases` crate

该层承接：

- `create_task`
- `create_project`
- `create_space`
- 后续可复用的查询和规则能力

这样主应用与 `Command Agent` 都可以调用同一套创建逻辑，而不是互相复制。

---

## 当前 Space 共享策略

系统级 `Global Command` 最大的语义问题不是“怎么弹窗”，而是：

> 它创建的任务到底该落到哪个 `Space`

### 第一版推荐策略

- 主应用在用户切换 `Space` 时，把当前 `active_space_id` 写入一份共享运行时状态
- `Command Agent` 唤起时读取这份共享状态
- 若读取失败，则退回默认 `Space`

### 第一版不建议

- 每次都要求用户在 Quick Capture 里重新选 `Space`
- 依赖主应用进程内内存来判断当前 `Space`

### 共享状态的可选存储

- 轻量配置文件
- Store 文件
- 独立运行时状态文件

第一版不建议为这个问题额外引入新的业务级核心实体。

## 执行顺序

### 第 1 段：共享创建能力收口

目标：

- 把 `create_task` 从主应用 UI 触发中抽出来，形成可复用的共享应用能力

包含内容：

- 抽出共享 `create_task` 用例
- 明确当前 `Space -> Inbox` 写入语义
- 明确错误类型与返回结构

完成标志：

- 主应用入口与未来 Agent 都可调用同一套创建逻辑

### 第 2 段：主应用内入口稳定化

目标：

- 先让主应用内的 Header `New task` 成为可靠入口

包含内容：

- Header 创建按钮接真实创建
- 成功后回到 Inbox 或局部刷新
- 最小错误反馈与测试

完成标志：

- 应用内创建已经稳定，不再是静态壳层

### 第 3 段：Quick Capture 独立浮窗

目标：

- 把创建入口从主界面中抽离成独立轻量浮窗

包含内容：

- 独立浮窗窗口模型
- 打开、关闭、聚焦、Esc 退出
- 输入框与最小文案

完成标志：

- 不依赖主界面即可承接创建动作

### 第 4 段：Command Agent / Helper

目标：

- 让系统级入口脱离主应用生命周期

包含内容：

- Agent / Helper 进程形态确定
- 常驻策略
- 主应用与 Agent 的边界确定

完成标志：

- 主应用不在前台时，系统级捕获仍可正常工作

### 第 5 段：系统级快捷键与异常恢复

目标：

- 真正完成应用外唤起

包含内容：

- 注册全局快捷键
- 防止重复唤起
- 已打开浮窗时的重入策略
- 创建失败时的反馈与恢复

完成标志：

- 在应用外按快捷键可稳定唤起并创建任务

### 第 6 段：主应用同步与测试收口

目标：

- 把体验从“能用”收口到“可信”

包含内容：

- 主应用打开时对新任务的刷新策略
- Agent / 浮窗 / 数据写入链路测试
- 真机自用压力验证

完成标志：

- 一周自用中，系统级 Global Command 可稳定承接高频捕获

## 与里程碑的对应关系

| 能力 | 放在哪一段 |
|------|------|
| 共享 `create_task` 能力 | `M2-B` 起步，`M4` 复用 |
| 主应用内 `New task` 入口 | `M2-B` |
| Inbox / Project / Drawer / 删除主链路 | `M2-C ~ M2-F` |
| 独立 Quick Capture 浮窗 | `M4` |
| Command Agent / Helper | `M4` |
| 系统级全局快捷键 | `M4` |
| Command 自用打磨与异常恢复 | `M4` |

---

## 验收标准

以下标准全部满足后，才可认为 `V1` 的系统级 `Global Command` 已完成：

- [ ] 用户可以在应用外按下全局快捷键唤起 `Quick Capture`
- [ ] `Quick Capture` 不依赖主窗口当前处于前台
- [ ] 用户输入一句话后可直接创建任务
- [ ] 新任务默认进入当前 `Space` 的 `Inbox`
- [ ] 当前 `Space` 解析失败时会安全退回默认 `Space`
- [ ] 创建失败时有明确反馈，不会静默丢任务
- [ ] 主应用已打开时，新任务能被可靠感知
- [ ] 高频连续创建下，不会出现重复写入、窗口失焦或异常卡死

---

## 当前不并入该文档的内容

- 自然语言解析命令
- 全局搜索所有任务
- 全局跳转到任意 Project / Task
- 全局执行批量动作
- 系统级资源挂载
- AI 驱动命令建议

这些都属于 `V2+` 扩展，不是 `V1` 的系统级捕获底线。

---

## 一句话执行结论

StoneFlow 的系统级 `Global Command` 在 `V1` 中仍然是必做项，但它不并入 `M2` 主链路，而是以“共享创建能力 -> 应用内入口 -> Quick Capture -> Command Agent -> 全局快捷键 -> 自用收口”的顺序，在 `M4` 统一落地。
