# E1 · V1 M4 拆分执行文档

> 最后更新：2026-04-22 · 当前版本：V1 · 适用范围：`E1-V1执行文档.md` 中的 `M4`

## 文档目标

本文档用于把 `E1` 中承担“系统级 Global Command、体验打磨、测试补齐与自用验收”的 `M4` 拆成六段顺序执行，让 StoneFlow 从“核心主链路已经可用”进入“应用外可极速捕获、关键路径可信、可以连续自用”的状态。

说明：

- `E1-V1执行文档.md` 仍然定义 `V1` 的总目标、总范围与总验收标准
- `E1-V1-Global-Command执行文档.md` 仍然定义系统级 `Global Command` 的目标架构与边界
- 本文档只负责回答 `M4` 应该怎么拆、按什么顺序做、每段做到什么算完成
- 后续实际推进 `M4` 时，以本文档中的 `M4-A ~ M4-F` 作为执行颗粒度

---

## 为什么要把 M4 拆成六段

原始 `M4` 同时包含：

- 系统级 `Global Command / Quick Capture`
- 独立 `Command Agent / Helper`
- 应用外全局快捷键
- 主应用与捕获入口之间的状态同步
- Sidebar / Focus / Inbox / Project / Drawer 的体验打磨
- 前端与 Rust 测试补齐
- 一周自用验收与 V1 收口

这些内容如果继续放在一个大里程碑里，会有几个明显问题：

- `Global Command` 涉及平台壳、进程生命周期、快捷键和窗口焦点，和普通页面功能不是同一类工作
- 如果先做全局快捷键，底层创建能力、当前 Space 解析和异常恢复没稳定，会把问题藏到系统级入口里
- 如果只做体验打磨不做系统级捕获，StoneFlow 的 V1 核心卖点会少一半
- 如果最后才补测试，会很难判断是 Global Command 引入了问题，还是 M1 ~ M3 的旧链路本来就不稳
- 自用验收需要真实连续使用，不应该和功能开发混在同一天里草草结束

因此这里把 `M4` 改成“六段顺序推进”：先收口捕获底座，再做 Quick Capture 和 Agent，再接全局快捷键，最后做同步打磨、测试和自用验收。

## M4 拆分总览

| 段 | 名称 | 目标 | 完成标志 |
|------|------|------|------|
| M4-A | 捕获底座与当前 Space 状态 | 先让系统级捕获有可靠的数据写入和上下文来源 | 共享创建能力、当前 Space 解析、错误契约可被主应用和未来 Agent 复用 |
| M4-B | Quick Capture 独立浮窗 | 先做不依赖主界面的轻量捕获窗口 | 独立浮窗可打开、输入、提交、关闭，并写入 Inbox |
| M4-C | Command Agent / Helper 生命周期 | 让捕获入口脱离主应用前台生命周期 | Helper 形态明确，主应用不在前台时仍可唤起 Quick Capture |
| M4-D | 系统级快捷键与重入恢复 | 真正完成应用外极速唤起 | 应用外快捷键可稳定唤起，重复触发、失败、失焦都有明确处理 |
| M4-E | 主应用同步与体验打磨 | 把系统级捕获接回主应用，并收口核心交互细节 | 新任务刷新可靠，关键页面空状态、反馈、Drawer 动效与行状态已打磨 |
| M4-F | 最终验收与交付硬化 | 把 V1 捕获主链路从“自动测试通过”推进到“真实运行可交付” | 自动化验证通过，真实 `Option+Space` 捕获链路有验收记录，已知限制与后续 archive 输入明确 |

## 官方执行顺序

`M4-A -> M4-B -> M4-C -> M4-D -> M4-E -> M4-F`

原因：

- `M4-A` 先解决“捕获写到哪里、按什么语义写、失败怎么表达”的问题
- `M4-B` 再把捕获体验抽成独立窗口，但仍先不急着做系统级快捷键
- `M4-C` 处理 Helper 生命周期，否则 Quick Capture 仍然只是主应用内部能力
- `M4-D` 最后接应用外全局快捷键，避免把未稳定的窗口和状态问题放大
- `M4-E` 回到主应用体验，把系统级捕获带来的刷新、反馈和交互细节收口
- `M4-F` 用测试和真实自用验证 V1 是否真的可以长期使用

这样做的收益是：系统级 `Global Command` 会按“能力可靠 -> 窗口可用 -> 生命周期独立 -> 快捷键唤起 -> 主应用同步 -> 自用验收”的顺序成型，而不是一上来就陷入平台快捷键和多窗口细节。

## 分段定义

### M4-A · 捕获底座与当前 Space 状态

**目标**：

先把系统级捕获依赖的共享创建能力和当前 `Space` 解析立住，让主应用入口和未来 `Command Agent` 不需要复制两套写入逻辑。

**包含内容**：

- 回查现有 `create_task` 用例，确认它可作为 Quick Capture 的共享写入入口
- 明确 Quick Capture 创建任务的最小输入：
  - 当前 `Space`
  - 任务标题
  - 可选备注或后续扩展字段
- 明确新任务默认进入当前 `Space` 的 Inbox
- 建立当前 `Space` 的共享运行时状态：
  - 主应用切换 `Space` 时写入
  - Quick Capture 唤起时读取
  - 读取失败时退回默认 `Space`
- 统一捕获失败的错误契约与前端反馈口径

**完成标志**：

- 主应用内创建入口与未来 Quick Capture 可调用同一套创建语义
- 当前 `Space` 状态有稳定读取与回退策略
- 捕获失败不会静默丢任务

**这一段的意义**：

系统级入口最怕“看起来很快，但写入语义不可靠”。`M4-A` 先把数据事实和上下文来源固定住，后面做浮窗和快捷键才不会返工。

补充约束：

- 第一版不为当前 `Space` 新增业务实体
- 第一版不要求 Quick Capture 里选择 `Space`
- 不引入自然语言解析或多命令协议

---

### M4-B · Quick Capture 独立浮窗

**目标**：

把创建任务从主界面中抽离成独立轻量浮窗，让用户不进入完整工作台也能完成捕获。

**包含内容**：

- 创建独立 `Quick Capture` 窗口模型
- 定义浮窗尺寸、位置、层级与焦点策略
- 实现单一输入框体验：
  - 输入标题
  - 回车创建
  - Esc 关闭
  - 创建成功后的关闭或保留策略
- 接入 `M4-A` 的共享创建能力与当前 `Space` 解析
- 提供最小加载、成功、失败反馈

**完成标志**：

- Quick Capture 可独立打开、聚焦、提交、关闭
- 输入一句话后可创建任务并进入当前 `Space` 的 Inbox
- 创建失败有明确反馈，不需要打开主应用才能知道结果

**这一段的意义**：

这是系统级 `Global Command` 的体验核心。先把浮窗本身做稳，再接 Agent 和全局快捷键，能把窗口体验问题和平台生命周期问题拆开验证。

补充约束：

- 第一版只做单输入框捕获
- 不做全文搜索、候选列表、多动作命令或 AI 建议
- 不把主应用完整页面嵌进浮窗

---

### M4-C · Command Agent / Helper 生命周期

**目标**：

让 `Quick Capture` 从主应用前台生命周期中解耦，具备系统级入口所需的常驻或辅助进程形态。

**包含内容**：

- 明确 `Command Agent / Helper` 的实现形态：
  - 是否作为 Tauri 辅助窗口 / sidecar / 独立 helper
  - 是否随主应用启动
  - 退出与重启策略
- 明确 Main App 与 Helper 的职责边界：
  - Main App 负责完整工作台
  - Helper 负责快捷键、浮窗和捕获
  - 共享创建能力负责写入
- 实现 Helper 唤起 Quick Capture 的最小链路
- 处理主应用已打开、主应用未聚焦、主应用未打开时的基本行为

**完成标志**：

- 主应用不在前台时，Helper 仍可唤起 Quick Capture
- Helper 不复制主应用的业务创建逻辑
- Helper 生命周期、退出与重启策略已明确

**这一段的意义**：

系统级捕获不是“把主窗口叫出来”。`M4-C` 负责让捕获入口真正从主界面中分离出来，为应用外快捷键做准备。

补充约束：

- 不在本段引入复杂后台同步系统
- 不把 Helper 扩展成完整第二应用
- 不做跨设备、云同步或账号状态

---

### M4-D · 系统级快捷键与重入恢复

**目标**：

真正完成应用外极速唤起，让用户在任何应用里按下快捷键都能进入 Quick Capture。

**包含内容**：

- 注册系统级全局快捷键
- 明确默认快捷键与冲突处理策略
- 实现快捷键唤起 Quick Capture
- 处理重复触发：
  - 浮窗未打开时打开
  - 浮窗已打开时关闭，保持 `Option+Space` 作为 toggle 入口
  - 提交中重复触发不重复写入
- 处理异常恢复：
  - 创建失败
  - 当前 `Space` 读取失败
  - Helper 不可用或浮窗失焦
- 补齐键盘交互细节：
  - 回车提交
  - Esc 关闭
  - Cmd/Ctrl 快捷行为不误触

**完成标志**：

- 用户可以在应用外按下全局快捷键唤起 Quick Capture
- 高频连续唤起不会出现重复窗口、重复写入或异常卡死
- 快捷键冲突和失败路径有明确反馈或降级策略

**这一段的意义**：

这是 `M4` 的核心验收点，也是 StoneFlow 与普通任务管理器拉开差异的关键入口。

补充约束：

- 第一版不做用户自定义快捷键 UI，除非平台实现要求必须暴露
- 不把系统级快捷键扩展成全局搜索或跳转入口
- 不引入批量动作和复杂命令面板

---

### M4-E · 主应用同步与体验打磨

**目标**：

把系统级捕获带回主应用可见状态，并收口 V1 关键页面和核心交互的体验细节。

**包含内容**：

- 主应用打开时感知 Quick Capture 新建任务
- Inbox / Focus / Project / Sidebar 的相关数据刷新策略
- 完善 Sidebar、Focus、Inbox、Project 的空状态
- 完善删除、恢复、完成任务、pin / unpin 的反馈表现
- 实现或收口 Drawer 的轻遮罩与过渡动画
- 打磨 Task Row 的 hover、active、done 状态
- 打磨 Focus 页 tabs、筛选与上下文信息表达
- 回查系统级捕获后任务是否能被 Inbox、Focus、搜索和 Drawer 正确读取

**完成标志**：

- Quick Capture 新建任务后，主应用能可靠感知
- 核心页面不再有明显静态示意残留或空白断点
- Drawer、Task Row、Focus tabs 等高频交互具备稳定视觉和反馈

**这一段的意义**：

系统级入口只是把任务送进来，`M4-E` 负责保证任务进入系统后，主应用马上能接住、能看到、能继续整理。

补充约束：

- 不重做 M1 ~ M3 的信息架构
- 不把体验打磨扩展成大规模视觉重设计
- 不新增 V2 功能，只修 V1 高频路径的断点

---

### M4-F · 最终验收与交付硬化

**目标**：

把 V1 捕获主链路从“功能能跑、自动测试通过”推进到“可以真实运行、可以诊断、可以交付记录”，用最终验收清单、运行态硬化、文档和问题清单完成 M4 收口。

**包含内容**：

- 建立 V1 捕获主链路最终验收清单：
  - Helper 启动
  - `Option+Space` 唤起与 toggle
  - Quick Capture 写入
  - 主应用 Inbox 刷新
  - 搜索打开 Drawer
  - Inbox 整理后 Project / Focus 承接
  - Trash 删除与恢复
- 明确自动化与手工验收边界：
  - Vitest / Rust 测试覆盖可稳定模拟的逻辑
  - macOS 全局快捷键、真实窗口激活、跨进程生命周期用手工记录承接
- 检查真实运行环境中的恢复路径：
  - Helper 启动失败
  - IPC 创建失败
  - 主窗口隐藏
  - 重复唤起
  - 退出重启
  - Space 回退
- 更新 M4 交付记录，明确当前实现、运行方式、已知限制和后续 archive 输入
- 清理或修正仍指向旧 Quick Capture 主 App 入口、旧 helper 宿主目录或过期命令的描述

**完成标志**：

- `bun run build`、受影响 Vitest、Rust workspace 测试与 OpenSpec 校验已通过
- 真实 `Option+Space` 捕获链路有手工验收记录
- Helper / IPC / Space 回退等异常路径具备可诊断反馈或明确排障入口
- V1 捕获主链路的已知限制、后续任务与 archive 输入已经记录清楚
- 交付记录详见 `E1-V1-M4-F最终验收与交付记录.md`

**这一段的意义**：

`M4-F` 是 M4 的出门验收，不再增加大能力，而是用真实运行、自动化验证和交付记录把前面所有能力串起来。

补充约束：

- 最终验收不等于继续加功能
- 测试优先覆盖关键路径，不追求低价值覆盖率数字
- 阻塞日常使用的问题优先于视觉小瑕疵
- 不在本段引入云同步、自定义快捷键、自然语言解析或发布签名流水线

## 当前默认假设

以下假设用于支撑当前 `M4` 拆分，如后续决策变化，应同步回收：

- `M1 ~ M3` 的主链路能力已经基本成立，`M4` 不再重做主信息架构
- Quick Capture 第一版只负责“输入一句话创建任务”，不做全局搜索和复杂命令解析
- 新任务默认写入当前 `Space` 的 Inbox；当前 `Space` 解析失败时退回默认 `Space`
- 系统级 Global Command 以独立 `Command Agent / Helper` 方向推进，而不是简单唤起主窗口
- 主应用与 Quick Capture 共享创建语义，不复制两套创建逻辑
- `M4` 的体验打磨只处理 V1 高频路径，不引入 V2 能力
