# E1 · V1 M2 拆分执行文档

> 最后更新：2026-04-19 · 当前版本：V1 · 适用范围：`E1-V1执行文档.md` 中的 `M2`

## 文档目标

本文档用于把 `E1` 中承担“核心任务链路打通”的 `M2` 拆成六段顺序执行，降低单段复杂度，缩短业务反馈周期，并确保 StoneFlow 尽快进入“可真实捕获、整理、执行任务”的状态。

说明：

- `E1-V1执行文档.md` 仍然定义 `V1` 的总目标、总范围与总验收标准
- 本文档只负责回答 `M2` 应该怎么拆、按什么顺序做、每段做到什么算完成
- 后续实际推进 `M2` 时，以本文档中的 `M2-A ~ M2-F` 作为执行颗粒度

---

## 为什么要把 M2 拆成六段

原始 `M2` 同时包含：

- 核心实体建模与初始化
- 全局创建入口
- Inbox 查询与归类规则
- Project 执行视图
- Drawer 详情编辑
- 删除动作与元信息流转

这些内容如果继续放在一个大里程碑里，会有几个明显问题：

- 数据建模、命令接口、页面渲染、交互规则会互相缠绕，导致推进节奏失控
- 如果先把所有表和 command 一口气做完，会连续很久看不到真实可用链路
- 如果先堆页面，再补规则校验和时间流转，后面很容易返工
- 删除、Drawer、Project 这类尾段动作如果过早混入，会稀释“先打通主链路”的优先级

因此这里把 `M2` 改成“六段顺序推进”的执行方式：先立住数据与创建入口，再打通 Inbox 到 Project 的主链路，最后补齐 Drawer 编辑与删除收口。

---

## M2 拆分总览

| 段 | 名称 | 目标 | 完成标志 |
|------|------|------|------|
| M2-A | 核心实体与初始化底座 | 把 M2 所需的数据边界先立住 | 核心表、实体与默认初始化已可稳定支撑主链路 |
| M2-B | 创建链路与应用内入口 | 先打通“任务如何进入系统” | 用户可通过应用内入口创建任务并落入当前 Space Inbox |
| M2-C | Inbox 承接与归类规则 | 让新任务有地方接住并完成第一次整理 | 创建后的任务可在 Inbox 中查看并完成归类 |
| M2-D | Project 执行视图 | 让任务从“待整理”进入“可执行” | 已归类任务可在 Project 中查看与切换完成状态 |
| M2-E | Drawer 详情编辑 | 补齐任务详情的主编辑入口 | 用户可打开 Drawer 查看并编辑基础详情 |
| M2-F | 删除动作与一致性收口 | 把主链路最后一个生命周期动作补齐 | Task 删除与元信息流转可用，并为 M3 Trash 链路留好基础 |

---

## 官方执行顺序

`M2-A -> M2-B -> M2-C -> M2-D -> M2-E -> M2-F`

原因：

- `M2-A` 先解决“数据能不能正确表达主链路”的问题
- `M2-B` 先解决“任务能不能稳定进入系统”的问题
- `M2-C + M2-D` 先把 `创建 -> Inbox -> Project -> 完成` 这条主链路打通
- `M2-E + M2-F` 再补齐详情编辑和删除收口，避免过早被边缘交互拖慢节奏

这样做的收益是：你能尽早得到一条真实可跑的任务闭环，而不是同时推进一堆彼此依赖的半成品能力。

## 分段定义

### M2-A · 核心实体与初始化底座

**目标**：

先把 `M2` 需要的核心实体边界和初始化逻辑立住，让后续命令、列表和交互都建立在稳定底座上。

**包含内容**：

- 建立 `spaces / projects / tasks / resources / focus_views / trash_entries` 表结构
- 生成或编写对应 `SeaORM` 实体
- 明确 `created_at / updated_at / completed_at / deleted_at` 等基础时间字段约定
- 统一 `Project / Task` 的软删除时间语义为 `deleted_at`
- 初始化默认 `Space`
- 初始化系统 `focus / upcoming / recent / high_priority` 四个 `Focus tabs`

**完成标志**：

- `M2` 所需核心表已建立并可稳定读写
- Rust 侧已具备可靠的实体表达与基础读写能力
- 默认 `Space` 与 4 个系统 `Focus tabs` 已可幂等初始化

**这一段的意义**：

这一步先解决“主链路的数据骨架是否成立”，但不急着把所有 UI 和业务动作一起塞进来，避免 `M2` 一开始就失控。

---

### M2-B · 创建链路与应用内入口

**目标**：

先把 StoneFlow 最关键的创建链路打通，证明任务可以真实进入系统，并先由主应用内入口承接第一版捕获体验。

**包含内容**：

- 实现创建 `Space / Project / Task` 的基础创建能力
- 实现应用内入口创建 `Task`
- 约束新任务默认进入当前 `Space` 的 `Inbox`
- 建立创建时的最小字段校验与返回结构

**完成标志**：

- 用户可以通过应用内入口创建任务
- 新任务会稳定进入当前 `Space` 的 `Inbox`
- 创建链路中的基础参数校验与错误返回可用

**这一段的意义**：

`M2-B` 完成后，StoneFlow 才真正拥有“任务可以进入系统”的业务入口，否则后面的 Inbox 和 Project 只是静态承接层。

补充说明：

- 这里的“入口”指主应用内入口，例如 Header 的 `New task` 按钮或主应用内最小创建层。
- 系统级 `Global Command / Quick Capture` 不并入 `M2-B`，而是作为 `V1` 后段基础设施在 `M4` 单独收口。

---

### M2-C · Inbox 承接与归类规则

**目标**：

让新任务进入系统后，不是堆在数据库里，而是能够在 Inbox 中被看到、被整理、被送往下一步。

**包含内容**：

- 实现 Inbox 列表查询与渲染
- 实现 Inbox 行内归类动作：
  - 选择 `priority`
  - 选择 `project`
  - 保持 `status` 为 `todo`
- 实现 Task 离开 Inbox 的规则校验
- 保证 Inbox 视图与创建链路的数据一致性

**完成标志**：

- 新任务可稳定出现在 Inbox
- 用户可在 Inbox 中完成优先级与项目归类
- 不满足归类条件的 Task 不会错误离开 Inbox

**这一段的意义**：

这一段负责把“捕获”变成“整理”，它是 StoneFlow 主链路里的第一个真实筛选面，而不是简单列表展示。

---

### M2-D · Project 执行视图

**目标**：

让已归类任务进入 Project 语境中执行，形成真正的“整理后继续推进”链路。

**包含内容**：

- 实现 Project 列表页与任务列表
- 实现归类后 Task 在 Project 中的查询与渲染
- 实现 Task `todo / done` 状态切换
- 建立 `completed_at` 的基础流转规则

**完成标志**：

- 已归类任务可在对应 Project 中稳定查看
- 用户可在 Project 中切换 Task 的 `todo / done`
- `done` 状态切换已驱动对应完成时间流转

**这一段的意义**：

`M2-D` 完成后，StoneFlow 才不只是一个任务收纳盒，而是开始具备“按项目执行任务”的核心能力。

---

### M2-E · Drawer 详情编辑

**目标**：

补齐任务详情侧的主编辑入口，让用户可以在不离开主视图的前提下查看与编辑任务基础信息。

**包含内容**：

- 实现 Task Drawer 的打开与关闭
- 实现 Task 基础详情查询
- 实现基础详情编辑：
  - 标题
  - 描述
  - priority
  - project
  - status
- 建立 `updated_at` 的更新流转

**完成标志**：

- 用户点击任务后可打开 Drawer
- Drawer 可稳定展示任务基础详情
- 基础编辑动作可回写并驱动更新时间变化

**这一段的意义**：

Drawer 是 StoneFlow 的核心交互面之一，但它应该建立在主链路已经跑通之后，而不是提前变成优先级更高的界面工程。

---

### M2-F · 删除动作与一致性收口

**目标**：

把 `M2` 主链路中的最后一个生命周期动作补齐，并为 `M3` 的 Trash 能力预埋可靠基础。

**包含内容**：

- 实现 Task 删除动作
- 建立删除后的 `trash_entries` 写入策略
- 明确删除后的列表剔除与详情关闭行为
- 校验 `updated_at / deleted_at` 等基础元信息流转

**完成标志**：

- 用户可删除 Task
- 删除后的 Task 不再错误出现在 Inbox / Project 主列表中
- 删除动作已为后续 Trash 恢复链路保留必要数据

**这一段的意义**：

这里先解决“删除是否可控且可追溯”，但不把 Trash 页面的完整查看与恢复能力提前并入 `M2`，以免把 `M3` 的范围偷渡进来。

## 命名约定

当前推荐使用两套映射：

- 执行层正式编号：`M2-A ~ M2-F`
- 看板或 TODO 可选别名：`M2-1 ~ M2-6`

推荐保留字母编号作为正式执行命名，因为它更适合表达“同一主里程碑下的顺序分段”，并且与 `M1` 的执行层表达保持一致。

## 与 E1 主文档的关系

- `E1-V1执行文档.md` 中的 `M2` 继续保留为“总范围定义”
- 本文档负责把 `M2` 从“主链路目标”拆成“可顺序推进的执行段”
- `M2` 的拆分原则是先主链路、后侧向补齐，避免把 `M3` 的能力提前混入

---

## 当前默认假设

以下假设用于支撑当前 `M2` 拆分，如后续决策变化，应同步回收：

- `Task 删除` 在 `M2` 阶段按“进入 Trash 数据层”处理，而不是物理删除
- `resources` 表与 `focus_views` 表在 `M2` 阶段先完成建模与初始化，不展开完整 UI 能力
- 一层子项目能力仍归 `M3`，不提前并入 `M2`
- `done -> todo` 时 `completed_at` 的最终保留策略，暂继续视为待确认项
- 系统级 `Global Command` 在 `V1` 中仍是必做项，但不并入 `M2` 主链路，而是在 `M4` 作为独立基础设施收口

---

## 一句话执行结论

StoneFlow 的 `M2` 不再按一个大阶段推进，而是改为 `M2-A -> M2-B -> M2-C -> M2-D -> M2-E -> M2-F` 六段顺序执行，先打通“创建 -> Inbox -> Project -> Drawer -> 删除”的核心任务闭环，再把聚合视图、资源挂载与回收能力留给 `M3`。
