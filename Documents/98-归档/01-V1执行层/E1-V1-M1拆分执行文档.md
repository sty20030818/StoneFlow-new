# E1 · V1 M1 拆分执行文档

> 最后更新：2026-04-18 · 当前版本：V1 · 适用范围：`E1-V1执行文档.md` 中的 `M1`

## 文档目标

本文件用于把 `E1` 中原本跨度过大的 `M1` 拆成五段顺序执行，降低单段范围，缩短反馈周期，并让 StoneFlow 更早进入“可看、可用、可继续开发”的状态。

说明：

- `E1-V1执行文档.md` 仍然定义 `V1` 的总目标、总范围与总验收标准
- 本文件只负责回答 `M1` 应该怎么拆、按什么顺序做、每段做到什么算完成
- 后续实际推进 `M1` 时，以本文件中的 `M1-A ~ M1-E` 作为执行颗粒度

---

## 为什么要把 M1 拆成五段

原始 `M1` 同时包含：

- 工程初始化
- 设计令牌
- App Shell
- Rust 数据底座
- 前后端通信闭环

这几个部分放在一个大里程碑里，问题很明显：

- 范围过大，容易让开发过程失去节奏感
- 如果先做数据层，会连续几天都看不到 StoneFlow 的产品形态
- 如果边做页面边补 UI 基建，后面很容易返工
- 如果太晚才验证前后端通信，会推迟暴露基础架构问题

因此这里把 `M1` 改成“五段顺序推进”的执行方式：先立住工程，再立住视觉与壳层，最后补数据底座和通信闭环。
\
---

## M1 拆分总览

| 段 | 名称 | 目标 | 完成标志 |
|------|------|------|------|
| M1-A | 工程初始化与目录骨架 | 把项目从空仓库变成可持续开发的工程 | 应用可基础启动，目录结构成型 |
| M1-B | 设计令牌与 UI 基建 | 把 StoneFlow 的视觉底座和组件底座立住 | 全局 token、基础组件、主题约束可复用 |
| M1-C | App Shell 与路由静态骨架 | 先把产品主结构做出来 | 能看到完整静态壳层并完成基础路由切换 |
| M1-D | Rust 数据底座与迁移基础设施 | 先把本地数据底座接通 | 数据库初始化、migration 与 Rust 数据基础设施可用 |
| M1-E | 最小前后端通信闭环 | 验证不是静态壳，而是已打通工程 | 前端可稳定调用 Rust 并拿到可验证结果 |

---

## 官方执行顺序

`M1-A -> M1-B -> M1-C -> M1-D -> M1-E`

原因：

- `M1-A` 先解决“能不能开工”的问题
- `M1-B + M1-C` 先把 StoneFlow 的长相和壳层结构立起来
- `M1-D + M1-E` 再把数据底座和通信闭环补齐

这样做的收益是：在很早阶段你就能看到一个像样的 StoneFlow，而不是先埋头做数据库好几天却没有可见成果。

## 分段定义

### M1-A · 工程初始化与目录骨架

**目标**：

先把项目从“空仓库”变成“可持续开发的工程”。

**包含内容**：

- 初始化 `Tauri + React + TypeScript` 项目
- 接入 `bun`
- 配置 `React Router`、`Zustand`
- 建立前端 `feature-first` 目录骨架
- 建立 Rust workspace 基础结构

**完成标志**：

- 项目可以安装依赖
- 前后端目录结构已经成型
- 应用可以基础启动

**这一段的意义**：

这是所有后续工作的前置依赖。如果 `M1-A` 不稳定，后面的 UI、数据层和通信链路都会频繁返工。

---

### M1-B · 设计令牌与 UI 基建

**目标**：

先把视觉和组件底座立住，避免后面边写页面边返工。

**包含内容**：

- 接入 `Tailwind CSS`
- 接入 `shadcn/ui` 基础设施
- 落地主题令牌：
  - 颜色
  - 字体
  - 间距
  - 圆角
  - 阴影
  - 动效
- 建立最基础的通用 UI 约束

**完成标志**：

- 已有全局主题和 token
- 基础组件可复用
- 默认 `shadcn` 风格已被收束到符合 StoneFlow 气质

**这一段的意义**：

`M1-B` 做完后，后面的页面骨架才不会“长歪”，也不会出现写一个页面定一套样式的失控状态。

---

### M1-C · App Shell 与路由静态骨架

**目标**：

先把产品主结构做出来，让界面开始像 StoneFlow。

**包含内容**：

- 落地 `Window Chrome`
- 落地 `Global Command Bar`
- 落地 `Sidebar`
- 落地 `Main`
- 落地 `Drawer Overlay`
- 建立基础路由骨架

**路由范围**：

- `/space/:spaceId/inbox`
- `/space/:spaceId/focus`
- `/space/:spaceId/project/:projectId`
- `/space/:spaceId/trash`

**完成标志**：

- 可以在应用里看到完整静态壳层
- 路由切换可用
- `Drawer` 是覆盖式而不是挤压式

**这一段的意义**：

这一段优先验证 `U1` 与 `ADR-007` 的壳层决策是否顺手，确保产品主结构成立。

---

### M1-D · Rust 数据底座与迁移基础设施

**目标**：

把本地数据底座接通，但先不急着做完整业务。

**包含内容**：

- 建立 `entity / migration / core / desktop-app` 基础 crate
- 接入 `SQLite`
- 接入 `SeaORM`
- 创建第一版 migration 框架
- 准备迁移执行入口

**完成标志**：

- 应用启动时可以初始化数据库
- migration 能跑通
- Rust 端已有稳定的数据基础设施

**这一段的意义**：

这一步先解决“能存、能迁移”，不急着把所有业务表一次写全，避免 M1 过早混入 M2 的领域建模工作。

---

### M1-E · 最小前后端通信闭环

**目标**：

证明整个工程不是拼起来的静态壳，而是真正打通了。

**包含内容**：

- 建立第一个 `health check command`
- 前端调用 Rust command
- 把调用结果回显到界面或调试入口
- 顺手校验基础错误处理链路

**完成标志**：

- 前端能稳定调用 Rust
- Rust 能返回可验证结果
- 至少有一个真实的“请求 -> 响应”闭环

**这一段的意义**：

`M1-E` 完成后，`M1` 才算真正落地，因为这时工程、UI、路由、数据底座和通信链路已经形成一个最小完整系统。

---

## 命名约定

当前推荐使用两套映射：

- 执行层正式编号：`M1-A ~ M1-E`
- 看板或 TODO 可选别名：`M1-1 ~ M1-5`

推荐保留字母编号作为正式执行命名，因为它更适合表达“同一主里程碑下的顺序分段”，不会和后续 `M2 / M3 / M4` 产生视觉混淆。

## 一句话执行结论

StoneFlow 的 `M1` 不再按一个大阶段推进，而是改为 `M1-A -> M1-B -> M1-C -> M1-D -> M1-E` 五段顺序执行，先立工程和产品长相，再补数据底座与通信闭环。
