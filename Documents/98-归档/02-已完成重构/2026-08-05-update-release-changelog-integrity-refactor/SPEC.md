# 更新事务、跨平台独立发布与 Changelog 契约重构 - Spec

## 背景与目标

StoneFlow 已经具备 Stable / Beta 双渠道、分平台 updater pointer、签名验证、下载取消、会话恢复和应用内更新日志等基础能力，正常检查、下载和发布路径已经可用。当前主要缺口不在功能数量，而在异常路径的一致性：

1. 更新包下载完成后，安装阶段会重新读取当前渠道并查询可变远端 pointer，导致“已验证安装包”与“安装上下文”可能错位；安装失败还会丢失已下载包。
2. 重复下载请求可能把“仍在下载”误报为“已就绪”，而缺少完整暂存更新时仍可退化为普通重启。
3. “全局版本身份”和“某平台可用版本”的产品模型正确，但版本分配、commit 绑定、不可变产物和并发 pointer 更新缺少可靠护栏。
4. 根 `CHANGELOG.md` 已是全局唯一内容源，但尚未形成 Keep a Changelog 格式契约、发布目标版本门禁和跨跳过版本的累计展示能力。

**目标：** 将应用内更新收口为可证明的下载—安装事务，将发布收口为“同一渠道的全局版本序列 + 平台独立可用指针”，并让 changelog 成为可验证的全局发布契约。

一句话：**更新包一旦 Ready，安装身份就不得变；版本号一旦发布，对应代码和产物就不得变；Mac 与 Windows 可以各自停在不同的可用版本。**

---

## 范围

### In scope

1. **下载—安装事务一致性**
   - 已验证更新与其版本、渠道、安装上下文和完整安装包保持同一身份
   - 安装不依赖远端 pointer 在下载后继续存在或保持不变
   - 安装失败不丢失可重试的已下载更新，不误记更新完成，不意外重启

2. **更新状态机和并发边界**
   - Ready 仅表示存在完整、可安装的暂存更新
   - 重复下载、手动检查与自动下载竞争时，不重复发起网络下载，不误进入 Ready
   - 安装和重启入口单次执行，前端状态只作为后端会话的展示投影
   - 渠道设置只决定后续检查来源，不能改写已开始或已暂存更新的身份
   - 当前设置与暂存更新渠道不一致时，安装前明确展示原渠道和版本并要求用户确认
   - renderer 不再拥有绕过 StoneFlow 更新状态机的原生 updater workflow 权限

3. **跨平台独立发布与版本不变式**
   - Stable 与 Beta 各自维护一条跨平台的全局版本序列，不按 Mac / Windows 分别编号
   - 同一渠道内，一个版本只能对应一个确定 commit，同一 commit 补发其他平台时复用原版本
   - 一个版本可以只发布部分平台，平台可跳过中间版本，不需要补发或逐版安装
   - 新版本 commit 必须包含同渠道上一全局版本 commit，分叉代码不得冒充后继版本
   - 版本记录和分平台产物不可被不同内容覆盖，平台 pointer 只在当前平台产物完整可用后向前推进
   - 并发发布、重试和中途失败不得产生同版本异 commit、产物覆盖或 pointer 回退

4. **Changelog 全局契约与跨版本展示**
   - 根 `CHANGELOG.md` 继续作为 Stable / Beta 和所有平台的唯一用户内容源，不按平台拆分
   - 内容结构遵循 Keep a Changelog 1.1.0 的 `未发布`、版本日期、逆序，以及新增、变更、弃用、移除、修复、安全六类中文契约
   - Beta 条目记录相对上一 Beta 的增量变化，Stable 条目保持面向稳定版用户的策展摘要
   - 发布前验证目标版本条目存在且非空，`未发布` 不被当作已发布版本
   - 当当前平台跳过中间版本时，更新界面展示 `(currentVersion, targetVersion]` 区间内的有效条目；Stable 只展示 Stable，Beta 展示 Beta 与 Stable
   - 远端 changelog 临时失败后不永久粘住过期快照，恢复后可在不重启应用的情况下刷新

### Out of scope（不做什么）

1. **不**要求 macOS 与 Windows 同步构建或发布，不建立强制跨平台 CI matrix
2. **不**要求每个版本齐全所有平台产物，不要求平台补发或客户端逐个安装已跳过版本
3. **不**引入数据库、常驻发布服务、新运行时或为未来团队预留的通用发布框架
4. **不**实现断点续传、差分更新、增量安装包或跨进程持久化已下载包
5. **不**实现安装器接管进程后的自动降级或回滚；问题版本通过发布更高版本前进修复
6. **不**改变 updater 签名算法、更换签名密钥、扩展 Linux 发布，不扩展为 CSP 或其他 Tauri capability 的全面安全整改
7. **不**重做 changelog 弹窗的视觉设计，不从 Git commit 自动生成用户更新日志，不新增平台专属 changelog
8. **不**顺带修复本轮未确认的设置并发覆盖、检查超时或 404 语义等其他审计项
9. **不**为旧的全局 updater endpoint、旧 manifest 形状或并行版本分配路径保留兼容双轨
10. **不**在未单独授权时执行真实生产发布、Git Tag 推送、R2 对象删除/覆盖或真实安装重启

## 用户场景与需求

- 作为 StoneFlow 用户，我想在更新包下载完成后即使断网也能安装该精确版本，以便远端 pointer 或渠道设置变化时不会安装错位或被迫重新下载。
- 作为 StoneFlow 用户，我想只在安装包真正完整就绪时看到“立即重启”，以便不会因重复点击或后台竞争中断更新。
- 作为 StoneFlow 用户，我想在安装失败后看到明确错误并重试同一个已下载版本，以便应用不会无更新地重启或误报完成。
- 作为发布维护者，我想在 Mac 发布 `0.1.2-beta.3` 后，回到 Windows 基于包含该 commit 的新代码直接发布 `0.1.2-beta.4`，以便 Windows 无需补发 beta.3，Mac 也可继续停在 beta.3。
- 作为发布维护者，我想在同一 commit 之后补发另一平台时复用原版本，以便版本始终代表唯一代码身份而不是某台机器的构建次数。
- 作为 Beta 用户，我想在本平台从 beta.2 直接更新到 beta.4 时看到 beta.3 和 beta.4 的全部有效变化，以便不因平台跳过发布而遗漏用户可见内容。
- 作为维护者，我想使每次发布在未推进平台 pointer 前完成身份、产物、签名和 changelog 验证，以便发布失败只留下可重试的不可变事实，不影响用户当前更新路径。

## 能力边界

| 能力 | 边界 |
|------|------|
| 更新会话 | 后端会话是状态与并发约束的唯一权威；前端只展示后端快照和事件 |
| Ready | 当且仅当完整、可安装的暂存更新存在时成立 |
| 更新渠道 | 决定后续检查来源；不改写已开始或已 Ready 事务的身份；设置与暂存渠道不一致时，安装必须明确提示并确认 |
| 前端权限 | renderer 只能请求 StoneFlow 自有更新用例，不能直接调用原生 updater 完成检查、下载或安装 |
| 版本序列 | Stable 与 Beta 各自维护跨平台全局序列；平台不独立生成同名但不同代码的版本 |
| 版本身份 | 同一渠道内的 version 与 commit 一一绑定；不可重绑、覆盖或静默重用 |
| 平台可用性 | `channel × platform` pointer 只表示该平台真正可下载安装的最高版本，不代表其他平台状态 |
| 产物 | 版本与分平台产物是不可变事实；只有 pointer 是可变对象，且只能向前推进 |
| Changelog | 根 `CHANGELOG.md` 是全局用户内容唯一源；更新模块按版本区间只读消费，不拥有或反向修改内容；Stable 只消费 Stable 条目，Beta 消费 Beta 与 Stable 条目 |
| 真实发布 | 代码与文档可实现和验证发布契约；生产 Tag / R2 / 安装变更仍以当前用户授权为边界 |

## Definition of Done

- 所有验收标准均已通过自动化测试或受控端到端验收，并留有可复核结果
- 改动范围的 TypeScript / Rust 测试、类型检查、lint、边界检查与格式检查通过；根质量入口已执行且未新增失败
- macOS 与 Windows 各完成至少一次受控的签名 release 包端到端更新验收；在未获生产授权时，必须使用隔离的验证环境，不推进生产 pointer
- 完成后需同步的全局与模块长期文档已按 PLAN 登记项更新，任务归档前逐条核对验收标准
- 实施结果不存在未登记的范围偏差；如发生偏差，必须先回写并重新确认 SPEC / PLAN

## 验收标准

### 更新事务与状态

- **AC-1**：当某版本安装包下载完成且验证成功时，系统应当将其版本、来源渠道、已验证安装上下文和完整安装包作为同一暂存更新，且 Ready 展示版本必须与最终安装版本一致。
- **AC-2**：当用户在 Ready 状态发起安装时，系统应当安装该暂存更新的精确版本，不得重新查询远端端点或改用当前设置中的渠道拼装安装身份。
- **AC-3**：如果安装包已完整暂存后网络不可用、远端 pointer 被更新或删除，则系统应当仍能安装该精确版本，不得强制用户重新下载。
- **AC-4**：如果不存在完整暂存更新或当前状态不是 Ready，则系统应当拒绝“重启并安装”，不得退化为普通重启。
- **AC-5**：如果安装在成功交给系统安装器之前失败，则系统应当保留原暂存更新并显示可理解错误；用户重试时应当直接消费该事务，不重新检查远端或重新下载，断网时仍可重试，失败期间不得重启、记录或误报更新完成。
- **AC-6**：当一次下载正在进行时，系统收到重复下载请求应当保持 Downloading，不得发起第二次网络下载、返回已完成或发出 Ready 事件。
- **AC-7**：当一次安装正在进行时，系统收到其他安装或重启请求应当保持单次执行，所有用户入口均应当禁止重复操作，且只能启动一次安装器或应用重启。
- **AC-8**：当更新事务已开始下载或进入 Ready 后渠道设置发生变化时，系统应当保持该事务原版本和原渠道身份，新渠道仅对该事务结束后的检查生效；如果安装时当前设置与暂存渠道不同，界面必须明确显示仍将安装的原渠道与版本，并在用户确认后才继续。
- **AC-9**：当 renderer 试图绕过 StoneFlow 更新用例直接调用原生 updater 的检查、下载或安装能力时，系统应当拒绝该请求；前端状态篡改不得绕过后端状态与前置条件。

### 版本身份与平台发布

- **AC-10**：当任一平台发布某渠道的新版本时，系统应当从该渠道跨平台共享的版本序列分配版本号，不得根据当前平台自己的最新版本单独编号。
- **AC-11**：当同一渠道的同一 commit 已绑定发布版本时，系统应当在补发其他平台时复用该版本，不得再次递增版本号。
- **AC-12**：当 Mac 发布 `0.1.2-beta.3` 后，Windows 以包含该版本 commit 的后继 commit 发布 `0.1.2-beta.4` 时，系统应当只将 Windows Beta pointer 推进到 beta.4，保持 Mac Beta pointer 为 beta.3，且不要求 Windows 补发 beta.3。
- **AC-13**：如果新版本候选 commit 不包含同渠道上一全局版本 commit，则系统应当在构建和上传前中止发布，且不得修改任何远端状态。
- **AC-14**：如果发布来源存在未提交修改、无法取得唯一 commit SHA，或该 commit 无法从发布配置指定的共享 Git remote 的公开分支或 tag 历史中到达，则系统应当在构建和上传前中止发布。
- **AC-15**：如果候选版本已绑定其他 commit，或当前 commit 在同渠道已绑定另一版本，则系统应当拒绝发布，且不得覆盖已有绑定、产物或 pointer。
- **AC-16**：当两个不同 commit 并发争用同一下一版本号时，系统应当至多允许其中一个建立版本绑定，失败方不得覆盖成功方的版本、产物或 pointer。
- **AC-17**：当两个平台并发补发同一渠道、版本和 commit 时，系统应当保留各自已成功建立的不可变产物记录与分平台 pointer，一个平台的结果不得覆盖、删除或回退另一平台的结果。
- **AC-18**：如果同一渠道、版本和平台的远端产物已存在，则系统应当仅在安装包字节摘要、签名和不可变版本元数据均一致时视为幂等成功；任一项不同时应当中止并保留原产物。
- **AC-19**：当准备更新某渠道的平台 pointer 时，系统应当仅允许其按 SemVer 向更高版本推进；相同版本仅在版本、产物 URL、签名和其他客户端消费字段均一致时视为幂等成功，回退或同版本不同有效载荷应当被拒绝。
- **AC-20**：如果当前平台的产物、签名或版本记录尚未完整可用，或 pointer 写入前任一前置步骤失败，则系统不得推进该平台 pointer，原 pointer 所指版本应当继续可下载安装。如果条件写已成功，随后的公开面终检或本地清理失败不得回滚 pointer，并必须按“已公开”状态报告。
- **AC-21**：当客户端检查更新时，系统应当只返回其当前渠道和平台已发布的最高版本；其他平台存在更高版本时，不得向该客户端宣告该版本可安装。

### Changelog 契约

- **AC-22**：当发布前校验根 `CHANGELOG.md` 时，系统应当要求唯一顶部 `未发布`、按新到旧排列的 SemVer + ISO 日期版本标题、可选 `[已撤回]` 与文末比较链接；版本内容的分类标题只能使用新增、变更、弃用、移除、修复、安全六类中文标记中的非空子集，不接受英文标题或别名，且比较链接不得被解析为最旧版本正文。任一格式条件不满足时，应当在构建、上传和远端变更前阻断发布。
- **AC-23**：当准备发布某目标版本时，系统应当要求根 `CHANGELOG.md` 中存在该版本的非空有效条目，且不得将 `未发布` 或其他版本的内容当作目标版本说明。
- **AC-24**：当当前版本低于本平台目标版本且期间跳过一个或多个版本时，更新界面应当按新到旧展示 `(currentVersion, targetVersion]` 区间内的有效 changelog 条目并排除区间外条目；Stable 目标只展示 Stable 版本条目，Beta 目标展示 Beta 与 Stable 版本条目。
- **AC-25**：当 Windows 从 `0.1.2-beta.2` 直接更新到 `0.1.2-beta.4` 时，系统应当展示 beta.3 与 beta.4 的有效变化，不得要求 Windows 曾发布或安装 beta.3。
- **AC-26**：如果累计区间内部分版本没有有效 changelog 条目，则系统应当展示其余有效条目并继续提供更新；当区间内没有有效条目时，应当使用无说明状态且不得阻断更新。
- **AC-27**：如果远端 changelog 首次加载失败而使用了打包快照，则网络恢复后用户再次打开更新日志时，系统应当重新请求远端内容并在内容有效时更新展示，不得要求用户重启应用。

## 当前技术方案

本任务采用“后端 exact-handle 更新事务 + Git Tag 全局版本身份 / channel ledger 并发仲裁 + R2 分平台 CAS pointer + 单一 Changelog 契约”的已确认方案，详见 [PLAN.md](./PLAN.md)。跨模块且难逆转的发布身份决策记录于 [ADR-0001](../../../01-架构/adr/ADR-0001-global-release-identity-and-platform-pointers.md)。
