# 同步数据模型与原理（白话）

## 1. 两套库，职责不同

| | 本机 SQLite | 云端 Postgres |
|---|---|---|
| 是什么 | **业务库**：UI 读写的完整数据 | **同步中枢**：操作日志 + 实体投影 |
| 有没有「任务表」 | 有完整 `tasks` 行（标题、备注、时间…） | **没有**业务 Task 表 |
| 怎么表示一个任务 | `tasks` 一行 | `sync_entity_state` 里 `entity_type=task` 的一行投影 + 历史上的 change_log |
| 谁写 | 本机 SeaORM 唯一业务 writer | 各设备通过协议 push 写入 |

所以你在 Neon 里看不到和本地一模一样的 `tasks` 表，是**设计如此**，不是丢了半套库。

## 2. 用很少的数据怎么同步？

核心是 **操作复制 + 字段级合并**，不是「整库文件对拷」。

```text
本机改标题
  → 写入 SQLite tasks
  → 同时往 outbox 塞一条 mutation（只含改动的字段）
  → 上传到云端 change_log（分配 server_seq）
  → 更新云端 entity_state 投影
  → 另一台设备按 server_seq 下载 mutation
  → 在本机 apply 并写回 SQLite
```

算法要点：

1. **单调序号 `server_seq`**：云端全局顺序，像磁带位置。  
2. **字段 LWW**：同一字段谁序号大听谁；不同字段可合并。  
3. **generation + tombstone**：永久删除后旧 generation 不能复活。  
4. **幂等**：`(device_id, operation_id)` 重复上传只算一次。

这就是为什么 148 条「投影」能代表整站任务/项目，而不需要在云端再存一份完整业务 schema。

## 3. 云端五张表分工

| 表 | 白话 | 作用 |
|---|---|---|
| `sync_schema` | 协议版本 | 防止新旧客户端乱改表 |
| `sync_change_log` | **变更流水账** | 有序 mutation；下载靠 `server_seq > cursor` |
| `sync_entity_state` | **当前投影** | 每个实体最新字段+生命周期；全量同步时用 |
| `sync_upload_acks` | **上传回执** | 幂等，防重复提交 |
| `sync_tombstones` | **删除碑** | 永久删除标记 |

本机还有：

| 表/键 | 作用 |
|---|---|
| `outbox` | 待上传队列 |
| `sync_cursors`（`last_pulled_server_seq`） | 本机同步位置 |
| `tasks` / `projects` / … | 真正给 UI 用的业务表 |

## 4. 诊断里「本地 151 vs 远端 148」

常见原因（已修计数口径）：

- 本地曾 `COUNT(*)` **含已删除行**，云端投影只有存活实体 → 本地偏大。  
- 首次灌库 seed=148 与远端 148 对齐 → **上传是成功的**。  
- cursor 本地=远端=149 → **已对齐到同一同步序号**。  
- 待同步 0 → outbox 空，没有积压。

差 3 条时优先想：是否含回收站/永久删除前残留；刷新诊断（修口径后）应更接近。

## 5. 和「全库备份」的区别

| | 整库备份/文件同步 | 本方案 |
|---|---|---|
| 冲突 | 难自动合并 | 字段级 LWW |
| 离线 | 整文件易冲突 | 本地先写，上线再传 |
| 云端体积 | 整库拷贝 | 只存变更与投影 |
| 多设备 | 后写覆盖整库 | 按字段收敛 |
