# 调研方案与流程

> 作用：定义如何一步步解构 StoneFlow 前端，从 As-Is 到 To-Be 到 Migrate。  
> 本文件是方法论；具体模块事实写在 `01-As-Is/`。

---

## 1. 我们在解什么问题

不是再写一份「分层口号」，而是产出能支撑决策的材料：

| 问题 | 必须回答 |
|------|----------|
| 有什么 | 几乎无漏的模块清单（到子模块 / 包边界 / 关键文件） |
| 干什么 | 职责、不负责、输入输出、真相源 |
| 怎么连 | 依赖方向、跨层调用、谁装配谁 |
| 好不好 | 高内聚低耦合？可独立删除？符合规范与最佳实践？ |
| 怎么改 | 目标边界差、重构切片、验收标准 |

理想终态（决策 2=A）：

```txt
删除一个 feature
→ 去掉 Shell/Provider 装配
→ 去掉对应 route 叶子（或 redirect）
→ 去掉该 feature 目录
→ 其余功能几乎不受影响
```

调研期**不预设** feature 互依最终策略（决策 3=C），先画清现状再定。

## 2. 四阶段总流程（严格顺序）

```txt
Phase A  现状调研（As-Is）     ← 当前
   ↓
Phase B  评估与差距（Gap）
   ↓
Phase C  目标架构（To-Be）
   ↓
Phase D  重构路线图（Migrate）
```

### 硬约束

1. A 未完成的大模块，不进入 C 的文件级搬迁设计（可写目标原则）。
2. 每个调研 session **只深挖 1 个大模块或 1 组同质 feature**，产出可合并的文档补丁。
3. 代码与文档冲突 → **以代码为准**，标 `DOC-DRIFT` 进附录（决策 8=B，本阶段不批量改 T1 等）。
4. 调研阶段不做大规模重构；最多「边界注释 / 小测试锁定行为」。
5. 本轮范围 = **前端 only**（决策 6=C）。Rust 架构不在本目录展开。

## 3. Phase A · 调研 Wave 顺序

从「壳」到「能力」到「共享」，避免一上来被最大 feature（`task`）拖死。

| Wave | 对象 | 为什么 | 产出 |
|------|------|--------|------|
| **W0** | 骨架 + 注册表 + 本方案 | 先有容器 | 本目录 |
| **W1** | `routes/` + `app/router` + `app/navigation` | 刚收口，边界清晰，当**颗粒度标尺** | `02-routes-and-navigation.md` |
| **W2** | `app/` providers、layouts、入口 | 壳装配面 | `03-app-shell-and-layouts.md` |
| **W3** | features · 平台能力 | 全局副作用、高入度 | `04-features-platform.md` |
| **W4** | features · 领域实体 | 数据与规则核心 | `05-features-domain.md` |
| **W5** | features · 页面/场景 | 含单文件壳 | `06-features-scenes.md` |
| **W6** | `shared/*` + `styles/*` + `test/*` | 共享层易成杂物间 | `07-shared-and-styles.md` |
| **W7** | 跨模块依赖图 | 需注册表齐全 | `08-dependency-matrix.md` |
| **W8** | Query / Store / IPC facade / Events | 数据面 | `09-data-and-state-map.md` |

### Feature 调研建议优先级（W3–W5 内）

1. `command` → `task` → `quick-create` → `bulk-action`  
2. `display-options` / `metadata-fields` / `selection` / `entity-detail`  
3. `project` / `space` / `lifecycle` / `view`  
4. `settings` / `update` / `sync` / `workspace`  
5. 单文件 scene：`inbox` `archive` `trash` `all-tasks` `no-project` `views`…  
6. 空壳：`task-drawer`、空 `api/model` 目录

## 4. 每个模块的标准调研协议

**强制使用同一张卡**，模板见 [`00-调研协议.md`](./00-调研协议.md)。

摘要六卡：

| 卡 | 内容 |
|----|------|
| A 身份 | 路径、层级、职责/不负责、规模、公开/私有面 |
| B 结构 | 子树、内部分层、barrel/死目录、命名 |
| C 行为 | Query / Client state / IPC / URL / Side effects |
| D 依赖 | 上游、下游、装配点、耦合类型、Delete Test 1–5 |
| E 质量 | 项目规范 + Vercel React BP + Composition 逐项 Pass/Partial/Fail |
| F 结论 | 评级、Top 风险、不改的理由、Keep/Split/Merge/Delete/Extract |

颗粒度要求（决策 7：越细越好）：

- 大模块：写到**文件级职责表**（每个 `.ts/.tsx` 一行职责或「测试/生成」标注）。
- Feature：公开 API 列出具体可 import 文件；私有目录明确禁止跨 feature import。
- Route：每个叶子 path、layout 链、loader/redirect、页面来自哪个 feature。
- Shared/ui：按子包（base/board/row/…）分别建卡，不合成一坨。

## 5. 调研手段（工具链）

每 session 固定组合，避免只靠印象：

1. **目录与规模**：`find` / 文件计数  
2. **Codegraph / 符号探索**：入口 → 调用路径 → 爆炸半径（优先于盲目全文 grep）  
3. **Import 图**：`from '@/features/xxx'` / 相对路径消费者  
4. **对照已有短契约**：`src/**/ARCHITECTURE.md`、openspec、执行计划 → 漂移进附录  
5. **运行时抽检**（可选）：provider 树、一条 happy path 数据流  
6. **写回**：只改本 Wave 章节 + 注册表 + Session 日志  

### 推荐验证命令（改代码时；纯文档可跳过）

```bash
bun run typecheck
bun run lint
bun run test:run
```

## 6. Session 节奏模板（约 1–2 小时）

```txt
1. 选 Wave 中 1 个目标（或 1 个 feature）
2. 身份卡 + 结构卡（含文件级表）     ~30–40min
3. 依赖卡 + Delete Test              ~30–40min
4. 质量卡 + 结论卡                   ~20min
5. 更新：
   - 01-As-Is 对应章节
   - 00-模块注册表.md 对应行
   - 附录/Session调研日志.md
   - 若有漂移 → 附录/文档漂移日志.md
6. 留下：下一入口 + ≤3 个未决问题
```

禁止：一个 session 同时「深挖 task + 设计 To-Be 搬家 + 开重构 PR」。

## 7. Phase B · Gap（As-Is 达标后）

**输入**：填满的模块卡 + 依赖矩阵 + 数据面地图  

**输出**：

- `02-Gap/01-债台账.md`：全债 ID 台账  
- `02-Gap/评估矩阵.md`：模块 × 原则评分汇总  
- `02-Gap/耦合热点与反模式.md`：枢纽模块、环、God Layout、假 feature、空目录、双真相源  

**规则**：每条债务必须有**证据路径**；禁止空泛「不优雅」。  
排序维度建议：可删除性阻碍 > 真相源混乱 > 依赖环 > 规范违反 > 纯整洁度。

**波次（不要一次做完）**：见 [`02-Gap/00-Gap波次方案.md`](./02-Gap/00-Gap波次方案.md)

| Wave | 主题 |
|------|------|
| G0 | 债台账 + 评分尺 |
| G1 | P0：shared 反向依赖 + God Shell |
| G2 | P1：command + 三列表 DRY |
| G3 | P2：领域环 + 死代码 + 数据双通道 |
| G4 | P3 + 不做清单 |
| G5 | 收官汇总 → To-Be 输入 |

---

## 8. Phase C · To-Be（差距清晰后）

**输入**：Gap + 产品边界（P1/P2 只作背景，不在此重写产品）  

**输出**：

- `03-To-Be/目标架构.md`：目标分层、feature 分类、依赖规则（此处才固化决策 3）  
- `03-To-Be/模块边界契约.md`：公开 API、禁止依赖、装配约定、删除检查清单  

**原则**：

- 最优 ≠ 最多文件夹  
- 可删除性是一等指标  
- 与 TanStack / Query 官方模型同构，少自造 DSL  
- 空壳、假抽象优先删除或合并，而不是再包一层  

---

## 9. Phase D · Migrate

**输入**：To-Be  

**输出**：`04-Migrate/重构切片路线图.md`  

**切片原则**：

1. 先锁行为（测试 / 纯规则单测）  
2. 再抽边界（公开 API、切断私有 import）  
3. 再搬文件 / 合并 / 删除  
4. 每切片可独立合并、可回滚  
5. 禁止大爆炸「周末重写 features」  

建议切片顺序（示意，以 Gap 为准）：

```txt
死代码/空目录删除
→ 文档与短契约对齐（此时才批量清 DOC-DRIFT）
→ 导航/路由边界加固（若 W1 仍有债）
→ 平台 feature 公开 API 收口
→ 领域 feature 拆分/减重
→ scene 壳去留
→ shared 降级回 feature
```

## 10. 文档与代码契约的双轨制

| 轨道 | 位置 | 内容 | 更新频率 |
|------|------|------|----------|
| 短契约 | `src/**/ARCHITECTURE.md`、`CONVENTIONS.md` | 日常落点、不变式 | 改边界时同步 |
| 解构工作区 | `Docs/03-前端架构解析/` | 细颗粒 As-Is / Gap / To-Be / Migrate | 每个调研 session |
| 系统总览 | `Docs/T1-系统设计.md` 等 | 全栈长期叙述 | **As-Is 完成后**按漂移日志批量修（决策 8=B） |

禁止：把 As-Is 细表整份复制进 `src/ARCHITECTURE.md` 把短契约撑爆。

## 11. 与 Vercel / 项目规范的关系

调研与评分时显式对照，不凭感觉：

### 项目内

- 依赖方向、无裸 `invoke`、无 Query 双写 store、无第二路由 DSL  
- 无无意义 barrel、直接 import  
- 导航文件边界固定在 `app/navigation`  

### Vercel React Best Practices（桌面场景适用子集）

- bundle：direct import、可分析路径、重模块按需  
- async：独立工作并行、避免无谓 waterfall  
- client data：订阅去重、监听去重  
- rerender：细粒度订阅、不在组件内定义子组件、event 优于 effect 堆逻辑  
- （SSR/RSC 规则多数 N/A，标 N/A 即可）  

### Vercel Composition Patterns

- 避免 boolean props 组合爆炸  
- compound components / children  
- Provider 只暴露 state / actions / meta

## 12. 风险与反模式（调研中要主动抓）

| 信号 | 可能问题 |
|------|----------|
| Feature 目录 0～1 文件但名字很重 | 假 feature / 壳 |
| 空 `api/` `model/` 目录 | 历史残留 |
| `shared` 出现 task/project 业务判断 | 分层泄漏 |
| ShellLayout 挂载 Provider 过多且含业务规则 | God 装配 |
| 多处手拼 path | 导航真相分叉 |
| Store 镜像 URL 或 Query 数据 | 双真相源 |
| barrel `index.ts` 再导出整个 feature | 依赖面膨胀 |
| 组件一串 `isX/isY/showZ` | composition 债 |
