# 模块白话导读（给人读）

> 日期：2026-07-17
> 作用：用中文说明**现在有哪些模块、谁大谁小、大的干什么**。方便以后快速建立心智，不必先啃表格。
> 精确 ID / 路径表见：[01-模块全景清单.md](./01-模块全景清单.md)
> 讨论节奏见：[02-讨论与治理计划.md](./02-讨论与治理计划.md)
> 口径：以现网 `src/` 为准（不是旧 As-Is 路径）。

---

## 先建立一张地图

整个前端可以想成六块地：

| 地块 | 白话 |
|------|------|
| **app** | 开机、全局 Provider、导航规则 |
| **layout** | 侧栏/顶栏/主区壳子，把功能「装」上去 |
| **routes** | 网址对应哪一页（尽量薄） |
| **features** | 真正的业务/能力模块（最多、最重要） |
| **shared** | 没业务归属的零件库 |
| **styles / test** | 样式真相、测试工具 |

**目录骨架**（`app / layout / routes / features / shared`）已经对齐完；后面治理重点是**每个模块内部是否整洁、边界是否清楚**，不是再大搬家。

---

## 一、大模块（核心：改起来牵一发动全身）

按「重要 + 体量/耦合」排，不是严格文件数排序。

### 1. `task`（任务）— 最大的业务内核

| | |
|--|--|
| **体量** | feature 里最大（约 80+ 文件） |
| **作用** | 任务列表（收件箱/全部/无项目共用一套场景）、看板、详情（整页/抽屉/预览）、任务相关快捷键 |
| **为啥重要** | 产品主路径几乎都绕着任务转；列表页已经不再各建 feature，都挂在它上面 |

### 2. `command`（命令与快捷键）— 最大的平台能力

| | |
|--|--|
| **体量** | 第二大（约 60 文件），另有千行级命令菜单组件 |
| **作用** | 命令注册、快捷键、命令面板、运行时；壳通过 command-bridge 把它和业务接上 |
| **为啥重要** | 键盘流、全局操作入口；边界乱会全仓跟着乱 |

### 3. `layout`（应用铬架）— 壳本身

| | |
|--|--|
| **体量** | 整棵 `src/layout`（顶栏、侧栏、主区、抽屉、命令桥、EntityScene…） |
| **作用** | 画出应用外壳；挂 Provider；把各 feature 的 public 能力「装配」起来；**不写**任务/项目业务规则 |
| **为啥重要** | 所有主界面都住在壳里；壳变胖 = 上帝组件卷土重来 |

### 4. `app/navigation`（导航语义）— 文件不大，极重要

| | |
|--|--|
| **体量** | 不大（十几个文件） |
| **作用** | URL ↔ 产品语义（你在 inbox 还是某 space 的 tasks）、拼路径、启动恢复、会话前进后退 |
| **为啥重要** | command、面包屑、侧栏、记忆路由都依赖它；比很多「大文件夹」更关键 |

### 5. `launcher`（Launcher 窗）— 独立大功能

| | |
|--|--|
| **体量** | 约 50 文件 |
| **作用** | 独立窗口里的快速建任务/捕获；自有 runtime / 布局 / UI |
| **为啥重要** | 主窗之外的第二条主路径；边界要跟主 layout 分开 |

### 6. `bulk-action`（批量操作）— 大平台

| | |
|--|--|
| **体量** | 约 40 文件 |
| **作用** | 多选后的批量改状态/归档等；registry + adapter + UI |
| **为啥重要** | 和 selection、task/project 交织；边界不清会变成「页面私货」 |

### 7. `routes`（路由树）— 代码中等，结构大

| | |
|--|--|
| **体量** | 一堆薄页 + `_shell/all` 与 `spaces` 对称 |
| **作用** | 匹配 URL、redirect、挂 feature 的页面出口 |
| **为啥重要** | 场景入口表；应保持**薄**，厚逻辑不该堆这里 |

### 8. `project`（项目）— 第二业务内核

| | |
|--|--|
| **体量** | 中等（约 20 文件） |
| **作用** | 项目详情、侧栏数据、创建/更新、项目看板 |
| **为啥重要** | 和 task、space 强相关；侧栏/概览都吃它的数据 |

### 9. `metadata-fields` + `display-options` — 列表体验大件

| | |
|--|--|
| **体量** | 各约 25～30 文件 |
| **作用** | 字段控件（日期/优先级等）、列表显示选项（分组/排序/列） |
| **为啥重要** | 任务行、创建流、QC 都用；容易和 task 缠成一团 |

### 10. `settings`（设置）— 中等 scene

| | |
|--|--|
| **体量** | 约 18 文件 |
| **作用** | 设置页、侧栏偏好、设备相关配置入口（三入口：主 / contract / page） |
| **为啥重要** | 壳导航、侧栏显示都会碰到 |

### 也算大、略次一档

| 模块 | 主要作用 |
|------|----------|
| **view** | 自定义视图定义与跑列表 |
| **lifecycle** | 归档 / 回收站编排与列表 |
| **update / sync** | 应用更新、云同步状态 |
| **global-search** | 全局搜索 |
| **shared/components** | 通用 UI（board/row/main-card/shadcn）— 不是业务，但是地基 |

## 二、中等模块

有存在感，但边界相对清楚，或体量可控。

| 模块 | 主要作用 |
|------|----------|
| **space** | 工作区/空间实体、当前 scope |
| **selection** | 多选、命令选中上下文 |
| **entity-detail** | 抽屉「打开谁」跟 URL search 走 |
| **filter** | 页级筛选 Provider |
| **activity** | 活动时间线 / 调试页 |
| **project-overview** | 项目总览页（数据多走 project） |
| **layout 子块** | header / sidebar / command-bridge / entity-scene（可并进「壳」一场谈） |
| **app/providers · router** | Query 默认值、Router 实例 |

## 三、小模块（小 ≠ 不重要）

| 模块 | 作用 | 备注 |
|------|------|------|
| **submit** | 表单注册「当前可提交目标」，给命令 Enter 用 | 小而精，常作边界标杆 |
| **danger-confirm** | 危险操作确认框 | 同上 |
| **workspace** | 听事件 → 刷新 Query | 文件少，doctor 噪音可能多 |
| **shared/query · events · lib · types…** | 跨模块工具 | 必须保持「无业务」 |
| **styles** | 设计 token / 全局 CSS | 真相源，宜稳 |
| **test** | 测试 render 工具 | 基建 |
| **main / routeTree** | 入口与生成路由树 | 别手改 gen |

## 四、没有独立文件夹、但仍算「场景」

这些**不再**各建 `features/xxx`，但产品上仍是一块能力，挂在路由 + domain 上：

| 场景 | 实际归属 |
|------|----------|
| 收件箱 / 全部任务 / 无项目 | **task** 列表场景 |
| 归档 / 回收站 | **lifecycle** |
| 任务详情页 | **task** |
| 项目列表页 | **project-overview** + **project** |
| 视图页 | **view** |

## 五、一句话分层重要性

```txt
第一梯队（先懂、后治）：
  task · command · layout · navigation · launcher · bulk-action

第二梯队（业务与列表体验）：
  project · space · metadata-fields · display-options · settings · view · lifecycle

第三梯队（横切小件 / 系统服务）：
  selection · submit · filter · entity-detail · search · sync · update · workspace · activity

地基（少动、守边界）：
  shared/* · styles · routes（保持薄）· app 启动件
```

## 六、和整体目标的关系

| 已经怎样 | 还差什么 |
|----------|----------|
| 目录格子画好了（Phase D） | 每个格子是否「高内聚、低耦合、可组合」 |
| 跨模块有 public + boundaries 闸门 | 模块**内部**巨石、boolean 丛林、Query/状态是否干净 |
| 全景清单 + 讨论计划已有 | 按梯队逐个谈边界 → 可选整改 |

**大模块**优先谈/改（task、command、layout、navigation）。
**小模块**很多已接近标杆（submit、danger），可当对照，不必先开刀。

品质怎么算达标：见 [`../03-To-Be/08-Feature品质验收标准.md`](../03-To-Be/08-Feature品质验收标准.md)。
