# U1 · 设计系统

> 最后更新：2026-04-17 · 当前版本：V1

## 1. 文档目标

本文件用于定义 StoneFlow 第一版的视觉系统、交互风格、设计令牌与核心组件规范。

它服务于四件事：

- 给产品界面一个统一且长期可维护的视觉基线
- 给前端实现提供可直接映射到主题变量和组件的语义令牌
- 给后续页面设计、组件封装和交互动效提供统一标准
- 明确 StoneFlow 的 UI 与 UX 参考边界，避免“像很多产品拼起来”

---

## 2. 设计定位

### 2.1 设计关键词

- 快
- 专业
- 克制
- 清晰
- 桌面感
- 键盘优先
- 高密度但不压抑

### 2.2 参考来源拆分

StoneFlow 的设计参考不是整体照搬，而是拆开吸收：

- `Linear`
  - 参考：浅色风格、视觉秩序、信息密度、专业感、状态表达的克制方式
  - 不参考：团队协作产品心智、过强的工程管理气质
- `Raycast`
  - 参考：全局唤起、命令输入、模糊搜索、键盘优先、低摩擦任务创建
  - 不参考：深色视觉、图标主导的科技感皮肤
- `Things`
  - 参考：个人任务管理的完整性、过渡态处理、任务执行心智
  - 不参考：偏生活工具化的柔和表达

### 2.3 StoneFlow 的最终气质

StoneFlow 第一版应呈现为：

- 一个面向个人执行系统的 macOS 桌面工具
- 比普通 Todo 更专业，但不做企业后台感
- 比效率工具更有秩序，但不做冷硬系统软件感
- 比原生轻应用更完整，但不显得厚重

一句话概括：

> StoneFlow 是一个以浅色、克制、精密反馈和键盘优先为核心的个人执行工作台。

---

## 3. 设计原则

### 3.1 聚焦优先于装饰

- 视觉服务于任务整理和执行，不为炫技服务
- 装饰性元素只能增强层级和状态，不得干扰扫描效率

### 3.2 快速优先于完整展开

- 默认优先展示最少但足够的信息
- 详情通过 Drawer、Hover、Command、二级区域补充

### 3.3 状态必须可见

- 每个对象都必须让用户一眼知道“它现在是什么”
- 状态通过文案、位置、颜色、分组和交互反馈共同表达

### 3.4 结构必须稳定

- Sidebar、Main、Drawer 的空间关系不能频繁变化
- 页面切换要清楚，模块切换要干净，局部更新要足够快

### 3.5 反馈必须明显但克制

- 完成任务、归类任务、恢复任务、删除任务都要有反馈
- 反馈应该“有存在感”，但不能像游戏特效一样喧宾夺主

### 3.6 键盘优先，但鼠标不吃亏

- 高频流程必须支持键盘闭环
- 低频确认、批量整理、查看详情要对鼠标操作同样顺手

---

## 4. 界面骨架

StoneFlow 第一版固定采用以下骨架：

```text
┌──────────────────────────────────────────────────────────────┐
│ Window Chrome + Global Command Bar                           │
├───────────────┬──────────────────────────────────────────────┤
│ Sidebar       │ Main Content                                 │
│ - Space Tabs  │                                              │
│ - Navigation  │                            Drawer Overlay -> │
└───────────────┴──────────────────────────────────────────────┘
```

### 4.1 结构职责

- `Window Chrome + Global Command Bar`
  - 承担窗口顶部区域和全局 Command 入口
- `Sidebar`
  - 承载当前 Space 下的 Space Tabs、Inbox、Focus、Projects、Trash
- `Main Content`
  - 承载列表、聚合视图、项目视图等主工作区
- `Drawer Overlay`
  - 默认隐藏
  - 从右侧覆盖打开
  - 展示和编辑 Task / Project 详情

### 4.2 层级表达方式

层级不依赖大面积重阴影，而依赖以下组合：

- 轻微背景差
- 细边框
- 精准留白
- 少量层级阴影
- 激活态描边和强调条

其中：

- `Global Command Bar` 属于最稳定的顶层工作入口
- `Sidebar + Main` 构成默认工作骨架
- `Drawer Overlay` 属于按需出现的上层信息面板

这意味着 StoneFlow 的分层应该更像“精密面板”，而不是“漂浮卡片堆”。

## 5. 视觉令牌系统

## 5.1 命名原则

设计令牌统一采用语义化命名，而不是直接暴露原始颜色值。

推荐命名结构：

- `--sf-color-*`
- `--sf-space-*`
- `--sf-radius-*`
- `--sf-shadow-*`
- `--sf-font-*`
- `--sf-duration-*`
- `--sf-ease-*`

不建议：

- `--gray-100`
- `--blue-500`
- `--radius-card`

原因：

- 前者太底层，难以表达界面语义
- 后者过度绑定具体组件，后期难复用

---

## 5.2 色彩系统

### 5.2.1 总体方向

StoneFlow 第一版采用：

- 浅色主界面
- 偏冷静的中性色背景
- 克制的蓝色作为交互强调色
- 极少量状态色用于风险、完成、提醒表达

底色方向建议：

- `stone / zinc / warm neutral` 混合中性体系
- 不走纯白实验室风
- 不走彩色品牌皮肤路线

### 5.2.2 基础语义色

| Token | 建议值 | 用途 |
|------|--------|------|
| `--sf-color-bg-app` | `#F5F6F8` | 应用总背景 |
| `--sf-color-bg-sidebar` | `#F2F4F7` | Sidebar 背景 |
| `--sf-color-bg-surface` | `#FFFFFF` | 主内容容器、卡片、面板 |
| `--sf-color-bg-surface-muted` | `#FAFBFC` | 次级容器、聚合块背景 |
| `--sf-color-bg-elevated` | `#FCFCFD` | 浮层、Command、Drawer 顶层面 |
| `--sf-color-border-subtle` | `#E6E9EE` | 普通边框 |
| `--sf-color-border-strong` | `#D8DDE6` | 激活区块或强分隔 |
| `--sf-color-text-primary` | `#151821` | 主文本 |
| `--sf-color-text-secondary` | `#4A5565` | 次级文本 |
| `--sf-color-text-tertiary` | `#697386` | 辅助文本 |
| `--sf-color-text-disabled` | `#98A2B3` | 禁用文本 |
| `--sf-color-accent-primary` | `#4C6FFF` | 主强调色 |

| `--sf-color-focus-ring` | `#7C96FF` | 焦点描边 |

### 5.2.3 状态色

| Token | 建议值 | 用途 |
|------|--------|------|
| `--sf-color-success` | `#1F9D62` | 完成、恢复成功 |
| `--sf-color-success-soft` | `#EAF8F1` | 完成态背景 |
| `--sf-color-warning` | `#C9831B` | 接近截止、提醒 |
| `--sf-color-warning-soft` | `#FFF6E8` | 提醒态背景 |
| `--sf-color-danger` | `#D14343` | 删除、危险动作 |
| `--sf-color-danger-soft` | `#FDEEEE` | 危险态背景 |
| `--sf-color-info` | `#3A7AFE` | 信息提示 |
| `--sf-color-info-soft` | `#EEF4FF` | 信息背景 |

### 5.2.4 任务优先级色

优先级是高频信息，但不应做成强烈警报系统。

建议第一版采用“点状提示 + 轻量文字色”：

| 优先级 | 建议色 | 表达方式 |
|------|--------|----------|
| `P0` | `#D14343` | 红色小点 + 文字 |
| `P1` | `#C9831B` | 琥珀色小点 + 文字 |
| `P2` | `#4C6FFF` | 蓝色小点 + 文字 |
| `P3` | `#8A94A6` | 灰蓝色小点 + 文字 |

说明：

- 若后续优先级分层发生变化，只改 token 映射，不改组件结构
- 列表中优先级永远不应压过标题本身

## 5.3 字体系统

### 5.3.1 字体策略

StoneFlow 是 macOS 桌面产品，第一版建议优先使用系统体验更好的字体组合：

- 主字体：`SF Pro Text`
- 标题字体：`SF Pro Display`
- 等宽字体：`SF Mono`

如果工程上不方便直接使用系统字体别名，则降级为：

- `ui-sans-serif, -apple-system, BlinkMacSystemFont, "Helvetica Neue", sans-serif`
- 等宽：`ui-monospace, "SF Mono", "JetBrains Mono", monospace`

原因：

- 更贴合 macOS 桌面气质
- 比通用网页字体更稳
- 能支撑高密度界面而不显廉价

### 5.3.2 字号层级

| Token | 建议值 | 用途 |
|------|--------|------|
| `--sf-font-size-11` | `11px` | 辅助标记、元信息 |
| `--sf-font-size-12` | `12px` | 标签、Badge、二级说明 |
| `--sf-font-size-13` | `13px` | 列表正文、Sidebar 主要信息 |
| `--sf-font-size-14` | `14px` | 标准正文、输入框、Drawer 内容 |
| `--sf-font-size-16` | `16px` | 页面标题、小型模块标题 |
| `--sf-font-size-20` | `20px` | 页面主标题 |

### 5.3.3 字重策略

| Token | 建议值 | 用途 |
|------|--------|------|
| `--sf-font-weight-regular` | `400` | 正文 |
| `--sf-font-weight-medium` | `500` | 普通强调、列表标题 |
| `--sf-font-weight-semibold` | `600` | 模块标题、按钮文字 |

原则：

- 少用粗体换层级，多用留白和色彩关系换层级
- 标题不追求“重”，而追求“准”

---

## 5.4 间距系统

StoneFlow 第一版采用 4pt 基础栅格。

| Token | 值 |
|------|----|
| `--sf-space-1` | `4px` |
| `--sf-space-2` | `8px` |
| `--sf-space-3` | `12px` |
| `--sf-space-4` | `16px` |
| `--sf-space-5` | `20px` |
| `--sf-space-6` | `24px` |
| `--sf-space-8` | `32px` |
| `--sf-space-10` | `40px` |

推荐规则：

- 行内小组件：优先 `8px / 12px`
- 列表单元内边距：优先 `12px / 16px`
- 模块间距：优先 `16px / 24px`
- 页面主区块间距：优先 `24px / 32px`

---

## 5.5 圆角系统

StoneFlow 不应过圆，不做消费级卡片感。

| Token | 值 | 场景 |
|------|----|------|
| `--sf-radius-xs` | `6px` | Badge、小标签、小输入区 |
| `--sf-radius-sm` | `8px` | 列表项、按钮、轻面板 |
| `--sf-radius-md` | `10px` | Card、Drawer 内模块 |
| `--sf-radius-lg` | `12px` | Command 面板、较大容器 |
| `--sf-radius-xl` | `16px` | 极少数大浮层 |

原则：

- 默认以 `8px` 和 `10px` 为主
- 不建议在同一页面出现过多不同圆角层级

---

## 5.6 阴影与描边

### 5.6.1 阴影策略

StoneFlow 的层级主要靠边框和背景差，阴影只是补充。

| Token | 建议值 | 用途 |
|------|--------|------|
| `--sf-shadow-xs` | `0 1px 2px rgba(16, 24, 40, 0.04)` | 普通面板 |
| `--sf-shadow-sm` | `0 8px 24px rgba(16, 24, 40, 0.08)` | Command / Popover |
| `--sf-shadow-md` | `0 16px 40px rgba(16, 24, 40, 0.12)` | 大浮层、特殊强调 |

### 5.6.2 描边策略

- 大多数分层优先用 `1px` 边框解决
- 当前激活对象可通过左侧强调条、边框加深或弱色填充表达
- 不建议大量使用发光边框和重 ring

---

## 5.7 动效令牌

StoneFlow 的动效目标不是“炫”，而是“准确”。

| Token | 值 | 用途 |
|------|----|------|
| `--sf-duration-fast` | `120ms` | hover、press、切换高亮 |
| `--sf-duration-normal` | `180ms` | tabs、drawer 微过渡 |
| `--sf-duration-slow` | `240ms` | command 展开、列表完成反馈 |
| `--sf-ease-standard` | `cubic-bezier(0.2, 0.8, 0.2, 1)` | 默认过渡 |
| `--sf-ease-emphasis` | `cubic-bezier(0.16, 1, 0.3, 1)` | 明显但克制的入场 |

动效使用原则：

- 高频微反馈短而准
- 页面结构切换要干净，不拖泥带水
- 完成任务的反馈可以略长于普通 hover，但必须克制

## 6. 核心交互原则

## 6.1 Command 是产品入口，不是装饰弹窗

Command 必须承担三类能力：

- 快速创建任务
- 快速搜索任务 / 项目 / 页面
- 快速执行高频动作

Command 不是辅助功能，而是 StoneFlow 的主入口之一。

## 6.2 任务创建必须低摩擦

默认创建路径必须尽量短：

1. 全局唤起
2. 输入标题
3. 可选调整优先级 / 项目 / 标签 / 截止时间
4. 回车创建

其中默认约束：

- 新任务默认进入当前 Space 的 `Inbox`
- 默认状态为 `todo`
- 若用户在 Command 中直接指定 `Project`，该信息只作为预填归类信息，任务仍先进入 `Inbox`

这样可以同时满足两件事：

- 保持捕获链路统一
- 减少后续整理成本

## 6.3 聚合页服务执行，不服务归档

- `Focus`、`Upcoming`、`最近添加`、`高优先级` 都属于执行和回看视图
- 聚合页必须强调“筛选结果”感，而不是“另一个数据层”

## 6.4 Drawer 服务编辑，不服务跳页

- 任务详情优先在右侧 Drawer 完成
- 用户不应频繁进入整页详情再退回

## 6.5 列表扫描效率优先

- 任务列表的一屏信息密度要高
- 但每一行都必须保留足够留白，让眼睛能快速分块

## 7. Command 体验规范

## 7.1 角色定义

StoneFlow 的 Command 是：

- 全局唤起入口
- 搜索入口
- 快速创建入口
- 快速动作执行入口

它在 UX 上参考 `Raycast`，但在 UI 上应保持 `Linear` 式浅色精密面板感。

## 7.2 视觉形态

建议规格：

- 面板宽度：`720px - 800px`
- 顶部距窗口上缘：约 `10vh - 12vh`
- 面板背景：`--sf-color-bg-elevated`
- 边框：`1px solid --sf-color-border-subtle`
- 圆角：`--sf-radius-lg`
- 阴影：`--sf-shadow-sm`

整体感受应是：

- 干净
- 稳
- 精密
- 不厚重

## 7.3 结构分区

Command 面板建议拆成三层：

1. 输入区
2. 上下文参数区
3. 结果区

推荐结构：

```text
┌─────────────────────────────────────┐
│ 输入框 / 命令行                      │
│ 左：优先级  右：Project / Space      │
├─────────────────────────────────────┤
│ 分组结果列表                         │
│ 最近任务 / 项目 / 动作 / 搜索结果     │
└─────────────────────────────────────┘
```

## 7.4 默认行为

当用户直接输入自然语言时：

- 优先解释为“创建任务”

当用户输入带明显命令意图的前缀时：

- 进入动作模式或搜索模式

建议后续支持的命令式语义：

- 创建任务
- 搜索任务
- 打开项目
- 打开 Focus
- 打开 Inbox

具体命令语法暂不在本文件锁死，只定义交互方向。

## 7.5 键盘行为

必须支持：

- `↑ / ↓` 选择结果
- `Enter` 确认
- `Cmd/Ctrl + Enter` 执行次级动作
- `Tab` 切换可编辑参数
- `Esc` 关闭或逐级返回
- `Cmd/Ctrl + K` 全局唤起

## 7.6 创建任务时的参数布局

基于你当前已确认方向，第一版建议：

- 左侧：优先级选择
- 右侧：所属 Project 选择
- 状态默认：`todo`
- 标签：可选
- 截止时间：可选

说明：

- 这是高频创建路径，应尽量一屏完成
- 参数不宜默认全部展开
- 默认极简，展开后仍需保持轻量

## 7.7 结果列表样式

结果行建议统一为：

- 左侧图标或类型标识
- 中间主文本
- 右侧上下文信息
- hover / active 时出现弱强调背景

不建议：

- 每行都放大量彩色图标
- 每行都显示过多辅助字段

## 8. 主要页面与组件规格

## 8.1 App Shell

### 角色

- 承接 Window Chrome、Global Command Bar、Sidebar、Main、Drawer Overlay 的整体壳层结构

### 规范

- 应用背景使用 `--sf-color-bg-app`
- 顶部保留独立的窗口头部区域和全局 Command Bar
- Sidebar 与 Main 用细边界分开
- Drawer 默认隐藏
- Drawer 打开后从右侧覆盖进入，不挤压 Main 宽度
- Drawer 打开后 Main 仍保持可见
- Drawer 打开后允许叠加非常轻的背景遮罩，用于提示焦点已切到详情层

### 交互要求

- 切换 Space 时，Sidebar 内容重建，但 App Shell 骨架不闪烁
- Global Command Bar 始终处于稳定位置，不因页面切换变化
- 打开 Drawer 时主布局不重排
- Drawer 打开和关闭都应短促、干净，不制造厚重 modal 感

## 8.2 Space Tabs

### 角色

- Sidebar 顶部的顶级领域切换器

### 视觉要求

- 视觉接近轻量 segmented control
- 默认态低存在感
- 激活态通过背景块 + 文本强调表达

### 行为要求

- 切换应快速、干净
- 当前 Space 必须非常明确

## 8.3 Sidebar

### 角色

- 承接系统模块和项目树

### 结构

- Space Tabs
- Inbox
- Focus
- Projects List
- Trash

### 样式原则

- 信息密度高于网页常规 Sidebar
- 但不能堆成文件管理器
- 项目树层级表达靠缩进、字重和弱辅助线，不靠重色块

## 8.4 Focus 聚合页

### 角色

- 承载多个执行视图的统一容器

### 内部 Tabs

- Focus
- Upcoming
- 最近添加
- 高优先级

### 视觉要求

- Tabs 要轻，但激活态必须清楚
- 内容区要像“同一问题的不同切面”，而不是四个完全不同页面

## 8.5 Inbox 页面

### 角色

- 快速捕获后的整理区

### 关键设计点

- 顶部必须有清晰提示，强调“这里是过渡态”
- 每条任务支持快速归类
- 优先级、Project 等高频操作必须足够近

### 视觉语气

- 比普通列表更有“待整理”意味
- 但不能做成错误页或警报页

## 8.6 Project 页面

### 角色

- 长期任务归宿与执行容器

### 结构

- 顶部摘要区
- 按状态分组的任务列表

### 项目摘要区字段

- 名称
- 状态
- 备注
- 轻量进度
- 创建时间
- 更新时间

### 视觉要求

- 摘要区默认展开，可折叠
- 摘要区像“项目头部面板”，不是传统资料卡片

## 8.7 Task Row

### 角色

- 列表中的核心信息载体

### 第一版建议展示字段

- 标题
- 状态
- 备注摘要
- 轻量元信息
- 截止时间
- 优先级

### 视觉规范

- 行高紧凑但不压缩到难点
- 选中态、hover 态、完成态必须能快速区分
- Done 态允许降低对比度，但不能彻底灰掉看不见

### 完成反馈

- 勾选完成后出现明显但短促的完成反馈
- 可包含：
  - 勾选态切换
  - 文本淡出或划线
  - 行背景轻微闪过完成色

## 8.8 Task Drawer

### 角色

- Task 的主要查看与编辑空间

### 打开方式

- 默认隐藏
- 点击 Task Row 后从右侧覆盖进入
- 不挤压 Main 内容区
- 打开时允许叠加一层极轻遮罩

### 遮罩原则

- 遮罩是“降噪层”，不是“阻断层”
- 不使用重黑遮罩
- 遮罩只用于提示当前焦点切换到详情编辑态

### 建议结构

- 顶部：标题与主操作
- 主区：描述、字段、资源、历史
- 可折叠摘要区：创建时间、更新时间等元信息

### 第一版字段顺序建议

- 所属项目 / 子项目
- 资源
- 快捷操作
- 历史记录
- 创建时间 / 更新时间

### 视觉原则

- 结构清楚，段落分明
- 不做表单森林
- 不把每个字段都包成厚重卡片

## 8.9 Resource Attachment

### 第一版资源类型

- 文档链接
- 本地文件
- 本地文件夹

### 表达方式

- 以轻量资源块或列表项展示
- 支持一键打开
- 资源元信息只显示必要字段

不建议第一版做：

- 大型预览区
- 复杂附件管理器

## 8.10 Trash

### 角色

- 承接已删除 Task 和 Project

### 设计要求

- 删除对象类型必须清楚
- 恢复操作必须直接
- 恢复到原位需要有明确提示

### 视觉语气

- 应显得“可回退”，而不是“最终销毁”

## 9. 反馈系统

## 9.1 反馈层级

StoneFlow 第一版建议使用三层反馈：

- 行内反馈
- 页面局部反馈
- 全局 Toast / Notice

## 9.2 不同行为的反馈建议

| 行为 | 反馈方式 |
|------|----------|
| 创建任务 | 立即插入列表 / Toast 提示成功 |
| 完成任务 | 行内状态切换 + 短促强调动画 |
| 从 Inbox 归类 | 行消失或迁移提示 + 成功反馈 |
| 删除对象 | 行移出 + Toast + 可撤销 |
| 恢复对象 | Toast + 返回原位提示 |
| 打开 Drawer | 右侧覆盖滑入 + 极轻遮罩 + 主区保持稳定 |

## 9.3 完成感原则

你明确提出“完成 todo 的成就感”是理念之一，所以第一版必须保证：

- 勾选完成有明确反馈
- 不只是颜色变灰
- 但也不做夸张庆祝动画

推荐方向：

- 完成时出现短促的成功色扫过
- checkbox / status 图标有干净的切换动画
- 若任务位于 Focus，可在局部给出“已完成”完成感，而不是强打断式提示

---

## 10. 响应式与窗口适配

StoneFlow 第一版不做移动端，但必须适配不同桌面窗口宽度。

### 10.1 宽屏

- 保持顶部 Command Bar、Sidebar、Main 三段稳定
- Drawer 作为右侧覆盖层按需出现
- Main 允许更宽列表和更多字段

### 10.2 中等窗口

- Drawer 宽度收缩
- 列表辅助字段减少

### 10.3 较窄桌面窗口

- Drawer 保持覆盖式侧板
- Sidebar 可切换为折叠态

原则：

- 骨架变化要少
- 信息优先级变化要明显
- 不要为了响应式把产品做成网页后台感

---

## 11. 无障碍与可用性要求

第一版至少满足以下基线：

- 所有可交互元素必须有明确 focus 态
- Command 必须完整支持键盘导航
- Tabs、Drawer、Dialog、Menu 语义正确
- 文本与背景对比度足够
- 状态不只靠颜色表达

---

## 12. 与前端实现的映射约束

## 12.1 对 Tailwind 的约束

- 使用语义 token 驱动主题，而不是在组件里到处写裸色值
- 优先通过主题变量映射 `background / foreground / border / accent / muted`
- 尽量避免页面里散落大量一次性 arbitrary value

## 12.2 对 shadcn/ui 的约束

- shadcn/ui 只作为 primitive 和无障碍底座
- 不直接照搬默认视觉
- 所有高频组件都需要经过 StoneFlow 自己的二次封装

重点包括：

- Button
- Tabs
- Command
- Sheet / Drawer
- Badge
- Tooltip
- Dropdown Menu

## 12.3 对组件架构的约束

- 业务组件优先放在 `features/*/ui`
- 真正可复用的基础组件放在 `shared/ui`
- 不通过不断叠加布尔属性制造“万能组件”
- 优先采用组合式结构表达复杂组件

---

## 13. 首版待确认事项

以下内容暂未最终锁死：

- 优先级等级是否固定为 `P0-P3`
- Focus 是否长期保留“高优先级”独立 tab
- Focus 后续是否支持多套自定义视图模板
- Project 状态集合的最终定义
- Drawer 内摘要区的最终视觉形式
- 项目树是否在第一版就暴露子项目的全部交互能力

---

## 14. 首版落地建议

如果按实现顺序推进，建议优先完成：

1. 主题变量与设计令牌
2. App Shell 骨架
3. Sidebar / Space Tabs
4. Command
5. Task Row
6. Drawer
7. Focus / Inbox / Project 三个核心页面

原因：

- 这几块共同决定 StoneFlow 的第一印象和核心效率体验
- 如果先堆业务功能，再回头补设计系统，后面会反复返工

---

## 15. 一句话设计结论

StoneFlow 第一版的设计方向应当是：

> 用 Linear 式浅色、秩序和专业感承载 Raycast 式命令效率，把任务管理做成一个干净、快速、可信赖的个人执行工作台。
