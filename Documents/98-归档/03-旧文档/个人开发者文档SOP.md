> 适用范围：个人独立开发者，主导从零到上线的完整产品周期。
> 设计目标：文档数量足够但不冗余，每个文档职责单一，可拆分给 AI 使用，可随版本演进。

## 一、文档清单总览

| 编号    | 文档名称    | 层级  | 核心问题                | 写作时机        |
| ----- | ------- | --- | ------------------- | ----------- |
| INDEX | 文档索引    | 入口  | 这套文档体系是什么，去哪找什么     | 建文档体系时第一个写  |
| P1    | 产品内核    | 常青层 | 我在做什么，为谁做，做到什么程度    | 启动项目第一天     |
| P2    | 产品蓝图    | 常青层 | 产品长什么样，功能边界在哪       | P1 确定后      |
| D1    | 领域与数据模型 | 常青层 | 核心对象是什么，数据如何定义和存储   | P2 确定后      |
| T1    | 系统设计    | 常青层 | 用什么技术，怎么组织代码，关键架构决策 | D1 确定后      |
| U1    | 设计系统    | 常青层 | 视觉交互规范是什么，组件怎么定义    | 开始写 UI 时    |
| E{n}  | 阶段执行文档  | 执行层 | 这个版本做什么，怎么验收        | 每个版本启动时     |

**常青层**：跨版本稳定，不随迭代销毁，只持续演进。
**执行层**：版本专属，完成后归档锁定，不再修改。

## 二、为什么是这 7 类文档

### 2.1 设计原则

这套文档体系基于一个核心原则：**每个文档回答一个且只回答一个问题，且只有这个文档回答这个问题。**

如果你发现两个文档都在描述同一件事，说明职责划分出了问题。如果你不知道某个信息该去哪个文档找，说明文档边界不清晰。

### 2.2 为什么需要 INDEX

个人开发者很容易在文档多了之后迷失：打开一个文档，发现自己要找的东西不在这里，但也不知道去哪里找。INDEX 解决的是**导航问题**，不是内容问题。

INDEX 也是给 AI 的入口文件。每次开启新的 AI 会话，先丢 INDEX，再按需丢具体文档。

### 2.3 为什么 P1 和 P2 要分开

P1（产品内核）回答的是"为什么做这个产品"，P2（产品蓝图）回答的是"产品具体长什么样"。

这两件事的稳定性不同。P1 定下来之后几乎不变；P2 会随着你对产品理解的加深而持续调整。如果合并，P2 的频繁改动会让 P1 的核心定义变得不稳定，你很快会不清楚自己最初的产品主张是什么。

### 2.4 为什么 D1 和 T1 要分开

D1（领域模型）描述的是**业务语言**：用户、文档、版本、权限——这些概念在产品层面成立，与技术无关。T1（系统设计）描述的是**技术语言**：SQLite、IndexedDB、状态机、模块边界。

分开的好处是：当你换技术栈时，D1 不需要动；当你调整产品概念时，T1 不需要动。

### 2.5 为什么执行文档要独立

每个版本的执行文档（任务、里程碑、验收标准）完成后就应该归档锁定。你不应该回过头去修改已完成版本的执行文档。

如果把执行内容混进常青层，你永远不知道哪些是当前有效的，哪些是历史的。

### 2.6 为什么 X1 要单独存在

决策和结论是两件事。P1、T1 记录的是结论；X1 记录的是决策过程——当时面对哪些选项，为什么选了这个，为什么不选那个。

六个月后你回来读代码，发现一个奇怪的架构选择，X1 应该能告诉你当时的原因。没有 X1，你只能猜。

## 三、各文档详解

### INDEX · 文档索引

**回答的问题**：这套文档体系是什么，每个文档在哪里，去哪里找什么信息。

**什么时候写**：建立文档体系的第一天。此后每次新增文档时更新。

**给 AI 用的方式**：每次新会话的第一条消息附上 INDEX，让 AI 理解文档全貌，再按需索取具体文档。

**写什么**：
- 项目名称和一句话描述
- 当前活跃版本
- 每个文档的路径、名称、一句话说明它回答什么问题
- 文档最后更新时间（可选，有助于判断文档新鲜度）

**不写什么**：不写内容摘要，不重复各文档的具体内容。INDEX 是目录，不是摘要。

**大纲模板**：

```markdown
# [项目名称] 文档索引

> [一句话描述这个产品]
> 当前版本：V1 · 最后更新：YYYY-MM-DD

## 文档清单

| 文档 | 路径 | 回答的问题 |
|------|------|------------|
| P1 产品内核 | /P1-产品内核.md | 我在做什么，为谁做，边界在哪 |
| P2 产品蓝图 | /P2-产品蓝图.md | 产品形态、功能模块、用户路径 |
| D1 领域与数据模型 | /D1-领域与数据模型.md | 核心实体定义、数据结构、存储方案 |
| T1 系统设计 | /T1-系统设计.md | 技术栈、架构边界、关键技术决策 |
| U1 设计系统 | /U1-设计系统.md | 视觉规范、组件、交互原则 |
| E1 V1执行文档 | /执行层/E1-V1执行.md | V1 做什么、里程碑、验收标准 |
| X1 决策日志 | /X1-决策日志.md | 重要决策的背景、选项、原因 |

## AI 使用指引

- 理解产品全貌：P1 + P2
- 讨论数据结构：D1
- 讨论技术方案：T1
- 讨论 UI/UX：P2 + U1
- 当前版本开发任务：E1
- 查阅历史决策：X1
```

### P1 · 产品内核

**回答的问题**：我在做什么，为谁做，这个产品的边界在哪里。

**什么时候写**：启动项目第一天，在写任何代码之前。

**稳定性**：高。P1 一旦确定，除非产品发生根本性转向，否则不应频繁改动。如果你发现自己经常在改 P1，说明产品方向还没想清楚，应该先停下来思考，而不是继续写代码。

**写什么**：
- **一句话定义**：用一句话说清楚这个产品是什么。不能用"平台"、"工具"、"解决方案"这类模糊词。要能回答"它帮谁做了什么事"。
- **目标用户**：具体描述你在为谁做这个产品。不是"所有人"，而是一个具体的人群画像。
- **北极星指标**：一个数字，当这个数字健康时，你确信产品在正确方向上。
- **当前版本目标**：这个版本结束时，你希望达到什么状态。要可验证，不能是"做得更好"。
- **不做什么**：明确列出当前版本有意不做的事。这比列功能更重要，因为它防止范围蔓延。
- **当前最大风险**：你认为最可能导致产品失败的一件事是什么。

**不写什么**：不写功能列表（那是 P2 的事），不写技术选型（那是 T1 的事），不写用户故事（那是 E{n} 的事）。

**大纲模板**：

```markdown
# P1 · 产品内核

> 最后更新：YYYY-MM-DD · 版本：V1

## 一句话定义

[产品名] 是一个帮助 [目标用户] [完成什么核心任务] 的 [产品形态]。

示例："StoneDraw 是一个帮助独立创作者在本地管理和绘制的桌面应用。"

## 目标用户

**主要用户**：[具体描述，包括他们现在用什么工具、面临什么问题]

**不是我们的用户**：[明确排除的人群，防止产品方向被边缘需求拉偏]

## 北极星指标

[指标名称]：[定义和计算方式]

为什么选这个指标：[说明它为什么能代表产品核心价值]

## 当前版本目标（V1）

V1 结束时，我们应该能验证：
- [ ] [可验证的目标 1]
- [ ] [可验证的目标 2]

## 不做什么（V1）

- [有意不做的功能或方向 1]
- [有意不做的功能或方向 2]

每条都要注明原因：是"V2 再做"还是"永远不做"。

## 当前最大风险

[描述你认为最可能导致失败的一件事，以及你打算怎么应对或验证它]
```

### P2 · 产品蓝图

**回答的问题**：产品具体长什么样，有哪些功能模块，用户怎么使用它。

**什么时候写**：P1 确定后，开始写代码前。

**稳定性**：中。P2 会随着产品理解加深而演进，但每次修改都应该能追溯到 P1 的某个变化或用户反馈。

**写什么**：
- **核心功能模块**：产品由哪些主要功能组成，每个模块的职责边界是什么。

### D1 · 领域与数据模型

**回答的问题**：这个产品里有哪些核心概念，它们的数据结构是什么，它们之间什么关系，如何存储。

**什么时候写**：P2 确定后，开始写数据层代码前。

**稳定性**：中低。核心实体相对稳定，但字段和关系会随版本演进。版本差异用标注区分，不拆文档。

**关于版本标注的约定**：对于在不同版本才引入的字段或关系，在文档内用 `[V1]`、`[V2]`、`[V3]` 标注，而不是把文档拆成三份。这样你能在一个地方看到数据模型的完整演进路径。

**写什么**：
- **核心实体列表**：产品中有哪些主要的业务对象。
- **实体字段定义**：每个实体有哪些字段，字段类型，是否必填，默认值。
- **实体关系**：实体之间如何关联，一对一/一对多/多对多。
- **生命周期**：实体如何被创建、修改、归档、删除。
- **本地存储模型**：数据在本地如何持久化（文件格式、数据库方案）。
- **同步策略**（V2+ 标注）：数据如何在多端同步，冲突如何处理。

**不写什么**：不写技术实现细节（那是 T1 的事），不写 UI 交互（那是 P2 的事）。D1 描述的是业务语言，不是代码语言。

### T1 · 系统设计

**回答的问题**：用什么技术，代码如何组织，关键的架构决策是什么。

**什么时候写**：D1 确定后，写主体代码前。

**稳定性**：中。技术栈选定后相对稳定，但模块边界和数据流会随产品复杂度增长而演进。

**写什么**：
- **技术栈**：列出所有主要的框架、库、工具，以及选择它们的原因。

- **模块划分**：代码层面的目录结构和分层逻辑。
- **状态管理方案**：应用状态如何管理，使用什么模式或库。

- **性能与安全**：关键的性能约束和安全考虑。

### U1 · 设计系统

**回答的问题**：视觉交互规范是什么，如何保证 UI 的一致性。

**什么时候写**：开始写 UI 组件之前。不需要在项目第一天就写完，可以边做边完善，但第一个组件写出来之前要定好基础规范（色彩、字体、间距）。

**稳定性**：中高。基础规范（色彩系统、字体规范、间距系统）一旦确定就很少改；组件库会随产品功能增加而扩充。

**写什么**：
- **视觉规范**：色彩系统、字体规范、间距系统、圆角规范。
- **核心组件库**：关键 UI 组件的规格定义（不是代码，是规格）。
- **交互原则**：产品的交互设计原则，比如"操作可撤销"、"即时反馈"。

- **响应式规则**：如果适用，窗口尺寸的适配断点。

### E{n} · 阶段执行文档

**回答的问题**：这个版本具体做什么，任务怎么拆，怎么验收。

**什么时候写**：每个版本启动时写，完成后归档不再修改。

**命名约定**：E1 对应 V1，E2 对应 V2，以此类推。E3 等到 E2 完成后再写，不提前写。

**关于任务状态（now/next/done）的处理**：任务状态不写进这个文档。这个文档定义"这个版本要做什么和怎么验收"，任务状态放在 GitHub Projects、Notion 看板或者一个独立的 TODO.md 文件里。原因是：任务状态高频变动，如果写进文档，文档永远是过时的；里程碑和验收标准是相对稳定的承诺，应该被记录和追溯。

**写什么**：
- **版本目标**：这个版本结束时，产品应该处于什么状态。
- **功能范围**：明确列出这个版本包含什么，不包含什么。
- **里程碑**：将版本分成 2-4 个阶段，每个阶段的完成标志。
- **任务拆解**：里程碑下的具体开发任务，粒度到"能在一天内完成"。
- **验收标准**：如何判断这个版本可以发布，每条标准可测试。
- **已知风险**：启动时已知的风险项和应对预案。

**不写什么**：不写技术实现方案（那是 T1 的事），不写任务的完成状态（那是看板的事），不写下个版本的规划（那是下个版本的执行文档的事）。


### X1 · 决策日志（ADR）

**回答的问题**：为什么这么做，当时面对哪些选项，为什么没选其他的。

**什么时候写**：每次做出重要决策后，在 24 小时内记录。不需要等到版本结束时再补写——那时你已经记不清当时的思考了。

**什么算"重要决策"**：
- 技术栈选型
- 架构模式选择
- 数据模型的重大改动
- 明确放弃某个功能方向的决定
- 对产品定位或用户群的调整

**什么不算**：日常的代码实现细节，命名规范，小的 UI 调整。

**格式约定**：每条决策一个独立条目，时间倒序排列（最新的在最上面）。用 `ADR-XXX` 编号，方便在其他文档中引用（如在 T1 中写"技术栈选择见 ADR-003"）。

**写什么（每条条目）**：
- 背景：当时面临的情况和需要做的决定
- 决策：最终选了什么
- 备选方案：考虑过哪些选项
- 为什么不选：每个备选方案被否决的原因
- 影响范围：这个决策影响了哪些文档、哪些代码

**不写什么**：不写决策的实现过程，不写实现遇到的问题（那是注释和提交信息的事）。

**大纲模板**：

```markdown

> 排序：时间倒序，最新在最上
```

## 四、如何使用这套系统

### 4.1 从零启动一个新项目

按以下顺序写文档。每个文档写到"够用"就停，不追求完美——文档是为了帮你思考和开发，不是要交作业。

```JSON
第 1 步
└── 建文件夹结构
└── 写 P1（产品内核）
    ↓ 想清楚"做什么、为谁做、边界在哪"之前不要往下走

第 2 步
└── 写 P2（产品蓝图）
    ↓ 至少把核心用户路径和信息架构想清楚

第 3 步
└── 写 D1（领域与数据模型）
    ↓ 先写 V1 部分，V2/V3 的字段先空着或标注[V2 待定]

第 4 步
└── 写 T1（系统设计）
    ↓ 技术栈选型、模块划分、数据流想清楚

第 5 步
└── 写 E1（V1 执行文档）
    ↓ 明确里程碑和验收标准后才开始写代码

开始写 UI 之前
└── 写 U1（设计系统）
    至少定好色彩系统和字体规范

随时
└── 更新 X1（决策日志）
    每次重要决策后 24 小时内记录
    
最后
└── 建 INDEX.md，把所有文档登记进去
```

**一个重要原则**：P1 没想清楚，不要写 P2。P2 没想清楚，不要写 D1。这个顺序不是形式，是因为后面的文档依赖前面的结论。如果你发现写 D1 的时候不断要回去改 P1，说明 P1 还没想清楚。

### 4.2 日常开发中使用文档

**开启一个新的 AI 会话时**：
1. 先发 INDEX.md，告诉 AI 文档体系的全貌
2. 根据要做的事，发相关的具体文档
3. 例：讨论新功能 → 发 P1 + P2；讨论数据库设计 → 发 D1；讨论技术方案 → 发 T1

**开始一个新功能开发任务时**：
1. 查 E1 确认任务在当前版本范围内
2. 查 P2 了解功能的用户路径
3. 查 D1 了解涉及的实体
4. 查 T1 了解涉及的模块边界

**做了重要决策时**：
- 立即在 X1 新增一条 ADR 条目
- 如果决策影响了某个文档的内容，同时更新那个文档
- 在被影响的文档里加注引用（如"见 ADR-005"）

### 4.3 版本演进：从 V1 到 V2

**V1 完成时**：
1. 将 E1 状态标记为"已完成"，填写实际完成日期
2. 归档 E1（移至 `/执行层/archive/` 文件夹，或在文件名加前缀 `[DONE]`）
3. 回顾 P1，确认北极星指标和产品方向是否需要更新
4. 更新 INDEX.md 的"当前版本"字段

**V2 启动时**：
1. 新建 E2 文档，定义 V2 的范围、里程碑、验收标准
2. 更新 D1 中标注了 `[V2]` 的部分，将其从"待实现"改为具体的字段定义
3. 更新 T1 中 V2 引入的新架构变化
4. 如果 V2 涉及 P1/P2 的变化，更新对应文档并在 X1 记录决策

**关于 D1 和 T1 的版本演进**：
- 不要为每个版本创建新的 D1/T1 文件
- 在同一个文件内，用 `[V1]`、`[V2]` 标注区分
- 当 V2 实现了某个 `[V2]` 标注的内容，把标注改成具体的描述
- 这样做的好处是：你在一个文档里能看到完整的演进历史

**判断什么时候需要更新常青层文档**：

| 发生的事 | 需要更新的文档 |
|----------|---------------|
| 新版本改变了产品定位 | P1, 同时在 X1 记录决策 |
| 新版本增加了主要功能模块 | P2 |
| 新版本引入了新的数据实体或字段 | D1 |
| 新版本改变了技术架构或引入新依赖 | T1, 在 X1 记录决策 |
| 新版本引入了新的设计规范 | U1 |

### 4.4 给 AI 提供上下文的最佳实践

**原则**：给 AI 的上下文要精准，不要"以防万一"地全部丢进去。上下文越多，AI 越容易被不相关的内容干扰。

**按任务类型选择文档**：

| 任务类型 | 推荐发送的文档 |
|----------|---------------|
| 讨论产品方向或功能取舍 | INDEX + P1 + P2 |
| 设计数据库 schema | D1 |
| 讨论技术架构 | T1 + D1（仅实体部分）|
| 实现某个具体功能 | P2（相关用户路径）+ D1（相关实体）+ T1（相关模块）|
| UI 组件开发 | U1 + P2（相关页面部分）|
| 规划版本任务 | P1 + P2 + E{n}（当前版本）|
| 回顾某个历史决策 | X1（相关 ADR 条目）|

**一个好习惯**：在每次 AI 会话的开头，用一句话说清楚"这次要做什么"，然后附上相关文档。不要让 AI 去猜你的目标。

## 六、常见问题

**Q：文档写到多长算合适？**

每个文档有自己的"够用"标准：P1 超过两页说明你没想清楚；D1 和 T1 可以长一些，但如果你发现某个章节已经在描述实现细节，说明该停了。总原则是：文档应该让你（和 AI）能在 5 分钟内理解这个维度的全貌。

**Q：文档过时了怎么办？**

发现文档和现实不符，立刻更新，不要等"有时间了再更新"。更新文档的时候顺手在 X1 记一条决策，说明为什么现实偏离了文档的描述。

**Q：两个文档之间的内容有重叠怎么办？**

这通常意味着职责边界有问题。回到"每个文档回答一个且只回答一个问题"的原则，判断这个内容本质上在回答哪个问题，然后把它移到正确的文档，另一个文档改成引用。

**Q：U1（设计系统）真的需要吗？如果只是自己用呢？**

即使是个人项目，U1 的价值在于让你做 UI 决策时有依据，而不是每次都重新想。你不需要写得很细，但至少要把色彩系统和字体规范定下来——这两个决策一旦混乱，后期改起来非常痛苦。

**Q：执行文档完成后真的要"锁定"不能改吗？**

是的。如果你发现 V1 的执行文档需要修改，通常意味着你在用 V2 的视角重新解读 V1 的决策。正确的做法是：在 V2 的执行文档里说明"V2 在 V1 基础上调整了什么"，而不是回头修改 V1 的记录。这样你保留了完整的产品演进历史。
