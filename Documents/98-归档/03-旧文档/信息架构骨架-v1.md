## 1. 产品定位

StoneFlow 是一个以极速捕获为入口、以清晰整理和持续执行为目标的 macOS 个人任务系统。

它的核心不是"记一条待办"，而是：

- 低摩擦地把任务收入系统
- 快速把任务整理到正确位置
- 用聚合视图驱动日常执行
- 用专业、顺手、有反馈感的交互支撑长期使用

---

## 2. 顶层结构

StoneFlow 第一版信息架构采用以下顶层结构：

1. `Space Tabs`
2. `Sidebar`
3. `Main Content`
4. `Task Drawer`

对应关系如下：

- 顶部切换不同 `Space`
- 左侧 `Sidebar` 展示当前 `Space` 下的系统模块与项目树
- 中间 `Main Content` 展示当前页面的任务列表或项目内容
- 右侧 `Task Drawer` 展示任务详情

---

## 3. 顶层对象模型

### 3.1 Space

`Space` 是顶级领域容器。

第一版典型例子：

- 工作
- 学习
- 生活

规则：

- 每个 `Project` 必须归属于某个 `Space`
- `Inbox` 也归属于某个 `Space`
- `Focus` 里的视图内容基于当前 `Space` 生效

### 3.2 Project

`Project` 是 `Space` 下的任务容器。

当前定义偏向：

- 第一版以"容器"为主
- 但允许带有轻量执行语义

第一版字段：

- 名称
- 状态
- 备注
- 可选截止时间
- 创建时间
- 更新时间

派生字段：

- 进度
	- 由任务完成情况计算，不单独存储

层级规则：

- `Project` 必须属于某个 `Space`
- 第一版支持 `一层子项目`
- 暂不支持无限层级

### 3.3 Task

`Task` 是最小执行单元。

第一版核心字段：

- 标题
- 状态
- 优先级
- 备注
- 标签
- 截止时间

第一版状态：

- `todo`
- `done`

补充字段：

- 所属 Project
- 所属子项目
- 创建时间
- 更新时间
- 资源列表
- 历史记录

### 3.4 Inbox

`Inbox` 是当前 `Space` 下的特殊系统模块。

它的定位不是状态，而是过渡位置。

特点：

- 看起来像项目
- 但不是普通 `Project`
- 不能有子项目
- 不适合长期存放任务
- 核心职责是整理，而不是长期管理

任务进入 Inbox 后，离开条件至少包括：

- 已设置优先级
- 已设置所属 Project
- 状态为 `todo`

可选但非强制字段：

- 标签
- 截止时间

### 3.5 Focus

`Focus` 是聚合视图容器。

它不是一个单独视图，而是一组视图的承载页。

第一版定位：

- 承载多种规则视图
- 用 tabs 切换不同聚合结果

当前确定的思路：

- 第一版 `Focus` 默认主页更适合作为"手动 pin 的任务页"
- 其他视图放在 `Focus` 内部 tabs 中

### 3.6 Trash

`Trash` 是回收站模块。

第一版定位：

- 承接已删除的 `Project`
- 承接已删除的 `Task`

当前仍待继续明确：

- 是否支持恢复
- 恢复粒度与交互方式

## 4. Sidebar 结构

当前确认的 Sidebar 第一版骨架如下：

1. `Space Tabs`
2. `Inbox`
3. `Focus`
4. `Projects List`
5. `Trash`

展开后可理解为：

```text
Space Tabs
  工作 | 学习 | 生活

Current Space Sidebar
  Inbox
  Focus
  Projects
    Project A
      Subproject A-1
    Project B
    Project C
  Trash
```

说明：

- `Inbox` 是系统模块
- `Focus` 是聚合视图入口
- `Trash` 是系统模块，位置放在 `Projects List` 下方
- `Projects List` 展示当前 Space 下全部项目树
- `Projects List` 第一版默认先按名称排序

---

## 5. Focus 页面模型

`Focus` 不是单一页面，而是一个聚合容器页。

### 5.1 第一版目标

让用户在一个地方切换不同的执行视图，而不是把所有视图都摊在 Sidebar 里。

### 5.2 第一版建议 Tabs

根据当前讨论，第一版优先考虑：

1. `Focus`
2. `Upcoming`
3. `最近添加`
4. `高优先级`

### 5.3 各 Tab 的初步语义

#### Focus

- 第一版先作为"手动 pin 的任务集合"
- 后续可扩展：
	- 今日到期
	- 高优先级
	- AI 推荐

#### Upcoming

- 展示带明确 deadline 的未来任务
- 第一版主方式按截止日期组织

#### 最近添加

- 按创建时间回看最近捕获的任务

#### 高优先级

- 第一版先作为独立 tab 保留
- 默认只看最高优先级任务
- 后续继续观察它与 `Focus` 的重叠程度

### 5.4 视图系统原则

- 这些页面本质上都是视图
- 同一个任务可以同时出现在多个视图中
- 第一版允许视图保存：
	- 筛选
	- 排序
	- 分组

## 6. Project 页面模型

### 6.1 页面职责

`Project` 页负责展示该项目下的任务集合。

它不是单纯详情页，而是任务管理页。

### 6.2 第一版默认视图

第一版默认采用：

- `按状态分组的列表`

不优先：

- 纯列表
- 看板

这两个可后续扩展。

### 6.3 页面结构

推荐结构：

1. `Project Header`
2. `可折叠摘要区`
3. `任务分组列表`
4. `Task Drawer`

### 6.4 摘要区字段

第一版摘要区建议包含：

- 名称
- 状态
- 备注
- 轻量进度
- 创建时间
- 更新时间

摘要区应支持：

- 第一版默认展开
- 可折叠

---

## 7. Task Drawer 模型

### 7.1 打开方式

- 在 `Project` 页中点击任务
- 右侧打开 `Drawer`

### 7.2 第一层信息

第一层显示最刚需字段：

- 标题
- 状态
- 优先级
- 备注
- 标签
- 截止时间
- 创建时间
- 更新时间

### 7.3 第二层信息

第二层优先顺序：

1. 所属项目 / 子项目
2. 资源
3. 快捷操作
4. 历史记录

说明：

- 第一层解决"立刻看懂和快速编辑"
- 第二层解决"归属、上下文、操作与追踪"

---

## 8. Inbox 页面模型

### 8.1 页面职责

Inbox 是整理页。

它不是"长期放任务的地方"，而是"把任务推进到系统里正确位置的地方"。

### 8.2 第一版行为原则

- 顶部必须有明显提示
	- 例如：还有多少条待整理
- 每条任务必须有快捷整理入口
- 任务只有补齐必选信息后才能离开 Inbox

### 8.3 必选信息

第一版至少包括：

- 优先级
- 所属 Project
- 状态 `todo`

可选：

- 标签
- 截止时间

### 8.4 与普通 Project 的区别

- 不能有子项目
- 不强调项目级语义
- 强调清理引导
- 强调快速归类

---

## 9. 资源模型 V0

第一版优先支持的资源类型：

1. 文档链接
2. 本地文件
3. 本地文件夹

交互要求：

- 必须支持一键打开

第一版 UI 建议：

- 在 Drawer 第二层设置 `Resources` 区块
- 资源按紧凑列表展示
- 每行至少有：
	- 类型图标
	- 名称
	- 来源或路径
	- 打开动作

## 10. 第一版主导航摘要

StoneFlow 第一版主导航结构可以先定义为：

```text
Space Tabs
  当前 Space
    Inbox
    Focus
      - Focus
      - Upcoming
      - 最近添加
      - 高优先级
    Projects List
      - Project
      - Subproject
```

## 11. 当前信息架构判断

到目前为止，StoneFlow 更接近：

- 一个有 `Linear` 式专业组织能力的个人任务系统
- 一个有 `Raycast` 式低摩擦入口的桌面工具
- 一个不满足于"简单清单"，而是强调整理和执行流转的系统

它已经不是传统意义上的极简 TODO 了。

它更像：

`一个面向个人的、带有专业信息架构和强执行视图的任务操作系统。`

---

## 12. 下一步建议

基于当前骨架，下一轮最值得继续收口的是：

1. `Focus` 内部 tabs 最终集合
2. `Trash` 的恢复机制
3. `Focus` 与 `高优先级` 的长期边界
4. `Task` 状态是否继续保持两态
5. 第一版 MVP 范围
