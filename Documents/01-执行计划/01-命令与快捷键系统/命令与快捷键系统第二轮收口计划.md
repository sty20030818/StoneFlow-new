# StoneFlow 命令与快捷键系统第二轮收口计划

> 创建日期：2026-05-16
> 目标：基于当前实现清单和 v2 使用指南，分阶段补齐多选、上下文 Command Menu、Row 属性修改快捷键、命令补全和必要基础设施。

---

## 1. 文档定位

这份文档不是重写第一轮命令系统，而是在现有架构已经具备以下基础后，继续做第二轮收口：

- `src/features/command` 已经承载 Command Registry、Keybinding、CommandRuntime、Command Menu、Shortcut Help、Chord Hint；
- `src/features/task/shortcuts` 已经承载 Row 层快捷键和 row target 解析；
- `src/shared/ui/shortcut-menu` 已经承载 Dropdown 数字选择；
- `src-tauri/crates/helper-app` 已经承载系统级 `Option+Space` 和 Quick Create；
- 当前缺口已经记录在《StoneFlow 命令与快捷键系统实现清单》第 10 节。

第二轮目标不是“把所有 v2 想法一次性做完”，而是把会明显影响键盘主链体验的能力按依赖顺序收口，避免散装监听、重复状态、过早抽象和 UI 行为分裂。

---

## 2. 核心结论

### 2.1 推荐推进顺序

```txt
选择状态与 Esc
-> Command Context 统一选择上下文
-> Command Menu 选中对象展示与上下文命令排序
-> P / S / D scoped picker
-> Shift+↑/↓ 范围多选与批量命令
-> M / F / General / Layout 等快捷键补齐
-> command-only 命令补齐
-> Tauri / Rust 系统命令补齐
-> 最终验收与文档同步
```

### 2.2 最重要的取舍

1. 多选状态应成为 Command Runtime 的上下文，而不是只属于底部 `BulkActionBar`。
2. 底部多选操作栏保持当前极简形态，不扩展成一排命令按钮；最右侧按钮和 `Cmd/Ctrl+K` 都打开同一个 `CommandMenu`，只是上下文不同。
3. P / S / D 不建议继续模拟点击 Row 内 dropdown trigger；快捷键应打开 Command Menu 的 scoped picker，让键盘路径和命令体系统一。
4. `Shift+↑/↓` 范围多选必须依赖 keyboard focus / anchor，不应该用 hover 推断范围。
5. 全量命令补齐要先补 CommandId 和 metadata，再接真实业务；不能为了“列表完整”写假执行。
6. Tauri/Rust 能力只处理系统边界，例如打开数据文件夹、导入导出、备份；应用内 Row 操作和 Command Menu 不下沉到 Helper。

## 3. 已确认需求

### 3.1 多选与取消

- 支持 `Shift+↑/↓` 连续多选。
- 支持 `Esc` 取消多选状态。
- 多选后底部 active bar 仍然存在。
- 多选后按 `Cmd/Ctrl+K` 打开的 Command Menu 必须知道当前选中的任务或项目。
- 多选后底部 active bar 不承载完整命令面，只保留当前形态；最右侧按钮打开同一个 Command Menu。
- 多选后的 Command Menu 需要有一个“批量操作”board / 分组，集中展示所有可对当前 selection 执行的命令。

### 3.2 Command Menu 展示选中对象

- Command Menu 打开时，如果当前有选中对象，输入框下方显示一排 outline 按钮。
- outline 按钮展示当前选中的任务或项目。
- 这些按钮不只是装饰，应作为当前 command context 的可见表达。
- 多选任务和多选项目都需要支持，但任务优先。

### 3.3 Row 属性修改快捷键

- `P` 打开优先级选择。
- `S` 打开状态选择。
- `D` 打开日期选择。
- 这三个快捷键不再优先走 Row 内 dropdown 点击模拟，而是打开 Command Menu scoped picker。
- scoped picker 复用现有 Command Menu 容器，不新建第二套弹窗。

### 3.4 命令补全

- 最终目标是把清单里的命令补全。
- 补全包括：CommandId、metadata、keybinding、visible/enabled、disabled reason、真实动作、测试和文档。
- 但低频、危险、依赖后期模型的命令可以先 command-only 或 disabled，不强行绑定默认快捷键。

---

## 4. 关键假设

1. 当前阶段仍以任务为第一主链，项目多选和项目命令可以复用通用选择模型，但不要为了项目提前做过度抽象。
2. `CommandMenu` 继续作为统一弹窗容器，后续扩展 mode，而不是新增 `PriorityPickerDialog`、`StatusPickerDialog`、`DatePickerDialog`。
3. 任务属性修改可以先支持“对当前 row target 或当前 selection 生效”，不需要先做复杂的混合对象选择。
4. `Esc` 先解决 Command Menu / Dropdown / Modal / 多选清空 / 路由返回的层级顺序，再考虑更复杂的撤销语义。
5. Space 相关命令、收藏、模板、活动记录、导入导出等后期能力，不进入高频主链。

---

## 5. 总体架构方案

### 5.1 选择上下文

当前多个页面各自调用 `useTaskSelection(taskIds)`，这能工作，但 Command Menu 很难全局读取当前选中对象。第二轮建议引入一个轻量选择上下文。

推荐最小结构：

```txt
src/features/selection/
  model/
    selection.types.ts
    useEntitySelection.ts
    SelectionContextProvider.tsx
    selectionContext.ts
```

第一阶段不需要把所有页面都重构成复杂通用系统。可以先做到：

- 保留 `useTaskSelection` 对外 API；
- 内部逐步接入 `useEntitySelection`；
- 当前页面通过 Provider 暴露 selection snapshot；
- Command Runtime 从 snapshot 读取 `selection.ids / type / selectedItems`。

不建议一开始就做：

- 支持任意实体的高级选择 DSL；
- 跨页面持久多选；
- 自定义 selection policy 插件；
- 跨 Space 混合选择。

### 5.2 Command Context 扩展

当前 `CommandContext.selection` 只有 ids 和类型信息，不足以直接渲染 Command Menu 中的选中对象标签。

建议新增 UI 友好的 selected entities snapshot：

```ts
type CommandSelectedEntity = {
  id: string
  type: 'task' | 'project' | 'view'
  title: string
  subtitle?: string
  status?: string
  priority?: string
}
```

扩展点：

- `CommandSelectionContext.entities: CommandSelectedEntity[]`
- `CommandSelectionContext.primaryEntity?: CommandSelectedEntity`
- `CommandSelectionContext.source: 'none' | 'row' | 'selection' | 'bulk-bar' | 'command-menu'`

这样 Command Menu 不需要反查 store，也不会把任务 store、项目 store 硬塞进 UI 组件。

### 5.3 Command Menu 组合方式

按 React 组合实践，避免给 `CommandMenu` 加大量布尔 props。推荐拆成明确子组件：

```txt
CommandMenu
  CommandMenuInput
  CommandMenuSelectionChips
  CommandMenuScopedResults
  CommandMenuDefaultGroups
```

或者保留单文件，但内部显式拆函数组件。重点是：

- mode 决定数据模型，不靠多个 `showXxx` 布尔开关；
- selected chips 是独立渲染区；
- scoped picker 是统一能力，不为 P/S/D/M/F 分别写弹窗；
- CommandMenu 不直接改任务数据，只调用传入的 command action 或 runtime。

### 5.4 Scoped Picker 模式扩展

当前已有：

```ts
type CommandMenuMode = 'default' | 'task-picker' | 'project-picker'
```

建议扩展为：

```ts
type CommandMenuMode =
  | 'default'
  | 'task-picker'
  | 'project-picker'
  | 'task-priority-picker'
  | 'task-status-picker'
  | 'task-date-picker'
  | 'task-project-picker'
  | 'filter-picker'
```

说明：

- `task-priority-picker`：由 `P` 打开，显示优先级选项；
- `task-status-picker`：由 `S` 打开，显示状态选项；
- `task-date-picker`：由 `D` 打开，显示日期 preset 和自定义日期入口；
- `task-project-picker`：由 `M P` 打开，显示项目列表和搜索；
- `filter-picker`：后续给 `F*` 使用。

这仍然是同一个 `CommandMenu`，不是新弹窗。

### 5.5 Active Bar 与 Command Menu 关系

底部 `BulkActionBar` 不应该拥有独立业务分发，也不应该扩展成第二个命令面板。它只负责展示：

- 已选数量；
- 清空选择按钮；
- 当前保留的主要操作入口；
- 最右侧“操作”按钮。

推荐行为：

| 入口 | 行为 |
|---|---|
| active bar 的清空按钮 | 清空当前 selection |
| active bar 当前已有的主要按钮 | 保持现状，不在本轮强行增加更多按钮 |
| active bar 最右侧“操作”按钮 | 打开 `default` Command Menu，带当前 selection chips，并默认展示“批量操作”board / 分组 |
| `Cmd/Ctrl+K` | 打开 `default` Command Menu，也带当前 selection chips |

这样 active bar 仍然轻量，鼠标路径和键盘路径不会分叉，所有批量操作集中在 Command Menu 中维护。

### 5.6 Tauri / Rust 边界

Tauri/Rust 只处理桌面系统边界：

- 打开数据文件夹；
- 导出数据；
- 导入数据；
- 备份；
- 后续打开文件或外部链接；
- Helper 的系统级快捷键。

应用内命令仍由前端 CommandRuntime 调度。Rust command 要求：

- 返回 `Result<T, E>`；
- 错误信息可序列化；
- 不在 command 里 panic；
- 不持锁跨 await；
- 路径打开必须 allowlist 或明确作用域。

## 6. 分阶段执行计划

## 阶段 A：选择状态基建与 Esc 清空多选

### 目标

先把“当前选中了什么”变成稳定上下文，让后续 Command Menu 和 BulkActionBar 都能复用。

### 任务

1. 扩展当前 `useTaskSelection`：
   - 增加 `selectRangeTo(taskId)`；
   - 增加 `setFocusedTaskId(taskId)`；
   - 增加 `selectionAnchorId`；
   - 增加 `clearSelection()` 的稳定语义；
   - 保留当前 `toggleTaskSelection`，避免一次性改太多页面。

2. 建立选择 snapshot：
   - 当前选中 ids；
   - 当前选中 entities；
   - 当前 selection type；
   - 当前 selection source；
   - 是否 multi selection。

3. 接入 `Esc`：
   - 如果 Dropdown / Context Menu 打开，先交给菜单；
   - 如果 Modal 打开，先关闭 Modal；
   - 如果 Command Menu 打开，关闭 Command Menu；
   - 如果有多选，清空多选；
   - 如果有单选且产品要求清空，也清空单选；
   - 最后才考虑 route goBack。

4. 补测试：
   - 数据刷新后剔除失效选择；
   - `Esc` 清空多选；
   - 有弹层时 `Esc` 不穿透到底层 selection；
   - 输入态不触发普通清空逻辑。

### 不做

- 不做 Command Menu chips；
- 不做 `Shift+↑/↓`；
- 不做项目多选通用化。

### 验收

- 多选状态可以被统一读取；
- `Esc` 可以取消多选；
- 弹层优先级不回归；
- 页面现有 checkbox 多选不回归。

---

## 阶段 B：Command Context 接入选中对象

### 目标

让 `Cmd/Ctrl+K` 打开的 Command Menu 能知道当前选中的任务或项目。

### 任务

1. 扩展 `CommandSelectionContext`：
   - 加入 `entities`；
   - 加入 `primaryEntity`；
   - 加入 `source`；
   - 保持 `ids / hasSelection / isSingleSelection / isMultiSelection` 兼容。

2. 在页面层或布局层注入 selection snapshot：
   - Inbox；
   - All Tasks；
   - No Project；
   - Project Page；
   - Views Page；
   - Project Overview 可后续接入。

3. 更新 `use-command-context`：
   - 不直接依赖具体页面 store；
   - 只读 selection provider 暴露的 snapshot。

4. 调整 command priority：
   - 有任务 selection 时，任务命令优先；
   - 多选时，批量命令优先；
   - 无 selection 时，维持当前全局命令排序。

### 不做

- 不改 Command Menu UI；
- 不接真实批量业务；
- 不补所有 command-only。

### 验收

- CommandRuntime 上下文能拿到当前选中任务；
- Command Menu 里的任务命令能根据 selection 改变 visible / enabled / priority；
- 无 selection 时行为不变。

---

## 阶段 C：Command Menu 选中对象 Chips、批量操作 Board 与 Active Bar 入口统一

### 目标

实现你说的“输入框下面一排 outline 按钮，显示当前选中的任务或者项目”，并让 active bar 最右侧按钮和 `Cmd/Ctrl+K` 走同一个入口。底部 active bar 不增加一堆操作按钮，批量操作集中展示在 Command Menu 的“批量操作”board / 分组中。

### 任务

1. 新增 `CommandMenuSelectionChips`：
   - 显示在 `CommandInput` 下方；
   - 每个 chip 显示任务标题 / 项目名；
   - 多选数量较多时显示前 N 个 + “还有 X 项”；
   - chip 使用 outline 风格；
   - 长标题截断，hover 可显示完整 title。

2. Chip 行为：
   - 点击单个 chip 可以打开对应任务或项目；
   - 可选：chip 右侧小 `x` 移除该项；
   - 不建议第一版做拖拽排序、分组、批量编辑。

3. 新增 Command Menu 的“批量操作”board / 分组：
   - 只在 `selection.isMultiSelection` 或存在 selection 时出现；
   - 优先展示可批量执行的任务命令；
   - 第一版建议展示 `完成 / 设置优先级 / 设置状态 / 设置日期 / 移动到项目 / 移动到 Inbox / 移到独立事项 / 归档 / 删除`；
   - 每个条目仍然是 command entry，不单独写一套 active bar action；
   - 不可执行项必须 disabled 并显示原因。

4. `BulkActionBar` 接 Command Menu 入口：
   - 保留清空按钮；
   - 保持当前按钮数量和视觉结构；
   - 最右侧“操作”按钮打开 `CommandMenu` default mode；
   - 不在 active bar 里新增 `P / S / D / M` 等一排按钮。

5. `Cmd/Ctrl+K` 行为：
   - 无 selection：普通 default Command Menu；
   - 有 selection：default Command Menu + chips + “批量操作”board / 分组前置。

6. 视觉要求：
   - 选中对象 chips 是信息层，不要抢命令输入框焦点；
   - 行高控制在一行或最多两行；
   - 超出时横向滚动或折叠，避免撑高 Command Menu。

### 不做

- 不做复杂对象预览卡片；
- 不做 chip 内联编辑；
- 不做跨页保留 selection。

### 验收

- 多选后点击 active bar 最右侧“操作”按钮和按 `Cmd/Ctrl+K` 都能看到同一组选中对象；
- 多选后 Command Menu 中有独立“批量操作”board / 分组；
- Command Menu 不因 chips 失焦；
- 选中对象多时布局不崩；
- active bar 不扩展成第二个命令面板。

---

## 阶段 D：Row 层 P / S / D 接入 Command Scoped Picker

### 目标

把 `P / S / D` 从“模拟点击行内 dropdown trigger”改为“打开 Command Menu scoped picker”，统一键盘操作体验。

### 任务

1. 扩展 Command Menu mode：
   - `task-priority-picker`；
   - `task-status-picker`；
   - `task-date-picker`。

2. 增加 scoped picker 数据模型：
   - 优先级选项来自 `TASK_PRIORITY_OPTIONS`；
   - 状态选项来自 `TASK_STATUS_OPTIONS`；
   - 日期选项先支持 `无时间 / 今天 / 明天 / 本周 / 自定义`；
   - 后续再扩展真实 date picker。

3. 修改 Row 快捷键动作：
   - `P` 打开 `task-priority-picker`；
   - `S` 打开 `task-status-picker`；
   - `D` 打开 `task-date-picker`；
   - target 优先级沿用当前 row target 解析；
   - 多选时对 selection 批量生效。

4. 执行动作：
   - 选择优先级后批量调用 `updateTaskPriority`；
   - 选择状态后批量调用 `updateTaskStatus`；
   - 选择日期后批量调用日期更新服务；
   - 成功后关闭 Command Menu；
   - 失败时保留错误提示，不静默失败。

5. 保留鼠标路径：
   - Row 内原有 PriorityCell / StatusCell / Date cell 可以继续使用 dropdown；
   - 快捷键路径统一走 Command Menu scoped picker。

### 不做

- 不移除现有 dropdown 数字选择；
- 不在第一版做复杂自然语言日期输入；
- 不做 `D T / D M / D W` 日期 chord。

### 验收

- `P / S / D` 都打开 Command Menu scoped picker；
- 单选和多选都能正确应用；
- 无目标时不触发；
- 输入态和弹层打开时不穿透；
- Row 内鼠标 dropdown 不回归。

---

## 阶段 E：`Shift+↑/↓` 范围多选与列表焦点模型

### 目标

支持按住 Shift 加上下方向键进行连续多选。

### 任务

1. 建立 keyboard focus index：
   - 当前 focus task id；
   - 当前 focus index；
   - 当前 anchor id；
   - 当前可见 task id 顺序。

2. 扩展 `useTaskSelection`：
   - `moveFocus(delta)`；
   - `rangeSelectTo(taskId)`；
   - `selectOnly(taskId)`；
   - `clearSelection()`。

3. 快捷键规则：
   - `↑/↓`：移动 keyboard focus，不改变 selection；
   - `Shift+↑/↓`：从 anchor 到新 focus 做范围选择；
   - `X`：切换当前 focus/hover/target 的选择；
   - `Esc`：清空 selection；
   - 多选后 `Space / Enter / R` 默认不执行，避免歧义。

4. UI 表达：
   - keyboard-focused row 需要有可见 focus 样式；
   - selected group position 继续复用当前 row selection group 样式；
   - hover 不应该覆盖 keyboard focus 的语义。

5. 测试：
   - 从中间行 `Shift+↓` 连续扩展；
   - 反向 `Shift+↑` 收缩或扩展；
   - 数据过滤后 anchor 失效的处理；
   - 输入态不触发；
   - Dropdown / Command Menu 打开时不触发。

### 不做

- 不做 Vim-like `J/K`；
- 不做 `GG`、跳顶、跳底；
- 不做跨分页范围选择。

### 验收

- `Shift+↑/↓` 可稳定多选；
- active bar 计数正确；
- `Esc` 可取消多选；
- Command Menu 能展示这些选中对象。

---

## 阶段 F：Move 命令与批量整理流

### 目标

补齐 `M P / M I / M N`，让 Inbox 整理和批量整理成为完整键盘流。

### 任务

1. 补默认快捷键：
   - `task.moveToProject` -> `M P`；
   - `task.moveToInbox` -> `M I`；
   - `task.moveToNoProject` -> `M N`。

2. `M P` 打开 `task-project-picker`：
   - 展示项目列表；
   - 支持搜索；
   - 支持对当前 row target 或多选 selection 批量移动。

3. `M I`：
   - 直接移动到 Inbox；
   - 成功后保留或清空 selection 需要确认，默认建议保留 selection 直到用户 `Esc` 清空。

4. `M N`：
   - 直接移动到独立事项 / 无项目；
   - 项目页内执行后，该任务可能离开当前列表，需要 selection 自动剔除失效项。

5. 批量整理入口放在 Command Menu：
   - active bar 不增加移动类按钮；
   - `Cmd/Ctrl+K` 或 active bar 最右侧按钮打开 Command Menu；
   - “批量操作”board 中提供移动到项目、移动到 Inbox、移到独立事项。

### 不做

- 不做 Move to Space，除非 Space 模型已经明确；
- 不做复杂批量冲突弹窗；

## 阶段 I：Tauri / Rust 系统命令收口

### 目标

补齐本地桌面能力，但不让系统级能力污染应用内命令层。

### 任务

1. `system.openDataFolder`：
   - 使用 Tauri opener 或 Rust command 打开数据目录；
   - 路径必须来自应用受控目录；

   - 先定义 command-only；
   - 明确文件 picker、路径权限、错误返回；

   - command 返回 `Result<T, E>`；

### 不做

- 不做系统级 Command Menu；
- 不做大量全局热键；
- 不做跨进程共享 selection。

### 验收

- `Option+Space` 不回归；
- Open Data Folder 可用且安全；
- 系统命令失败有可见错误；
- 主应用和 Helper 没有重复命令注册表。

## 8. 模块化与复杂度控制原则

### 8.1 必须模块化的地方

- selection snapshot：因为 Command Menu、BulkActionBar、Row Shortcut 都要读；
- scoped picker model：因为 P/S/D/M/F 都复用；
- command metadata：因为 Command Menu、Shortcut Help、Chord Hint 都要读；
- Tauri system commands：因为权限和错误处理边界独立。

### 8.2 不应过早抽象的地方

- 不要一开始做万能 `EntitySelectionEngine`；
- 不要为每个 picker 建独立框架；
- 不要为每个命令做插件式 executor；
- 不要为了未来 Space / Favorite / Template 先改大量类型；
- 不要把单次使用的 command-only 命令抽成复杂类。

### 8.3 React 实现约束

- Provider 负责状态，组件负责展示；
- CommandMenu mode 用明确联合类型，不用一堆 boolean props；
- 全局事件监听只保留在 ShortcutLayer / RowShortcutScope；
- 避免组件内定义子组件导致重渲染和引用变化；
- 多选列表中重复查询用 `Map` / `Set`；
- 输入搜索相关渲染可以用 `useDeferredValue`；
- 批量更新后的非紧急 UI 刷新可以用 `startTransition`。

### 8.4 Rust / Tauri 实现约束

- Rust command 不接收不可信任路径直接打开；
- 系统命令失败必须返回错误，不 panic；
- IPC payload 用明确类型，不用任意 JSON；
- 能前端完成的 UI 状态不要下沉 Rust；
- Helper 不参与主窗口 selection 和 Command Menu。

## 9. 风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| selection 状态散落在各页面 | Command Menu 无法统一上下文 | 先做 selection snapshot，再做 UI。 |
| P/S/D 同时保留 dropdown 点击模拟和 scoped picker 两套快捷键路径 | 行为分裂，难测 | 快捷键只走 scoped picker，鼠标保留 dropdown。 |
| `Esc` 处理顺序不清 | 关闭弹层和清空多选互相穿透 | 阶段 A 先定义层级顺序并测试。 |
| Command Menu mode 变多后组件膨胀 | 维护困难 | 用 mode model + 子组件拆分，避免布尔 prop。 |
| 全量命令补齐范围过大 | 阶段失控 | 高频命令优先，低频先 command-only 或 disabled。 |
| Tauri 系统能力过早扩张 | 权限和安全复杂度增加 | 只做 Open Data Folder 等明确命令。 |

## 10. 待确认问题

这些问题会影响具体实现顺序或默认行为，需要在进入对应阶段前确认。

1. `Esc` 在“单选一个任务”时是否也清空选择，还是只清空多选？
2. `M I / M N` 批量移动成功后，是否保留 selection，还是自动清空 selection？
3. Command Menu chips 中单个任务 chip 是否需要提供移除按钮，还是第一版只展示和可点击打开？
4. `P / S / D` scoped picker 对多选应用后，是否立即关闭 Command Menu？
5. 日期 `D` 第一版是否只做 preset，不做完整 date picker？
6. `[` / `]` 是否确定作为默认快捷键切换侧边栏 / 预览栏？我倾向先不默认绑定，等布局状态稳定后再接。
7. `Cmd/Ctrl+Shift+C` 复制任务标题是否真的要默认绑定？我倾向先 command-only，避免过度占用系统复制心智。
8. 项目多选是否需要和任务多选同阶段完成？我倾向任务先完成，项目复用模型后补。

如果要开始实施，建议第一批只做：

1. 阶段 A：selection snapshot + `Esc` 清空多选；
2. 阶段 B：Command Context 读取 selection；

## 12. Active Bar 收窄后的优化建议

### 12.1 批量操作 board 不建议做成独立 mode

更优方案是：`Cmd/Ctrl+K` 和 active bar 最右侧按钮都打开 `default` Command Menu，然后由当前 selection 决定是否显示“批量操作”board。

原因：

- 不需要新增 `bulk-picker` mode；
- 用户仍然处在“我要执行命令”的心智里；
- 搜索命令、批量命令、普通命令可以共存；
- 后续 Command Menu 排序可以统一处理，不需要两套列表模型。

推荐展示顺序：

```txt
选中对象 chips
> 批量操作 board
> 当前上下文命令
> 高频全局命令
> 导航 / 创建 / 系统命令
```

### 12.2 批量操作 board 的第一版内容

第一版建议只放真正高频、低歧义、能批量执行的命令：

| 命令 | 行为 |
|---|---|
| 完成 / 取消完成 | 对当前 selection 批量执行 |
| 设置优先级 | 打开 `task-priority-picker` |
| 设置状态 | 打开 `task-status-picker` |
| 设置日期 | 打开 `task-date-picker` |
| 移动到项目 | 打开 `task-project-picker` |
| 移动到 Inbox | 直接执行，成功后按移动结果更新 selection |
| 移到独立事项 | 直接执行，成功后按移动结果更新 selection |
| 归档 | 使用 shadcn `AlertDialog` 确认后执行，成功后清空 selection |
| 删除 | 使用 shadcn `AlertDialog` 确认后执行，成功后清空 selection |

不建议第一版放：

- 复制为 Markdown；
- 复制 URL / ID；
- 活动记录；
- 导出；
- 转项目；
- AI 整理。

这些可以通过搜索命令找到，但不应挤占批量操作 board 的主位。

### 12.3 搜索过滤规则

当 Command Menu 有 selection 时：

- 用户不输入时，优先显示批量操作 board；
- 用户输入关键词时，仍然全局搜索 command；
- 匹配到批量命令时保持靠前；
- 不匹配时不强行显示完整批量 board，避免干扰搜索。

### 12.4 默认焦点建议

从 active bar 最右侧“操作”按钮打开 Command Menu 时：

- 默认焦点仍在输入框；
- 第一条可选命令可以是“设置优先级”或“完成选中任务”，但不要抢输入；
- 用户按 `↓` 后进入批量操作 board；
- 用户直接输入 `priority / 状态 / 移动` 时走搜索。

### 12.5 已确认决策

1. active bar 当前最右侧按钮名称使用“操作”。
2. 所有删除和归档动作都必须显示确认弹窗，统一使用 shadcn `AlertDialog`。
3. 批量归档成功后清空 selection。
4. 批量设置优先级 / 状态 / 日期后保留 selection，方便连续整理。
