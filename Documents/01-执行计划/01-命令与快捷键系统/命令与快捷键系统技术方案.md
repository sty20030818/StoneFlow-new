> Command First 的键盘驱动架构设计

---

## 1. 文档目标

StoneFlow 是一个以「快」为主旨的个人任务管理工具。命令与快捷键系统是 StoneFlow 键盘驱动体验的底层基础。

本文档用于定义 StoneFlow 命令系统的技术架构、核心模型、模块职责、执行流程、快捷键处理、Command Menu 接入方式，以及 V1 的实现阶段。

这是一份偏技术实现 / 架构落地的文档，目标是让后续开发或 AI 生成代码时能够遵循统一方案，避免把快捷键、业务逻辑、UI 事件和页面状态混在一起。

---

## 2. 背景与目标

### 2.1 背景

StoneFlow 需要支持大量键盘操作：

- 快速创建任务；
- 快速跳转页面；
- 快速打开任务、项目、视图；
- 快速修改任务状态、优先级、日期、项目；
- 快速执行批量操作；
- 快速从 Command Menu 中搜索并执行所有命令。

如果每个页面各自监听快捷键，每个按钮各自写业务逻辑，很快会出现以下问题：

- 快捷键冲突难以管理；
- 页面间行为不一致；
- Command Menu 和按钮逻辑重复；
- 单选 / 多选场景难以维护；
- 输入框中容易误触快捷键；
- 后期无法支持快捷键自定义；
- 无法从统一数据源生成快捷键帮助页。

因此 StoneFlow 需要一个中心化的 Command 系统。

### 2.2 核心目标

V1 技术目标：

- 建立统一 Command 抽象；
- 建立统一 Keybinding 快捷键模型；
- 建立统一 Command Context 上下文模型；
- 支持应用内快捷键；
- 支持两段式前缀快捷键；
- 支持 Command Menu 从 Registry 自动读取命令；
- 支持不同上下文下的命令可见、可用、排序；
- 支持输入框保护；
- 支持快捷键帮助页自动生成；
- 为后续自定义快捷键、AI 命令、插件化命令预留结构。

### 2.3 非目标

V1 暂不实现：

- 用户自定义快捷键；
- 快捷键云同步；
- Vim-like 模式；
- 三段及以上复杂 chord；
- 完整插件系统；
- AI 自动命令编排；
- 完整 Undo Stack；
- 跨窗口复杂命令同步。

这些能力可以预留字段和扩展点，但不进入 V1 实现范围。

## 3. 总体架构

### 3.1 核心思想

StoneFlow 的所有操作都应统一抽象为 `Command`。

快捷键、Command Menu、按钮点击、右键菜单、顶部菜单，本质上都是触发 Command 的不同入口。

```txt
Button / Menu / Shortcut / Command Menu / Context Menu
                          ↓
                      Command
                          ↓
                  Application Service
                          ↓
              Store / Router / SQLite / Tauri
```

### 3.2 Command First 原则

任何可被用户执行的操作，都应优先思考它是否是一个 Command。

例如：

| 用户操作 | Command |
|---|---|
| 完成任务 | `task.complete` |
| 修改优先级 | `task.setPriority` |
| 跳转收件箱 | `navigation.goInbox` |
| 打开项目 | `open.project` |
| 新建任务 | `new.task` |
| 移动到项目 | `task.moveToProject` |
| 清空筛选 | `filter.clearAll` |

这样做的好处是：

- 同一个操作可以被按钮、快捷键、Command Menu 复用；
- 权限、可见性、禁用原因统一判断；
- 快捷键帮助页可以自动生成；
- 后期用户自定义快捷键更容易实现；
- 后期 AI / 自动化也可以直接调用 Command。

### 3.3 分层结构

建议分为 5 层：

```txt
UI Trigger Layer
Command Runtime Layer
Command Registry Layer
Application Service Layer
State / Router / DB Layer
```

| 层级 | 职责 |
|---|---|
| UI Trigger Layer | 按钮、菜单、快捷键、Command Menu、右键菜单触发命令 |
| Command Runtime Layer | 判断命令可见性、可执行性、排序权重，并执行命令 |
| Command Registry Layer | 注册和管理所有 Command |
| Application Service Layer | 执行业务逻辑，例如 taskService、projectService |
| State / Router / DB Layer | Zustand、React Router、SQLite、Tauri API 等底层状态和能力 |

### 3.4 模块边界

命令系统不应该直接成为业务系统，也不应该直接成为 UI 系统。

它的职责是：

- 描述「有哪些命令」；
- 描述「命令什么时候出现」；
- 描述「命令什么时候能执行」；
- 描述「命令如何被触发」；
- 描述「命令触发后调用哪个业务服务」。

它不应该直接负责：

- 复杂业务流程；
- 具体数据库 SQL；
- 具体页面布局；
- 具体弹窗视觉样式；
- 复杂 UI 状态编排。

### 4.1 目录职责说明

| 目录 | 职责 |
|---|---|
| `core` | Command 的核心类型、注册、运行、上下文、排序 |
| `keybinding` | 快捷键类型、解析、匹配、前缀状态、冲突检测 |
| `commands` | 按业务领域拆分的命令定义 |
| `ui` | Command Menu、快捷键帮助页、按键展示组件 |
| `hooks` | 给 React 组件使用的命令相关 hook |
| `stores` | 命令菜单状态、快捷键状态、最近使用命令 |

### 4.2 与业务模块的关系

业务模块可以位于：

```txt
src/features/task/
src/features/project/
src/features/view/
src/features/filter/
```

Command 模块调用业务模块暴露出来的 service，不直接写业务细节。

例如：

```ts
// command/commands/task.commands.ts
run: async (ctx) => {
  await taskService.completeTasks(ctx.selection.ids)
}
```

而不是在 Command 中直接操作数据库。

## 5. Command 模型设计

### 5.1 基础类型

```ts
type CommandId = string

type Command = {
  id: CommandId
  title: string
  description?: string
  category: CommandCategory
  keywords?: string[]

  defaultShortcut?: Shortcut
  scope: CommandScope[]

  isVisible?: (ctx: CommandContext) => boolean
  isEnabled?: (ctx: CommandContext) => boolean
  getPriority?: (ctx: CommandContext) => number
  getDisabledReason?: (ctx: CommandContext) => string | undefined

  run: (ctx: CommandContext) => void | Promise<void>
}
```

### 5.2 字段说明

| 字段 | 说明 |
|---|---|
| `id` | 命令唯一 ID |
| `title` | 命令展示名称 |
| `description` | 命令说明 |
| `category` | 命令分类，用于 Command Menu 和帮助页分组 |
| `keywords` | 搜索关键词 |
| `defaultShortcut` | 默认快捷键 |
| `scope` | 命令适用范围 |
| `isVisible` | 是否在当前上下文中展示 |
| `isEnabled` | 是否在当前上下文中可执行 |
| `getPriority` | 当前上下文中的排序权重 |
| `getDisabledReason` | 禁用原因 |
| `run` | 命令执行函数 |

### 5.3 CommandId 命名规则

使用点分命名。

```txt
domain.action
domain.action.target
domain.action.variant
```

示例：

```txt
general.openCommandMenu
general.openSearch
navigation.goInbox
navigation.goProjects
open.task
open.project
new.task
new.project
task.complete
task.rename
task.setPriority
task.setStatus
task.openDateMenu
task.moveToProject
task.archive
task.delete
project.rename
project.archive
filter.byStatus
filter.clearAll
layout.toggleSidebar
layout.togglePreview
```

### 5.4 CommandCategory

V1 建议分类：

```ts
type CommandCategory =
  | "general"
  | "navigation"
  | "open"
  | "new"
  | "list"
  | "task"
  | "project"
  | "view"
  | "filter"
  | "inbox"
  | "layout"
  | "system"
```

### 5.5 CommandScope

```ts
type CommandScope =
  | "global"
  | "task-list"
  | "project-list"
  | "project-page"
  | "inbox-page"
  | "views-page"
  | "trash-page"
  | "preview-drawer"
  | "detail-drawer"
  | "modal"
```

`scope` 用于描述命令适合出现在哪些区域，不直接替代 `isVisible`。

`scope` 是粗粒度限制，`isVisible` 是细粒度判断。

## 6. Command Context 上下文设计

### 6.1 上下文的作用

Command Context 是命令系统的核心输入。

它用于判断：

- 当前命令是否可见；
- 当前命令是否可执行；
- 当前命令执行时作用于哪个对象；
- 当前命令在 Command Menu 中应该排多高；
- 当前快捷键是否应该生效。

### 6.2 上下文来源

Command Context 应该由当前应用状态统一生成，而不是由每个命令临时到处读取状态。

来源包括：

- Router 当前页面；
- 当前 Space；
- 当前 Project；
- 当前 View；
- 当前 selectionStore；
- 当前 focusStore；
- 当前 uiStore；
- 当前筛选状态；
- 当前 Drawer / Modal 状态。

### 6.3 Context 基础结构

```ts
type CommandContext = {
  route: RouteContext
  selection: SelectionContext
  focus: FocusContext
  space: SpaceContext
  project: ProjectContext
  view: ViewContext
  ui: UIContext
}
```

### 6.4 RouteContext

```ts
type RouteContext = {
```

### 6.5 SelectionContext


### 6.8 Space / Project / View Context

```ts

  currentSpaceId?: string
}

  currentProjectId?: string
}

  currentViewId?: string
  hasActiveFilters: boolean
}
```

### 6.9 Context 生成原则

Command Context 应该：

- 在执行命令前实时生成；
- 不长期缓存关键状态；
- 不直接暴露复杂 Store；
- 尽量保持只读；
- 作为所有命令判断的唯一输入。

## 7. Command Registry 设计

### 7.1 Registry 职责

Command Registry 负责：

- 注册所有命令；
- 根据 id 获取命令；
- 获取全部命令；
- 按 category 获取命令；
- 校验重复 id；
- 给 Command Runtime、Command Menu、Shortcut Manager、快捷键帮助页提供数据源。

### 7.2 注册方式

命令按领域拆分。

```ts
export const taskCommands: Command[] = [
  completeTaskCommand,
  renameTaskCommand,
  setTaskPriorityCommand,
  setTaskStatusCommand,
  moveTaskToProjectCommand,
]
```

统一汇总：

```ts
export const allCommands: Command[] = [
  ...generalCommands,
  ...navigationCommands,
  ...openCommands,
  ...newCommands,
  ...listCommands,
  ...taskCommands,
  ...projectCommands,
  ...viewCommands,
  ...filterCommands,
  ...inboxCommands,
  ...layoutCommands,
  ...systemCommands,
]
```

### 7.3 Registry 示例

```ts
class CommandRegistry {
  private commands = new Map<CommandId, Command>()

  register(command: Command) {
    if (this.commands.has(command.id)) {
      throw new Error(`Duplicate command id: ${command.id}`)
    }

    this.commands.set(command.id, command)
  }

  registerMany(commands: Command[]) {
    commands.forEach((command) => this.register(command))
  }

  get(commandId: CommandId) {
    return this.commands.get(commandId)
  }

  getAll() {
    return Array.from(this.commands.values())
  }

  getByCategory(category: CommandCategory) {
    return this.getAll().filter((command) => command.category === category)
  }
}
```

### 7.4 Registry 不应该做的事

Command Registry 不应该：

- 监听键盘事件；
- 读取 DOM；
- 直接写数据库；
- 处理 UI 展示；
- 在注册阶段执行命令；
- 保存运行时上下文。

## 8. Command Runtime 设计

### 8.1 Runtime 职责

Command Runtime 是命令执行前后的统一处理层。

负责：

- 判断命令是否可见；
- 判断命令是否可执行；
- 获取禁用原因；
- 计算命令排序权重；
- 执行命令；
- 统一错误处理；
- 记录最近使用命令；
- 后期接入 Activity Log。

### 8.2 执行流程

```txt
trigger command
      ↓
get current context
      ↓
find command by id
      ↓
check visible
      ↓
check enabled
      ↓
run command
      ↓
handle result / error
      ↓
record recent command
```

### 8.3 Runtime 示例

```ts
class CommandRuntime {
  constructor(
    private registry: CommandRegistry,
    private getContext: () => CommandContext,
  ) {}

  canExecute(command: Command, ctx: CommandContext) {
    return command.isEnabled?.(ctx) ?? true
  }

  isVisible(command: Command, ctx: CommandContext) {
    return command.isVisible?.(ctx) ?? true
  }

  getPriority(command: Command, ctx: CommandContext) {
    return command.getPriority?.(ctx) ?? 0
  }

  async execute(commandId: CommandId) {
    const command = this.registry.get(commandId)
    if (!command) return

    const ctx = this.getContext()

    if (!this.isVisible(command, ctx)) return
    if (!this.canExecute(command, ctx)) {
      const reason = command.getDisabledReason?.(ctx)
      // toast(reason ?? "Command is disabled")
      return
    }

    try {
      await command.run(ctx)
      // recentCommandStore.record(command.id)
    } catch (error) {
      // log error
      // toast error
    }
  }
}
```

### 8.4 隐藏与禁用规则

有些命令应该隐藏，有些命令应该禁用。

| 情况 | 处理 |
|---|---|
| 当前场景完全不相关 | 隐藏 |
| 当前场景相关但条件不足 | 禁用 |
| 没有选中任务 | Rename Task 隐藏 |
| 当前任务没有日期 | Remove Due Date 禁用 |
| 在回收站中 | Archive Task 隐藏，Restore Task 显示 |
| 正在输入中 | 普通单键命令不触发 |

### 8.5 错误处理

命令执行失败时：

- 不应导致应用崩溃；
- 应显示轻量错误提示；
- 应保留用户当前上下文；
- 应记录错误日志；
- 危险操作失败时应明确告知用户。

## 9. Command Priority 排序设计

### 9.1 排序目标

Command Menu 的排序不是静态的。

同一个命令在不同上下文下应该有不同权重。

例如：

- 选中任务时，`task.setPriority` 权重提高；
- 选中多个任务时，批量操作权重提高；
- 在项目页，`new.taskInCurrentProject` 权重提高；
- 在收件箱，`task.moveToProject` 权重提高。

### 9.2 推荐评分公式

```ts
score =
  basePriority
  + contextBoost
  + selectionBoost
  + routeBoost
  + recentBoost
  + searchMatchBoost
```

### 9.3 权重来源

| 权重 | 说明 |
|---|---|
| `basePriority` | 命令基础优先级 |
| `contextBoost` | 当前上下文加权 |
| `selectionBoost` | 单选 / 多选加权 |
| `routeBoost` | 当前页面加权 |
| `recentBoost` | 最近使用加权 |
| `searchMatchBoost` | 搜索匹配加权 |

### 9.4 示例

```ts
const setTaskPriorityCommand: Command = {
  id: "task.setPriority",
  title: "Change Priority",
  category: "task",
  defaultShortcut: "P",
  scope: ["task-list", "project-page", "inbox-page"],
  isVisible: (ctx) => ctx.selection.type === "task" && ctx.selection.hasSelection,
  getPriority: (ctx) => {
    let score = 50

    if (ctx.selection.isSingleSelection) score += 20
    if (ctx.selection.isMultiSelection) score += 30
    if (ctx.route.page === "inbox") score += 20

    return score
  },
  run: async (ctx) => {
    // open priority menu for selected tasks
  },
}
```

## 10. Keybinding 快捷键模型设计

### 10.1 基础类型

```ts
type Keybinding = {
  commandId: CommandId

```

### 10.2 字段说明

| 字段 | 说明 |
|---|---|
| `commandId` | 绑定的命令 ID |
| `keys` | 快捷键字符串，例如 `G I`、`CmdOrCtrl+K` |
| `scope` | 快捷键适用范围 |
| `when` | 生效条件 |
| `preventDefault` | 是否阻止浏览器默认行为 |

### 10.3 KeybindingScope

```ts
type KeybindingScope =
  | "global"
  | "app"
  | "page"
  | "list"
  | "modal"
  | "drawer"
  | "input"
```

### 10.4 快捷键字符串规范

文档中使用：

```txt
Cmd/Ctrl + K
Cmd/Ctrl + Enter
Shift + D
N T
G I
O P
M P
```

代码中建议使用：

```txt
CmdOrCtrl+K
CmdOrCtrl+Enter
Shift+D
N T
G I

```

### 10.5 NormalizedShortcut

内部应将快捷键字符串标准化。

```ts
type NormalizedShortcut = {
  type: "single" | "chord"
  steps: ShortcutStep[]
}

type ShortcutStep = {
  key: string
  modifiers: {
    meta?: boolean
    ctrl?: boolean
    alt?: boolean
    shift?: boolean
  }
}
```

### 10.6 CmdOrCtrl 跨平台处理

| 平台 | CmdOrCtrl |
|---|---|
| macOS | Meta |
| Windows | Control |
| Linux | Control |

技术层统一使用 `CmdOrCtrl`，展示层根据平台显示为 `⌘` 或 `Ctrl`。

## 11. Keybinding Registry 设计

### 11.1 职责

Keybinding Registry 负责：

- 注册所有默认快捷键；
- 根据按键查找对应命令；
- 根据命令查找快捷键；
- 提供给 Shortcut Manager；
- 提供给快捷键帮助页；
- 后期合并用户自定义快捷键。

### 11.2 默认快捷键来源

可以有两种方式。

#### 方案 A：快捷键写在 Command 中

```ts
const completeTaskCommand: Command = {
  id: "task.complete",
  title: "Complete Task",
  defaultShortcut: "C",
  ...
}
```

优点：命令和快捷键靠得近，容易读。

缺点：后期自定义、冲突检测、平台差异会变复杂。

#### 方案 B：Command 与 Keybinding 分离

```ts
const keybindings: Keybinding[] = [
  {
    commandId: "task.complete",
    keys: "C",
    scope: "list",
    when: "selection.type == task && !focus.isInputFocused",
  },
]
```

优点：更清晰、更可扩展、更适合后期自定义。

缺点：需要在两个地方维护命令和默认快捷键。

#### V1 推荐

V1 推荐使用「混合方案」：

- Command 中可以保留 `defaultShortcut` 用于展示；
- Keybinding Registry 是真实执行来源；
- 启动时校验二者一致性。

这样既方便文档化，又方便后期扩展。

## 12. Shortcut Manager 设计

### 12.1 职责

Shortcut Manager 负责应用窗口内快捷键。

它负责：

- 监听 `keydown`；
- 标准化键盘事件；
- 判断是否处于输入状态；
- 判断当前活跃层级；
- 匹配单键快捷键；
- 将前缀键交给 Chord Manager；
- 调用 Command Runtime 执行命令。

### 12.2 触发流程

```txt
keydown
  ↓
normalize event
  ↓
check input guard
  ↓
check active layer
  ↓
match keybinding
  ↓
get command context
  ↓
commandRuntime.execute(commandId)
```

### 12.3 输入框保护

如果当前焦点在输入框、textarea、contenteditable 中：

允许：

- `Esc`；
- `CmdOrCtrl+Enter`；
- `CmdOrCtrl+K`；
- `CmdOrCtrl+Z`；
- `CmdOrCtrl+Shift+Z`。

阻止：

- 普通字母快捷键；
- 前缀快捷键；
- 任务操作快捷键；
- 页面导航快捷键。

### 12.4 层级优先级

快捷键应该优先作用于当前最上层 UI。

```txt
Dropdown / Select Menu
> Modal
> Command Menu
> Detail Drawer
> Preview Drawer
> Main Page
```

例如：

- 下拉菜单打开时，方向键优先移动菜单项；
- Modal 打开时，`Esc` 优先关闭 Modal；
- Command Menu 打开时，`Enter` 优先执行当前高亮命令；
- 输入框中，字母优先输入文本。

### 12.5 Shortcut Manager 不应该做的事

Shortcut Manager 不应该：

- 直接执行业务逻辑；
- 直接修改任务数据；
- 直接跳转页面；
- 直接控制复杂 UI；
- 写死命令列表。

它只负责把键盘事件转换为 Command 执行。

## 13. Chord Manager 前缀快捷键设计

### 13.1 支持范围

V1 只支持两段式 chord。

支持：

```txt
N T
N P
G I
G P
O T
O P
M P
M S
F P
F S
```

不支持：

```txt
G G T
M P S
N T P
```

### 13.2 状态机

```txt
idle
  ↓ press prefix
waiting_second_key
  ↓ press valid key
execute command
  ↓
idle
```

异常路径：

```txt
waiting_second_key
  ↓ timeout / Esc / invalid key
cancel
  ↓
idle
```

### 13.3 前缀定义

V1 支持 5 个前缀：

| 前缀 | 含义 |
|---|---|
| `N` | New |
| `G` | Go to |
| `O` | Open |
| `M` | Move |
| `F` | Filter |

### 13.4 超时规则

| 项 | 值 |
|---|---|
| chord 超时 | 1000ms |
| 最大步骤 | 2 |
| 错误输入 | 取消并轻提示 |
| `Esc` | 取消 chord |
| 输入框内 | 不进入 chord 状态 |

### 13.5 UI 提示

用户按下前缀键后，应显示轻量提示：

```txt
G …
N …
O …
M …
F …
```

如果按错：

```txt
No command for G Z
```

提示不应打断用户，短时间后自动消失。

### 13.6 Chord Manager 示例

```ts
type ChordState =
  | { status: "idle" }
  | { status: "waiting"; prefix: string; startedAt: number }

class ChordManager {
  private state: ChordState = { status: "idle" }
  private timer: number | undefined

  start(prefix: string) {
    this.state = { status: "waiting", prefix, startedAt: Date.now() }
    this.resetTimer()
  }

  cancel() {
    this.state = { status: "idle" }
    if (this.timer) window.clearTimeout(this.timer)
  }

  handleSecondKey(key: string) {
    if (this.state.status !== "waiting") return undefined

    const chord = `${this.state.prefix} ${key}`
    this.cancel()
    return chord
  }

  private resetTimer() {
    if (this.timer) window.clearTimeout(this.timer)
    this.timer = window.setTimeout(() => this.cancel(), 1000)
  }
}
```

## 14. Command Menu 技术设计

### 14.1 数据来源

Command Menu 不维护独立命令列表。

它消费以下数据源：

- Command Registry；
- Keybinding Registry；
- Command Context；
- Command Runtime；
- Recent Command Store；
- Search Query。

### 14.2 展示流程

```txt
open command menu
      ↓
get current context
      ↓
get all commands
      ↓
filter visible commands
      ↓
calculate enabled state
      ↓
calculate priority
      ↓
apply search ranking
      ↓
group by category
      ↓
render
```

### 14.3 搜索字段

搜索时应匹配：

- `title`；
- `keywords`；
- `category`；
- `shortcut`；
- `description`。

### 14.4 V1 搜索策略

V1 可先使用简单 fuzzy search。

排序优先级：

```txt
exact match
> prefix match
> keyword match
> fuzzy match
> recent used
```

### 14.5 展示字段

每个 Command Item 应展示：

- 命令标题；
- 命令说明，可选；
- 所属分类，可选；
- 快捷键；
- 禁用状态；
- 禁用原因，可选。

### 14.6 执行规则

用户在 Command Menu 中执行命令时：

1. 获取当前高亮命令；
2. 调用 `commandRuntime.execute(command.id)`；
3. 如果执行成功，关闭 Command Menu；
4. 如果命令打开了二级选择器，例如选择项目，则 Command Menu 可进入子模式；
5. 如果命令执行失败，保留 Command Menu 或给出错误提示。

### 14.7 子模式

部分命令不是立即完成，而是需要进一步选择。

例如：

- `task.setPriority` 需要选择优先级；
- `task.setStatus` 需要选择状态；
- `task.moveToProject` 需要选择目标项目；
- `open.project` 需要搜索项目；
- `filter.byProject` 需要选择项目。

V1 可以用简单方式处理：

- Command 执行后打开对应 Popover / Select / Dialog；
- 或 Command Menu 切换到二级列表。

长期更推荐 Command Menu 子模式，但 V1 可以先保持简单。

## 16. 状态管理设计

### 16.1 推荐 Store 划分

使用 Zustand 时建议拆分为：

```txt
selectionStore

uiStore
commandStore
recentCommandStore
shortcutStore
```

### 16.2 selectionStore

负责：

```ts
type SelectionStore = {
```

负责：

- 是否输入中；

### 16.4 uiStore

负责：

- Preview Drawer 状态；
- Detail Drawer 状态；
- Modal 状态；
- Dropdown 状态；

## 17. 与业务层的关系

### 17.1 Command 不直接写复杂业务

Command 的 `run` 应调用业务 service。

正确：

```ts
run: async (ctx) => {
  await taskService.completeTasks(ctx.selection.ids)
}
```

不推荐：

```ts
run: async (ctx) => {
  // 在这里直接写 SQL、更新多个 store、处理复杂副作用
}
```

### 17.2 推荐 Service 划分

```txt
taskService
projectService
viewService
navigationService
filterService
layoutService
```

### 17.3 Service 职责

| Service | 职责 |
|---|---|
| `taskService` | 创建、完成、移动、归档、删除、修改任务字段 |
| `projectService` | 创建、重命名、归档、删除项目 |
| `viewService` | 创建、保存、修改、删除视图 |
| `navigationService` | 路由跳转和对象打开 |
| `filterService` | 修改当前页面筛选条件 |
| `layoutService` | 控制 Sidebar、Preview、Detail、Layout |

### 17.4 Command 与 Store 边界

Command 可以通过 Context 读取当前状态，但不应该到处直接读取 Store。

推荐流程：

```txt
Command Runtime 生成 Context
        ↓
Command.run(ctx)
        ↓
调用 Service
        ↓
Service 更新 Store / DB / Router
```

## 18. 与 Tauri / 全局快捷键的关系

### 18.1 应用内快捷键

应用窗口内部快捷键由 React 前端的 Shortcut Manager 处理。

包括：

- `C`；
- `P`；
- `S`；
- `D`；
- `N T`；
- `G I`；
- `O P`；
- `Cmd/Ctrl + K`。

### 18.2 系统级全局快捷键

系统级全局快捷键由 Tauri / Helper 处理。

主要包括：

- 打开 Quick Create；
- 打开主窗口；
- 打开全局 Command Window，后期；
- 全局搜索，后期。

### 18.3 分工原则

| 类型 | 处理方 |
|---|---|
| 应用窗口内快捷键 | React Shortcut Manager |
| 系统级热键 | Tauri / Helper |
| 命令执行 | Command Runtime |
| 数据变更 | Service + Store + SQLite |
| 窗口显示隐藏 | Tauri Window API / Helper |

### 18.4 全局热键与 Command 的连接

Tauri / Helper 收到全局热键后，不应该直接写复杂业务。

推荐流程：

```txt
Global Shortcut
      ↓
Tauri / Helper
      ↓
show window / focus app
      ↓
frontend receives event
      ↓
execute Command or open Quick Create
```

系统级热键只负责唤起窗口或发送事件，具体业务仍由 Command / Service 处理。

## 19. 错误处理与安全规则

### 19.1 命令执行错误

命令执行失败时：

- 不崩溃应用；
- 显示 toast；
- 记录错误日志；
- 保持 UI 可恢复；
- 不丢失用户输入。

### 19.2 危险命令确认

| 命令 | V1 处理建议 |
|---|---|
| Delete Task | 移入回收站，不一定二次确认 |
| Delete Multiple Tasks | 可二次确认或提供 toast undo |
| Delete Project | 建议二次确认 |
| Empty Trash | 必须二次确认 |
| Archive Project | 可二次确认或 toast undo |

### 19.3 Undo 预留

用户侧保留 `Cmd/Ctrl + Z`。

技术上可以分阶段：

| 阶段 | 方案 |
|---|---|
| V1 | 局部 toast undo，例如删除任务后可撤销 |
| V2 | 引入 action log，实现更多撤销 |
| V3 | 完整 undo stack |

### 19.4 输入安全

所有普通快捷键必须尊重输入状态。

输入框中不能触发：

- `C` 完成任务；
- `P` 修改优先级；
- `S` 修改状态；
- `D` 日期菜单；
- `G I` 导航；
- `O P` 打开对象。

## 22. V1 验收标准

### 22.1 功能验收

V1 完成后，应支持：

- `Cmd/Ctrl + K` 打开 Command Menu；
- `/` 打开搜索；
- `N T` 新建任务；
- `N P` 新建项目；
- `G I` 跳转 Inbox；
- `G T` 跳转全部任务；
- `G P` 跳转项目页面；
- `O T` 打开任务搜索；
- `O P` 打开项目搜索；
- `Space` 预览任务；
- `Enter` 打开详情；
- `C` 完成任务；
- `P` 修改优先级；
- `S` 修改状态；
- `D` 打开日期菜单；
- `M P` 移动任务到项目；
- `F P / F S / F D` 筛选；
- `Esc` 正确关闭当前层级。

### 22.2 体验验收

必须满足：

- 输入框中普通字母不会触发快捷键；
- Command Menu 打开足够快；
- 前缀快捷键有轻提示；
- 快捷键帮助页与实际命令一致；
- 单选 / 多选任务下命令排序不同；
- 项目页、收件箱、回收站有不同上下文优先级；
- 危险命令不会误触穿透；
- `Esc` 行为稳定且符合层级规则。

### 22.3 架构验收

必须满足：

- 命令定义和快捷键监听分离；
- Command Menu 不维护独立命令列表；
- 快捷键帮助页不手写静态表；
- 业务逻辑主要在 Service 中；
- Command Runtime 统一处理执行；
- Context 是命令判断的统一输入；
- Registry 能检查重复 CommandId。

如果所有变更都经过 Command / Service，后期实现 Activity Log 和 Undo 会更容易。

## 25. 最终架构约定

StoneFlow 命令与快捷键系统采用以下核心约定：

```txt
Command 是一等公民
Shortcut 只是 Command 的入口
Command Menu 消费 Command Registry
Shortcut Manager 调用 Command Runtime
业务逻辑沉到 Service
上下文统一由 Command Context 提供
快捷键帮助页从 Registry 自动生成
```

核心执行链路：

```txt
Keyboard / Button / Command Menu
              ↓
        Command Runtime
              ↓
          Command.run(ctx)
              ↓
        Application Service
              ↓
    Store / Router / SQLite / Tauri
```

V1 的重点不是做一个复杂的快捷键平台，而是建立一套干净、稳定、可扩展的命令底座。

只要这套底座稳定，后续的快捷键自定义、Command Menu 智能排序、AI 命令、全局窗口、插件化能力都可以自然叠加。
