# P1 · 产品内核

> 最后更新：2026-04-17 · 版本：V1

## 一句话定义

StoneFlow 是一个帮助高频脑力工作者以极速捕获、清晰整理和聚焦执行来管理工作与生活任务的 macOS 桌面任务系统。

## 目标用户

**主要用户**：

- 第一目标用户是产品作者本人。
- 第二目标用户是与作者工作方式相近的程序员和高频脑力工作者。
- 这类用户通常同时管理工作、学习、生活等多个上下文。
- 他们已经使用过或研究过 TODO、任务管理、效率工具，但始终觉得现有产品要么不够顺手，要么不够专业，要么关键路径太长。
- 他们愿意长期使用一款桌面工具，但前提是它必须足够快、足够稳、足够清晰，并且真的能融入日常工作流。

**不是我们的用户**：

- 不是面向大众型、轻量打卡型、纯提醒型用户。
- 当前版本不是面向团队协作、项目协同、权限管理场景。
- 当前版本也不是面向重型项目管理、复杂文档协作、企业流程系统。

## 北极星指标

`每周活跃使用天数（WAU Days per User）`

定义：

- 单个用户在一周内，真实打开并完成至少一次“捕获、整理、查看、完成”任一关键任务流的天数。

为什么选这个指标：

- StoneFlow 的目标不是让用户偶尔记录任务，而是成为日常工作和生活的一部分。
- 如果用户一周内持续多天主动使用，说明它已经进入真实工作流，而不是停留在“装了但不用”。
- 对当前单机个人产品阶段来说，这个指标比注册数、任务总量更能代表产品是否真的有价值。

## 当前版本目标（V1）

V1 结束时，我们应该能验证：

- [ ] StoneFlow 已经可以支撑作者本人持续管理工作、学习、生活任务，而不是只做演示用途。
- [ ] 用户可以通过全局入口快速捕获任务，并能在系统内顺畅完成整理、查看与执行。
- [ ] 产品已经形成稳定的信息架构骨架，包括 `Space -> Project -> Task`、`Inbox`、`Focus`、`Trash` 等核心结构。
- [ ] 产品已经具备足够清晰的桌面交互体验，让“快、专业、顺手”成为真实体验而不是概念描述。

## 不做什么（V1）

- 不做团队协作。
  - 原因：`V2 再做或长期不做，取决于单机个人产品是否先跑通。`

- 不做账号系统与云同步。
  - 原因：`V2 再做。当前优先验证本地优先的单机任务系统是否成立。`

- 不做移动端与 Web 端。
  - 原因：`V2 再做或长期不做。当前明确聚焦 macOS 桌面端。`

- 不做复杂权限、成员、组织、审批流。
  - 原因：`当前版本永远不做。该方向会把产品拉向团队工作管理系统。`

- 不做重型项目管理能力。
  - 原因：`当前版本永远不做。StoneFlow 不是 Jira、Notion Project、飞书项目。`

- 不做子任务无限层级。
  - 原因：`V1 明确只支持一层子项目，不扩展为无限复杂结构。`

- 不做过度复杂的任务状态系统。
  - 原因：`V1 先保持 task 两态：todo / done，后续再决定是否扩展。`

- 不做复杂资源预览系统。
  - 原因：`V2 再做。V1 先保证资源可挂载、可识别、可一键打开。`

## 当前最大风险

当前最大风险是：

**StoneFlow 可能会在“想做完整个人执行系统”和“想保持极速、顺手、低摩擦”之间失去平衡，最后变成一个功能很多但不够爽的任务工具。**

为什么这是最大风险：

- 你已经明确不想做一个普通 TODO。
- 但你又希望它具备专业能力、项目结构、聚合视图、资源挂载、反馈系统等。
- 如果这些能力堆叠得太快，产品会牺牲掉最初最重要的价值，也就是“快”和“顺手”。

当前应对方式：

- 以“关键路径是否更短、更顺手”为最高裁决标准。
- 任何新增能力都必须回答：它是否让捕获、整理、执行更顺，而不是更重。
- 保持产品骨架清晰，先把 `Inbox / Focus / Project / Task Drawer` 这些核心结构做对，再扩张边缘能力。
