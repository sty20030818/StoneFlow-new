# StoneFlow UI 系统实验室

**Status:** completed; archived; manual acceptance transferred
**Triage:** completed
**日期:** 2026-08-26  
**采用基线:** HeroUI OSS 3.2.4、HeroUI Styles 3.2.4、HeroUI Pro 1.0.0-beta.8

2026-08-26，九个垂直切片、浏览器 UI Lab、自动化边界与生产构建隔离均已完成。真实 Tauri Main/Launcher、WebView、窗口缩放与跨窗口一致性仍在[统一产品验收](../../unified-product-acceptance/spec.md)中等待执行，不记为已经通过；本轮发现的共享 UI/UX 问题冻结在 09 ticket 的 Evidence 中，后续修复或迁移另建独立工作包。

## Problem Statement

StoneFlow 当前的 UI/UX 问题不是单个组件坏掉，而是缺少一处能够系统观察视觉契约、交互状态和组件归属的环境。按钮颜色、面包屑链接态、侧栏密度、输入框焦点、Overlay 焦点恢复等问题散落在 Main、Launcher、设置页和业务模块中；在真实产品里逐页寻找既慢，也很难判断问题来自 HeroUI、共享 recipe、产品 Module，还是具体页面覆盖。

现有证据表明，当前没有已确认的 P0 级 UI 阻断，但存在中等程度的一致性问题，以及更高程度的“不可观察性”问题。例如，部分共享状态在指针与键盘交互下可能表现不一致；按钮虽大量出现，但并非所有蓝色按钮都属于同一种语义；侧栏较紧凑也可能是有意密度，而不是天然缺陷。仅凭肉眼浏览源码或按页面截图，容易把个别现象误判成系统规则，也容易进行无证据的全局重构。

HeroUI 官网访问体验又不足以承担本地选型工作。项目已采用 HeroUI OSS 与 HeroUI Pro，但当前使用了哪些能力、哪些自实现组件可以被替换、候选组件需要哪些可选依赖，缺少一个与 StoneFlow 实际主题和产品语境一致的本地观察面。

因此，分别维护“StoneFlow 全组件页”和“HeroUI 全组件页”两个独立系统，收益不足且会制造重复导航、重复 fixture、重复状态管理和长期漂移。更有价值的方案是建设一个开发专用的系统级 UI Lab，在同一基础设施中提供两个视图：StoneFlow 界面审查与 HeroUI 候选库。它的目标不是恢复旧 StoneFlow 的外观，也不是立即修复发现的问题，而是建立一个更统一、规范、简洁、整齐、有条理且冷静的目标基线，并持续降低发现系统性 UI/UX 问题的成本。

## Solution

建设一个仅供本地开发使用的 StoneFlow UI 系统实验室，使用项目现有的 React、Vite、Tailwind、HeroUI OSS 和 HeroUI Pro，不引入新的组件浏览器、运行时注册框架或视觉回归服务。

实验室共用一个 Shell、搜索与分类导航，并提供两个互斥视图：

1. **StoneFlow 界面审查**：按视觉系统层级展示 Foundations、Actions、Fields、Navigation、Collections、Feedback、Overlays 和代表性 Product Scenes。每个样例只展示适用状态，不生成无意义的全组合矩阵。
2. **HeroUI 候选库**：只覆盖项目已使用的组件、已有明确替换对象的组件，以及少量值得探索但尚未采纳的组件。候选按“已采用”“替换候选”“探索中”分组，不以复制 HeroUI 官网或渲染其全部组件为目标。

实验室采用“目录可完整、预览按需挂载”的策略。导航可以看到完整覆盖范围，但页面同一时间只挂载当前选中的样例，避免 Overlay、焦点管理、动画和复杂组件相互干扰，也避免把实验室本身做成新的性能问题。

StoneFlow 样例默认采用目标视觉基线，而不是永久保留旧主题。需要比较迁移效果时，可以在单个任务期间放置临时对照，但完成硬切后必须删除旧样式、兼容别名和双轨 fixture。

覆盖分三批完成：

1. **第一批：视觉基线与高频交互**——Foundations、Actions、Fields、Navigation。
2. **第二批：复杂状态与浮层**——Collections、Feedback、Overlays。
3. **第三批：产品组合与候选评估**——代表性 Product Scenes、HeroUI 候选库、覆盖缺口收口。

每一批都必须形成可独立使用的审查面。新增样例的停止条件不是达到某个组件数量，而是继续增加样例已经不能发现新的共享规则、状态缺口或迁移机会。

## User Stories

### 访问与浏览

1. **作为 UI 审查者，我希望通过独立的开发入口打开 UI Lab，从而无需在真实业务数据和窗口流程中寻找组件。**
   - UI Lab 可以直接访问，不要求先进入 Main 或 Launcher 的业务路由。
   - UI Lab 不出现在生产导航、正式路由、桌面菜单或发布产物中。
   - 入口加载与失败不影响 Main 和 Launcher。

2. **作为 UI 审查者，我希望在 StoneFlow 与 HeroUI 两个视图之间切换，从而在同一主题和窗口条件下比较现状与候选方案。**
   - 切换入口清晰表达两个视图的不同目的。
   - 两个视图共用搜索、分类和预览布局，不各自复制一套 Shell。
   - 切换视图后，不保留会造成错误上下文的已选样例。

3. **作为 UI 审查者，我希望按分类浏览样例，从而按照系统层级而不是源码目录理解界面。**
   - StoneFlow 使用八个稳定分类：Foundations、Actions、Fields、Navigation、Collections、Feedback、Overlays、Product Scenes。
   - HeroUI 使用“已采用”“替换候选”“探索中”三个决策分类。
   - 分类为空时明确显示空状态，不隐藏结构问题。

4. **作为 UI 审查者，我希望按组件名、场景名和关键词搜索，从而快速定位想检查的对象。**
   - 搜索匹配用户可见名称与有限的同义关键词。
   - 无结果时给出清晰反馈，并允许一键清空查询。
   - 搜索不需要模糊搜索引擎、索引服务或运行时插件。

5. **作为开发者，我希望同一时间只挂载当前选中的样例，从而避免多个 Overlay、焦点陷阱或异步组件彼此干扰。**
   - 选择新样例会卸载旧样例。
   - 未选中的样例仍可在目录中检索，但不进入 DOM。
   - 预览卸载后不遗留 Portal、全局监听器或滚动锁。

6. **作为键盘用户，我希望完成切换视图、浏览分类、搜索和选择样例，从而不依赖鼠标完成 UI 审查。**
   - 所有导航控件具有明确名称、可见的键盘焦点和合理顺序。
   - 选择样例后，焦点不会无提示地丢失到页面起点。
   - UI Lab 自身不创建与被测组件冲突的快捷键。

### 覆盖清单与责任归属

7. **作为维护者，我希望每个样例显示稳定名称、分类和来源，从而知道它是基础值、共享组件、产品 Module 还是 HeroUI 候选。**
   - 来源信息只描述真实责任归属，不把文件数量当成组件数量。
   - 同一视觉单元只有一个主要 owner。
   - 复合产品场景可以列出多个依赖，但不能被误标为新的基础组件。

8. **作为维护者，我希望看到每个样例由 HeroUI、StoneFlow recipe 或产品 Module 中哪一层负责，从而把问题修在正确边界。**
   - Upstream 结构、全局语义值、共享 recipe 和产品结构四层清晰区分。
   - 不为展示方便创建一对一包装器来伪造 StoneFlow 所有权。
   - 责任不明确的样例标为待归属，而不是静默复制实现。

9. **作为维护者，我希望看到样例是否适合在 Lab 中验证，从而区分实验室证据与真实应用证据。**
   - 每个复杂场景标明“Lab 可验证”或“仅真实应用验证”。
   - 依赖窗口边界、真实 WebView、Tauri 命令或跨窗口状态的行为必须留给真实应用。
   - UI Lab 通过不能替代 Main 与 Launcher 的最终验收。

10. **作为 UI 审查者，我希望看到适用于样例的状态覆盖，从而不遗漏 Hover、Focus、Disabled、Invalid 等关键问题。**
    - 通用候选状态包括 Rest、Hover、Pressed、Selected/Current、Pointer Focus、Keyboard Focus Visible、Open、Disabled、Loading、Invalid、长中文和窄容器。
    - 只展示语义上适用的状态，不做笛卡尔积。
    - 浏览器无法可靠静态模拟的状态允许通过交互触发并给出操作提示。

11. **作为维护者，我希望覆盖目录能暴露缺口，从而知道哪些视觉表面尚未被审查。**
    - 缺失样例、仅真实应用验证和待归属项目可被筛选。
    - 覆盖信息用于审查范围，不成为第二套 issue tracker。
    - 缺口需要执行时，仍使用项目既有本地 ticket 流程。

### Foundations

12. **作为 UI 审查者，我希望查看颜色与语义角色，从而判断 Accent、文本、边框、Surface、Danger 和状态色是否冷静且一致。**
    - 展示实际生效的语义颜色，而不是另建一份 TypeScript token 镜像。
    - 颜色按用途组织，不把色阶目录当成产品语义。
    - 文本与交互关键状态满足基本对比度要求。

13. **作为 UI 审查者，我希望查看字体、字号、字重、行高和长文本换行，从而发现信息层级与扫描性问题。**
    - 至少覆盖页面标题、分组标题、正文、辅助信息、标签和紧凑元数据。
    - 同时展示短英文、常见中文和长中文。
    - 不为实验室引入新的字体或排版系统。

14. **作为 UI 审查者，我希望查看间距、圆角、控件高度、边框、阴影和图标基线，从而判断全局几何是否统一。**
    - 默认检查 4/8/12 间距节奏、28/32/36 控件高度和既有圆角层级。
    - 图标与文本对齐、点击目标和稠密度可以在同一画布比较。
    - Lab 只读取实际样式，不维护平行 token 表。

15. **作为鼠标与键盘用户，我希望比较 Pointer Focus 与 Keyboard Focus Visible，从而发现点击后错误焦点框或键盘焦点缺失。**
    - 指针点击与键盘 Tab 的视觉结果可以分别复现。
    - 键盘焦点不得通过全局去焦点规则被移除。
    - 焦点责任由真实组件和主题承担，不由 Lab 叠加修饰。

### Actions 与 Fields

16. **作为 UI 审查者，我希望比较 Button 的真实语义变体和尺寸，从而区分主操作、次操作、幽灵操作、危险操作与误用。**
    - 覆盖项目实际使用的变体与尺寸，不凭组件调用数量推断语义。
    - 同时覆盖文字按钮、图标按钮、加载、禁用和长文案。
    - 每个场景说明推荐语义，不把所有蓝色按钮一概判错。

17. **作为 UI 审查者，我希望查看 ButtonGroup、ToggleButtonGroup 与 Toolbar，从而检查相邻操作的分组、选择态和密度。**
    - 覆盖单选、复选、不可用和混合图标文字场景。
    - 不为 Lab 新建业务工具栏组件。

18. **作为 UI 审查者，我希望查看 Link、路由动作与面包屑动作的差异，从而避免链接蓝色、下划线和当前项语义混淆。**
    - 可导航链接、当前项和按钮式动作在语义与视觉上可区分。
    - 当前项不伪装成仍可激活的链接。
    - Hover 反馈不破坏产品的低噪声基线。

19. **作为 UI 审查者，我希望查看 Input、Textarea 与 SearchField 的完整状态，从而检查边框、Focus、占位符、清除和错误反馈。**
    - 覆盖空值、已填值、禁用、只读、加载、无效、长中文和窄宽度。
    - 指针点击后的边框与键盘 focus-visible 分开验证。
    - 使用真实 HeroUI/StoneFlow 组件，不复制简化版输入框。

20. **作为 UI 审查者，我希望查看 NumberField、DateField、Select 与 ComboBox，从而检查复合 Field 的对齐、弹层和校验。**
    - 已安装且实际使用的能力直接复用。
    - 需要新增可选依赖的候选先标记，不为“组件齐全”而安装。
    - 日期、数字和选择行为不由 Lab 重新实现。

21. **作为 UI 审查者，我希望查看 Checkbox、Radio、Switch 与 Toggle，从而检查选择控件的选中、半选、禁用和焦点状态。**
    - Label 点击目标与控件语义保持正确。
    - 颜色不能成为区分状态的唯一线索。

22. **作为 UI 审查者，我希望查看 Label、Hint、Required、Invalid 和 Read-only 的组合，从而统一表单信息顺序。**
    - 错误文本与帮助文本不会同时争夺主视觉层级。
    - 错误关联和必填语义对辅助技术可用。

### Navigation 与 Collections

23. **作为 UI 审查者，我希望查看 Breadcrumb、Sidebar、Tabs、Pagination、Command 和 Settings Navigation，从而比较不同层级导航的密度与当前态。**
    - 当前项、Hover、Pressed、Focus 和 Disabled 可被独立观察。
    - Sidebar 的 32 高度与上游 36 高度可以作为密度决策比较，但不预设其中一个必然错误。
    - 导航样例使用真实语义，不用静态 div 冒充交互控件。

24. **作为 UI 审查者，我希望查看 RowShell、Menu、ListBox 和 ListView，从而检查行高、分组、选择、动作显隐与键盘导航。**
    - 覆盖普通行、选中行、包含尾部操作的行和长文本行。
    - Hover 显示的动作仍可被键盘用户发现和操作。

25. **作为 UI 审查者，我希望查看 Task Row 与 Group Header，从而验证高频任务信息的扫描性和密度。**
    - 优先复用产品公开 Module 或稳定组合接口。
    - 若展示需要深导入内部组件或复制生产 JSX，则标为真实应用场景，不为 Lab 破坏边界。

26. **作为 UI 审查者，我希望查看 Table、Tag、Chip、Badge 与 Avatar，从而统一集合元数据和紧凑状态标识。**
    - 覆盖短值、长值、溢出、空值、选中和可移除状态。
    - 不为了齐全而实现项目没有真实需求的复杂数据表能力。

27. **作为 UI 审查者，我希望查看空集合、加载集合和错误集合，从而检查从无数据到可操作恢复的完整反馈。**
    - 空状态解释下一步，错误状态提供可理解的重试入口。
    - Skeleton、Spinner 和 Progress 按等待类型使用，不同时堆叠。

### Feedback 与 Overlays

28. **作为 UI 审查者，我希望查看 Empty、Skeleton、Spinner、Progress、Alert 与 Toast，从而统一反馈层级和语气。**
    - 覆盖一般信息、成功、警告、错误和进行中状态。
    - Toast 不承担必须长期保留或需要用户决策的信息。
    - Lab 使用最小 fixture 触发真实组件，不实现第二套通知系统。

29. **作为 UI 审查者，我希望查看 Pending、Disabled、Invalid、Danger、Save、Error 与 Retry 场景，从而判断状态是否既明确又不过度喧闹。**
    - 状态文字、图标、颜色与可操作性保持一致。
    - 危险态只用于真实不可逆或高风险动作。

30. **作为 UI 审查者，我希望分别查看 Tooltip、Dropdown、Popover 与 Context Menu，从而检查浮层位置、触发方式和退出行为。**
    - 每次只挂载一个 Overlay 样例。
    - Tooltip 不承载完成任务所必需的信息。
    - Pointer、键盘打开、Escape 关闭和焦点返回均可操作验证。

31. **作为 UI 审查者，我希望查看 Modal、AlertDialog 与 Sheet，从而检查阻塞层级、焦点陷阱、危险确认和窄窗口适配。**
    - 初始焦点、Tab 循环、Escape 策略与关闭后的焦点恢复清晰。
    - 真实窗口边界与 WebView 差异仍在 Tauri 中验收。
    - 不通过 Lab 修改既有 1024 宽度 Detail 响应式规则。

### Product Scenes

32. **作为产品负责人，我希望查看 Shell 与 Sidebar 的代表性组合，从而判断整体层级、密度和冷静程度，而不只看孤立组件。**
    - 场景只包含足以暴露 Shell 规则的最小内容。
    - 不复制完整应用状态、数据层或路由树。

33. **作为产品负责人，我希望查看 PageFrame 的标题、Toolbar、Filter 与内容组合，从而判断页面结构是否整齐且信息优先级清楚。**
    - 覆盖常规、窄容器和长标题。
    - PageFrame 的结构由产品 owner 负责，不下沉为 HeroUI 通用组件。

34. **作为产品负责人，我希望查看 Task Row、Task Board 与 Task Detail Section 的代表场景，从而评估组件组合后的真实密度与对齐。**
    - Task Board 继续遵守容器窄于 560 时的紧凑规则。
    - Task Detail 的 Sheet/Aside 切换仍以既有 1024 规则为准。
    - 无法脱离真实 Store、Router、Query 或 Tauri 环境可靠复现的场景标为仅真实应用验证。

35. **作为产品负责人，我希望查看 Settings Form，从而检查表单分组、保存、错误、危险区与键盘路径。**
    - 复用真实设置页公开组合或最小稳定场景。
    - 不让 Lab 成为第二个设置页面实现。

36. **作为产品负责人，我希望查看 Launcher 的搜索、创建、空状态与错误状态，从而检查跨窗口视觉一致性。**
    - Lab 只验证可移植的视觉组合。
    - 窗口激活、原生快捷键和真实创建流程留在 Launcher WebView 验收。

### HeroUI 候选评估与长期维护

37. **作为开发者，我希望优先看到项目当前已使用的 HeroUI 组件，从而快速查阅真实 API 和主题结果，而不是依赖卡顿的官网。**
    - 样例使用项目锁定版本和当前主题。
    - 不复制上游文档正文或源码。
    - Pro 组件仅在私有本地环境展示。

38. **作为开发者，我希望看到与现有自实现组件有明确对应关系的 HeroUI 候选，从而评估是否值得硬切替换。**
    - 候选记录替换对象、缺失能力和验证状态。
    - “能渲染”不等于“已批准迁移”。
    - 迁移必须另立 ticket，并在消费方、行为和可访问性均被验证后删除旧实现。

39. **作为维护者，我希望把未采纳候选与已采用组件区分，从而避免实验代码被误认为产品标准。**
    - 候选状态在导航和预览中清楚可见。
    - 未批准候选不得被生产 Module 依赖。
    - 没有明确 StoneFlow 场景的组件不因“HeroUI 有”而加入。

40. **作为依赖维护者，我希望可选 peer dependency 只在真实候选需要时加入，从而避免组件画廊扩大生产依赖面。**
    - 候选缺少 peer 时显示依赖要求，不自动安装。
    - 依赖引入、许可和包体影响由后续迁移 ticket 决策。

41. **作为架构维护者，我希望产品代码不依赖 UI Lab，从而保证实验室可删除、可替换且不会成为运行时基础设施。**
    - 依赖方向只能从 Lab 指向 HeroUI、全局样式、共享公开接口与产品公开接口。
    - 产品 Module、shared 层和样式层不得反向导入 Lab。
    - 不为单个 Lab 消费者创建新的公开 facade、Adapter 或注册协议。

42. **作为发布维护者，我希望生产构建与 Tauri 打包排除 UI Lab，从而避免发布内部审查面和 HeroUI Pro 示例。**
    - 生产构建只保留 Main 与 Launcher 入口。
    - 构建产物中不存在 UI Lab HTML。
    - UI Lab 的失败不能扩大为发布时运行时依赖。

43. **作为长期维护者，我希望 UI Lab 代表目标视觉规范而不是旧 StoneFlow 档案，从而让后续重构朝一个方向收敛。**
    - 新基线强调统一、简洁、整齐、有条理和冷静。
    - 已完成迁移的旧样式、兼容别名和重复 recipe 必须硬切删除。
    - 历史对照如确有审查价值，只能作为短期任务资产存在。

44. **作为维护者，我希望 UI Lab 的规模由发现价值约束，从而避免它变成需要独立维护的第二个产品。**
    - 优先覆盖共享规则和高频产品组合。
    - 新增样例必须能暴露新的状态、责任边界或替换决策。
    - 当新增样例不再提供新证据时停止扩张。

## Implementation Decisions

### 架构边界

- UI Lab 是开发专用的外层 Host，也是唯一新增的组合根；它不是 StoneFlow 领域 Module，也不进入生产路由。
- UI Lab 使用独立开发入口，共用一个 Shell、一个搜索输入、一个分类导航和一个预览区。StoneFlow 与 HeroUI 是同一 Host 下的两个视图，不建设两套应用。
- 产品依赖方向保持单向：UI Lab 可以消费 HeroUI、全局样式、共享公开 Interface 和产品公开 Interface；任何生产 Module 都不得依赖 UI Lab。
- UI Lab 不新增领域状态、后端 Port、Tauri Command、数据库 Schema 或跨窗口协议。样例优先使用纯 fixture；确需交互上下文时复用既有测试/应用 Provider。
- 复杂产品场景仅在现有公开 Interface 足以组合时进入 Lab。若必须深导入私有实现、为 Lab 暴露新的公共 API、复制生产 JSX，或伪造大量 Router、Query、Store、Tauri 状态，则保留在真实应用验收。

### 最小数据模型

- Lab 内部仅维护一个显式样例目录，包含稳定标识、显示名称、所属视图、分类、搜索关键词、责任归属、覆盖状态、验证边界和渲染入口。
- 样例目录是 Lab 的内部实现，不抽象为跨产品 registry、插件系统、Port/Adapter 协议或可配置平台。
- 覆盖状态只表达审查元数据，不承载 bug、优先级、负责人、进度或迁移审批；实际工作继续使用本地 ticket。
- 每次只渲染被选中的样例。目录项可以完整加载，昂贵样例的组件实现按需加载。
- 状态矩阵使用少量人工策划的适用状态，不自动生成所有 prop 与状态组合。

### 视觉所有权

- HeroUI 负责上游结构、交互状态、可访问性与基础行为；全局主题负责语义颜色、几何和全局状态值；共享 recipe 只负责确有多处消费的窄视觉规则；产品 Module 负责稳定产品结构、语义和动态几何。
- UI Lab 直接使用实际生效的主题和 recipe，不维护平行设计系统、TypeScript token 镜像、实验室专用 reset 或一对一 HeroUI 包装层。
- 目标几何沿用当前既定节奏作为起点：4/8/12 间距、28/32/36 控件高度、6/8/12 圆角层级和通常不大于 14 的内联图标；任何改变应由观察证据和后续 ticket 驱动。
- 指针 Hover 默认保持低噪声，键盘 focus-visible 必须可见；UI Lab 不用伪类覆盖掩盖真实组件问题。
- 不新增第一方动效系统。组件动效与 reduced-motion 行为继续由 HeroUI 和现有全局规则负责。

### 覆盖策略

- StoneFlow 视图固定覆盖 Foundations、Actions、Fields、Navigation、Collections、Feedback、Overlays 和 Product Scenes 八类。
- HeroUI 视图固定使用“已采用”“替换候选”“探索中”三类。首期不追求 HeroUI 全量组件，不复制官网组件索引。
- 已知问题只能作为首批种子样例，不能反向把覆盖范围限制为按钮、面包屑、侧栏和输入框四类。
- 代表性 Product Scenes 只保留暴露组合规则所需的最小状态，不复制完整页面或业务流程。
- 三批交付按“基础与高频交互 → 复杂状态与浮层 → 产品组合与候选收口”推进；每批完成后先审查发现价值，再决定是否增加样例。

### 迁移与许可

- UI Lab 默认展示新的统一目标基线，不承诺像素级恢复旧 StoneFlow。
- 发现可由 HeroUI 替换的自实现组件时，先在候选库中验证；真正迁移由独立 ticket 承担。迁移完成后硬切删除旧实现，不保留双主题、兼容 alias 或长期 Adapter。
- 初始实现不新增依赖。HeroUI 可选 peer 只有在明确候选需要、产品场景成立且迁移 ticket 批准后才加入。
- HeroUI Pro 组件只在私有仓库和本地 Lab 中展示，不公开部署 Lab，不复制或再分发 Pro 源码和大规模示例实现。
- 现有 UI 平台 ADR 足以约束本功能；除非实现中出现新的跨模块长期决策，否则不新增 ADR。

## Testing Decisions

### 最高自动化 seam

- 只新增一个 UI Lab 根级 DOM 集成测试，从用户可观察行为覆盖：默认进入 StoneFlow、切换 StoneFlow/HeroUI、分类导航、搜索、选择样例、仅挂载当前预览、空结果和基本键盘可达性。
- 测试通过 Lab 的公开根组件操作，不分别为 Foundations、每个 Demo、目录解析器或每个 HeroUI 候选建立单元测试。
- 产品组件内部行为继续由其现有 Module 测试负责；UI Lab 不重复证明 HeroUI、Breadcrumb、Sidebar、Field 或 Overlay 的已有行为。
- 需要 Router、Query、Command 或 Shortcut 上下文的少数真实场景复用现有测试 Provider，不复制第二套装配。

### 自动化边界

- DOM 测试只断言语义角色、可访问名称、选择结果、焦点移动、视图切换和挂载行为。
- 不断言 className、具体 CSS 数值、Hover 颜色、阴影或截图；jsdom 不能证明实际视觉质量。
- 现有类型检查、Lint、Feature 边界检查、格式检查和动效检查继续覆盖 Lab。Lab 内的深导入、反向依赖和未使用实现必须被现有门禁拒绝。
- 运行生产构建并检查真实产物：Main 与 Launcher 入口存在，UI Lab HTML 不存在。优先验证产物，不新增对 Vite 配置内部结构的脆弱快照。
- 本功能不涉及 Rust 逻辑，不新增 Rust 测试。

### 人工验收

- 在真实浏览器中逐类检查适用状态：Rest、Hover、Pressed、Selected/Current、Pointer Focus、Keyboard Focus Visible、Open、Disabled、Loading、Invalid、长中文和窄容器。
- 至少对 Field 的指针/键盘焦点、Navigation 当前态、Overlay 的 Escape 与焦点恢复、长中文和窄容器完成一次人工 smoke。
- 在真实 Tauri Main 与 Launcher 中继续验证 Portal、WebView 原生激活、窗口边界、焦点恢复、缩放、跨窗口一致性和真实业务布局。
- UI Lab 的人工通过只证明隔离场景的视觉和交互，不代签统一产品验收规格中的 Main/Launcher 验收项。

### 暂不引入

- 不引入 Storybook、Playwright、Chromatic、截图基线或 CI 视觉回归。
- 只有当 UI Lab 已稳定、人工检查出现高频重复且截图差异确实能降低回归成本时，才另立规格评估浏览器自动化与视觉回归。

## Out of Scope

- 本规格不修复审查中发现的按钮、面包屑、侧栏、输入框、焦点、Overlay 或其他 UI/UX 问题。
- 本规格不执行全站视觉重构、不修改业务流程，也不承诺恢复旧 StoneFlow 的像素样式。
- 本规格不为每个源文件导出 Demo，不把源码组件数量当作视觉覆盖数量。
- 本规格不渲染 HeroUI 的全部组件、全部 prop 或全部状态组合，也不复制其官网文档。
- 本规格不建设第二套设计系统、token 系统、通用 playground、插件平台、代码生成器、动态注释数据库或外部 issue tracker。
- 本规格不公开托管 UI Lab，不发布 HeroUI Pro 示例或源码。
- 本规格不引入新的生产依赖、可选 peer、字体、动效库或测试平台。
- 本规格不更改领域模型、数据库、Rust 后端、Tauri Command、同步协议、路由契约或跨窗口协议。
- 本规格不自动批准 HeroUI 迁移；候选验证与生产替换是后续独立 ticket。
- 本规格不取代真实 Tauri Main/Launcher 的视觉、键盘、窗口与缩放验收。

## Further Notes

- 本规格基于 [UI 组件审查与实验室研究](../../../Documents/04-专题研究/2026-08-26-ui-component-audit-lab-research.md)，其中记录了当前仓库观察、HeroUI 官方资料和方案比较。
- 现有 [统一产品验收规格](../../unified-product-acceptance/spec.md) 继续拥有 Main 与 Launcher 的最终真实应用验收；两个工作包职责互补，不互相替代。
- 已知的按钮、面包屑、侧栏、输入框和焦点问题是首批审查种子，不是预先确认的全局结论。UI Lab 的首要价值是让这些判断变得可复现、可归因。
- 当前 UI/UX 风险可判断为“系统一致性问题中等、观察与验收缺口较高”。因此，两个独立全量画廊不值得做；一个共用基础设施、系统级覆盖、按需挂载且排除生产的 UI Lab 值得做。
- 规格已经确定最高自动化 seam：一个 UI Lab 根级 DOM 集成测试。视觉结论由浏览器人工矩阵提供，桌面真实性由 Main/Launcher smoke 提供。
- `ready-for-agent` 表示本规格可以继续拆分本地实施 tickets；它不是对任何 UI 修复、HeroUI 迁移或视觉验收的完成声明。
