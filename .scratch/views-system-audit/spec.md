# Views 系统修复与执行契约收敛

**Status:** ready-for-agent

**Labels:** ready-for-agent

**日期：** 2026-09-13

**代码基线：** `5324f423` 及当前工作树

**证据：** [Views 系统审计](./report.md)

## 问题陈述（Problem Statement）

用户在任务页面的“未完成”里添加“待执行”筛选并保存 View，保存后没有看到新 View 的明确落点，切换选中项后又感觉任务仍被原筛选限制。界面没有提供足够信息，让用户分清当前基线、临时筛选、保存结果以及操作失败。

审计确认保存实际成功，但普通任务页丢弃了创建返回的 View，没有进入详情。另有同步把旧兼容字段写成错误格式的实际存量记录，会阻断后续重命名和覆盖；这些失败在界面上又缺少反馈。单条坏定义可能使整个视图库加载失败，负向条件与筛选菜单显示不一致，部分显示选项虽可选择却没有执行效果，项目查询边界与错误空态也不完整。

这些问题背后有四处需要一起修正的结构：保存流程在多个页面重复编排；排序只作用于已经分页取回的任务；Board 将通用分组拆成状态特例与其他分组旁路；View 当前业务仍受分散的旧协议编码牵制。

“真正切换到全部后仍只有待执行”的原生现场尚未复现，不能将现有隔离测试通过视为这一症状已解决。本工作包必须补齐真实页面和原生验收证据。

## 解决方案（Solution）

在同一个工作包内完成审计中的 10 项问题及四项架构调整。保存当前查询后直接打开新 Saved View；切换或恢复默认视图时准确清除对应临时筛选；保存失败保留输入并提供恢复动作。用户随时能检查当前完整条件，负向筛选不再被显示成未选择，也不会被普通值选择悄悄替换。

所有任务、独立事项、项目和 Saved View 详情使用一致的保存规则。视图库继续承担统一管理，不把所有 Saved View 塞进项目的默认视图选项。Default View 不入库，Filter Draft 继续由 URL 持有，Display 继续作为本机偏好。

用户选择的排序作用于完整匹配结果，第一页就是该顺序下的第一页。主分组、子分组、空组和完成项顺序真实生效，各种分组共享折叠、选择与既有任务操作规则。保留当前分页、虚拟列表和已加载项几何，不全量加载任务。

View 创建、读取、同步和再修改共用准确的定义校验与编码。已知错误旧格式获得有边界的兼容恢复；无法无损解释的定义单独标记不可用并允许清理，不影响其他视图，也不猜测或扩大用户查询范围。

## 用户故事（User Stories）

1. 作为项目用户，我希望从“未完成”添加“待执行”条件后只看到符合条件的项目任务，以便检查准备执行的工作。
2. 作为用户，我希望保存时准确保留当前 Space 范围、项目或独立事项边界、默认视图基线和有效筛选，以便再次打开时得到同一查询含义。
3. 作为用户，我希望保存成功后直接进入新 Saved View 并看到它的名称，以便明确知道保存结果在哪里。
4. 作为所有任务页面的用户，我希望保存采用与项目页相同的成功落点，以便不用因入口不同学习不同流程。
5. 作为独立事项用户，我希望保存后仍只查询当前 Space 的独立事项，以便不会混入项目任务或其他 Space。
6. 作为 Saved View 用户，我希望另存为创建独立 View 并打开它，以便保留原定义。
7. 作为 Saved View 用户，我希望覆盖只更新当前 View 的筛选，以便不会更改名称以外的固定查询边界或其他 View。
8. 作为用户，我希望回到默认“未完成”时看到其原有查询结果，以便保存操作不会改写默认视图。
9. 作为用户，我希望切到“全部”时不再带有上一基线的临时“待执行”筛选，以便选中项与任务结果一致。
10. 作为用户，我希望恢复当前 Saved View 时只丢弃临时修改，以便回到保存的条件。
11. 作为用户，我希望能临时清空一个非空 Saved View 的额外条件，以便“空草稿”和“没有草稿”不会被混为一谈。
12. 作为用户，我希望刷新和前进后退能恢复 URL 对应的筛选，以便继续此前的查询。
13. 作为用户，我希望保存失败时名称和筛选保持原样，并能看到明确错误和再次尝试，以便无需重新输入。
14. 作为用户，我希望重命名或覆盖失败时保留原记录和当前输入，以便不会产生半完成修改。
15. 作为用户，我希望删除失败时明确知道记录仍然存在并能重试，以便不误以为删除成功。
16. 作为用户，我希望一次提交期间不会重复创建相同 View，以便快速点击不会生成重复记录。
17. 作为用户，我希望关闭弹窗或切换页面后，迟到的保存结果不会清除新页面草稿或把我拉回旧页面，以便继续当前操作。
18. 作为用户，我希望视图库加载失败时能直接重试，以便不必重启应用。
19. 作为用户，我希望 Saved View 定义加载失败时既能重试也能返回视图库，以便有明确恢复路径。
20. 作为用户，我希望在干净的 Saved View 中也能检查当前完整查询边界和条件，以便知道结果为什么如此。
21. 作为用户，我希望“排除某状态”和“包含某状态”在筛选入口中显示准确，以便不会把正在生效的排除条件误认为未设置。
22. 作为用户，我希望修改负向条件的值时保持排除含义，只有明确更改操作符才切换为包含，以便筛选含义不会意外反转。
23. 作为用户，我希望仅检查条件和关闭筛选菜单不改变查询，明确选择的修改即时生效，以便检查与修改的结果都可预期。
24. 作为用户，我希望干净 View 不重复铺开筛选条，临时修改时再显示完整条件、恢复和保存，以便界面保持现有密度。
25. 作为多设备用户，我希望 View 同步到另一副本后仍能重命名、覆盖和删除，以便同步不会破坏后续编辑。
26. 作为已有 View 的用户，我希望已知格式错误可以恢复而不改变名称、查询和身份，以便保留已经保存的内容。
27. 作为用户，我希望一个损坏或无法迁移的 View 只影响它自己，以便仍能打开和管理其他 View。
28. 作为用户，我希望不可用 View 告诉我需要重建并允许删除，以便不必手工编辑数据库。
29. 作为用户，我希望范围无法识别的坏 View 也有可达的清理入口，以便坏记录不会永久隐藏。
30. 作为项目用户，我希望保存或打开 View 时校验项目存在及范围归属，以便定义矛盾不会被伪装成正常空结果。
31. 作为项目用户，我希望项目跨 Space 移动使原固定范围失效时得到明确说明，以便应用不会悄悄扩大或重新绑定查询。
32. 作为用户，我希望按优先级或日期排序时，即使重要任务原本位于第 151 条之后，也能出现在正确的第一页，以便排序覆盖全部匹配任务。
33. 作为用户，我希望继续加载时维持同一顺序且不重复或遗漏静态结果中的任务，以便可以连续浏览。
34. 作为用户，我希望切换排序、分组或筛选后从对应的新结果第一页开始，以便不会混入旧窗口。
35. 作为项目用户，我希望手动排序保持容器中的位置顺序，显式启用完成项特殊排列时才覆盖完成项的位置，以便修改任务标题或其他元数据不会自行重排位置。
36. 作为用户，我希望总数只反映匹配任务数量，以便分组、排序和显示空组不会改变计数。
37. 作为用户，我希望子分组把每个主组进一步组织为对应子组，以便面板选项与结果一致。
38. 作为用户，我希望状态、优先级、项目和日期分组都能按一致方式折叠和展开，以便切换维度不会失去基本交互。
39. 作为用户，我希望组内选择只作用于该组的已加载任务，并遵守现有批量操作范围，以便不会选中别组或未加载的任务。
40. 作为用户，我希望显示空分组时出现当前范围内有意义的空组，关闭时将其隐藏，以便能按需查看结构。
41. 作为用户，我希望“完成按近到远”按实际完成时间排列完成项，以便最近完成的工作出现在预期位置。
42. 作为用户，我希望显示偏好仍留在本机且能设为默认或恢复默认，以便整理方式不会改变 Saved View 的查询定义。
43. 作为用户，我希望筛选后没有匹配任务时看到“当前视图无匹配任务”和调整入口，以便不会被告知整个项目没有任务。
44. 作为用户，我希望首次加载、加载失败、零结果和续页失败呈现不同状态，以便不会把尚未返回的数据误认为空项目。
45. 作为键盘和辅助技术用户，我希望保存、筛选、重试和分组操作都有可达控件、清晰名称、可见焦点及可感知错误，以便不用鼠标也能完成流程。
46. 作为使用窄窗口或较大缩放的用户，我希望长 View 名称、错误信息和筛选条件不会遮挡操作，以便始终可以保存或恢复。
47. 作为长列表用户，我希望增加子分组后仍保持当前滚动、分页重试、焦点和预览恢复行为，以便功能修复不带来列表体验回退。

## 实施决定（Implementation Decisions）

### 1. 保留领域分工，统一保存流程所有者（AR1）

- Default View 仍是页面策略；Saved View 只保存 `scope + context + baseViewKey + filters`；Filter Draft 是 URL 中的完整筛选快照；Effective FilterQuery 由基线与 Draft 派生。禁止增加另一个可写 View store。
- View feature 拥有“保存当前查询”的共享用例：接收提交时的完整定义快照和保存模式，执行现有 mutation，返回实际 Saved View 身份及结果。其面向页面的流程接口统一成功后的导航与对应 Draft 清理策略；所有任务、独立事项、项目及 Saved View 详情复用。
- 页面提供上下文、当前来源和路由动作；共享流程不反向依赖页面或 layout，不把项目 CRUD 搬入 View。视觉 TaskWorkspace 继续负责布局组合，不承担数据库、协议或业务数据的第二份所有权。
- 修订 A2 中“工作台拥有全部接线”的笼统表述，明确逻辑工作台与纯视觉组件的区别，并与 task-workspace、view、task、filter 和 display-options 的模块文档一致。更新已有权威文档，不建立平行领域文档。

### 2. 保存、切换与异步完成规则（V02、V04）

- 创建与另存成功后进入返回 ID 对应的 Saved View，目标 URL 不携带来源 Draft；清理只作用于启动提交的来源会话，并与成功导航一同完成，不能先清 Draft 再尝试导航。导航失败保留来源 URL/Draft，显示“已保存，但未能打开”，恢复动作只打开已返回 ID，不重新创建。普通默认视图工具条仍只列内置项，Saved View 统一由 Library 管理。
- 覆盖只允许有效的当前 Saved View，保持 ID、scope、context、baseViewKey 不变，只更新被授权的 filters；重命名只修改名称。修改与 Outbox 同事务成功后才显示成功。
- 提交时固定名称、来源身份和有效查询快照，不在异步完成时重新读取另一个页面的定义。提交中防重复；失败保留输入、Draft 和原记录，显示就地可感知错误。删除失败保留记录并提供明确反馈。
- 继续允许提交中关闭弹窗。关闭、来源切换或开启新会话后，旧请求仍可正常完成并失效相应缓存，但不能触发旧页面导航、清除新 Draft、关闭新弹窗或覆盖新输入。区分数据库提交成功与后续导航失败，导航失败不能引导再次创建同一记录；保留打开已创建 View 的恢复动作。
- 切换 Default View 的同一交互更新选中项并清除旧 Draft；恢复只删除当前 Draft。URL、Query key、执行请求和结果必须最终对应同一来源，旧请求不得覆盖新结果。

### 3. View 编码、存量兼容与坏记录隔离（V01、V03、AR4）

- 收敛具体的 View 定义 codec 与协议投影，供 CRUD、初始 seed、协议基线回填和下载物化复用。已有领域校验继续作为当前定义的共同规则，不增加通用序列化框架。
- 当前业务成功条件只依赖当前定义和本次修改。已退出产品契约的 sort/group 字段由兼容边界生成 canonical 值，不能重新从损坏旧列取得业务权威。保留现有 schema 和 wire shape；修正 JSON 值与数据库 JSON 文本之间的编码。
- 对已确认的裸文本 `none` 采用精确、幂等的恢复规则：还原为 canonical JSON 表达，不改变 View ID、名称、查询定义或用户时间信息，不制造业务修改和重复 Outbox。恢复在正式应用的既有持久化边界完成；不以手写 SQL 修改用户正式库代替实现和验证。
- 未知旧值、损坏 scope 或无法无损转换的条件不能猜测成空查询或默认范围。读取必须逐条解码并返回有效、不可迁移或损坏状态；一条坏数据不能中断其他定义的列表与执行。
- scope 可识别的坏记录在其原 Library 中显示“需要重建”；scope 无法识别的记录在“所有空间”的 Library 中复用不可用行，展示最小身份、原因和删除动作，不归入任意 Space。列表 DTO 显式表达范围未知的错误条目，不伪造合法的 scope。此类记录不可执行、重命名或覆盖，允许按 ID 清理且不要求先成功解码定义。
- 同步结构验证与读取隔离协同：坏 View 不阻断同页有效实体，但业务投影或可清理的异常记录必须与协议状态、AppliedOps 和 cursor 同事务落盘，才可推进游标。禁止仅记日志跳过物化却提交 cursor；无法形成可恢复记录的物化失败应整体回滚，重放不重复。
- 冷协议状态收到 rename/filter patch 时，先利用已有业务行或完整协议快照补齐定义再应用；不足以恢复时进入既有完整快照恢复或明确失败，不把残缺 patch 当成完整定义覆盖。继续遵守 generation、tombstone 和字段合并规则。
- 无法解析的定义不自动重写或删除。兼容规则的退出条件是存量和受支持同步 producer 已不再产生旧形状，并有往返证据；物理删列和删 wire 字段另行核对旧设备消费者。

### 4. 查询边界与筛选语义（V05、V09）

- create、update 和执行 Saved View 的用例都校验 project context 的存在及其与 scope 的一致性；可解码但业务边界失效的记录以不可用定义呈现，不能转换成正常零结果。
- 对项目跨 Space 移动采用保守策略：已保存的固定 scope/context 不自动跟随或扩大；不一致时显示“项目范围已变化，需要重新保存视图”，提供返回 Library、删除和从有效项目重新保存的现有路径。无效期间保留原定义；项目重新满足原边界后按现有生命周期规则重新校验。全范围 scope 中仍然一致的 project context 不因移动被错误标为无效。
- 不改变项目本身的移动、归档或删除规则，不在本工作包加入跨 Space View 自动迁移。
- 复用现有 FilterMenu 提供完整查询检查入口：明确显示不可移除的 scope/context/base，以及 effective filters 的字段、操作符和值。clean FilterBar 仍隐藏；检查入口不能只是重命名弹窗。
- 编辑某字段的值时保留当前操作符；只有显式更改包含/排除才替换操作符。对于同字段多个有效条件，逐条表达其逻辑，不能选择一个值时无提示删除其他条件。保留现有选择即时应用的交互，不新增“应用”按钮或第二份待提交筛选状态；仅打开检查、Escape 或点击外部关闭都不产生筛选修改，关闭也不撤回已经明确选择并生效的修改。
- 前后端对受支持 FilterQuery 必须保持语义一致。重复 field/op 的旧 clauses 不得由前端合并为扩大结果的 OR；能等价规范化则无损规范化，当前模型无法表达则明确不可用。拒绝未知操作符、字段或非法值，不用空条件兜底。

### 5. 完整结果排序与分页共同执行（V07、AR2）

- 产品保证是完整匹配结果有序。Display 继续拥有本机偏好及排序意图，运行 Task Query 时将归一化的窗口顺序传入 Rust 共同执行器；Default 与 Saved 两个入口复用同一执行路径。Saved View 定义仍不保存 Display。
- 窗口顺序包括影响顺序的主分组、子分组、组内排序、方向与完成项顺序。SQL ORDER BY、keyset cursor 和前端 Query key 使用同一个有效顺序定义；只改字段可见性、折叠或空组呈现无需重取成员窗口。
- 有分组时先按主组、再按子组、最后按组内任务顺序执行；无分组时视为一个叶组。组顺序固定，不随叶组排序方向反转：状态为 doing、todo、waiting、done、canceled；优先级为 4 到 0；日期桶为逾期、今天、明天、本周剩余、更晚、未设置，按本地日历互斥划分。项目组采用名称二进制升序、同名 project ID 升序，独立事项组置后；SQL 与前端投影使用同一规则，不依赖 renderer locale。
- 叶组普通排序规则如下；只支持页面现有 capability 开放的字段，不扩大选项范围。

| 排序 | 确定规则 |
| --- | --- |
| manual | 容器 position 升序、ID 升序；维持现有支持页面，不额外开放到跨项目列表 |
| priority | 数值按方向排列；同值 updatedAt 降序、ID 升序 |
| status | doing、todo、waiting、done、canceled 为升序，降序反转；同值 updatedAt 降序、ID 升序 |
| 日期字段 | 所选字段按方向排列，两个方向都将空值置后；同值 updatedAt 降序、ID 升序；沿用现有派生时间字段语义 |
| smart | 固定状态业务序 → dueAt 优先、否则 plannedAt 的有效时间升序且空值最后 → priority 降序 → updatedAt 降序 → createdAt 降序 → ID 升序 |

- smart 和 manual 是固定顺序，面板不显示方向切换，归一化排除无效方向差异；其他方式的方向必须真实生效。manual 在完成项自然排列时完整遵守位置顺序；显式启用完成项特殊排列时仅覆盖相应完成项部分。修改 updatedAt 不改变手动位置，不为此增加任务列表 DTO 字段。
- 所有现有受支持的排序方式都在 SQL 截取第一页之前生效。前端消费有序窗口并投影分组，不再对已加载集合做会改变全局顺序的二次排序。
- cursor 带版本并绑定成员查询和有效顺序，携带末条任务的完整排序元组，使用相同的空值与复合键比较规则。错查询、错顺序、损坏或不支持版本的 cursor 返回可恢复错误，前端提供从第一页重试，不静默混用。改变 scope/context/base/filters 或窗口顺序时从第一页开始；旧 cursor 不可复用。
- 相对日期使用同一分页会话的时间基准；Query key 包含该基准与有效查询/顺序，但不包含无语义的 clause ID、字段显隐或折叠状态。跨天使窗口整体失效并以新基准从第一页开始；失效前发出的旧续页只能用于旧会话，不能与新结果拼接。
- count 继续只使用成员谓词，与排序、空组、折叠无关；仅首屏返回精确 totalCount，续页不重复 COUNT。默认窗口大小与 loaded-only 性能基线保留，不全量 materialize、不用服务端总数生成 spacer。
- 不承诺跨任务并发修改的数据库快照。受影响数据变更走既有失效和新窗口流程；静态数据续页必须无重复、无遗漏，旧查询响应不得拼接到新查询。

### 6. 统一分组投影并兑现显示能力（V06、AR3）

- Display 产出唯一分组投影，包含稳定 group key、主/子层级、标签、当前已加载成员以及必要的领域动作元数据。状态和非状态分组走同一路径，移除重复 regroup 和 customSections/statusOrder 双重事实源。
- Board 只消费投影及集合交互状态。TaskStatus 不再作为所有组的身份；status 只是支持状态预填等动作的可选元数据。非状态组获得同等折叠与已加载成员选择能力，不凭组名发明状态或写入任务属性。
- 子分组只允许现有 capability 声明的不同维度；主分组为 none 或主子同维度时，子分组归一为 none，UI 与执行一致。子组的 key 包含父组身份，避免相同标签串用状态。
- 折叠和选择继续由既有集合交互所有者持有；折叠身份区分工作台来源及分组配置，不因切换维度把旧状态应用到另一组。全选和批量动作维持现有已加载范围，不偷偷扩展为全部匹配任务。
- 真实空组与尚未加载任务的组必须区分。查询首屏按相同成员谓词提供当前主/子路径的精确分组摘要；这是有界聚合查询，不读取全部任务正文、不重复 COUNT 每个续页、不因摘要为未加载任务制造虚拟高度。组的总数与已加载数量分开表达；折叠、字段显隐不改变摘要。
- 显示空组的候选集：状态/优先级/日期使用有限枚举；项目使用当前 scope/context 的有效项目目录及适用的独立事项组，project context 只允许其指定项目，standalone context 只允许独立事项。空候选只用于呈现，不新增匹配任务或改变 totalCount。
- 关闭空组时只显示已到达窗口且有成员的组，不将尚未加载到的非空组标为 0。开启后可显示确认为 0 的候选组；尚未到达的非空组仍随分页到达。存在子分组时，只为已呈现主组补充有限枚举空子组，项目子组只呈现实际非空路径，不生成项目目录与全部父组的空笛卡尔积。续页按稳定 key 合并已有组。
- completedOrder 的 natural 表示遵守普通叶组排序；recency 表示每个叶组先放非 done 任务并保持普通顺序，再放 done 任务并按 completedAt 降序、空值最后、ID 升序排列。状态分组中仅 done 部分受到影响。面板将该语义明确表达为“已完成置底，最近优先”。此显式选项优先于 done 任务的 manual/普通顺序，不跨主/子组搬移任务，不改变成员资格。禁止仅在两项均为 done 时替换比较器，否则可能形成非传递顺序。
- 复用当前唯一虚拟 renderer、CollectionBody viewport、集合几何和焦点/选择实现；层级投影展开为可导航 flat items。主组/子组折叠、sticky 顶替、分页 sentinel、append anchor 与预览关闭恢复都消费同一投影，不再增加第二条渲染路径。
- 面板、capability、偏好归一化和实际执行必须一致；本工作包实现已承诺的子分组、空分组与完成项顺序，不用仅隐藏控件代替修复。

### 7. 错误、空态与界面一致性（V02、V08、V10）

- Library 与 Saved View 定义读取错误提供真实重试；Saved View 详情继续保留返回 Library。任务首屏和续页错误继续沿用各自恢复入口，不将定义错误伪装成任务为空。
- 已有任务但当前条件不匹配时使用视图/筛选空态；只有已知无筛选的完整项目结果为零时才使用“项目没有任务”的首次创建引导。不能为文案额外读取全量任务，也不能将未就绪 totalCount 当作 0。
- 沿用现有白色表面、紧凑布局、语义颜色与 HeroUI 控件，不把本轮扩大为视觉重设计。错误需可被辅助技术感知；控件具备名称、键盘可达与可见焦点；长名称和错误不能截断唯一恢复动作。

## 测试决定（Testing Decisions）

测试观察用户操作、返回结果、持久化效果与可恢复错误，不以 callback 被调用、选中样式变化或 Query 被失效代替流程正确。优先复用两个现有高层接缝；前端 IPC 替身无法证明 SQLite 与真实同步投影，原生边界因此需要独立证据，不为每个 hook 新建一套测试。

### 页面流程接缝

- 使用现有 Vitest、Testing Library、真实 Router/Query 装配与工作台页面组件，只替换外部 Tauri IPC 边界。复用现有页面、FilterBar、任务读取测试设施，审计中的隔离 Router 探针可作为回归素材，不能代替整页流程。
- 为所有任务、独立事项、项目、Saved View 来源运行相同的核心行为：增加条件 → 保存/另存 → 校验提交定义 → 进入返回 ID → 检查名称、URL 和任务结果 → 返回 Default → 切换“全部”。至少一条完整链使用 todo、doing、waiting、done 都存在的夹具。
- 覆盖非空基线上的空 Draft、恢复、刷新/历史导航、负向条件检查与编辑，以及慢旧请求返回后的新页面结果，断言实际定义与可见任务而非内部调用顺序。clean View 仅打开检查后 Escape/外部关闭，URL、dirty 和任务结果不变；明确选择后即时改变 Draft，关闭不回滚。
- 注入创建/重命名/覆盖/删除失败及读取失败，验证输入保留、错误可感知、重试成功；覆盖重复点击、提交中关闭/切换、新会话与迟到完成、提交成功但导航失败，确认不重复创建或破坏新状态。导航失败保留来源 Draft，点击“打开已保存视图”前后创建次数均为一次。
- 分组页面行为覆盖一个主/子组跨页追加、非状态组折叠与组选择、空组显隐、最近完成顺序、焦点/预览恢复和 sentinel 错误重试。纯投影测试仅补难以从页面稳定覆盖的 key、几何和日期边界，不复制全部 UI 用例。

### 应用、SQLite 与同步接缝

- 复用既有 Rust View application/storage 集成测试，以临时 SQLite 和真实 View 协议投影验证：创建 → Outbox → seed/下载物化到另一副本 → 读取 → 重命名 → 覆盖 → 删除。必须验证数据和同步字段效果，而不只验证序列化函数输出相等。
- 将裸 `none`、正常 canonical 值、不可迁移 filters、损坏 scope、缺失项目、scope/context 矛盾作为有界夹具。验证已知修复幂等且保留查询、单条隔离、清理可达、业务事务失败不部分写入、有效同步实体继续处理且坏记录不被永久丢弃。覆盖冷协议的 rename/filter patch 补齐、物化失败后业务/协议/cursor 同回滚，以及重放无重复。
- 使用超过两页的混合任务，至少包含原 position 第 151 条之后的最高优先级/最早日期任务；逐页串接结果与预期完整顺序比较，覆盖 manual、升降序、空日期、相同值、不同主/子组和 completedAt。校验每个 ID 恰好出现一次、count 不变、续页不重复 COUNT。
- 覆盖顺序/成员变化后的旧 cursor 拒绝和首屏恢复、相对日期跨午夜换会话、同组跨页连续性和数据变更后新查询；覆盖 smart/manual 无效方向归一、未加载非空组与真实空组区别，以及混合 done/非 done/不同优先级时 recency 仍为稳定总序。验证前后端 FilterQuery 规范化前后成员语义等价；无法等价转换的输入必须明确失败。
- 修改当前将 updatedAt 排序冻结为 manual 的错误断言，保留真正的手动位置契约。移除被正式回归取代的临时探针与重复测试，不弱化断言来迁就旧行为。

### 原生与交付验收

- 在可操作的实际 Tauri 主窗口使用可恢复的隔离测试数据，完成用户原场景：项目“未完成” → “待执行” → 保存 → 打开新 View → 返回“未完成” → “全部”；记录选中项、有效条件与不同状态任务。独立事项和所有任务再做代表性验证。
- 对原先正式数据仅做获准范围内的只读核验；不靠改写正式任务状态制造复现。若真实窗口仍无法操作，明确保留原生验收未完成，不能用 UI Lab 目录登记或两条 Router 探针结案。
- 同步 codec 往返测试通过与真实设备同步验收分开记录；不能把两份本地夹具称为跨设备通过。
- 检查键盘保存/取消/重试、焦点恢复、错误朗读、长 View 名、窄窗口与 200% 缩放；复用既有服务，不主动启动长期开发服务。
- 实施完成按根脚本运行 `bun typecheck`、`bun lint`、`bun run lint:boundaries`、`bun format:check`、`bun run test:run`、`bun run test:release` 以及受影响 Rust 检查。保存真实结果，区分聚焦测试、全局门禁和原生验收。

## 补充说明（Further Notes）

- 本规格综合用户已同意的功能修复与架构方向，不再重新访谈。全局排序、统一分组交互均为本包目标；项目移动采用固定定义失效的保守恢复策略，不自动改写查询范围。
- 石头鱼的工程规则在本包的作用是把共同业务知识收回实际所有者：保存流程分叉因此集中在 View 用例，排序跨页失真因此下推共同查询执行器，编码重复因此收敛 View codec。代价是同包调整前后端契约与消费者；保留领域三分法、现有 schema/wire 和唯一 renderer 控制迁移面。
- 可按“编码与恢复 → 保存与筛选 → 查询窗口与分组 → 原生验收”实施垂直切片，但这些切片共享本规格的完成判据，不能只修第一批症状便宣布整包完成。
- 审计基线已有 59 项筛选/工作台/显示测试、19 项 View 界面测试、13 项 Rust 名称匹配测试及 2 项隔离路由探针通过；这些只说明旧覆盖面，不是本规格目标已通过。源码证据、命令和未验证项见审计报告。
- 工作树中原有 9 个 staged 文件属于用户已确认改动，必须保留 staged/unstaged 边界。实施产物默认未暂存，不混入范围外修改。
- `ready-for-agent` 表示本地规格已可交给实施，不表示生产代码已修复。只有覆盖表中的功能、架构与原始现场证据全部闭合，才能声明整套 Views 问题解决。
